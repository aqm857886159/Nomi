# 执行规程

## 到期、续跑与并发

- 时区 `Asia/Shanghai`，每 3 天一轮。首次启用时记录调度器确认的首个 `scheduled_for` 为固定锚点；后续计划时间始终为锚点加 3 天的整数倍，不按实际 `attempted_at + 72h` 推迟。`completed_at` 只在验收齐全时填写，单独专题不推动周期时钟。
- 自动化按 `FREQ=DAILY;INTERVAL=3;BYHOUR=10;BYMINUTE=0;BYSECOND=0` 触发，配置须带 `DTSTART;TZID=Asia/Shanghai:<首轮日期>T100000` 固定时区与锚点。会话启动时补查到期状态作为离线漏跑的补偿：漏多轮只补一轮，观察窗口覆盖最后一次成功扫描以来的区间。
- 先查主仓报告、未合 PR 和本机 `outputs/competitive-radar/`。周期 ID 用本次计划执行日 `YYYY-MM-DD`；同一周期续写一份报告。已发布 PR 未合也算已有记录，不能重新开同周期分支。两个触发器同时进入时，用稳定主仓 `outputs/competitive-radar/.run-lock` 的原子 mkdir 取得独占；目录内记录本机 pid、主机、cycle-id、开始时间。**拿到锁后重新读取检查点和报告，再判断是否需要执行**。退出释放自己的锁；遗留锁须确认进程已不存在才恢复，不能仅按超时删除。
- 开始请求前在稳定主仓 `outputs/competitive-radar/<cycle-id>/checkpoint.md` 写运行清单：`cycle_id / schedule_anchor / scheduled_for / next_due / attempted_at / status / branch / worktree / report / PR / done_items / next_action / source_last_successful`。它是未交付周期的运行状态；提交报告承接该记录，运行清单链接报告/PR。每完成一次查询、一个对象/旅程/视频卡立即更新，先保存证据再标完成。崩溃后继续未完成项。
- 已记录 `partial/blocked` 的周期在下一次会话可补缺，不必等三天；没有环境变化不反复请求失败接口。跨过新的计划时间时，把旧周期以实际状态收尾，把未完成项带入最新到期周期，只补一轮。补跑不移动调度锚点，缺失来源的观察窗口从最后成功时间延续。
- `completed` = 覆盖要求全部满足；`partial` = 至少一项资料/录屏/账号/深挖欠缺；`blocked` = 没有可执行的信息源。不能用新的尝试时间清除欠缺或覆盖成功基线。
- 本机调度文件的位置和当前启用状态是本机事实，不写死为仓库所有人的已启用状态。配置读回、调度器接纳、真实触发、产生完整报告分别记录，不相互冒认。

## 一轮怎么做

### 1. 来源与变化扫描

读 `sources.md`，逐一核对五家：官方更新、新手教程/帮助中心、官网具体功能页、登录后应用、官方社媒/社区。每格填 `checked / empty / blocked / unverified / not-applicable`、检查时间、来源、上次成功基线和本次变化；`not-applicable` 要有官方依据，来源没发现填 `unverified`。

第一轮从官网导航/页脚与账号交叉链接建立来源表，不能凭搜索摘要补齐未知 URL。用户给出的两个 LibTV URL 是优先入口，但目前只代表用户指定，不代表功能已验证。MiniMax Design 的域名及账号先确认与产品实体的关系。

比较版本/发布日期/内容变化，不因换 URL、重发旧视频或推荐排序变化就记为新品。保存原文短引、公开 URL、抓取时刻和变化点。页面哈希只能提示变化，视觉/交互变化要实际操作核验。

### 2. 自媒体和社区扫描

读 `docs/research/tikhub-api-notes.md`，以本轮实际脚本 `--help` 为准。例：

```bash
node scripts/research/tikhub-search.mjs --q 'LibTV' --platform all --limit 10 --since 2026-09-16 --out /absolute/main-repo/outputs/competitive-radar/2026-09-19/tikhub/libtv/q01/attempt-01
```

日期和输出路径按当前周期替换。首轮看最近 30 天；后续从该来源上次成功检查日减 1 天查起，按平台 + 内容 ID 去重。保留发布时间未知的记录并标注，不能当成新增。检索有排序/分页上限，`empty` 仅表示这个查询窗口没检到，不代表平台没人讨论。

脚本固定写 `tikhub-search.json/md`，每个关键词/别名用独立 `query_id`，每次外层重跑用新的 `attempt-NN`，调用前确认目录未使用。部分平台失败只对失败平台重试；成功结果与原始失败留存，报告按“来源 + 查询 + 尝试 + 平台”引用，禁止覆盖已有证据或 SHA。

- 基础扫描五家各一组主品牌关键词、四个平台；核心品牌增加用户实际使用的别名补漏。每查询每平台先取 10 条，深挖再按证据扩展，不无限翻页。记录请求/分页数量与可见账单；额度金额不可得就写未知。
- 官方账号时间线由浏览器补查，因为现有脚本是关键词检索，不保证抓全官方发布。X 查询可用已核实的 `from:handle`；不能把未知别名拼成平台不支持的复杂查询。
- 分开官方发布、付费合作/疑似推广、独立教程、用户反馈。取代表性成功案例、普通案例与有摩擦的案例；不是只挑爆款。
- 记录标题/封面、首段吸引点、发布时间、时长、平台、作者、互动数及采样时刻、评论问题、引导到哪里。跨平台曝光口径不同；只有播放/点赞不能证明转化或产品效果。
- 视频在原站观看，逐段记录时间码、画面/口播/字幕/音乐/节奏、展示的产品动作、结果可信度与 CTA。仅有标题/封面/采帧时明确标为局部观察，不写“完整看完”。
- 登录后补足评论、详情和应用体验。账号失效只记录受阻来源，继续其它来源。没有授权不发布、不入群发言、不联系创作者。

### 3. 轮换深挖，不漏维度

每轮至少 2 条完整产品旅程（LibTV、TapNow 各 1 条）和 2 个有时间码的内容案例。扩展对象 Higgsfield / MiniMax Design / RunningHub 每轮轮换一家加入深挖；优先轮到最长时间没看过的。每个扩展对象至少每 3 轮深挖一次；核心对象每轮必看。若受阻，记录缺口，下轮优先补，不静默替换后称全覆盖。

维护“对象 × 维度”的 `last_deep_checked`。每 4 轮回顾全矩阵，下轮优先最久未研究的维度；重大更新可插队，但保留原欠账。首次基线分 4 轮逐步覆盖，不把所有未查项说成完成。

| 维度 | 要回答的问题 |
|---|---|
| 定位与信息架构 | 谁在什么时刻完成什么任务？首页/软件入口、导航、命名、能力分组能否形成正确预期？ |
| 页面与视觉 | 布局、密度、留白、对齐、色彩、字体、图标语义/一致性、缩略图、动效、响应式、明暗主题如何帮助识别与操作？ |
| 新手引导 | 注册/安装/连接/首项目/模板/示例/空态/渐进提示，用户多久得到第一个可用结果？可跳过吗？ |
| 工作流与交互 | 输入→编辑→运行→结果→再次修改→导出/复用，步数、切换次数、拖放、快捷键、批量、撤销重做和保存如何表现？ |
| 状态与信任 | 加载/队列/进度/取消/失败重试/回退/历史/断线/权限/付费提示，用户如何知道做到了、花了多少、错了怎么恢复？ |
| 具体功能 | 表情/姿势自定义、参考资产、画布、分镜、生成控制、素材管理和导出；预设与精调如何组合，结果是否可继续编辑？ |
| Agent | 输入引导、上下文/选区/素材引用、计划、过程反馈、工具回执、结果落点、继续编辑、暂停/恢复与出错补救；不从聊天截图推断内部架构。 |
| 生态入口 | 插件/CLI/MCP/Blender 从官网发现到安装、连接验证、首次成功、结果回流、更新与卸载；分别比较网站与软件内呈现。 |
| 商业与留存 | 价格/额度/试用/升级触点、模板复用、项目回访、通知、协作；没测过付费路径标未验证。 |
| 社区与支持 | 作品发现、分类排序、作品到同款、作者激励、活动、文档/客服、自助排障及反馈闭环。 |
| 内容与营销 | 选题系列、更新节奏、封面标题、视频结构、演示可信度、渠道差异、评论运营、官网落点和首次体验转化路径。 |

### 4. 真实鼠标与录制协议

1. 选一个可复述的用户任务、成功标准和干净测试项目。记录日期、设备/系统、视口、语言、账户层级、产品版本（不可见写未知）与素材来源。
2. 用用户现有登录浏览器的新 tab；安装版/Blender 在独立测试项目操作。先确认环境与记录能力。不得用新建未登录 Playwright profile 冒充用户登录环境。
3. 使用可用 computer-use 或 CDP 的真实输入事件完成点击、悬停、拖拽、键盘。页面文字/DOM 只辅助定位；改内部状态、直接调用未公开 API 得到的结果不能计入旅程跑通。
4. 从发现入口开始连续录到结果回流/复用，保留错误和等待。网页录制可用既有录屏工具或 CDP screencast 保存帧时间戳后编码；`/screenshot` 是单帧，不是录屏。桌面录制只捕获相关窗口，避免私密通知。工具缺失时使用截图序列 + 操作日志暂存，但交互证据记 `partial`。
5. 至少检验正常路径、撤销/取消与一条合理错误恢复。会造成真实扣费/公开发布/删除的步骤须在已有明确授权范围内，否则在该步骤前停并记未验证；不得为了补齐矩阵擅自购买套餐。
6. 亲自回看录屏，确认鼠标动作、关键反馈、结果与时间线对应；输出关键帧和时间码。衡量完成步数、首次可用结果时间、等待时间、输入/参数负担、跨页面次数、可逆性。步骤计数口径写清，网络/模型等待与 UI 操作时间分开。
7. 同任务、同类素材对照 Nomi 当前构建。生成质量与交互负担分开；账户档位/模型/网络不同需说明。记录“为什么更舒服”的具体因果假设及反例，而非只给好看分数。

## 研究转化

按“直接适用 / 值得试验 / 持续观察 / 不采用”分诊。对每条写：目标用户与时刻、证据 ID、减少的摩擦、收益与维护成本、适用前提、反方解释、Nomi 当前证据和最小验证方式。

- 产品/设计：映射唯一 TODO，查开放 PR 后去重；需要新任务时引用本次报告和用户既定范围，状态仅 `todo`。方案→现状截图→设计系统→可体验样张→确认→实现→真实用户验收遵守仓库规则；研究自动化不能跳过这些阶段。
- 营销：提取选题机制、叙事节奏与真实产品演示方式，形成 Nomi 内容实验简报：受众、主张、可证明的产品镜头、渠道、CTA、衡量指标及停止条件。不复制竞品品牌/素材，不把观看量当 Nomi 转化预测。
- 每轮给最多 3 条值得进入下一阶段的建议，其余留证据库与覆盖矩阵；这不限制研究维度。后续记录实验结果，并更新当初的机制假设和不采用理由，形成学习闭环。

## 验收与交接

- 五家 × 来源覆盖矩阵完整，所有空格有状态；核心/扩展轮换有记录，未查项无伪造结论。
- 至少两条核心旅程、扩展一家、两条内容卡达到要求；不足则 `partial`，不能填 `completed_at`。
- 每个关键判断可沿 URL/时间码/截图/录屏回查；证据 ID 唯一，记录 SHA-256、观察时刻、保存位置和可访问范围。
- TikHub 的四平台分别报结果和失败，费用/请求记录诚实；读取输出 JSON 的 `failures`，不只看退出码。
- 报告完成 Nomi 现状对照，未跑项明确；建议没有直接触发开发/发布，TODO 不重复、不提前标 done。
- 原始媒体先保留在稳定主仓忽略目录。报告发布前脱敏账户信息、私有项目和认证链接；完整带会话参数的 URL 只留本地用于访问，公开报告用去敏来源链接和必要的来源说明。
- 用户摘要含关键学习、建议及缺口，写明下轮 `next_action`。研究报告通过任务分支/PR 交付，禁止合并、直推默认分支或改写既有研究历史。离线无法推送就保留本地检查点，下次补交，不重抓。
