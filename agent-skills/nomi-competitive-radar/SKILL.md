# Nomi 竞品学习雷达

目标是理解别人如何降低用户摩擦、如何展示价值、如何获得和留住用户，并为 Nomi 提出有证据的验证任务。核心对标 LibTV、TapNow；其它对象用于扩展学习，不能因海外热度挤掉核心对象。

## 入口与运行模式

先定位 Nomi 仓库，读 `AGENTS.md`、`docs/ARCHITECTURE-NOW.md`、`docs/roadmap/TODO.md`、`docs/research/competitive/README.md` 与 `sources.md`。查最近报告和开放 PR，避免重复研究和重复待办。

- **建流程**：只调整规则、来源登记、模板、调度；不自动展开全量研究或开发。本轮用户指定此模式时优先。
- **三日周期**：读取 [执行规程](references/protocol.md)，检查全部对标对象，再轮换深挖。按该规程判断到期、恢复中断和记录缺口。
- **专题学习**：按用户任务选对象、真实旅程与内容案例，仍使用相同证据字段和 Nomi 对照。专题报告不冒充完成一次全量扫描。
- **转入实施**：先读研究证据，再走仓库设计流程和 TODO。提出研究建议不等于获准改产品或发布营销内容。

## 必须保留的判断

1. 每个结论区分 **官方声明 / 亲自操作验证 / 用户反馈 / 推断 / 未验证**。官网文案、视频演示与真实跑通是不同证据。
2. 官网、更新文档、新手教程、登录后应用、官方社媒与社区都要有来源记录。通过官网交叉确认账号身份；不猜官方账号，不把同名服务合并。
3. 执行联网任务时加载环境可用的 `web-access`；用用户日常浏览器的现有登录态、新建研究 tab。学习交互要真实鼠标/键盘操作并录屏，必须亲自回看关键片段；没有录屏能力则记录缺口，不能声称完整交互验收。
4. 自媒体扫描使用现有 `scripts/research/tikhub-search.mjs`；`TIKHUB_API_KEY` 只从环境读取，不回显。退出码 0 仍须检查每个平台 `summary`、`failures` 和缺字段。API 结果用于发现，核心视频必须打开原始页面观看。
5. 学习所有相关维度，包含“没做、删掉、合并了什么”及代价；不要把控件多、动画多或内容播放量高当成优质设计的充分条件。
6. 同一任务对比 Nomi 当前真实入口，记录构建/commit、步骤、反馈、回退和产物去向。旧方案不能当现状；未跑 Nomi 的结论只能是待验证差距。
7. 研究收敛为“用户摩擦 → 证据 → 机制解释 → Nomi 是否适用 → 最小实验 → 成败指标”。采用、试验、观察、不采用都要能说明原因；优先级服从 Nomi 本地优先、单人维护和现有路线图约束。

## 交付物

使用 `docs/research/competitive/TEMPLATE.md`。每轮交付覆盖矩阵、变化摘要、旅程卡、内容卡、Nomi 差距与决策、失败与下一轮重点。没有变化也要附检查时间/来源；没有新研究就不能刷新深挖日期。

原始媒体与私密内容放稳定主仓的 `outputs/competitive-radar/<cycle-id>/`，不放临时 worktree 或 Git；报告写证据相对路径、时间码和校验和。公开仓库只能提交脱敏摘要与最小必要引用。自动运行只研究和形成待办，不发帖、评论、私信，不更改账户/套餐，也不自动开发、合并或发布。

结束前按 [验收清单](references/protocol.md#验收与交接) 检查。用户摘要只说本轮最有价值的发现、适用性和未查成的部分，不把资料量当成果。
