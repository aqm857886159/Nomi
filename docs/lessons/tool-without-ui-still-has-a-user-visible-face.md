# 「这是内部工具，没有 UI」——确认卡就是它的 UI

**踩到日期**：2026-09-03（分镜表 `patch_shots` 工具）
**场景标签**：E 产品 / A 走查

## 现象

给 Agent 加了 `patch_shots` 工具。契约、执行器、9 个分派点、10256 条单测全绿，红灯探针四次全验，
于是我报「工具做完了」。

P3/R13 眼见链闸拦下：**改了代码就报完成，但整个窗口里没有一次对截图的 Read**。

我第一反应是「这是个工具，没有 UI，应该可以豁免」。查下来完全相反——而且比「漏了一块」更糟：

| 版本 | 确认卡上实际显示 | 问题 |
|---|---|---|
| 最初 | 「只建卡 · 不生成」 | 掉进 canvas-write 分支去找 `nodes`/`edges`（它没有）→ 两个都是 0 → **对一个改提示词的操作说「不生成」，主动误导** |
| 修一半 | 「查看细节」 | 落到兜底文案，**不说改哪几镜、改什么** |

## 这一类的判据

**任何需要用户批准的 Agent 能力，都有一个用户可见面：那张确认卡。**
工具本身没有像素，不等于它没有 UI——**确认卡就是它唯一的 UI，而且是用户唯一一次能拦住它的地方。**

判据（写码时自问）：这个能力会不会弹卡？会 → 它有用户可见面 → 卡上那行字必须自己看过。

危险在于**默认文案总是存在**：新 operation 不加分支不会报错、不会空白，它会安静地显示一句
「查看细节」或——更糟——匹配到别的分支显示一句**错的**。
「用户面对一张不说改了什么的卡点同意，那张卡就等于没有」——确认卡的存在意义就是让人看懂再点。

## 同类扫描（哪几处、逐条判）

扫 `readableToolPreview` / `readableToolTarget` 的分派：它们按工具名**字符串包含**匹配，
没有穷尽性检查——**新工具漏加分支永远不会编译报错**。这是与 canvas operation 那 4 处
裸字符串 allowlist 同一族的问题（见 [[silent-degradation-looks-like-feature-absent]]）。

- `readableToolPreview`：7 个分支 + 兜底。兜底是「查看细节」——**看起来像正常文案，不像缺口**。
- `readableToolTarget`：按 `record` 上有没有 `nodeIds`/`nodes`/`shots`/`clipIds` 猜对象数。
  **参数形状不同的新工具会被猜错**（`patch_shots` 的 `select` 不是数组，会一路掉到别的分支）。

## 通用处置

1. **加工具/加 operation 时，把「卡上显示什么」当成交付的一部分**，和 schema、执行器同等。
   已落 `residentToolDisplay.test.ts` 的三条断言 + 红灯探针（把分支条件改成永不命中 → 2 条红）。
2. **兜底文案不该长得像正常文案**。「查看细节」读起来完全正常，所以缺口能一直藏着。
   （未做：把兜底改成可被门岗识别的形态。记在这里，不假装已解决。）
3. **写完工具先问一句「它会弹卡吗」**，会就去把那张卡看一眼——这比任何单测都快地暴露问题。

## 顺带一条：探针没红 ≠ 门岗有效

做红灯探针时我把文件切坏了，vitest 报 `no tests` —— 我差点当成「红了」。
**`no tests` 不是红灯，是探针无效。** 重做了一个只把分支条件改成 `false &&` 的探针，
文件结构完整，才真红了 2 条。同一条教训在 [[silent-degradation-looks-like-feature-absent]]
的 §15.5 已经写过一次（探针必须走门岗真正走的那条路），这次是它的另一种形态：
**探针必须让被测代码仍然可运行，否则你测的是「文件坏了」不是「规则生效了」。**
