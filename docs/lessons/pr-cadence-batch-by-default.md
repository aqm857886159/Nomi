# PR 攒到阶段边界再开，默认不开 PR

> 📎 教训 · 首次记录 2026-08-26 · 状态：现行
> **触发场景**：一个切片 / 一个 bug / 一个门岗改完了，手已经伸向 `gh pr create`；或给 agent 写 brief 时没写 PR 纪律。

**结论**：**默认不开 PR**。活干完 → commit 到**阶段分支**（一个大阶段一条长命分支）→ 继续下一件。到了阶段边界才开一个 PR。这条取代了 2026-08-25 的旧标准「每天 ≤3 个 PR」——旧标准还是太碎。

> **⚠️ 前提（2026-09-02 补，踩过）**：「攒批」成立的前提是**你还要继续往下干**——攒的是「下一件活」，不是「攒着不交」。
> **手上没有下一件活、要把结果交回给用户的那一刻，就是阶段边界，必须开 PR。**
> 一句话判据：**问自己「这条分支上还会不会再有下一个 commit」——不会，就开 PR。**
> 反面实例：2026-09-02 把一个凭据不变量下沉的加固 commit 到一次性任务分支 `claude/kind-payne-00b92f`，然后援引本条「默认不开 PR」收工，还自称「攒到阶段边界」。可那条分支既没有后续工作可搭车、也没有 PR——活就**搁浅**在分支上，永远进不了 main。用户一句「你不开 PR 怎么合进去呢」当场点破。
> 误用的根因：本条写的是「commit 到**阶段分支**（长命）→ 继续下一件」，我却套在**一次性任务分支**上。一次性任务分支天然没有「下一件」可搭，套用这条 = 制造孤儿分支。

**为什么会踩**：单个 PR 的真实成本不是写码，是**墙钟**。

- Quality Gate 一轮 6–25 分钟；分支要 up-to-date 就得 `update-branch` 再等一轮。
- 多 PR 并行还得排合并列车。
- `package.json` 的 `gates` 链几乎必冲突，要人手解。

2026-08-25 一天合 16 个 PR，08-26 凌晨四个 PR 光合并环节就吃掉大量墙钟。**小 PR 的边际收益（独立回滚）远小于这份固定开销。** 次要一层：维护者不看板面（审合都在执行体这边），每个 PR 对他只是通知和变动感。

**怎么用**：

- 「大阶段」= 一个能对用户讲清价值的完整块（例：E1+E2 一起、harness 核心、测试框架整修）。**不是**单个切片、单个 bug、单个门岗。
- **但收工即边界**：一个块没攒满、手上却没有下一件活了，就按现有的量开 PR。宁可 PR 小，不可活搁浅——搁浅的成本（永不合入 + 分支越落越远 + 事后要 `update-branch` 追几百个 commit）远大于多跑一轮 CI。
- **文档、小修、体验摩擦、门岗、测试修复——全部搭车**，永远不单开。
- 派 agent 时 brief 必须写死：**「commit 到分支，不要开 PR、不要 merge」**（很多 agent 默认会自己开 PR，得明确拦住）。
- 对冲长命分支的代价：**定期把 `origin/main` 合进阶段分支**，别等到最后。尤其 `package.json` 的 `gates` 链冲突要按**并集**解——漏掉一个 check **不会报错**，门岗就此静默消失。
- 已经开着的 PR：别中途撤，验完照常合掉；新工作按新规矩走。

**出处**：2026-08-25 / 08-26 两天的合并墙钟实测。相关：[方案讨论期别急着 commit/PR](discuss-before-committing-docs.md)、[gates 全绿 ≠ 走查真的跑过](gates-green-does-not-mean-walkthrough-ran.md)（攒批期更要自己跑走查，别靠 CI 兜底）。
