# 样张交付 = 逐屏逐件走读，不是统计表汇总

> 📎 教训 · 首次记录 2026-09-02 · 状态：现行（用户拍板的交付制）
> **触发场景**：样张 / 设计稿 / 大改版做完了，要交给用户拍板；或发现自己正在用「改了 N 处、复用 M 件、负荷降了 X%」这类汇总表交差。

**结论**：设计类交付物必须是**逐屏逐件的人话走读文档**：每一屏、每一件，按「**这是什么 / 为什么这么设计 / 用户什么时候碰到它**」三段讲清。统计表式汇总（形态映射表、计数对账）不合格——那是给自己核账用的附录，不是给拍板人看的正文。

**为什么会踩**：Agent UI 重设计交付时先给了映射表 + 计数式汇总，拍板人读完复述不出任何一件「为什么长这样、我什么时候会碰到」——等于没交付（这是 `CLAUDE.md` D6 表达纪律在样张交付上的实例：读完要能复述「为什么」）。改为走读制后发现它不只是汇报礼仪：**走读文档是验收合同的上游事实源**——功能层一致性合同的每条行为承诺，就是从走读文档的「这是什么 / 什么时候碰」推导出来的；写不出三段式的元素，多半自己也没想清它凭什么存在。

**怎么用**：
- 交付正文按屏组织，每件三段：这是什么（人话，零内部术语）/ 为什么（设计理由 + 被它压掉的备选）/ 什么时候碰（真实任务里走到它的时刻）。
- 汇总表（复用源分布、负荷计数、形态映射）只作附录索引，不当正文交。
- 走读文档随定稿一起落仓，编排者拿它转述给用户；后续一致性合同从它推导承诺，别另起一份口径。
- 自检即 D6：拍板人读完能不能复述「为什么」和「我在纠结什么」——不能就重写。
