# 样张拍板只卡大 UI 改动

> 📎 流程纪律 · 首次记录 2026-08-25 · 状态：现行
> **触发场景**：一个 UI 改动做完样张、正准备停下来等拍板时；不确定某个改动要不要前置等人看时；等待拍板期间无事可做时。

**结论**：`CLAUDE.md` R8 的样张拍板**不是一刀切**。只有**改变产品面貌的大改动**要停下来等人亲眼看；小 UI 和非 UI 照常推进，**等待期并行推别的轨，不许闲等**。

**为什么这么定**（2026-08-25 拍板原话：「重要的样张还是需要我去观察和看的，比如 Agent 的完整界面，这属于很大的改动了。但是可以先推进不需要我去看的东西，不要卡住」）：

拍板这个动作有**墙钟成本**——它需要一个人类在场、看完、给判断。把每个小控件都排进这个队列，整条线会空转，直接违反 `CLAUDE.md` P0（默认自主推进到底）。而大 UI 改动值得付这个成本，是因为它**不可逆的部分多**：新的交互范式一旦铺开，后面所有功能都得跟着它长，返工代价远大于一次等待。所以判据是「返工代价 vs 等待代价」，不是「重不重要」。

**怎么用**：

- **大 UI 改动**（新完整界面、新常驻主栏、交互范式变更）：样张出完 → **停下等拍板** → **等待期间并行推进非 UI 轨**（harness / 后端 / legacy 收敛这类看不见的活）。
- **小 UI**（≤ L2 情境控件、已获批样张或已定稿词汇表模式的延伸）：**直接实现**，交付时附截图供观察。P3 对账仍然做，只是**不前置卡实施**。
- **非 UI**：照 P0 一杆到底。
- **拿不准时的判据**：「这个改动会不会让他打开 App 觉得换了个产品」——会 = 大改动，等拍板。

**注意**：这条只放宽**实施前的拍板闸**，不放宽交付后的验证。P3 / R13 / R16 那套体验走查仍然全量做，两者不冲突。
