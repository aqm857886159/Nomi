# 接到「修 X」先花 30 秒查在途 / 已合的修复

> 📎 教训 · 首次记录 2026-08-25 · 状态：现行
> **触发场景**：接到「修 bug X / 修 flake X」的任务，或准备把一个实施切片派给子 agent。任务描述看起来再完整都不豁免。

**结论**：动手前先扫在途和已合的修复：

```bash
gh pr list --state open --limit 15                  # 标题常直接写着同一个根因
git log --all --oneline -- <可疑文件>                # 未开 PR 的分支也能扫到
gh pr list --state merged --search "<切片关键词>" --limit 5
git log --oneline origin/main -20 | grep -i <关键词>
```

**为什么会踩**：本仓常态是 20+ worktree、多个 agent 会话并行，「同一个痛点两个 session 同时在修」不是小概率事件。任务描述本身也不可靠——任务作者往往不知道在途 PR。

- 2026-08-25 修 productionRun 单测 flake：任务给了 a/b/c 三个候选方案，按 c 修完 11 个文件、跑完 7 轮验证，才从一行记忆小字里发现 **open PR #139 早就用更深一层的方案（durability 分级）修了同一个 flake**，且已 13 轮验证全绿。两者在 11 个文件上硬冲突。最后把分支重组成叠在 #139 之上的 delta（只保留它没有的门岗 + 漏网文件），白做部分 ≈ 半小时 + 一整轮验证马拉松。任务给的三个方案里根本没有 #139 那条路。
- **变体（同日又踩一次）：派发实施切片前也要扫「已合修复」，不只 open PR。** 派 B1a–d 配置层切片给子 agent，agent 进场才发现 **PR #134 前一天就把整个切片合进 main** —— 交接卡没标已交付，派发人也没扫 merged。白派一轮，幸好 agent 守 P1 没重做、只做核对。

**怎么用**：

- 查到在途修复后别急着弃自己的：先比根因层次（谁更治本），再看能不能**叠**（delta 化）——相同部分采纳对方、独有部分保留。比赛跑或各写一版都好（P1 无并行版）。
- 派切片给 agent 前，把上面四条命令跑一遍再写 brief。

**出处**：2026-08-25 productionRun flake 返工（PR #139）与 B1a–d 切片空派（PR #134）。相关：[判测试翻红前先查别的 worktree](flaky-test-check-other-worktrees-first.md)（同机并行会话也会污染测试判断）。
