# 设计派线和等待之前先读官方的缓存规则，做完用真实 usage 验证

> 📎 教训 · 首次记录 2026-10-31 · 状态：现行
> **触发场景**：要写等待脚本、定一条线的上下文或线型、想改缓存时长或压缩设置；或者说不清子线的开销花在哪。

**结论**：这些设计都受官方的缓存、计费、上下文规则约束。动手前读官方文档，写出对这次设计的影响，用真实轨迹算账再定，做完用 usage 字段验证。这次凭印象定的等待脚本和价格都错了。

**为什么会踩**：
- **等待脚本超过缓存寿命**。协调会话写的等待脚本每次让子线等 9.5 分钟，子线缓存默认只活 5 分钟，订阅也一样，只有主会话在套餐用量内是 1 小时。隔够 5 分钟，下一步要把整段上下文重写一遍。两天里这种步只占子线步数的 3.6%，却花掉子线超过三分之一的开销。没人在写脚本前看过官方规则。
- **复盘时又凭印象记错价格**。把一个模型的缓存读价记成另一个模型的，算出来的倍数差了一半，核对官方价格表才发现。
- **1 小时缓存听着更好，算完并不是**。官方确实给了开关，但 1 小时档每次写入都更贵。按真实轨迹重放，它比 5 分钟加 4 分钟轮询贵 7%，等待超过 2 小时的线也一样。官方文档也写了短促的工作上它更贵。
- **不知道能给子线封顶**。同一份用户设置下，Opus 子线约 47 万就压缩，Sonnet 子线到 76.5 万也没压缩，每一步都在重读。官方提供了线型级的 `autoCompactWindow`，之前没查过。

**怎么用**：
- 单次等待和前台命令压在 4 分钟以内。5 分钟从上一个请求算起，生成时间也算在内，不要贴着 5 分钟等。
- 想动缓存时长、压缩窗口、线型工具，先用真实轨迹重放算账，别看一眼文档就改。这些取舍换了等待占比或价格就可能翻转。
- 分清官方写了的和只是实测的。官方没写订阅额度里读、写、输出各算多少，API 单价不能换算成额度。
- 量 token 必须按 API 消息 id 去重。同一条消息会记多行，不去重虚高一倍多。
- 目前的结论和字段名在编排手册 §20 第 8 条。
