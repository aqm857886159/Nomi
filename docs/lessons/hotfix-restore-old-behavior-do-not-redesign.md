# “以前能用、现在坏了”的热修：先查以前怎么做，最小恢复，别在热修里重新设计

> 📎 教训 · 首次记录 2026-09-29 · 状态：现行
> **触发场景**：热修一个“以前可以、现在不行”的能力；你开始想加新通道、新规则、新弹窗。

**结论**：先用 `git log` 找到是哪次改动把能力弄没的，用最小改动恢复原来的行为；结构性的毛病另记结构主题，并告诉用户这次只是止血。方向不确定就先问用户“以前是什么样”，不要自己设计一套新规则。

**为什么会踩**：新装机改不了某中转站接口地址这一单，代码只改了约 60 行，时间却花在三次改方向上——先是只放行官方域名，后来又要区分用户和程序、加专门通道和提醒弹窗，都是过度设计；最后用户一句“让他在填 API 的地方可以改不就行”才定下来。

**怎么用**：恢复能力要在规则的主人那里改；先回答“这个行为有人要吗”（见 [修回归前先问谁要它](restoring-a-regression-needs-a-user-reason.md)），再决定恢复。

**出处**：2026-09-29 该热修的复盘。
