# 判定「这段从没生效过」之前，先顺着效果找一遍所有来源

> 📎 教训 · 首次记录 2026-09-26 · 状态：现行
> **触发场景**：你准备以「main 上这段代码根本没生效」为理由删掉它，或者用这个前提说服用户改拍板；尤其是同一个可见效果（画布铺开、自动聚焦、自动滚动）可能有好几个触发点的时候。

**结论**：「这个函数从没生效」和「用户看到的这个效果从没出现」是两回事。删之前，先找出这个**效果**的所有写入口（`node scripts/door-map.mjs <执行动作的符号>`，例如 `requestCanvasFit`），再用走查在 main 上确认每一个场景的真实表现。

**为什么会踩**：

- PR #880 要删掉「打开项目时自动适应视图」（`useAutoFitOnLoad`）。证据很硬：它在节点量好尺寸之前就做判断，包围盒是空的，main 上从来不起作用。用户之前选了「保留」，也是基于它一直能用这个错误前提。
- 删掉之后，E2E 里「新手引导已自动铺开画布」挂了。引导示例之所以能铺开，靠的是另一条路：Agent 批量建卡之后，`applyCanvasToolCall` 发出的那一次 `requestCanvasFit`。同一个 PR 按「程序不主动移动画布」把这一次也删了。
- 结论本身没错（那个函数确实没生效），但以为「铺开这个效果只有它一个来源」是错的。有 E2E 兜底，这回没有带着问题发出去。

**怎么用**：

- 用户可见的「程序替你动一下」类效果（视口移动、聚焦、滚动、展开），一律按效果数门：执行动作的那个函数的所有调用者都列出来，不能只看你要删的那个调用者。
- 真要去掉一个效果时，把「谁在什么场景下还需要它」逐个列清楚。需要它的场景，由那个场景的 owner 显式调用一次（这次是新手引导自己在打开示例后适应一次），不要把全局的自动行为留下来。
- 允许移动视口的地方有登记表：`canvasViewportMovers.structure.test.ts`。新增一个移动者，必须写清是用户哪个动作触发的。

**出处**：PR #880（2026-09-26）CI 的 E2E `guided-canvas`；证据截图见该 PR 正文。
