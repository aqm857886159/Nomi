# 修已有的东西前，先问这一整块归谁，不要只问眼前那一段

> 📎 教训 · 首次记录 2026-11-22 · 状态：✅ 已固化（`scripts/check-direction-trailer.mjs` 查复盘模板 §5）
> **触发场景**：同一处反复被补（热点报警响了）、写类根因复盘、任务书里想写「同类产品：不适用」。

**结论**：报警响了、复盘也写了，同一处还是一层层往上补，是因为复盘只问了眼前那一段「有没有现成的」，答案自然是「这一段没有」。要先问整块：这件事整块叫什么、已经在用的库或标准是谁、我们哪里绕开了它。写不出这三样，就还没想清楚。

**为什么会踩**：

- 用 21 个真实旧案试跑（补 ≥3 次后才删 / 换 7 个，领域内反复修 3 个，修一次就好 11 个）：「补」压过「删 / 换」的漏口里，排第一的是「问题问窄了」，占 7/10。
- 报警本身是对的：热点计数命中、复盘模板也要求写「现成方案有哪些」。但库只问那一段、任务书写「同类产品：不适用」，复盘就成了对补丁的事后辩护。
- 照新规则回放同样的案例，误伤 2 个（把本该直接补的小事也拦了）；所以只加在已有的热点报警后面，不按目录另开触发，不把报警变成拦截。

**怎么用**：

- 写复盘时按模板 §5 写三行：`这一整块：`、`归谁：`（名字 + 版本 + 出处）、`我们哪里绕开了它：`（file:line）。
- 库本身做错了：照公认标准改、登记待换，不在库外另补一层。
- 要另写一层，理由只认「它做不到我们独有的哪一点」。
- 提交时 `check-direction-trailer` 对文件名日期 ≥ 2026-11-23 的复盘逐项核对；老复盘不追溯。
- 30 天后用试跑脚本对新发生的热点案例复测，看「问题问窄了」这一类是否减少。
