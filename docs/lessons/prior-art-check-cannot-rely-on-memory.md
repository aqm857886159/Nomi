# 查不查不能靠记性——「先看别人做了没」必须是机器逼出来的一步

> 📎 教训 · 首次记录 2026-09-07 · 状态：✅ 已固化（`check:prior-art` + R27 §15/§16 反方 agent 步骤接管）
> **触发场景**：准备动手写一个「通用能力」；派实施任务书；接框架 / 用它一个没用过的层；发现自己正在从零实现某个听起来很常见的东西。

**结论**：**动手之前先派一次反方**——它的交付物不是「做出来」，而是「证明这件事已经有人做过了」。报告落 `docs/research/<日期>-<主题>/prior-art.md`，方案里抄成 `## 先查别人` 一节（四问各带 URL 或 file:line），实施任务书引用那份方案的路径。没有它，任务书不发。`pnpm run check:prior-art` 会拦。

**为什么会踩**（三条机制，都不是「下次注意」能修的）：

1. **系统只奖励「做出来」，不惩罚「没查」。** 交付评价里，「写出来了 + 门岗全绿」有分；「查过了、发现已经有、于是什么都没写」看起来像空手一轮。在这个分数下跳过检索是**局部最优解**——不是懒，是理性。
2. **任务书的视角天生是「把这件事做出来」。** brief 写目标和验收，没有一格写「先证明没人做过」；每个实施体只看得见自己那一块，于是没人持有这个问题。2026-09-06 #546：接 pi SDK 时该查的都查过、结论也写进了文档，但**没有任何一份任务书引用它**，五个实施体把 pi 已有的会话持久化 / 重试 / steer / 资源加载 / 有序转录各重造了一遍，而且更差。
3. **文字提醒在高负载下必漏。** `CLAUDE.md` 里 R5 / R6 / R20 / R29 都写着要查，但提醒的命中率随上下文压力单调下降，而实施任务恰恰是上下文最满的时候。**提醒不是防线（R28）。** 用户因此不得不一次次亲口说「你先去查查别人做了没」——那句话是在替一道缺失的门岗干活。

**怎么用**：

- 方案文档里写 `## 先查别人`，四问各一行、每行带 URL 或 `file:line`：**依赖里已有？**（先看 `docs/engineering/dependency-capabilities.generated.json` 的能力词表，比人手写的登记表全）/ **仓库里已有？**（`git grep`，按签名搜别按报错串搜）/ **生态里已有？**（同类开源 + 官方文档，写清「为什么不用」）/ **TikHub 自媒体里怎么说？**（没查就明写「本轮未查」，别冒充覆盖）/ **结论**：用已有还是自研 + 理由。
- 收反方报告时**至少抽一格点开出处**：门岗只判形式（三条链接就能过），判不了查得认不认真。指不开 = 按没查处理。
- 自己是那个实施体时，把「找到已有」当成一次**成功**来报，不是空手——这条心态上的翻转是这整条教训的根。
