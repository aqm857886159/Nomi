# 方案讨论期别急着 commit / 开 PR

> 📎 教训 · 首次记录 2026-08-24 · 状态：现行
> **触发场景**：正在和用户来回打磨一份方案 / 设计文档，每改一版就想跑 gates → commit → PR。区分点：**方案还在对话里演化**，而不是执行一个已拍板的计划。

**结论**：设计 / 方案对话回合里，只改工作区文件，**不 commit、不开 PR**。等用户明确「就这样 / 落吧」或讨论自然收束，再走 gates → commit → PR。代码实施类工作（执行已拍板的计划）不受此限，照常自动 commit + push（R11）。

**为什么会踩**：讨论期的文档在快速演化，每轮小修就跑一遍 gates → commit → PR → merge，成本全是墙钟（Quality Gate 一轮 6–25 分钟 + 合并列车 + `gates` 链冲突要人解），而产出的中间版本第二轮就作废了——付了固定开销买了一个会被立刻覆盖的快照。

同时这也是 P0「自主推进到底」的边界：P0 不适用于**正在对话打磨中的方案本身**。那个时刻的「推进」= 把讨论质量拉满，不是把 git 流水走完。2026-08-24 用户在总体方案讨论中两次打断纠正过这一点。

**怎么用**：

- 判断闸：这份改动是「还在争论要不要这么做」还是「已拍板、正在实现」？前者不落 git，后者照常。
- 讨论收束后一次落定，把这一轮所有版本合成一个 commit，别把演化过程留在历史里。

**出处**：2026-08-24 方案讨论中的两次打断。相关：[PR 攒到阶段边界再开](pr-cadence-batch-by-default.md)（同一笔墙钟账，适用于实施期）。
