# 讲方向必须说人话：自造名词和标准术语都要解释

> 📎 教训 · 首次记录 2026-08-11 · 状态：现行（2026-08-24 复发一次，条件已收紧）
> **触发场景**：写方向提案 / 方案对比 / 取舍说明前；解释一个 bug 的成因前；对方回「这些是什么东西」「我没理解，仔细讲讲」时。

**结论**：讲方向、方案、取舍或 bug 成因时，**凡是对方没有的前置知识都要补**——自造的速记词要解释，**行业标准术语一样要解释**。并且**从对方看得见的东西起头**，不从机制起头。

**为什么会踩 —— 第一次（2026-08-11，自造名词）**：

MCP 体验研究汇报里连用「转述 / 行内进度 / 增强层 / 接线 / 对话原生」等自造速记词。对方读不懂，被迫反问「这些是什么东西」，并要求把这条写进规则。

机制：这些词对写的人是「显然的普通话」，对读的人是黑话——**尤其是为归纳机制而自造的名词**（把六件事压缩成「六条接线」这类）。决策质量取决于对方真读懂了机制；读不懂就无法拍板，整份汇报白写。

**为什么会踩 —— 第二次（2026-08-24，标准术语，同一条规则更严的版本）**：

讲 undici 那条 `ERR_INVALID_STATE` 竞态（上报 nodejs/undici#5715）时，用了 microtask / promise settle / uncaughtException / 异步可迭代 / call site 这些**行业标准词**，自认为讲得很清楚，对方直接回「不是，我没理解你说的什么，仔细讲讲」。

机制：第一次以为边界是「我自造的词要解释」，**真实边界是「对方没有的前置知识都要补」**——标准术语和自造词没有区别，都是黑话。而且当时是**从机制起头**讲的（先讲 `ReadableStream.from` 怎么错），对方根本不知道这跟他有什么关系。

**重讲对了的那版结构，照抄这五步**：
1. **从对方看得见的东西起头** —— 「之前有用户反馈 Windows 上弹错误框，拖进度条会出」，不从代码起头；
2. **陌生的第三方名词先交代身份** —— 「undici 是什么：Node 自带的底层库，我们没主动用它，但有一行代码会走进去」；
3. **机制换成日常比喻，而且比喻要能承重** —— 送水工去打水、回来时按规矩关水龙头、可水龙头已经被关了 → 「关两次、第二次没检查」。**配图也照这个比喻画，别画代码**；
4. **抽象后果也要落成比喻** —— 「接不住」讲成「已离职三个月的员工突然寄投诉信，公司里没部门认领」；
5. **最后才说要他定什么**，且只留一件事。

**怎么用**：
- 发出前扫一遍草稿，每个名词问一句「他上周会说这个词吗」——不会，就换比喻，或补一句身份说明。
- 自检标准（`CLAUDE.md` D6 原有）：对方能不能**不查任何资料**复述出「为什么」和「我在纠结什么」。不能 = 没讲清。
- **对方说「没理解」时不要在原文上打补丁，整段推倒重写**（第二次是重写才对的）。
