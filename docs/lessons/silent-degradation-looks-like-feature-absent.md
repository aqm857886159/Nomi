# 静默降级把「能力缺席」伪装成「这里本来就没这功能」

**踩到日期**：2026-09-03（分镜表 v5 首次真实付费闭环走查）
**场景标签**：D 平台 / E 产品

## 现象

真实付费走查在创作页一口气撞见三件事，看上去是三个独立 bug：

1. 侧栏「新建分镜方案」点了没反应
2. Agent 报「当前创作区文稿为空」——而文稿就在屏幕上
3. Agent 手里没有分镜规划工具

三条实测下来是**同一类机制**，而且都不是「写错了」，是「缺了但没人喊」：

| 症状 | 真根因 | 降级方式 |
|---|---|---|
| 入口哑火 | `d270d34e` agent-host 移植换掉旧创作面板，而旧面板是 `storyboardPlannerLauncher` 的**唯一注册者** | `launcher?.()` → 无操作；`onStoryboard={launcher ? … : undefined}` → 按钮直接不渲染 |
| 没有分镜工具 | 工具 profile 靠手写正则猜措辞，`STORYBOARD_INTENT` 里有「镜头卡/镜头设计」却没有「镜头」——而「拆镜头」是产品自己的按钮文案 | 正则不匹配 → 悄悄降级成基础 profile |
| 文稿为空 | 正文只能从**挂载中的** tiptap 桥读；分镜页/生成页不挂载编辑器 | 抛 `surface_port_stale` → 模型把「读不到」讲成「为空」 |

## 这一类的判据

**能力的可用性被绑在「某个 UI 组件的挂载生命周期」或「一张手写词表」上，而不是绑在数据/意图本身；
缺席时静默降级，降级后的样子与「这里本来就没这功能」完全不可区分。**

危险就在最后半句。三处全部：类型合法、无异常、无日志、49 个门岗全绿、CI 通过。缺口活了两天，
直到有人真的拿钱跑一遍闭环才撞见。**「没报错」在这一类里不是好消息，是症状本身。**

## 同类扫描（哪几处、逐条判）

扫了两种写法：

- **`?.()` 调用 store 里的能力**：全仓 0 处（本次那处已改）。
- **`onX={cond ? handler : undefined}` 让控件消失**：全仓 8 处。逐条看，多数是**正当的情境可用性**
  （不可拖时没有拖拽 handler、非端点时没有 hover），不属于本类——它们的 `cond` 描述的是
  「此刻状态如此」，不是「本该有的能力不见了」。唯一擦边的是
  `VendorOnboardCard.tsx:358` 的 `onToggle={hasApiKey ? … : undefined}`（没 key → 开关静默失效）。

真正危险的是更窄的一族：**能力桥接槽**——一个组件挂载时注册函数/接口，别处按需调用。全仓只有两个：
`creationDocumentTools`、`storyboardPlannerLauncher`。

## 通用处置

1. **缺席必须可见**：能力不在场时控件**禁用并说明为什么、去哪儿开**（§1.6 C4），不做成点了没反应。
   `?.()` 在能力槽上是禁用写法——它把「功能整条没了」和「这次没必要做」写成了同一个样子。
2. **注册者存在性要有测试钉住**：`src/workbench/capabilityBridgeSlots.test.ts` 逐个槽断言「至少有
   一个非 null 注册者」。**新增此类槽必须在该表登记**，否则下一次搬运还会静默丢掉它。
   只有两个实例，所以用测试不用 `check:*` 脚本——为两个实例造门岗是过度工程（R20）。
3. **我们自己知道意图时不要去猜**：入口按钮/菜单项显式声明（如 `toolProfile: 'storyboard'`），
   关键词表降为自由文本兜底；兜底表至少要收录**产品自己教给用户的说法**。词表与产品文案脱钩，
   就是「点自己的按钮却触发不了自己的功能」的成因。
4. **真相源别绑在 UI 生命周期上**：持久化的那份才是真相源，挂载中的组件是它的活视图。

## 复发一次（同一天，同一条链路）

修完上面三条、跑第二轮真实付费复验，**同一类机制第三次出现**：拆镜头入口拿到了工具
（`toolProfile` 显式声明生效了），但 Agent 收到指令后回「我先读全文，确认原稿内容…」
然后一次工具都没调——因为**还有第二张猜措辞的表**：`isAgentActionIntent` 决定「执行还是聊天」，
launcher 那句话没命中，被判成 chat 模式，于是它叙述而不行动。

**当时的同类扫描漏了它**，因为我只扫了「静默降级的写法」（`?.()`、`cond ? h : undefined`），
没扫「同一条链路上还有几张按措辞猜的判据表」。判据表本身才是这一类的核心，不是它降级的姿势。

**补充处置**：一个入口发出的请求，**沿途每一张判据表都要显式给全**——工具集给了、执行/聊天没给，
等于没给。数一数从入口到执行之间有几个「猜」的环节，一个都不许剩。

## 更要紧的一条

三个症状里，报告对根因的两处猜测事后实测**都是错的**（猜 `availableModels.ts:135-153` 按名字挑选、
猜能力白名单缺工具）。真根因分别在别处。**看起来对的猜测和实测长得一样，区别只在有没有跑。**
下判断前先跑一个最小探针把真实值打出来——本次三条根因全部是探针定的，读码全猜错。
