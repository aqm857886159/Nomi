# 评审要放在意见还能落地的时刻，不是每次 commit/push

> 📎 教训 · 首次记录 2026-09-15 · 状态：✅ 已固化（R25 改版 + `pnpm run review:branch` + pre-push 收据校验接管）
> **触发场景**：给任何「每次 X 都自动评一遍」的闸门做设计或复盘时；某个闸门开始「大多数时候有话说但没人听」时；想靠提高触发频率来提高质量时。

**结论**：自动评审的价值不由「跑了多少次」决定，而由「意见出来时人还愿不愿意改」决定。把评审钉在 commit/push 这种**活已经干完**的时刻，等于系统性地把它的输出扔掉——它只剩成本（墙钟、排队、体积上限、逼人拆提交）。评审要放在**交工前**：整段改动已成形、人还在现场、改一版的代价还是几分钟。

**为什么会踩**：R25 最初的判断是「越早拦越好」（R28 防线建在最早能拦住的那层），于是把评审接在 pre-commit / pre-push 上。这条推理对**正确性**闸门成立（敏感数据一进历史就是永久的，所以扫描必须留在 pre-commit），对**建议性**闸门不成立——建议没有「不可逆」这一维，它只有「被读到」和「没被读到」。

2026-09-14 一晚的 relay 数据把差别量出来了：

| 数字 | 值 |
|---|---|
| 评审次数 | 45 |
| 通过 | 19 |
| 「有发现但放行」 | 24 |
| 因 150KB 体积上限被挡 | 2 |
| 因内容被挡 | **0** |
| 那 24 段发现里被人读过的 | **0** |

三个连带的坑都是同一个根因的症状，不是独立问题：

- **重复审**：一条 17 个提交的分支，push 时按提交逐个送审 → 同一段代码审 17 遍。
- **体积上限反向塑形**：单次 150KB 的上限把「拆成合理的提交」变成「拆成能过闸的提交」，闸门开始决定提交的形状。
- **全机一把锁**：`/tmp/nomi-ponytail.lock` 让所有并行 lane 排队，等的是一件没人读的事。为了让锁不误伤，又长出「按 diff 字节 + 负载派生墙钟」的公式——一层补丁扣一层补丁，全都服务于「评审会拦住 Git 操作」这个前提。前提一删，三层全部删掉（P1）。

**怎么用**：
- 给闸门分类再选时机：**不可逆的** → 最早那层（pre-commit 敏感扫描、编译器、类型）；**建议性的** → 意见还能落地的那层（交工前、开 PR 前）。别把两类放在同一个 hook 里，它们的失败成本差好几个数量级。
- 判一个闸门是不是空转，只看一个数：**它的输出被读过几次**。「拦住过几次」会骗人——拦住 0 次而「有话说」24 次，就是纯成本。
- 想往闸门上加补丁（放宽超时、加锁、提上限、自适应公式）之前先问：这层补丁是在治病，还是在维持一个错误的触发时刻？三个以上补丁指向同一个前提，就该删那个前提。
- 评审的收据绑**内容**（树），不绑「人说审过了」：rebase、改提交信息不改树 → 不重审；改一行 → 树变、收据当场失效。手工 ACK 是旁路，机器签发的内容指纹不是。

**出处**：2026-09-14 relay 评审日志（45 次的分布见上表）；R25 改版见 `docs/engineering-rules.md` 的「R25 交工前 Ponytail 评审」与 `docs/fixes/2026-09-15-ponytail-review-before-handoff.root-cause.json`；实现在 `scripts/ponytail-review-branch.mjs`（评审 + 分块 + 收据）与 `scripts/ponytail-review-hook.mjs`（pre-push 只查收据）。
