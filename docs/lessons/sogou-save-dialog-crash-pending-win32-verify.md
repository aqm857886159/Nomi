# Windows 改保存名闪退：根因已修，但 win32 真机未验，尚未闭环

> 📎 教训 · 首次记录 2026-08-12 · 状态：现行（**未闭环**）
> **触发场景**：用户再次报「下载视频后重命名，整个 app 闪退」；或任何「只有某个第三方输入法会崩」的 Windows 崩溃；或有人要给 `dialog.show*Dialog` 传第二个参数（父窗口）而被结构闸拦下、想知道为什么。

**结论**：根因**不是**输入法本身，是**跨线程持有模态属主**。`downloadAsset.ts` 给原生保存对话框传了父窗口，而 Electron 把对话框跑在自己专用的 COM STA 线程上、父窗口 HWND 属于主 UI 线程 → 跨线程模态属主 → 两个线程的输入队列被绑定 → 第三方输入法 DLL 在 `TranslateMessage` / `PeekMessage` 里重入 `Imm*`（微软记录在案的 IME 崩溃族）。

**已修的部分**：彻底不再传父窗口，并加了全仓结构闸 `electron/nativeDialogParent.invariant.test.ts`——任何 `dialog.show*Dialog` 传第二个参数即红。改动在分支 `claude/practical-fermat-514235`（`5d1229a6`），五门全过。

**还差什么才算闭环**：**win32 真机未验证**——在 macOS 上复现不出（IME 栈不同），所以「mac 全绿」不构成修好的证据。2026-08-12 用户拍板：先发修复 + 观察，暂不把重命名搬进 Nomi 自己的输入框（那是备选方案，真崩了再动）。

**为什么会踩**：上一轮（2026-07-30）以为修好就收工，当时只换了「传哪个窗口」，没有去掉「跨线程持有属主」这件事本身——于是同类崩溃在 v0.19.0 又回来了。这次同样不能凭 mac 全绿就宣布修好。

**怎么用**（用户下次提这个 bug 时，**先要这两样证据再判断，别重新猜**）：

1. `app.getPath("logs")/nomi-crash.log` 的最后几行——若停在 `save-dialog:open` 而没有对应的 `closed`，就是崩在原生对话框里（面包屑是同步落盘的，进程被带走也留得下）。日志现在自带版本 + 平台，能对上用户装的是哪个构建。
2. `app.getPath("crashDumps")` 里的 minidump——能指名是哪个 DLL（找输入法自己的 `.ime` 模块，如 `SogouTSF.ime` / `SogouPY.ime`）。

若证据显示仍崩在对话框，就执行备选方案：把改名搬进 Nomi 自己的输入框（走 Chromium 输入栈，Nomi 各处该输入法输入都正常），原生对话框降级为次级的「换位置」入口。

**出处**：2026-07-30 首修（未除根）、2026-08-12 根因修复 + 结构闸（`5d1229a6`）。
