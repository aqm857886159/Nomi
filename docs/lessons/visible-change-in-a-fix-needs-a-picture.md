# 修 bug 时长出来的界面也要先出图，对过字不等于对过设计

> 📎 教训 · 首次记录 2026-11-02 · 状态：现行
> **触发场景**：修 bug 时新加了确认、提示、按钮或一个新状态，或者挪了它们的位置、换了颜色；准备在 PR 里写「纯修复、布局沿用」的时候；准备看自己的截图说「符合」的时候。

**结论**：用户看到的东西变了，不管这个 PR 叫什么，都先查以前定过什么、看真实样子、出图给用户看，再动手。聊天里对过字不算对过设计。自己看截图只能证明构建符合自己写的合同，不能证明设计是对的。

**为什么会踩**：把锁卡当 bug 修，只跟用户对了字，就说「界面布局不变」，PR 也写了不适用设计流程。真实界面上多了一个盖住卡片的浮层，一句没有上下文的话，一个泛词按钮；画布上的确认条还把免费的「重新取回」顶出了卡外。三页长成三个样子，又绕开了已有的花钱确认卡。设计系统 §1.9.2 早就写了花钱确认走确认框、写清后果、用具体动词，当时没查。用户看到截图才发现。

**怎么用**：
- 说「界面没变」之前，先把改动前后的真实截图放在一起看一遍。多了元素、挪了位置、多了状态，都走设计流程。
- 新的确认或提示先找已有的家（`spendConfirmationRequirement`、`SpendConfirmDialog`、`confirmDialog`），找到就不画第二套。
- 用户定过的字，如果和用户定过的设计系统对不上，停下来拿给用户定，不自己挑。
