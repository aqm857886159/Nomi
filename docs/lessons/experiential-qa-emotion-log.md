# 功能落地后要做体验测试并记情绪摩擦日志

> 📎 教训 · 首次记录 2026-08-25 · 状态：现行（R16「体验问题全修掉才算完成」的操作化协议）
> **触发场景**：某个用户可见功能 E2E 全绿、准备宣告完成；或在审查子 agent 交出的截图，正在逐项对账「要素在不在」。

**结论**：E2E 断言只证「路通」，证不了「走着舒服」。用户可见链路在合入后、宣告完成前必须跑一遍**体验走查协议**，把情绪摩擦全修掉——不是记 backlog，是修掉。

## 为什么会踩

等待没反馈、文案看不懂、节奏突兀、失败后不知所措——这些**断言全绿也全会漏**。

2026-08-25 维护者在一轮执行中定的要求：「除了代码测试，要仔细构建真实的用户使用过程来做价值测试，处理好用户的情绪——不爽、用的不舒服等。做了事之后站在用户角度仔细体验思考，要让他舒服地用，而不是仅仅实现功能。」并重申三件套方法论：**外部同类顶尖产品对标 + 内部代码实查 + 基于设计系统**。

## 体验走查协议

1. **以真实人物设定带真实任务走完整旅程**（例如一个做短剧、有预算焦虑的用户）——真 app，必要时真额度（测试额度默认授权，直接花）。
2. **逐秒记情绪摩擦日志**：
   - 哪里等得心慌（无进度反馈）
   - 哪里看不懂（术语 / 文案）
   - 哪里吓一跳（突兀跳变 / 静默失败）
   - 哪里想骂人（重复操作 / 丢状态）
3. **摩擦全修**——不是记 backlog，是修掉。
4. **复走确认**。

## 审查子 agent 交付时同理

截图不只对账「要素在不在」，**要问「这画面让人舒服吗」**。
