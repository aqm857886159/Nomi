# 本地旧构建的 `-h` ≠ 官方现役能力面

> 📎 教训 · 首次记录 2026-09-02 · 状态：现行
> **触发场景**：要判断某个厂商 CLI / SDK「支持不支持 X」「参数面长什么样」，而手边正好有一份本机装好的它——正准备直接 dump `-h` / 翻本地帮助当事实源。

**结论**：本机已装构建只是**历史快照**，不是现役能力面。判定能力前先跑官方安装 / 更新命令把工具刷新到最新，再逐子命令 dump `-h`；**官方 update log / release notes 才是「现在支持什么」的事实源**。这是 R5（查官方文档，禁凭记忆）的变种：凭旧本地构建判断 = 凭一份过期缓存判断，和凭记忆一样不作数。

**为什么会踩**：即梦（Dreamina）CLI 误判实证——评估时拿本机 build `54f1bdf`（`build_time 2026-06-18`）的 `-h` 当事实源，而官方当时已发到 `1.4.17`（`release_date 2026-08-18`，release notes 明写「为 seedance 2.5 增加 1080p 分辨率的参数支持」）。两个多月的版本差意味着整代参数面缺席：变体、分辨率枚举、必填参数、校验策略（新版「不支持的旧值直接拒绝，不再静默夹取」）全对不上，得出的能力矩阵整体过期。跑一遍官方安装命令（`curl -fsSL … | bash`）刷新后逐子命令重 dump 才纠正。本地构建的坑比记忆更阴险：它**看起来是实查**——命令真跑了、输出真贴了，唯独版本是旧的。

**怎么用**：
- dump `-h` 前先打两个版本戳：本机版本文件（如 `~/.dreamina_cli/version.json` 的 `release_date` / `build_time`）+ 官方渠道最新版本；对不上就先更新。
- 能力矩阵文档头部必须钉本次实测的版本号与日期，注明「从哪个版本的 `-h` 抓的」——下一个读者才能判断它过没过期。
- 官方 update log 逐版变更要与本机 `-h` 交叉验证（哪条印证了、哪条没印证），别单信任一边。
- 同族判断题一并自查：[中转平台的上限 ≠ 模型的上限](model-limits-first-party-over-reseller.md)（证据要最一手）；本条补的是**最现役**。

**出处**：`docs/research/2026-09-01-dreamina-cli-v1417-matrix.md`（头部明写「不从记忆、不从 6 月旧 `-h`、不从任何旧评估」，§4 版本变更映射 = 官方指南 vs 本机 `-h` 交叉验证）。
