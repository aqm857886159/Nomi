# 子 agent 起不来时的探针法（具体结论已过期）

> 📎 教训 · 首次记录 2026-08-20 · 状态：⛔ 已反转
> **触发场景**：派子 agent 秒挂（duration <1s、tool_uses=0），或你正准备根据某条「某某模型不能派 agent」的旧结论调整派工方式。

> ⚠️ **本文里所有关于具体模型 / 档位 / 配置项的结论都已过期**：当初那次 400 故障 2026-08-26 已由平台侧修复；「开 thinking 能救继承档」也已被实测证伪。**别把任何一条当前提**——遇到类似症状请按下面的方法重新实测。留着这条是为了**方法**和**两次误诊**。

**结论**：子 agent 起不来时，**用最小探针二分定位，别改 prompt、别换任务内容碰运气**。探针 = 派一个「只回复 OK，不许用任何工具」的 agent，逐档换一个变量（先换 model 档位，再逐项去掉配置），看哪一档能起。定位到是 harness 的配置冲突就去改配置或显式传参，跟任务内容毫无关系。

**探针法怎么做**：

1. **先造最小探针**：任务写死「回复 OK，别用工具」。零工具、零上下文，起不来就一定不是任务的问题。
2. **一次只动一个变量**：显式传 `model` 逐档试（当时试的是 opus / sonnet / haiku / fable）、换 `subagent_type`、去掉某个 env 或 settings 项。同一分钟内跑完一组，避免平台侧状态漂移混进结果。
3. **逐字读报错**，别看个「起不来」就归成同一个病。当时四种失败里，有的是 `output_config.effort ... is not supported`，有的其实是**额度耗尽**（`You've hit your limit · resets ...`）——两种文本完全不同，混为一谈直接导致了误诊二。
4. **换模型 / 改配置之后，第一次批量派工前先发一个探针判活**，再放开派。

**两次误诊，各错在哪**：

- **误诊一：把 harness 故障当成模型能力限制。** 看到 `effort 'max' is not supported when thinking is disabled on this model`，第一反应是「这个模型不行 / 这活它干不了」，于是去改 prompt、换 subagent_type 乱试。实际上这是**主会话 effort 档位继承给子 agent** 引发的配置冲突，与模型能力、与任务内容都无关。**症状里出现配置项名字（effort / thinking / output_config）就该往 harness 配置想，不是往模型能力想。**
- **误诊二：把「改了配置仍然失败」当成「配置没生效」。** 当时的假设是「开 thinking 就能救」，于是加了 `alwaysThinkingEnabled` 与 `MAX_THINKING_TOKENS`、重启、再试——**仍然 400**。正确的读法是「这条路是死的，该换思路」；当时却读成「大概还没生效，再重启一次」。
  - 分辨法：**先证明配置确实生效了**（`env | grep` 看进程环境、直接读 settings 文件确认键值在），生效之后仍失败 = 假设被证伪，掉头；而不是继续加固一条已经死掉的路。
  - 同期还有一次反向误判：某天报告「所有路径全挂」，据此推翻了前几天「显式传 model 可以起」的正确结论；几天后逐字复验才发现，那次「全挂」里混进了一条额度失败。**推翻旧结论前，先确认新证据和旧结论量的是同一个东西。**

**怎么用**：

- 子 agent 秒挂 → 先发最小探针，别动任务内容。
- 一次一个变量，逐字读报错文本，区分「配置冲突」和「额度 / 网络」两类失败。
- 断言「配置没生效」前先证明它到底生没生效；已生效仍失败 = 假设错了，换路。
- 推翻此前实测过的结论前，确认两次量的是同一现象。
- 本仓的结构性兜底：重活可交另一个执行体池（Codex CLI 是独立额度池），见 [`../engineering/agent-orchestration-playbook.md`](../engineering/agent-orchestration-playbook.md) §1（双池调度）、§8（Codex 专项）。
