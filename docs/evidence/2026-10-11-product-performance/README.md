## 执行条件

- 实测源码：`4e1eecdad8c3ab6a3d44d38065faeb769c613be4`，Nomi 0.23.1。提交前同步较新的 main 不会改变这些历史数据的源码身份，也不能算作对新版本的验证。

- 常规采样每格 1 次预热 + 5 次正式；诊断 0+1 与完整流程走查单列。冷启动、热状态、进入过方案和未进入方案分别保留，不能合并成一个统计总体。
- 真实鼠标/键盘、Playwright trace、renderer 帧/长任务、main/renderer CPU 和内存。`responseMs` 是输入到指定可见状态的观测延迟，不是物理首帧或完整 TTI。缺失指标保留 null。

## 用户体验发现

1. **删除绑定镜头后撤销，时间线片段未恢复。** 三档诊断均复现；small 片段 4→2→撤销仍 2，heavy 160→159→撤销/重开仍 159。镜头/画布恢复不能证明片段恢复，属于优先处理的数据完整性问题。
2. **文稿格式一次撤销可能无效。** 加粗/斜体后出现内容等价的额外历史步骤，第一次撤销仍有格式，第二次才恢复。相关源路径和回归方向记录在 findings 中。
3. **链接显示但不能持久保存。** 三档格式断言失败；当前规范化 mark 白名单缺少 link。完整有效 URL 输入流程尚未单独验证。
4. **进入过重档方案后切文稿明显变慢。** 历史重档第一文稿切换中位 2143.1 ms，最后文稿 1035.9 ms，方案进入 4251.6 ms。独立诊断支持隐藏的 320 行方案仍参与布局工作；具体浏览器调用点未完全归因。
5. 新短批次中，未进入方案的文稿切换中位 small 4.8 / typical 7.2 / heavy 15.3 ms；typical 方案进入 233 ms。这些不同历史/协议的数据不是优化前后对照，不能宣称提速。

完整说明和局限见 `confirmed-findings-register.json`。内存增长趋势不能单凭本批次称作泄漏。帧掉帧值为采样估算；网络/模型等待未独立取得的部分不从 UI 延迟中扣除。
