窗口窄时，预览页左栏不再被压成一条缝

今天发生了什么

1280 宽、Nomi 开着：中间只剩 814px，三栏最小宽加起来要 240 + 480 + 200 = 920，放不下。面板库把左栏缩到 32px，但左栏里仍按展开画，空态说明一字一行竖排，「收起」也被拆成两行。

同一类的另两处：关掉 Nomi 后，左右两栏被按比例撑宽（属性栏撑到 420 上限），这个宽度还被当成你拖出来的存下；1100 宽时反过来，属性栏明明收着，收起条却被拉成 192px 的空白。

根子：栏「画成展开还是收起条」看的是存档里的开关，栏「实际多宽」由面板库按空间算，两份各说各的。

修后四条规则

  1. 侧栏要么有可读宽度（左栏 ≥ 240、属性 ≥ 200），要么就是 32px 收起条（图标 + 竖排名字，今天点「收起」就是它），不会挤着画。
  2. 窗口变窄、打开 Nomi 不算你改主意：存下的开合和栏宽都不动，宽度差额全给预览；窗口变宽，被自动收起的栏自己回来。
  3. 两边都开时预览至少留 480；不够就先把右侧「属性」收成条，左栏「镜头 / 素材」留着。
  4. 点收起条一定有用：点哪边开哪边，另一边让成收起条（窄窗下两边轮流开）；你点开的那边一直开着，必要时预览最窄让到 400。

拍板结果

Q1 两边放不下，先收哪边？ 已定：先收属性（用户原话「先收属性」）。预览页的主活是把镜头拖进成片，左栏用得最多；属性要先选中片段才有内容，要看时点它的收起条就开，左栏让成条。 Q2 点收起条但没地方放？ 已定（按默认）：打开它，另一边让成收起条。不这样的话，1280 开着 Nomi 时点属性收起条什么都不会发生。 Q3 你点开的那边放不下时，预览可以从 480 让到 400？ 已定（按默认）：可以。只在窗口 1100–1170 宽、开着 Nomi 时会发生；不让的话这个宽度下点收起条没反应。自动收栏仍按 480 判断，平时预览不会变小。400 由「最窄内容区 684 = 左栏 240 + 收起条 32 + 预览」推出，测试按公式守。 Q4 开关 Nomi、改窗口宽时左右栏保持你定的宽度？ 已定（按默认）：是，差额给预览。今天会按比例撑宽并存下（属性栏 240 → 420）。

先查别人

  • macOS NSSplitViewItem.canCollapseFromWindowResize：随窗口变窄自动收、变宽自动回来，不改用户设定 → 确认规则 2；先收哪边按 Nomi 预览页的主活定（规则 3）。
  • VS Code #1029：侧栏挤到最窄时按钮被裁掉、没有提示 → 确认规则 1，宁可收成条也不挤。
  • react-resizable-panels：库只改宽度不管内容；onLayoutChanged 的 isUserInteraction 区分「用户拖的」和「约束重算」→ 改了写回：只记用户亲手拖的。
  • Obsidian「窗口窄时隐藏侧栏」插件：低于阈值收、变宽恢复 → 确认规则 2。

不变的

  • 收起条、「‹ 收起」、标签栏、空态文案的样子和文字都不改。
  • 顶栏「布局」菜单的开关和预设、⌘Z 撤销布局、拖分隔条收起 / 展开 / 改宽照旧。
  • Agent 的 layout.read / layout.write 读写的仍是你选的开合与宽度。
  • 老项目里存的布局原样读，不迁移；只是以后不再把窗口挤出来的宽度写回去。
