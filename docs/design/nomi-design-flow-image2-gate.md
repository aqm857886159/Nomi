# Nomi 设计流程 · image2 视觉确认门

> 日期：2026-09-04 · 状态：执行规范
>
> 目的：在 Nomi 既有设计流程上增加一道独立的视觉方向确认门。设计不再由 Agent 直接凭文字或 HTML 自行定稿：先把需求和视觉意图写成 Prompt Brief，再使用内置 image2/image_gen 生成视觉探索，交给用户核对；只有用户确认后，才能冻结 visual direction/design contract，进入红测、真实组件实现、绿测和 Electron 视觉走查。
>
> 适用：所有用户可见或用户可操作的 UI 改动，包括 Agent、MCP、分镜表、画布、视频拆解、确认卡、工具行、节点、面板、空态、异常态、弹层、动效和用户可见文案排版。

## 0. 一句话结论

现有流程已经有从真实现状到真实任务闭环的七道闸，但“视觉方向是否真正符合用户意图”仍主要依赖 HTML 样张或 Agent 自己的判断。新增流程把它补成一个不可跳过的用户确认门：

```text
需求澄清
  → 真实组件 / 设计系统勘察
  → Prompt Brief
  → image2/image_gen 视觉探索
  → 用户核对
  → 冻结 visual direction / design contract
  → 红测
  → 真实组件实现
  → 绿测
  → Electron / 打包截图视觉走查
  → 用户或指定 reviewer sign-off
```

关键边界：

- image2 只验证视觉方向、信息层级、构图、密度、气质和状态表达，不验证实现正确性。
- image2 不替代 HTML/React/真实数据、交互原型、契约测试、真实任务走查或打包验证。
- 未获用户确认的生成图不得作为实现依据，不得据此写生产 UI。
- 每次视觉迭代只改一个变量；不能把布局、色彩、密度、文案、组件形态同时改掉后再问用户“喜欢哪版”。
- Prompt、生成图路径、版本、用户反馈、决策和最终 design contract 必须留痕；没有留痕的“口头确认”不算冻结。

## 2. 当前已有流程

### 2.1 已有的正确骨架

当前流程不是没有设计门，而是设计门的种类和职责没有被明确拆开。已经存在的有效步骤如下：

1. **摸现状**：读完整 `Shell`/外壳组件或打开真实截图，确认页面实际由谁渲染、控件住在哪里、哪些状态已经存在。
2. **判层级**：按“10 次里会用几次”确定 L1/L2/L3/L4，执行“一功能一个家”，先分组、去重、归位、就近，最后才收纳。
3. **出可体验样张**：样张要使用真实布局、真实品牌、真实 token；交互改动要做成可点、可拖、可切换的 widget，而不是只放一张静态图。
4. **定实现规范**：明确 DOM 结构、token、组件复用、状态、数据绑定、可访问性和控件交互契约。
5. **机器门岗**：跑 token、dangling token、控件契约、文件大小、i18n、走查脚本等门岗；门岗采用只减不增的棘轮。
6. **真机走查**：在真实 Electron、真实入口和真实构建上截图，逐个打开交互态，做几何检查并由人眼判断。
7. **真实任务闭环**：使用至少 2–3 条创作目标跑通从输入到结果的闭环，修掉过程中发现的体验、设计、UI、UX、产品感和功能问题。

### 2.2 当前流程的交付物

| 阶段 | 当前产物 | 作用 |
|---|---|---|
| 现状 | file:line 盘点、真实截图、调用点地图 | 防止从局部代码脑补全局布局 |
| 层级 | before → after 控件表 | 防止新功能继续堆进常驻条 |
| 样张 | 自包含 HTML / 可体验 widget | 让用户理解结构和交互意图 |
| 规范 | token、组件、状态、数据与交互契约 | 让实现可复核、可测试 |
| 验证 | contracts、unit、Electron walkthrough、截图、真实任务 | 证明代码、体验和闭环分别成立 |

## 3. 审计发现的漏洞

### P0：视觉方向在实现前没有独立的用户确认物

- **现象**：已有流程要求“出样张并用户拍板”，但样张通常是 Agent 直接编写 HTML；当结构方向错时，Agent 可能连续修改实现细节，却没有先把“为什么这样组织信息”交给用户确认。
- **影响**：用户看到的是已经被实现逻辑牵引的方案，返工发生在 React 和状态链路之后；“能跑”可能掩盖“看不懂、不能用、不喜欢”。
- **根因假设**：HTML 样张同时承担视觉探索、交互说明和实现合同三种职责，缺少一个低成本、独立、可否决的视觉方向物。
- **修法**：在 HTML 样张之前加入 Prompt Brief → image2 → 用户核对 → visual direction 冻结；未冻结不得进入实现。

### P0：图像生成结果容易被误当成产品完成度

- **现象**：一张漂亮的图可以表达大致气质，但不能证明真实字段、长文案、空态、错误态、交互、持久化或真实数据能工作。
- **影响**：视觉通过被错误地等同于功能通过，最终出现“样张很好看、真实组件不能用”的落差。
- **根因假设**：视觉证据与实现证据的边界没有单独写成规则。
- **修法**：明确 image2 的证据范围；其后强制生成 HTML/React 真实组件、红测、绿测、Electron 截图和真实任务证据。

### P1：迭代中一次改变太多变量，无法知道用户究竟否定了什么

- **现象**：布局、颜色、卡片形态、字段密度和文案一起变化。
- **影响**：反馈不可归因，设计在多个版本间摇摆；用户说“不喜欢”后，Agent 容易自行解释成另一个方向。
- **修法**：每个 image2 版本声明一个 `changedVariable`，一次只改一个变量；其他变量从上一版冻结的基准继承。

### P1：生成图、反馈和决策没有形成可追溯链

- **现象**：图在对话中出现，但没有稳定的 prompt、文件路径、版本号、用户原话、最终决定和对应实现合同。
- **影响**：后续实现者无法判断哪一版是被否决的、哪一版被确认，也无法解释为什么实现没有照某张图。
- **修法**：每个设计任务必须建立视觉台账；没有 `confirmed` 记录的图一律是探索稿。

### P1：失败样张没有被当作设计资产管理

- **现象**：失败样张可能被继续微调，或者被误链接为当前推荐方向。
- **影响**：同一错误方向重复消耗时间，后续 Agent 又把失败图当参考图。
- **修法**：失败图只读归档，标注 `rejected`、用户反馈、失败原因和不可继承的部分；新方向建立新版本，不覆盖旧图。

### P1：视觉确认与功能/数据确认没有共享同一个 use case

- **现象**：图里是抽象的“分镜表”或“Agent 面板”，没有明确用户正在完成什么任务、真实字段是什么、数据量和状态是什么。
- **影响**：视觉确认的是概念，不是 Nomi 的实际使用场景。
- **修法**：Prompt Brief 必须先写 use case、用户任务、真实字段和状态；生成图只允许验证该任务下的视觉方向。

## 4. 新增流程：image2 视觉确认门

### 4.1 阶段 0：需求澄清

先把问题从“改得更好看”改写成一个可验证的用户任务：

```text
我是谁 / 当前在哪个面
我带着什么输入
我想完成什么创作任务
我希望得到什么结果
成功标准是什么
这次明确不改什么
```

必须记录：

- `featureId` / 任务名称 / 日期 / owner。
- 当前真实入口和目标入口。
- 用户任务及成功标准。
- 用户可见范围和不动项。
- 是否涉及 Agent、MCP、分镜表、画布、视频拆解中的一个或多个调用者。
- 需要用户确认的不可逆视觉方向，以及可以由团队自行决定的实现细节。

没有明确用户任务时，不开始 image2 生成；先补需求澄清。

### 4.2 阶段 1：真实组件与设计系统勘察

这一步继承 P5 / R8，必须在 Prompt Brief 前完成。

#### 必查内容

1. 读完整真实外壳，而不是只读局部 body：页面入口、左右栏、顶部、底部 composer、portal、弹层和响应式断点。
2. 看真实构建截图或使用真实 Electron 截图；改现有 UI 时必须记录“现状长什么样”。
3. 查 `docs/design/nomi-design-system.md`：token 真相源、现有组件、控件层级、状态词表、图标规则和可访问性。
4. 查同一功能的现有调用点，确认“一功能一个家”，不在 Agent、MCP、画布、分镜表之间重复造入口。
5. 盘点真实字段和状态：正常、空、加载、失败、禁用、确认、拒绝、成功、持久化恢复、长文案、超多行和窄窗口。
6. 对 MCP 或 Agent 变更，确认工具名、operation、能力、确认策略、receipt、错误和恢复路径；不能拿 UI 图推断链路已接通。
7. 对画布变更，确认 React Flow 单内核、Zustand/domain 持久化真相源、选择/拖拽/连接/缩放和边界几何。

#### 产物

生成一份带 `file:line` 的现状盘点，并附真实截图路径。没有 file:line 或真实截图的“现状”不允许进入 Prompt Brief。

### 4.3 阶段 2：Prompt Brief

Prompt Brief 是 image2 的输入合同，不是随手写的一段描述。它必须同时描述用户任务、真实产品结构和视觉约束。

#### 必填模板

```markdown
# Prompt Brief · [featureId] · v[版本]

## 1. Use case
- use case：明确写 `ui-mockup` 或 `page-mockup`，不能只写“设计一个界面”
- 用户：
- 当前入口 / 真实外壳：
- 用户任务：
- 成功标准：

## 2. 页面结构
- 页面/工作区整体骨架：
- 主内容区：
- 辅助区 / Agent dock / 结果卡区：
- 控件层级：L1 / L2 / L3 / L4，各自为什么住这里：
- 视口与断点：桌面、窄窗、最小可用窗口：

## 3. 真实内容
- 真实字段：
- 示例数据来源：
- 数据量：
- 真实文案或文案长度范围：
- 必须出现的交互态：正常、空、加载、失败、确认、拒绝、完成、恢复：

## 4. 视觉语言
- Nomi 设计系统 token / 组件：
- 品牌资产：
- 信息层级：
- 密度目标：
- 光/暗模式：
- 对齐、留白、圆角、阴影、图标和动效方向：

## 5. 约束
- 必须保留的现有结构：
- 必须复用的组件：
- 不能新增的入口：
- 不得发明的字段、状态和能力：
- 不得由图像推断的内容：

## 6. Avoid
- 不要营销落地页风格、不要装饰性大留白、不要泛用 AI 星光/羽毛 logo：
- 不要假下拉、假进度、假的可点击控件：
- 不要把用户不可见的内部术语作为 UI：
- 不要把不同作用域的控件无标签混排：
- 不要画出未在真实代码中存在的字段或能力：

## 7. 版本控制
- changedVariable：本轮只允许改变的一个变量：
- inheritedFrom：继承哪一版的哪些内容：
- promptPath：
- generatedImagePath：待生成
- decisionStatus：draft / awaiting-user-confirmation / confirmed / rejected
```

#### Prompt Brief 的写法要求

- `use case` 必须明确标为 `ui-mockup`，并写清“这是产品 UI 视觉探索，不是海报、营销页、概念艺术或品牌宣传图”。
- 页面结构必须以真实外壳为基准；image2 看不见真实组件时，Prompt Brief 必须引用真实截图或明确需要之后用 HTML 复刻验证。
- 真实字段必须来自代码契约、schema、store 或现有数据，不得为了画面好看编造字段。
- 真实状态必须列出来；只画正常态的视觉探索不能直接支持异常态实现。
- `avoid` 不是装饰性负面提示，而是把既有踩坑写成不可继承的边界。

### 4.4 阶段 3：使用内置 image2/image_gen 生成视觉探索

使用内置 `image2/image_gen` 生成一张或一组视觉探索图。生成时保留完整 Prompt Brief、生成参数、版本号和输出路径。

#### 生成规则

1. 首轮最多 2–3 个方向；方向差异必须是可命名的一个变量，例如“表格密度”或“结果卡停靠方式”，不能只是随机换色。
2. 每个方向都写清 `changedVariable`；同一方向的下一轮只能改变一个变量。
3. 图中出现 Nomi 品牌时使用真实 Nomi 品牌方向；不得用泛化的 AI logo、星光、羽毛或未经批准的占位品牌。
4. 图中展示的字段、状态、操作和文案必须能回指 Prompt Brief 的真实字段清单。
5. 对交互密集界面，图中必须标出或表达关键状态，但不能把静态图当成交互证据。
6. 对多个视口，桌面、窄窗和最小窗口分别生成或明确说明未覆盖；不能只用桌面图推断响应式成立。
7. 生成图必须标记为 `exploration`，直到用户确认；文件名和元数据不得使用 `final`、`approved` 或 `production`。

#### 证据边界

image2 能够帮助判断：

- 页面骨架和主要区域的相对关系。
- 信息层级、视觉焦点、密度和留白。
- 颜色、材质、圆角、阴影、图标气质和品牌一致性。
- 状态之间是否容易区分，以及用户是否能快速找到下一步。

image2 不能证明：

- React 组件是否存在、是否复用正确、是否符合 token-only。
- 真实字段是否完整、长文案是否溢出、数据量变化是否可用。
- 点击、拖拽、键盘、确认、拒绝、撤销、receipt、持久化和重启恢复。
- Agent/MCP 工具是否真的被暴露、调用、授权、执行和回执。
- 画布 React Flow、性能、边界几何或视频解码/生成链路。

### 4.5 阶段 4：交给用户核对

不能只把图片作为附件丢给用户，必须用一段短走读说明让用户能做方向决策：

```text
这张图验证的是：[一个视觉变量]
保持不变的是：[其余基准]
请核对：
1. 结构是否符合你的工作方式？
2. 重点信息是否一眼可见？
3. 这个密度和留白是否适合长时间生产？
4. 关键状态和下一步是否清楚？
5. 是否有任何你明确不想要的视觉语言？
```

用户反馈必须原文或等义记录在视觉台账中。以下反馈都不能被 Agent 自行解释成“继续微调”而跳过重新确认：

- “不喜欢”“太垃圾”“看不懂”“不是人能用的”。
- 用户明确否定某种结构、密度、布局、视觉语言或交互暗示。
- 用户指出样张与真实工作方式不一致。

这些反馈意味着当前版本 `rejected`，不是“待实现”。

### 4.6 阶段 5：用户确认后冻结 visual direction / design contract

只有用户明确确认，或指定 reviewer 按授权范围明确确认，版本才可变为 `confirmed`。确认记录至少包括：

- 确认人、日期、版本和生成图路径。
- 确认范围：确认的是结构、密度、色彩、状态表达、组件关系中的哪些项。
- 不确认范围：哪些仍需在 HTML/真实组件中验证。
- 保留的用户反馈和未决项。
- 对应的 design contract 路径。

`design contract` 要把图像语言转成可实施条款：

- 页面结构和区域边界。
- 复用的真实组件与 import 路径。
- token 名称，而非随意 hex/px。
- 真实字段、数据来源和每个状态。
- 作用域、入口层级、键盘/读屏、禁用原因和焦点环。
- 允许的响应式变化。
- 哪些 image2 细节是探索性的，不得照抄。

没有冻结合同时，任何生产 UI 变更都视为未获批准。

### 4.7 阶段 6：红测（先红）

冻结合同后先写能证明“当前尚未完成”的测试或证据，再实现。红测必须命中真实生产形状，不得只测 mock 或测试探针。

红测至少覆盖与本次变更相关的：

- 结构锚点、区域顺序、控件层级和作用域。
- 真实字段与状态的存在/缺失。
- 交互承诺：可点即有效，不能用假按钮、假下拉、假进度。
- Agent/MCP 的 canonical tool、operation、确认、拒绝、receipt 和错误边界。
- 分镜表的选中、引用、局部 patch、回写和恢复。
- 画布的选择、几何、React Flow 单内核和持久化边界。
- 视频拆解的结果驱动、唯一结果卡、失败态、重试和 Agent 调用者共用。

红测输出必须记录：命令、失败原因、失败 commit、失败日志路径。若红测意外通过，要检查是不是测到了旧工具名、静态样张、测试注入或错误入口，而不是直接把它标绿。

### 测试门与真实用户任务

设计冻结后，必须先在真实生产形状上得到红测，再进入实现；不得因为 image2 或 HTML 样张已获确认就跳过功能测试。该测试门至少包含：

- 真实 Electron 入口和真实构建，而不是静态样张、测试专用桥接或脱离应用外壳的组件孤测。
- 正常、异常、空态、加载、失败、确认/拒绝、完成以及相关超时状态；超时必须有可观察的等待、失败和恢复路径。
- 写入后重新打开或重启应用，验证持久化数据、选择/上下文、操作结果和 receipt 能恢复，且失败不会静默丢失或伪装成成功。
- 至少 2–3 条真实用户任务，从真实输入开始，经过操作、反馈、确认或拒绝，到结果可编辑/可继续使用；记录每条任务的入口、动作、结果和未决问题。

绿测必须逐项对应红测，并保留命令、失败/通过输出、截图或日志路径、构建 SHA 和重启恢复证据。视觉走查只验证视觉方向、层级、密度、状态表达和真实外壳中的呈现，不能替代契约测试、功能测试、持久化/重启测试、异常/空态/超时测试或真实用户任务闭环；视觉通过不等于功能完成。

### 4.8 阶段 7：真实组件实现

红测成立后才实现：

- 使用冻结合同指定的真实组件、token 和数据源。
- 复用已有入口和状态 owner；新增组件先走设计系统新增协议。
- image2 不能直接变成 HTML/React 的像素拷贝；实现应保留用户确认的视觉关系，但必须服从真实数据、交互、可访问性和响应式约束。
- 交互改动必须包含正常态、异常态、加载态、空态、禁用态、确认/拒绝态和恢复态中适用的全部状态。
- 不增加第二套 Agent、MCP、分镜表或画布事实源。

### 4.9 阶段 8：绿测

实现后跑与红测对应的绿测，证明：

- 测试命中了真实生产入口，而不是测试专用桥接。
- 所有真实字段、状态、作用域和数据绑定正确。
- Agent/MCP 的真实 canonical 路径能完成“请求 → 选择/上下文 → 预览或确认 → 执行 → receipt → 持久化 → 重启恢复”。
- 分镜表、画布、视频拆解和 Agent 的多调用者路径读写同一份事实，而不是各自显示一份看似相同的结果。
- 阳性对照成立：故意改错一个字段、tool name、operation、选择集或状态后，测试确实会红。

绿测通过只是代码和契约条件满足，不代表视觉或用户任务完成。

### 4.10 阶段 9：Electron / 打包截图视觉走查

使用真实构建、真实入口和目标平台走查：

1. 打开正常、空、加载、错误、确认、拒绝、完成、收起/展开、长文案、窄窗口和相关异常态。
2. 每个状态截图并打开查看；截图存在不等于已经看过。
3. 对照已确认的 image2 视觉方向和 design contract，逐项核对结构、层级、密度、颜色、组件、文案和状态。
4. 用 `getBoundingClientRect` 检查裁切、溢出、重叠、portal、弹层和视口边界。
5. 对 Agent/MCP/分镜表/画布/视频拆解，检查真实任务下的动作反馈、等待、确认、错误和恢复，而不是只看静态首屏。
6. 运行 R13 的人眼判断，并按 R16 的真实创作任务跑完整闭环。

截图、构建 SHA、平台、入口、视口、走查人和问题清单必须留在验证记录中。

### 4.11 阶段 10：用户 / 指定 reviewer sign-off

最终 sign-off 必须同时回答：

- 视觉方向是否仍与已确认 image2 一致？
- 真实组件是否比图像多承担了必要的状态、数据和交互，而没有改变已确认的核心方向？
- 真实任务是否办成，用户能否完成目标？
- Agent/MCP/分镜表/画布/视频拆解的相关链路是否有对应证据？
- 未决项是否明确标为未完成，而不是藏在“看起来完成”里？

只有 sign-off 后才能称为“完成”。否则只能称为“实现完成，体验待验收”或“方向已确认，功能未完成”等精确状态。

## 5. 设计台账与版本规则

每个设计任务必须保留以下目录或等价结构。路径可以按仓库现有目录调整，但不能省略字段：

```text
docs/design/records/<featureId>/
  00-requirement.md
  01-current-state.md
  02-prompt-brief-v1.md
  03-image2/
    v1-exploration.png
    v2-exploration.png
  04-user-feedback.md
  05-visual-decision.md
  06-design-contract.md
  07-red-green-evidence.md
  08-electron-visual-walkthrough.md
  09-sign-off.md
```

每张图至少记录：

| 字段 | 要求 |
|---|---|
| `featureId` | 稳定 ID，不能随版本改名 |
| `version` | `v1`、`v2`…；失败版本不能复用编号 |
| `status` | `exploration` / `awaiting-user-confirmation` / `confirmed` / `rejected` / `implemented` / `signed-off` |
| `promptPath` | 完整 Prompt Brief 路径 |
| `generatedImagePath` | 生成图的仓内或受管输出路径 |
| `changedVariable` | 本轮唯一改变的变量 |
| `inheritedFrom` | 继承上一版的基准 |
| `userFeedback` | 用户原话或等义记录 |
| `decision` | 保留、否决、待验证的具体项 |
| `designContractPath` | 用户确认后才填写 confirmed 合同 |
| `implementationEvidence` | 红测、绿测、截图、构建 SHA 和 sign-off 路径 |

### 5.1 版本命名和失败版本

- 失败版本保留，不覆盖、不删除、不移动到“当前”目录。
- 文件名不得在确认前包含 `final`、`approved`、`production`。
- 用户否定的是方向时，下一版必须更换 `changedVariable` 或重新写 Prompt Brief，不能只把颜色改一点继续沿用同一错误骨架。
- 用户只否定一个变量时，其他变量可继承，但台账要写明继承关系。
- 设计合同与生产实现若发生差异，要记录差异原因；不能静默漂移。

## 6. #454 锚行 / 参数条失败样张归档规则

### 6.1 当前判定

PR #454 的锚行/参数条样张：

```text
docs/design/mockups/2026-09-03-storyboard-anchor-row-and-param-rail.html
```

该样张已经收到明确否定反馈，且 PR 说明其方向未获批准、没有作为真实生产组件的最终设计。它的状态必须是：

```text
status: rejected
reason: 用户否定视觉方向与可用性，不是像素级小修
implementation: prohibited
source: PR #454 / 其设计交接文档
```

### 6.2 如何归档

1. 原文件保留为只读失败证据，不删除、不覆盖、不改名为“最终版”。
2. 在视觉台账中记录用户反馈、版本、生成/修改历史、失败原因和“不可继承的结构”。
3. 失败原因至少拆成：信息架构、控件层级、密度、可操作性、状态表达、与真实分镜表外壳的偏差；不能只写“审美不喜欢”。
4. 新方向使用新的 `featureId` 版本或明确的 `v-next` 记录，重新走 Prompt Brief → image2 → 用户核对；不得直接在旧 HTML 上继续堆修补。
5. 旧样张中的功能事实仍可作为代码审计输入，但视觉形式不具备继承效力。功能完成度要由真实 schema、Agent/MCP 链路、真实组件和 Electron 走查单独证明。
6. 如果旧样张和已确认的 Agent/分镜表设计文档冲突，优先保留冲突记录并停在决策门，不由实现者自行选择。

### 6.3 #454 后续实现的最低门

锚行/参数条的新实现必须同时具备：

- 一个新的 Prompt Brief，明确分镜表用户任务、真实字段和真实状态。
- 至少一个 image2 视觉探索版本和用户确认记录。
- 真实组件实现，不把 HTML 样张或生成图当产品 UI。
- 红测先红、绿测再绿。
- 真实 Electron 截图与已确认方向逐项对账。
- Agent 右侧修改分镜的真实 canonical 链路证据：选择注入 → `nomi_canvas_plan` → `operation=patch_shots` → 预览/确认 → 执行 → receipt → 落盘 → 重启恢复。

## 7. 各功能域如何复用这套门

### 7.1 Agent UI

- 以真实 `ProjectAgentResidentShell`、Agent dock、composer、会话流、计划卡、确认卡、回执卡和异常态为勘察对象。
- Prompt Brief 要写用户正在完成的创作任务，不写“做一个更像 Claude Code 的面板”。
- image2 只确认右栏骨架、信息层级、卡片密度、状态语言和与工作区的关系；21 种形态、状态词表和批准策略仍以现有 Agent 设计合同为准。
- 真实组件必须继续验证流式、折叠、回到最新、确认/拒绝、撤销、有出入、失败、加载和恢复。
- Agent 面板的 image2 方向确认不能证明工具真的可用；必须另跑 Agent 真实任务闭环。

### 7.2 MCP

- MCP UI 改动先明确工具使用者、操作风险、授权方式和用户看到的确认/进度/回执。
- Prompt Brief 中的工具名、operation、字段和状态必须来自 canonical manifest/schema；不能用图片里的“调用工具”文案替代真实协议。
- image2 只能确认 MCP 结果如何呈现，不证明工具目录、schema、lease、授权、receipt、持久化、Skills 或 packaged journey 已完成。
- 红测/绿测必须覆盖真实 MCP canonical path；直接喂旧工具名、静态 projection 或测试专用 window bridge，只能作为辅助测试。
- 涉及付费、外部写入、账号、发布、删除或不可逆动作时，视觉方向确认不能代替既有硬闸。

### 7.3 分镜表

- Prompt Brief 必须列真实镜头字段、镜头数量、场景折叠、锚点、选择、引用、局部 patch、生成状态、失败态和结果接收。
- image2 用来确认“用户如何看懂和改一组镜头”，不确认数据正确性或 Agent patch 执行能力。
- 分镜表的新视觉不得另造与画布节点、Agent 结果卡或视频拆解重复的事实视图；必须记录诞生点、消费点和唯一事实源。
- 右侧 Agent 修改分镜必须使用真实选中集和真实 canonical operation；视觉图中画出“已修改”不等于状态已经持久化。

### 7.4 画布

- 勘察必须以真实 React Flow 生产画布、节点、边、工具栏、浮层和 Zustand/domain 状态为准。
- image2 只验证布局、密度、浮层层级、节点视觉和交互 affordance 的方向；不能替代几何、性能、拖拽、连接、缩放、选择和持久化测试。
- 设计合同必须明确哪些是迁移等价、哪些是产品明确改变；不能借视觉探索顺手改掉 React Flow 迁移合同。
- Electron 走查必须覆盖画布边缘、窄窗口、节点重叠、portal 裁切、拖拽反馈和长任务期间的状态。

### 7.5 视频拆解

- Prompt Brief 必须明确源视频、拆解结果、镜头表、勾选、加入画布、起稿、失败/部分失败和 Agent 调用者。
- image2 可以确认结果卡、右槽共存、镜头表层级和状态表达；不能证明真实视频解析、OCR/ASR、provider、重试、落节点、编组或重启恢复。
- 视觉上要保持“结果驱动、调用者无关、唯一结果卡”的方向；节点入口和 Agent 入口不能各画一份互不相同的结果。
- R13/R16 走查要从真实视频到用户拿到可编辑草稿，不能停在默认注入结果或静态样张。

## 8. 完成状态词表

| 状态 | 含义 | 允许做什么 |
|---|---|---|
| `exploration` | image2 探索稿，未交给用户或尚未形成决定 | 只能比较和继续探索 |
| `awaiting-user-confirmation` | 已交给用户核对，等待明确反馈 | 不得实现 |
| `rejected` | 用户否定该方向或该版本 | 只读归档，不得实现 |
| `confirmed` | 用户确认了视觉方向和范围 | 可以冻结 design contract 并写红测 |
| `red` | 合同已有，当前实现或测试仍未满足 | 进入实现与修复 |
| `implemented` | 组件和功能已写，绿测或走查未全部完成 | 不得称完成 |
| `green` | 对应机器门岗、契约和功能测试通过 | 仍需视觉与真实任务验收 |
| `signed-off` | 用户/指定 reviewer 完成最终视觉与任务签字 | 才能称该范围完成 |

禁止把 `exploration`、`confirmed`、`green` 互相混称：它们分别是视觉探索、方向确认和代码验证，不是同一个完成度。

## 9. 最终执行清单

每个用户可见设计任务收尾前，逐项回答并附证据：

- [ ] 需求澄清：用户任务、成功标准和不动项明确。
- [ ] 真实勘察：完整外壳、真实截图、设计系统、组件、字段、状态和调用者已盘点。
- [ ] Prompt Brief：`ui-mockup`、页面结构、任务、字段、状态、视觉语言、约束和 `avoid` 齐全。
- [ ] image2：生成图路径、版本和本轮唯一 `changedVariable` 已记录。
- [ ] 用户核对：用户反馈已记录，否定方向已标 `rejected`。
- [ ] 视觉冻结：用户确认范围、design contract 和未决项已记录。
- [ ] 红测：在真实生产形状上先得到红状态。
- [ ] 实现：使用真实 React/组件/token/数据，不把图像或 HTML 当产品实现。
- [ ] 绿测：对应契约、功能、Agent/MCP/持久化/恢复证据通过；阳性对照有效。
- [ ] Electron / 打包视觉走查：真实构建、真实入口、各交互态截图已打开并人工核对。
- [ ] R16：至少 2–3 条真实用户任务闭环完成，过程中发现的问题已修复。
- [ ] sign-off：用户或指定 reviewer 明确签字，未决项没有被伪装成完成。

任何一项缺失，都只能报告为部分完成，并明确卡在哪一道门。
