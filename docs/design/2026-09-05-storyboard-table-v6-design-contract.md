## ① 背后逻辑：解决哪个真实摩擦

**用户原话（一字不改）**：

> 表格框架必须保留，是为了批量生成和冗余观察，一行一镜。只有顶部的锚（角色图/场景图/道具，被下面反复引用的东西）需要展开/收起两态：收起时排成一条紧凑参考条，方便下面镜头引用。每一镜生成前是编辑态（选模型、选提示词、加参考），生成后结果回到同一行；视频要能播放、图片按比例显示。模型、模式、时长、比例、状态、操作这些不要变成列，放进提示词框，提示词框下面选参数，就像图片节点那样。不同模型的参考模式不一样、能参考的数量和种类不一样，参考槽要按模型能力出。下面的镜头引用上面的锚，也能 @ 引用任何已有素材。生成好之后要能自动被引用去做下一步生成。旧分镜表的功能一个都不能少，这是它的升级版；体验要和画布里的图片/视频节点一致。兜底方案：把图片节点/视频节点的参数框整个抄过来放行里，生成物在第一列。设计必须基于现在真实页面的排版做，不许全变。

**这解决的是哪个真实摩擦（大白话）**：

用户在分镜表里同时要做两件性质完全不同的事——**「扫一眼全片、批量处理」**（冗余观察：这一场有几镜、哪几镜还没生成、哪几镜缺参考）和**「一镜一镜精细调」**（编辑态：选模型、写提示词、挑参考、调参数）。现在这版表格把第二件事的控件（模型/模式/时长/画幅/状态/操作）摊成一排排的胶囊挤在行上沿，行一多就成了一条控件河，反而看不清「谁做完了、谁没做」——这正是表格本该负责的第一件事。

v6 的核心动作是**把这两件事的视觉预算分开**：批量观察继续靠表格骨架（行、场分组、画面格、状态色）；精细调参数的控件全部收进提示词框下方的「底栏」，和画布里生成节点的参数区**长一个样**——用户已经在画布上学会了这套手感，不需要在表格里重新学一遍。

**他要权衡的那个核心东西（一句话点破）**：这么做每行会比现在高出约 30px（底栏占了原来省下的空间），换来的是「模型/模式/参数」不再和「这镜做完没有」抢视觉带宽——**批量观察越干净，单行操作就得多留一点高度**，这是本设计唯一的正面取舍，不是缺陷。

**升级点（相对旧分镜表）**：旧版分镜表只是"剧本 → 落画布 → 在画布上生成"的中间产物，选完模型就得导出去画布才能点生成；这版的升级是**在表格里原地生成**，不用再导一次。旧版的其余功能一个不少（对账见 §5）。

## ② 信息架构

### 2.1 表壳（编辑器外壳，`StoryboardPlanEditor` 的视觉不变）

自上而下五段，与现役 `StoryboardPlanEditor.tsx:276` 的 `grid-template-rows: auto auto auto minmax(0,1fr) auto` 完全一致，**这层壳不变**：

1. **标题栏**（48px）：图标 + 方案名（可改）+ 镜数/场数/总时长 pill + 右侧「从原稿重新拆分镜」「放弃方案」。
2. **提示行**：「AI 草拟，随便改 · 先生成参考卡锁住长相，再生成镜头 · 每次生成前确认花费」。
3. **全部镜头批量条**（sticky，`bg-nomi-ink-05`）：类型/模型/画幅/时长四个 `NomiSelect size=xs` + 「改这里 = N 个镜头一起改」提示。**时长不进批量**（图片镜没有统一时长语义），批量条改的是**整片**，与逐镜设置是不同作用域，位置排在锚区和分镜表之前（§1.5.3：不同作用域视觉可分）。
4. **滚动主体**：锚区 → 分镜表（场分组 + 行）。
5. **footer**（sticky）：左「返回原稿」+ 进度文案 + 「选中 N 镜 · 交给 Agent 改」；右「将跑 N 镜」提示 + 主按钮「生成未生成的 N 镜」。

### 2.2 锚区两态（`跨镜头要一致的`）

**存在的理由**：角色/场景/道具/风格这些资产被下面**多个**镜头反复引用；锚区不是"分镜表的第一段"，是"下面所有镜头共享的参考池"。

**两态**（用户原话："只有顶部的锚需要展开/收起两态"）：

| 态 | 形态 | 高度 |
|---|---|---|
| **收起（合并态）** | 一条紧凑参考条：每张锚 = 40px 缩略 + 名字 + 「被 N 镜引用」/生成状态一行小字，`border:1px solid #e3e1de; border-radius:10px` 胶囊；一行排不下自动换行 | 48px/行（`.mini` 40×40 + padding） |
| **展开** | 和下面镜头行**完全同一套解剖**（画面格 / 参考列 / 提示词框 + 底栏），在这里直接生成参考图；文字锚（如"全片风格"）没有画面格，只有一个提示词框，因为它**不生成图，只是写进每一镜的提示词** | 与镜头行等高（≈132–144px/行） |

- **不是「少了」或「不用了」，只是收起来排在那里**——收起态依然是锚的完整表示，不是摘要视图。
- **「全部展开 / 全部收起」** 在小节标题行右侧，一次性切换全部锚的态（不支持逐张展开——逐张展开的交互复杂度不值得，用户没有提这个需求）。
- 收起态点一张锚 = 反查过滤（现役已有：`StoryboardPlanEditor.tsx:385-398`，只看引用它的镜）。
- 锚的生成态（空/生成中/失败/已生成/已锁/文字）见 §3 状态表。

### 2.3 行骨架（分镜行 = 锚展开行，同一套解剖）

**这是 v6 与 v5（当前实现）最大的结构性差异**，改动只在这一处：

| | v5（当前实现，`StoryboardShotRow.tsx:182`） | v6（本合同） |
|---|---|---|
| 行 grid | `14px 84px 136px minmax(0,1fr)` | **`14px 136px 200px minmax(0,1fr)`** |
| 画面格列 | 固定 84px 列宽，格子本身写死 76×132（竖版专用，无横版实现，见 brief §C3-1） | **固定 136px 列宽，媒体框按比例缩放**（9:16 用 76×135，16:9 用 136×77，1:1 用 108×108——同一列宽内混排仍左对齐、仍整齐） |
| 参考列 | 136px，槽形态随 mode 变但没有固定行为约束 | **固定 200px、单行、最多 3 格、不换行**（规则见 §4） |
| 模型/模式/参数位置 | 行上沿一排 `NomiSelect size=xs` 胶囊（`StoryboardShotRow.tsx:317`），与提示词框分离 | **搬进提示词框下方的固定参数网格**（`.composer .bar`），和画布节点参数框同一手感 |
| 动作浮条 | 半透明浮层 **压在**画面格上（hover 才现，见 token-sheet §11「悬停动作浮条」） | **移到画面格下方**，不压图（`.acts` 一行常驻小图标按钮；解决 brief §E4 点名的 §1.5.3 违规——半透明按钮压在缩略图上是已知反例，不是本合同引入的新债） |

行内三块的阅读顺序不变（沿用 v5 已拍板顺序，`2026-09-01-storyboard-table-image-first.intent.mjs` 的既有意图）：**画面格（要生成的）→ 参考列（拿来参考的）→ 提示词块（怎么描述）**。

**提示词块内部结构（`.composer`，即"和图片节点一样"）**：

```
┌───────────────────────────────────────────┐
│ 远景，雨后天台，@林薇 独自站在栏杆边，霓虹反光，缓推   │  ← 提示词文本（TipTap，@ 挂 mention chip）
├───────────────────────────────────────────┤
│ [模型▾] [模式▾] [画幅▾] [时长▾] [清晰度▾] [音频·尾帧] [生成] │  ← 固定列网格；继承画幅保留空位
└───────────────────────────────────────────┘
```

- 底栏胶囊顺序：**类型不再作为逐镜选项**（类型由批量条统一整片声明，逐镜只能换模型/模式，与用户口述"模型、模式、时长、比例、状态、操作这些不要变成列"一致——它们不是列，是底栏里的胶囊，视觉上属于提示词块，不属于表格列）。
- 图片镜的底栏没有「模式」以外的时长控件，改显示「停留」时长（时间轴停留语义，v5 已有此语义改变，见 C1-15，v6 保留）。
- 已生成/已锁定的镜，底栏用一枚 `tag g`/`tag n`（"已生成 · 已作为 镜 03 首帧" / "已锁定 · 不进批量"）替换「生成」按钮位置，不额外加行。
- **分镜行只有四块**：产物、参考槽、提示词、提示词下方参数行。行尾没有展开按钮，也没有展开区；台词/转场字段及其分镜数据投影删除。字幕轨与接缝转场由剪辑面维护。
- ~~参数行固定七列……容器不足时整行按同一断点换行~~ **（2026-09-06 用户反馈三作废，见下）**

**§2.3 修订（2026-09-06 用户逐字打回）**：「参数框为啥那么多？我们画布上的图片节点本身参数没那么多。能不能变成**一行**、再简洁些，最右边就是「生成」。现在很乱。」

对照现场：画布节点底栏（`InlineParameterBar`）只有**三枚**——模型芯片 + 变体 + 一枚摘要 pill，全部参数收在 pill 点开的面板里。分镜行摆到了九枚，还每枚带前缀小标签。所以七列换行那条规则整条作废，换成四条：

1. **永远一行**（`flex-nowrap`）。上一版"装不下就整表换两行"的整套（列宽测量 + 全表断点作用域）删除——它把一枚胶囊的溢出换成了全表行高抖动，而真正的问题是胶囊本来就太多。
2. **摆出来的只有 select**（模型 · 模式 · 画幅「有覆盖才显」· 时长/停留 · 清晰度 …），因为 select 显示的是一个**值**，扫一列就看得出哪镜不一样；**boolean 开关收进行尾 ⋯**（生成音频 / 返回尾帧…），开着的用一颗小圆点报信。一排同形同色的开关摆在扫视行上读不出差别，只剩噪音——开关的家是那枚 ⋯（一功能一个家）。
3. **胶囊不带前缀小标签**（「模型 Seedance 2.5」→「Seedance 2.5」），语义进 `aria-label` / `title`，与画布摘要 pill 的读法一致。近邻 MiniMax Design 的一行也是 `[模型] [画幅] [时长] [清晰度]` 这种量级。
4. **窄了只缩文字，不换行、不截断重叠**：值 `truncate`（「Seedance 2.5」→「Seedanc…」，`title` 里读得到全名），前缀与 ▾ 是 `shrink-0`；**「生成」`ml-auto` 钉最右**，与所有胶囊同一基线。
- **底栏里出现哪些胶囊，由当前选中的「模型 × 模式」derive，不出灰控件（2026-09-05 用户拍板 · 修订 2）**。一个控件要么因为这个模型/模式真的支持而出现（可点），要么因为不支持而**整枚不渲染**——不允许"渲染出来但置灰"这种第三态。理由：置灰控件是"这里本来该有个东西"的视觉噪音，用户还得去猜它为什么点不动；而分镜表的最高优先级是批量扫视（§1），每行多一枚死控件就多一份干扰。
  - 依据的近邻：**Krea Seedance Studio**——"你能用的模型、设置和参考类型，取决于你选的是图还是视频、以及选了哪个模型"，且"设置模型提供的选项，比如画幅、清晰度、时长、音频、质量或出图数量"（§⑩ K1）。Krea 的做法就是**控件集合是模型能力的投影**，不是一张固定表单。
  - 对实现方的硬约束：底栏控件列表必须从档案（`ArchetypeMode` 及其参数声明）**运行时 derive**，不得在组件里写死一张"模型→控件"的映射表（那是 P1 的并行版：档案改了 UI 不跟着改）。清晰度/音频/出图数量这类可选参数，档案没声明就不渲染。
  - 与 §4 的对偶关系：参考列的槽随 `ArchetypeMode.slots` derive，底栏的控件随同一个 mode 的参数声明 derive——**同一份档案，两个投影**，换 mode 时两边必须同帧重画，不允许一边换了一边留着上一个 mode 的残留。

### 2.4 画面格比例规则

- **列宽固定 136px**（不随内容变化，这样批量竖向扫视时左边缘永远对齐）。
- **媒体框按 mode 的 `aspect_ratio` 缩放**，高度以行内容自然高度（≈132–144px）为基准反算宽度，宽度不超过 136px：
  - 9:16 → 约 76×135（贴近竖屏项目主画幅，用户 2026-09-02 已拍板过"图是主角"原则，参见 v5 intent 契约）
  - 16:9 → 约 136×77（占满列宽，高度让出）
  - 1:1 → 约 108×108
  - **横版首次有真实表达**（v5 唯一没做的 `.row.land` 缺口，见 brief §C3-1，v6 用"列宽不变、媒体框变"解决，而不是 v5 样张原方案"整行列宽切换成 176px"——切换列宽会让混合画幅的行失去左右对齐，是 09-05 讨论中明确否决的取舍，见 canvas.json 注解 a-main 末段）。
- ~~未生成态用批量条声明的整片默认画幅撑出占位尺寸；一旦该镜单独换了画幅，占位框跟着换。~~ **（2026-09-06 用户反馈四作废，见下）**

**§2.4 修订（2026-09-06 用户逐字打回）**：「不同画幅的行一放进来整个框就不齐。前两列——产物列和参考列——不同比例时排版要齐；至少大家都同一个比例（比如从上到下都 16:9）时，单个分镜行要排得很好、对齐。」

上面那条「列宽固定就够齐了」**在混排下不成立**：列宽齐、盒子不齐，而人眼读的是盒子（9:16 是 76×135、16:9 是 136×77，底线与右边缘全错开，参考列和参数行跟着上下浮动）。所以媒体盒从**行级**升到**表级**（`shotFrameGeometry.tableFrameMediaBox`）：

- **全表同一画幅** → 盒 = 该画幅的框（16:9 → 136×77、9:16 → 76×135、1:1 → 108×108）。缩略图正好铺满、没有一条黑边；每行的顶线、媒体盒、参数行、生成钮四条线逐行对齐。
- **混合画幅** → 全表共用一只盒：宽取列宽上限、高取短边上限（`136×108`，两个数都是本节已有的两条封顶，不是新编的）。横版贴满宽、竖版贴满高、方图居中，各自 **`object-contain` letterbox 在盒内**——不拉伸（会让人对不上真实出画比例）也不裁切（会把已经生成出来的画面切掉一块）。
- 盒**不随行内容变形**，未生成的虚线框、缺必填的红虚框、生成中/失败态全部用同一只盒。行高因此稳定，跨行网格线对得上。
- **动作条在图下方**，横向一排小图标按钮（重生成/变体/锁定/放大/用作…），不悬浮、不压图，常驻可见（不是 hover 才出——媒体框下方本来就是空白区，不需要用悬浮遮挡内容来省这点空间）。

### 2.4.1 画幅的作用域：项目级默认 + 行级覆盖（2026-09-05 用户拍板 · 修订 2）

**规则（三条，实现方按这三条写）**：

1. **画幅是项目级设置**，住在批量条（§2.1 第 3 段）的「画幅」胶囊里，声明**整片默认画幅**。新建/拆分镜出来的每一行都继承它。
2. **行级可以覆盖**：某一镜确实要不同画幅时，在该行底栏单独改——覆盖是逐行的，不影响其它行，也不改项目默认值。
3. **只有覆盖了的行，底栏才显示画幅胶囊**。没覆盖的行**底栏里根本没有这枚胶囊**（不是显示成灰的、也不是显示成"继承 9:16"）——它的画幅由项目默认决定，画面格照样按该画幅缩放（§2.4），但底栏不为"我用的是默认值"这件事花视觉预算。改项目默认时，已覆盖的行不跟着变（批量条右侧提示要如实写出"已覆盖画幅的 N 镜不跟着变"）。

**为什么这么定（底层逻辑）**：一部片子 95% 的镜头共享同一个画幅——这是拍片的常识，不是产品假设。旧设计把画幅当成"每镜都要选一次"的逐镜参数，代价是**每一行都常驻一枚永远显示同一个值的胶囊**：它占着底栏的横向预算，却在 95% 的行里一个字节的信息量都没有。把它提到项目级之后，底栏里剩下的胶囊全都是"这一镜真的和别人不一样"的信号——**胶囊出现本身就成了信息**。

**用户体验是什么**：默认路径上用户只在开头选一次画幅，之后每一行的底栏都短一截、扫得更快；真的要出一镜横版时，在那一行改，改完那一行会长出一枚**带「· 覆盖」标记的蓝色胶囊**，在一列竖版行里一眼就认得出来"这镜被我动过"。

**依据的近邻（四家都把画幅放在项目级，没有一家做成逐镜必选项）**：

| 近邻 | 画幅住在哪 | §⑩ 编号 |
|---|---|---|
| LTX Studio | 生成分镜时**为所有镜头一次性设定**画幅（16:9 / 9:16 / 1:1），"设在前面，保证第一镜起画面就符合 brief" | L1 |
| Boords | 画幅（frame size）是 **storyboard 级**设置，住在 storyboard 侧栏（Frame Fields 之上）；改它是对整块板生效，且会追问已有图片是 Pad to fit 还是 Crop to fill | B1 |
| Higgsfield（Popcorn / Shots） | 在生成时选定画幅，一组镜头**整组保持同一比例**；官方建议输入与目标输出比例保持一致 | H1 |
| Kling | 画幅是生成参数、随该次生成走，不是一张分镜表逐格的常驻字段 | K3 |

**与 §2.4 的关系**：§2.4 讲的是"画面格怎么按画幅缩放"（几何），本节讲的是"这个画幅值从哪来"（作用域）。两者不冲突：不管画幅是继承来的还是覆盖来的，画面格一律按 §2.4 的规则在固定 136px 列宽内缩放，混排仍左对齐。

### 2.8 拆分镜时锚点自动绑到行（2026-09-05 用户拍板 · 修订 2）

**规则**：从剧本拆分镜（§2.7 入口 1）时，系统按**剧本里这一镜实际出现的角色/场景**，把对应的锚**自动填进该镜的参考槽**，并在提示词里落成 `@名字` mention chip。填进去的绑定**全部可改**：可以删、可以换成别的锚、可以再 `@` 加。

**为什么这么定**：拆分镜之后逐镜手动挑参考，是这条流程里最钝的一段——剧本里已经白纸黑字写了"林薇站在天台栏杆边"，让用户再去参考列里手动把「林薇」和「天台夜景」各点一遍，是让人**把机器已经知道的事再录一遍**（D1：任何让用户多配置一次的东西，默认砍）。自动绑定之后，用户在这一步的动作从"逐镜配参考"变成"扫一眼、改错的那几个"。

**"可改"是硬要求，不是补充说明**：自动匹配一定会有错（同名角色、一镜里出现但不该入镜的道具、剧本没写但用户想加的风格锚）。所以自动绑定的结果必须长成**普通的槽内容**——和用户手填的一模一样，没有"这是自动的所以你动不了"的锁；也不做"自动/手动"两套视觉（那是 P1 的并行版）。唯一允许的差别是**首次落地时**在参考列上方给一行可关闭的小字提示"已按剧本自动填了 N 个参考，可改"，让用户知道这些不是他填的。

**依据的近邻**：
- **Boords · Cast Images**：导入剧本时有一个 auto-generate 开关，开着就**自动从剧本识别主要角色**（跨多场出现的那些）并为每个角色生成整身参考图，后续生成分镜画面时用它保持一致；关掉就直接进分镜表（§⑩ B2）。
- **LTX Studio · Elements**：官方写得更直接——"当你从剧本生成分镜时，LTX Studio 会**自动识别角色、物件和场景，并拉入匹配的 Elements**"（§⑩ L2）。

两家的共同结论：**从剧本到参考的这一跳，是工具该替用户走的，不是用户该手工走的。**

### 2.9 结果回同一行：历史变体抽屉 + 显式「采用」（2026-09-05 用户拍板 · 修订 2）

用户原本的要求是"每一镜生成前是编辑态，生成后结果回到同一行"（§1）。修订 2 把"回到同一行"这件事拆成两段，补齐了**"回来的时候，上一次的结果去哪了"**这个之前没定的问题：

| 段 | 是什么 | 规则 |
|---|---|---|
| **第一段：画面格（当前采用的那一张）** | 行里那个固定 136px 列的画面格，永远显示**当前被采用的**那一版结果 | 它是这一镜对外的唯一答案：落时间轴、被下一镜引用、算进"已完成 X/Y"的都是它 |
| **第二段：历史变体抽屉** | 画面格下方动作条上的一枚「变体 ×N」按钮，点开是这一镜的**全部历史产出**（含被替换掉的旧版），按时间倒序 | 每一版带模型/模式/参考/提示词快照；抽屉里可以放大对比、删除某一版 |

**核心规则（这条是本节的重点）：重新生成 = 往抽屉里追加一版，不覆盖画面格；只有用户在抽屉里显式点「采用」，画面格才换成那一版。**

**为什么这么定**：现在这套"点重生成 → 画面格直接被新图顶掉"的做法，把**一个不可逆的破坏性动作藏在了一枚看起来很轻的按钮后面**。用户点「重生成」时想的是"我再看一个别的可能"，不是"我要丢掉刚才那张"——两者是完全不同的意图，但现在共用同一个按钮、同一个结果。更糟的是，被顶掉的那张可能已经被下一镜当首帧引用了（本合同 §3.1 `done` 态就写了"已作为 镜 03 首帧"），覆盖它等于在用户不知情的情况下改了别处。

**用户体验是什么**：点「重生成」→ 画面格**不动**，动作条上的「变体」计数 +1 并轻微高亮 → 用户点开抽屉，新旧并排 → 满意就点「采用」，不满意就关掉抽屉，什么都没变。**"我再试一个"这件事从此零风险。**

**依据的近邻**：
- **Boords**：生成环节的花费点不在"生成"上，而在**"插入"**上——官方写的是"每次一张 AI 图**被插入到分镜里**，就消耗一个 image credit"（§⑩ B3）。也就是说"多看几版"和"决定用哪版"在 Boords 里本来就是**两个分开的动作**，且只有后者有代价。
- **Runway · Sessions**："Sessions 就是你做生成的地方"，一个 session 是一次创作里**一组生成物的集合**，可重命名、按最近使用排序（§⑩ R1）。Runway 的心智是**生成物是累积的历史，不是一个会被覆盖的单值**。

**Nomi 与它们的差别（要说清，别照抄）**：Boords 的免费/扣费分界是商业模型，Nomi 的额度模型不同（每次生成都真金白银），所以**我们不承诺"预览免费"**——我们抄的是**它把"看"和"定"拆成两个动作**这个交互结构，不是它的计费方式。这也是 §9 新增走查项要验的东西。

### 2.10 行级「本次跳过」 + 产出自动带 @tag（2026-09-05 用户拍板 · 修订 2）

**（a）行级复选框「本次跳过」**

每行 grip 旁的复选框（现役已用于多选）新增一个语义明确的用法：勾上 = **本次批量跳过这一镜**。

- 「跳过」**不是删除，也不是锁定**：这一镜的内容、参考、参数原样留着，只是不进 footer「生成未生成的 N 镜」这一次的批次。
- 视觉：行整体降到 60% 不透明度 + 行首一枚 `tag n`「本次跳过」；footer 的 N 实时减掉它。
- **作用域是"本次"**：跑完这一批之后跳过标记自动清空——它是一次性的批次筛选，不是持久属性。持久的那个叫「锁定」（§3.1 `locked`），两者语义不同、视觉不同、清除时机不同，不许混成一个。

**为什么要有它**：批量生成时最常见的动作不是"生成全部"，也不是"一个个点"，而是**"这批里除了 03 和 07 都跑"**。没有跳过就只能靠删掉、或者临时锁定、或者一个个手点——三条路都要用户为一次临时决定付出一个持久代价（D1：不该让用户为临时意图改持久状态）。

**（b）每个产出自动拿一个 @tag，可被后续镜引用**

任何一次生成产出（镜头结果、锚的参考图、抽屉里的历史变体）落地时**自动获得一个 `@tag`**，从此可以在任何一镜的提示词里 `@` 出来当参考——不需要先"存成锚"、不需要下载再上传。

- tag 名默认从来源 derive（如 `@镜03`、`@林薇-v2`），可改名。
- 这条直接兑现用户原话里的"生成好之后要能自动被引用去做下一步生成"（§1），并且和 §4.1 的规则①咬合：`@tag` 进的是**槽**，槽在参考列里仍然是一个格。
- 抽屉里没被采用的变体**也有 tag**——"这版不适合这一镜，但适合下一镜"是真实存在的用法。

**依据的近邻 · Krea Seedance Studio**："结果出现在项目 feed 里，**每一个完成的结果都会拿到一个 `@tag`；点它就能把那个结果附加进你的下一条提示词并 mention 它**"，此外还能复用它的参数（§⑩ K2）。Krea 把"产出 → 下一次生成的输入"这条路做成了零操作，Nomi 的分镜表是同一个诉求的表格版。

### 3.3 行的批量参与度与画幅归属（2026-09-05 用户拍板 · 修订 2）

这两组状态**不是生成态**（§3.1 才是），它们描述的是"这一行和整片的关系"，所以单独一张表——实现时不要塞进 `PlanShot` 的生成态枚举里去。

| 维度 | 取值 | 视觉信号 | 对 footer「将跑 N 镜」的影响 |
|---|---|---|---|
| **画幅归属** | `inherited`（默认，跟随项目级画幅） | 底栏**没有**画幅胶囊 | 无 |
| | `overridden`（本行单独覆盖） | 底栏出现蓝色 `pill.ovr`「画幅 16:9 · 覆盖」 | 无；但改项目默认画幅时该行不跟着变 |
| **本次参与度** | `included`（默认） | 常态 | 计入 |
| | `skipped`（本次跳过，勾选复选框） | 行 60% 不透明度 + `tag n`「本次跳过」 | **不计入**，且跑完自动清除 |
| | `locked`（锁定，见 §3.1 `locked`） | 🔒 徽章 + "不进批量"常显 | 不计入，**持久**，需显式解锁 |

**`skipped` 与 `locked` 的边界（实现时最容易混的一处）**：`skipped` 是"这一批不跑"，跑完即清；`locked` 是"这镜定稿了，别再动它"，要用户显式解锁。同一行可以同时是 `overridden` + `skipped`，它们是正交的两个维度，不是一个状态机的两个态。

## ④ 参考列规则 + 槽矩阵

### 4.1 参考列的两条硬规则（2026-09-05 用户提问后追加拍板，逐字保留）

> ① 一个槽一个格，不是一张图一个格——首帧/尾帧/图片/视频/音频各一格；能放多张的槽画成叠放格+计数角标（12/30），点开是浮层网格，在里面加删排序；锚名照旧在提示词里以 @ 出现。
> ② 参考列固定单行、最多三格、200px、永不换行——所有已声明模式的槽数 ≤ 3，左中永远对齐。

**这两条规则解决的问题**：v5 的参考区曾经"一张图一个格"（`StoryboardShotRow.tsx:274-279` 逐张渲染 tile），槽一多（如 Seedance `omni` 的 30 图）行高会被参考区撑爆；v6 改成**槽是格的单位，不是素材是格的单位**——一个 `image_ref` 槽不管里面装了 1 张还是 30 张，在参考列里永远只占**一个格**（叠放显示 + 计数角标），行高因此稳定。第②条规则保证了参考列本身也不会因为模型换了就撑爆整行——已知六种真实档案里最多同时出现的具名槽数是 3（`first_frame`+`last_frame`+`image_ref`，或 `image_ref`+`video_ref`+`audio_ref`），单行三格是**按已知真实数据定的上限，不是拍脑袋**。

**§4.1 修订（2026-09-06 用户反馈四）**：规则②里的「200px」作废，改成两条 derive：

- **槽用一只固定盒**（`REFERENCE_SLOT_BOX` = 扇面全开的旋转包围盒，65×73）。上一版按"这一槽装了几张"算尺寸（0 张 56×56、2 张 56×65、3 张 65×73），于是同一行三个槽一高一矮、行与行又各不相同——参考列成了整张表最参差的一块。固定之后：参考 / 白膜预览 / 参考音频三个槽、叠放堆、单张 tile、缺输入图的红虚框全部**同宽同高、同一条顶线**，caption 落在一条线上。
- **列宽是结果不是常数**：`REFERENCE_COLUMN_WIDTH = 盒宽 × 3 + 间距 × 2 = 211`。原来的 200 是样张量出来的估值，盒子一变就横向溢出（滚动条还会把 caption 那条线压掉一格）。行网格模板 `STORYBOARD_ROW_GRID_TEMPLATE` 同样从 `FRAME_COLUMN_WIDTH` / `REFERENCE_COLUMN_WIDTH` 拼出来，不写字面量。
- 参考列与画面格**共用同一条顶线**：去掉旧的 `min-h-[135px] justify-center`——16:9 的行画面格只有 77 高，参考卡却仍落在 135 的中线上，两列从此错开。

### 4.2 每种槽形态的画法

| 槽状态 | 画法 |
|---|---|
| 不吃参考（`slots: []`，如 t2v） | 一行灰字「此模型不吃参考」，`@` 仍可引用锚写进提示词 |
| 具名槽 · 必填未填（`min≥1` 且为空） | 虚线**红**框 tile，caption 红字「首帧」/「尾帧」 |
| 具名槽 · 可选未填（`min=0`） | 虚线灰框 tile，caption 灰字 |
| 具名槽 · 已填 1 张 | 单张缩略图 tile，caption 是引用来源（锚名/镜号） |
| 数组槽 · 已填 ≥2 张 | **叠放格**（手抓扑克，见 §2.6）+ 右下角 `N/max` 计数角标；`max` 缺省时角标只显 `N`（不显示分母——不能拦一个供应商没公布上限的东西） |
| `characterIndexed` 的数组槽 | 叠放格最上面那张左上角加 `①` 编号（对应 prompt 里的 `character1`），点开浮层里可拖拽调整顺序 |
| 通用 `@` 加槽 | 虚线灰框 + `+` 图标 + 右下角 `已用/上限` 角标（如 `0/10`）；无上限时只显 `+` 无角标 |

**derive 规则（对实现方的硬约束，不是建议）**：
- 只画**当前选中 mode** 声明的槽（`ArchetypeMode.slots`），换 mode 参考列整个重画，不保留上一个 mode 的槽形态。
- `min ≥ 1` → 红「必填」；`min = 0` → 灰「可选」——**必填判定只看 `min`，`ArchetypeReferenceSlot` 类型上没有 `required` 字段**（brief §D1 已核实,不要凭空发明这个字段）。
- `characterIndexed` 才给编号，其余槽不编号（`requiresAnyOf` 依赖只在提交时校验，不在参考列拦，见 brief §D1：容量在放入时拦，依赖只在运行时拦）。
- `max` 缺省 = 供应商没公布上限，UI 必须能画一个"无上限"的槽，不能编造一个假上限。

### 4.4 槽引用锚点时携带什么：不只是图（2026-09-05 用户拍板 · 修订 2）

**规则**：行内某个参考槽引用一个锚时，进到这次生成里的**不只是那张图**，还包括这个锚的三段声明：

| 段 | 内容 | 进到哪 |
|---|---|---|
| **名字** | 锚名（如「林薇」） | 提示词里的 `@林薇` mention chip；也是槽 caption 上显示的那行字 |
| **描述** | 这个锚是什么、有哪些关键特征（如「28 岁，短发，深色风衣，左眉有疤」） | 随槽一起提交给模型（供应商支持 element/reference 描述字段时走该字段；不支持时并进提示词） |
| **要忽略的特征** | 明确让模型**不要跟**的部分（如「背景的霓虹招牌」「拍这张时穿的那双鞋」） | 同上 |

也就是说：**槽不是一个图片容器，是一个"带说明的引用"**。参考列里那个格子在视觉上是一张缩略图，但它的数据形态是 `{ 锚, 名字, 描述, 要忽略的特征 }`。

**为什么要有第三段（"要忽略"）**：参考图永远是"多带了东西"的——你为了锁住脸，顺手把那张图的背景、光线、服装也一起喂给了模型。没有一个显式的"忽略"通道，用户唯一能做的就是**去 P 图或重拍一张更干净的参考**，这是把工具的缺口转嫁成用户的活。

**依据的近邻 · Kling Element Library**：创建一个 Element 时填的就是这两块——**名字**（"给你的主体起个名字，建议取有辨识度、相关的名字，方便之后查找与复用"）+ **描述**（可手写也可 AI 生成），而描述里官方明确要求写三样东西：这个 element 的**核心特征**、**关键细节**，以及 **"你希望模型在生成时忽略的特征"**（§⑩ K4）。Kling 把"要忽略什么"当成 element 声明的一等公民，不是提示词里的临时否定句。

**对 Nomi 的落法（不照抄）**：Nomi 的锚（`AssetReference` + `generationProfile`）本来就是声明式的（见 memory `nomi-reference-slots-are-already-declarative`），所以这三段**住在锚上、不住在槽上**——同一个锚被 5 镜引用，描述与忽略项只写一次。槽只是引用它。行内允许对**这一次引用**追加临时的忽略项（如"这镜别跟那件风衣"），存在槽上，不回写锚。

**参考列的视觉不变**：三段声明**不占参考列的横向预算**（§4.1 规则②：固定 200px 单行三格仍然成立）——名字进 caption，描述与忽略项在**点开槽的浮层里**编辑（浮层已由 §4.2 定义为叠放格的展开位置，不新增第二种浮层）。

## ⑧ 不做项

| 不做的东西 | 为什么 |
|---|---|
| **方向 B**（参考槽塞进提示词框头部，横向 chip） | 参考跟提示词挤在同一个框里，横向少一列换来的是"哪几镜缺参考"这个批量观察能力变弱；多槽模型（全能参考 3 种×上限）在一行芯片里会挤爆。与"批量生成和冗余观察"这条最高优先级摩擦冲突（见 §1）。 |
| **方向 C**（兜底：整块照搬节点参数框放进行里） | 用户自己提出的兜底方案，评估后没有必要——代价是分段条+说明+槽+提示词+底栏五层堆叠，单行高度 ≈220px，一屏只能看 3 镜，"冗余观察"几乎失效，模式切换还会占掉提示词的位置。方向 A 已经吸收了"和图片/视频节点一致"这条要求（底栏形态相同），不需要照搬整个节点面板。 |
| **HyperFrames / 完整 Excel 式表格** | 用户口述从未提出要做电子表格意义上的"任意单元格可编辑、可拖拽公式"，分镜表的表格骨架服务于"一行一镜"的批量观察，不是通用数据表格产品；引入完整表格能力（虚拟滚动、列排序、单元格级选区）远超本次摩擦的范围，也不在 D2 讲的"solo 团队扛得动的护城河"上。 |
| **横版列宽切换方案**（v5 样张原 `.row.land` 176px 整行切换） | 09-05 讨论中明确否决：切换列宽会让混合画幅的行左右不对齐，表格失去"扫一列看全片"的价值；改用"列宽固定 136，媒体框按比例缩放"实现同样的横版表达（见 §2.4）。 |
| **逐张展开锚**（只展开一张锚，其余保持收起） | 用户只要求"全部展开/全部收起"这一种交互；逐张展开会引入"哪些张是展开的"这个额外状态，复杂度不值得。 |
| **参考列的"接受什么媒体类型"提示文案** | 槽上没有这个字段（brief §D1 已核实，类型由 `kind` 推导），设计不应该在参考列里编造一个不存在的提示文案，实现阶段从 `kind` derive 即可，不需要额外的 UI 元素承载它。 |
| **多视图（批量改文案视图 / 纯审片视图）**（2026-09-05 用户拍板 · 修订 2） | **单表本身就是 Nomi 的差异化**，先不拆视图——见下方「已知取舍」。 |
| **"预览免费、采用才扣费"的计费模型**（修订 2） | §2.9 抄的是 Boords「看」与「定」分成两个动作的**交互结构**，不是它的计费结构。Nomi 每次生成都真实消耗额度，承诺"预览免费"会变成一句做不到的话（D4：缺口明着标，不糊弄）。抽屉降低的是**心理成本**（不怕丢东西），不是金钱成本。 |

### 8.1 已知取舍：单表 vs 多视图（2026-09-05 用户拍板 · 修订 2）

**取舍是什么**：Boords 把同一份内容摊成了好几个视图——脚本视图、分镜网格视图、shot list 表格视图、动态分镜（animatic）、评审/签核链接、版本对比、图库（§⑩ B4）。每个视图只服务一种任务，切过去就只看得到那件事该看的东西。Nomi v6 走的是**相反的方向：一张表，一行一镜，什么都在这一行里**。

**为什么先选单表（底层逻辑）**：

1. **单表是差异化，不是妥协。** Nomi 的招牌是"在同一张表里原地生成"（§1 的升级点）——生成态、参考、参数、结果全在一行上，这正是多视图工具做不到的：它们的分镜表是**计划**，生成在别处；Nomi 的分镜表是**计划 + 执行同一处**。一旦拆成多视图，"原地"这个词就失效了，我们会退化成又一个 Boords。
2. **多视图的代价是 solo 团队扛不动的那种代价。** 不是"多写几个组件"，是**每多一个视图就多一份"同一份数据的第二种解释"**——排序、选中、过滤、撤销、Agent 改动的落点，都要在 N 个视图之间保持一致（R14.1 的"同一语义有几份定义"横扫，正是在数这种东西）。D2：广度是敌人。
3. **我们还不知道这两个视图真的被需要。** "批量改文案"和"纯审片"是**推测出来的场景**，不是从真实使用里量到的摩擦。

**所以怎么处置（不是"永不做"，是"等证据"）**：

| 场景 | 现在怎么办 | 什么时候重新评估 |
|---|---|---|
| **批量改文案**（一次改多镜的提示词） | 用现有的多选 +「交给 Agent 改」（§2.7）：选中 N 镜 → 说一句"把这几镜的提示词改得更口语一点" | 真实使用中出现"用户宁可导出到别处改再贴回来"的行为时 |
| **纯审片**（只看画面、不看参数，连着过一遍） | 用现有的「顺播」（`Main.html` 分镜小节标题旁已有）+ 时间轴预览 | 真实使用中出现"用户为了看片专门缩小窗口/滚动躲开控件"的行为时 |

**判据写死在这里，防止下次凭感觉重开这个议题**：只有当 R13/R16 的真实任务走查（§9.2）里**观察到上述行为**，或用户在真实使用后明确提出，才启动"是否加视图"的决策；到时按 R3 出对比表，不在本合同里预留半个实现。

7. **J7 "我再试一个"零风险**：对一个已生成的镜点「重生成」→ **画面格必须原地不动**，「变体」计数 +1 → 点开抽屉新旧并排 → 关掉抽屉，画面格仍是旧的 → 再点开、点「采用」新版，画面格才换 → 检查引用了这一镜的下游镜（如"已作为 镜 03 首帧"）此时才收到"参考已变"提示。**中途任何一步都不许出现"图被悄悄换掉"**。
8. **J8 批量里跳过两镜**：5 镜里勾掉 2 镜的「本次跳过」→ footer 从「生成未生成的 5 镜」变成 3 镜 → 跑完后跳过标记**自动清空**（不是留着），且被跳过的两镜内容原样未动。
9. **J9 产出立刻当下一镜的参考**：生成镜 01 → 在镜 02 的提示词里打 `@` → 能直接搜到镜 01 的产出 tag → 选中后它进的是**槽**（参考列多出一格），不是只在提示词里留了段文字。

每条走查按 R13 用 Playwright 真实 Electron 截图人眼判断（"舒服吗"而不只是"在不在"），过程中冒出的体验问题必须修完才算交付（R16，不留半成品）。

### 9.3 已知需要实现阶段回头补的债（本合同已标注，非本次遗漏）

- `missingRequiredSlots` 判定逻辑目前只认 `image_ref`（brief §D4-i），v6 的红/灰参考列要求覆盖全部槽种类，这处判定必须同步修，否则 Seedance 首尾帧/Veo 帧模式的参考列会继续错误地"永远报缺"。
- 具名槽（首帧/尾帧/源视频）在表层目前没有真正的上传/绑定实现，只会插入 `@` 文本（brief §D4-ii）。本合同的视觉规则已经定义清楚"这个格子该长什么样"，但"点击后怎么真正把素材传上去"是数据/交互层工作，必须在实现阶段一并做，否则参考列的红格永远填不满。

**修订 2 追加的债**：

- **画幅现在是不是逐镜字段，要先查真相源。** §2.4.1 把画幅定成"项目级默认 + 行级覆盖"，实现前必须先确认现役数据模型里画幅住在哪（项目 / 方案 / `PlanShot`），以及是不是已经有第二处在写它。**如果发现两处都在写，那是 R14.1 的"同一语义两份定义"，按 P2 修在最早共享边界，不许在 UI 层加一个"读哪一个"的判断。**
- **`skipped` 是新状态，必须进同一份 derive。** §3.3 的"本次跳过"会影响 footer/场组头的计数，而 §3.1 已经写死"行/组/footer 的计数必须同一份 derive（`exec/storyboardRowStatus.ts`）"。实现时把 `skipped` 加进那一份，**不许在 footer 处单独减一次**——那正是计数对不上的经典成因。
- **历史变体是新的持久化对象。** §2.9 的抽屉要求每一版产出连同它的模型/模式/参考/提示词快照一起留存，这不是 UI 状态，是要落盘的数据。实现前要先定它的存储位置与清理策略（一镜生成 20 版之后磁盘怎么办），否则会变成一个只涨不落的坑。
