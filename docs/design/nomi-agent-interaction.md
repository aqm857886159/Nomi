## 0. 这份文档管什么 / 不管什么

**管**：Agent 与用户协作的四段合同：输入如何带上画布与外部上下文、执行如何选工作方式与权限、反馈如何投影任务和多媒体结果、失败或跑偏后如何恢复。对话词汇、composer、队列、画布定位与结果暂存都在范围内。

**为什么必须单独成章**：B5 要落 21 种对话形态，而设计系统主文档里此前**没有任何 agent 章节**（grep 只命中付费确认弹窗与 logo）。没有依据就动手 = 每个形态各写各的，正是 `CanvasAssistantPanel`(770 行) / `CreationAiPanel`(800 行) 长成今天这样的原因。

## 1. 一句话主张

> **对话是任务的索引与回执，画布是产物的真相源。**

对话负责说清「我收到了什么、现在在做什么、结果在哪里、还能怎么处理」；图片、视频、音频、文档与 3D 的正式版本、派生关系和编辑状态都归画布。聊天卡不能悄悄保存一份与画布不同步的“第二个产物”。

推出三条能判对错的原则：

**① 原位更新，不追加。**
聊天记录只能往下追加，说过的话不会变；agent 干活不是。「排队第 3 位」→「进行中 3/5」→「完成 · 5 镜」必须是**同一条在变**，不是刷屏三条。

这决定了底层：**每件事有稳定 id，UI 订阅它变化**，而不是往消息数组里 push。不先定这条，21 种形态全都要返工。

> 行业依据（`docs/research/2026-08-24-agent-conversation-vocabulary-survey.md`）：「进度/中止：独立任务中心（虾条 8 态）或画布节点；**对话内原位进度无人做**」。别家把进度挪出对话，正是因为做不到原位更新。

**② 一件事一行，展开才有细节。**
21 种形态若都是卡片，对话流会变成卡片墙。所以默认全是单行，只有两类升级成卡片：**要你做决定的**、**产物本身**。21 种形态 → 视觉上只有 3 个层级。

**③ 诚实优先于好看。**
价格标出来、失败标人话原因 + 是否计费、上下文压缩了要说。

> 行业依据：「花钱确认：确认卡+点击才扣是主流；**没有一家卡上显示价格**」。TapNow 原文「手动确认只是让消耗发生在点击之后，不会免除消耗」= 半诚实反例。**反着做就是护城河。**

**④ 发出去的上下文必须看得见、冻得住。**
当前画布选中自动进入 composer 上方的上下文架，`@` 负责补充非当前对象；发送时把引用版本、裁剪区域、时间段或 3D 视角冻结成快照。原对象后来变化，要显示「引用后已变化」，不能让历史指令偷偷漂移。

## 2. 统一状态词表（核心 · 先落这个）

### 2.1 现状：四套互不认识的说法

| 在哪 | 现在的词表 | 文件 |
|---|---|---|
| 消息 | `pending / streaming / done / error / cancelled` | [workbenchAiTypes.ts:14](../../src/workbench/ai/workbenchAiTypes.ts) |
| 步骤徽标 | `done / active / warn` | [AssistantTimeline.tsx:23](../../src/workbench/generationCanvas/components/AssistantTimeline.tsx) |
| 画布节点 | `idle / queued / running / success / error / recoverable` | [generationCanvasTypes.ts:8](../../src/workbench/generationCanvas/model/generationCanvasTypes.ts) |
| 镜头占位卡 | 第四套（用 `phase` 不用 `status`） | [ProductionShotPlaceholder.tsx:62](../../src/workbench/generationCanvas/nodes/ProductionShotPlaceholder.tsx) |
| **审批** | **没有词表** —— 靠 `pendingToolCalls[]` + `committedProposal` + `deviationReport` + `contentDeviations` 四个独立 state 拼 | `CanvasAssistantPanel.tsx` |

后果：`AssistantTimeline` 吃 15 个 props；每加一种 agent 行为要同时改四处。

### 2.2 目标：一套 8 态 + 2 标志

**8 个态**（互斥，任一时刻只处于一个）：

| 态 | 界面说法 | 什么时候 | 取代 |
|---|---|---|---|
| `drafting` | （无字，扫光中） | agent 还在流式吐这条 | 消息 `streaming` |
| `proposed` | 等你确认 | 提出来了，等用户点头 | `pendingToolCalls`（此前无名） |
| `declined` | 你拒绝了 | 用户拒了 | 此前无 |
| `queued` | 排队中 · 前面还有 N 个 | 已批准，等资源/等前置 | 节点 `queued` |
| `running` | 进行中 | 真在跑 | 节点 `running`、徽标 `active` |
| `done` | 完成 | 成了 | 节点 `success`、消息 `done` |
| `failed` | 失败 | 挂了 | 节点 `error`、消息 `error` |
| `stopped` | 已停止 | 用户中途叫停 | 消息 `cancelled` |

**2 个标志**（挂在态上，不是独立态）：

| 标志 | 挂在 | 取代 | 为什么不做成独立态 |
|---|---|---|---|
| `retryable` | `failed` | 节点独立态 `recoverable` | 它本来就是「failed + 能重试」。做成独立态 = 每个渲染分支都要多处理一个 case |
| `deviated` | `done` | 徽标 `warn` | 事实是「做完了 **且** 和批准的不一样」，不是 done 的替代。现在 warn 与 done 互斥是错的 |

### 2.3 颜色只有 4 组（不是 8 种）

| 组 | 含哪些 | token |
|---|---|---|
| 中性 · 在走 | `drafting` `queued` `running` | `--nomi-ink-40` |
| **要你动手** | `proposed` · 反问 · 付费 | `--nomi-accent` |
| 成了 | `done` · 写入回执 | `--workbench-success-ink` |
| 出事了 | `failed` `stopped` | `--workbench-danger` |
| 有偏差 | `done + deviated` | `--nomi-warning` |

## 3. 三个视觉层级

| 层级 | 什么进来 | 形态 |
|---|---|---|
| **一行** | 过程性的、不需要你做任何事 | 思考条 / 阶段线 / 工具条 / 排队 / 进度 / 写入回执 / 压缩线 / 上下文用量 |
| **可展开的一行** | 过程性但你可能想看细节 | 思考条（展开看推理）/ 计划行（展开改单镜参数） |
| **卡片** | ① 要你做决定 ② 产物本身 | 计划卡 / 付费卡 / 反问卡 / 失败卡 / 有出入卡 / 产物卡 / 多候选组 |

**纪律**：新增形态先问「它要不要你做决定、是不是产物」。都不是 → 只能是一行。

### 4.1 `queue` 现在是真 bug，不是新功能

输入框在 agent 忙时**没有禁用**，但 [CanvasAssistantPanel.tsx:220](../../src/workbench/generationCanvas/components/CanvasAssistantPanel.tsx) 是 `if ((!text && !readyAttachments.length) || busy) return` —— 用户打字按回车，**消息被静默丢弃，屏幕上什么都不发生**。视频生成动辄几分钟，这期间用户必然想说下一句。

这两条建议提前到第一批 —— 它们不是锦上添花，是用户会当成「这软件坏了」的洞。

## 5. 等待指示器：工序图示

**不用品牌 N**（2026-08-27 用户否决）。理由是语义撞车：每条 assistant 消息头上已有 `NomiLogoMark`（[AssistantMessageView.tsx:20](../../src/workbench/ai/AssistantMessageView.tsx)），一屏能出七八个 N；且 **N = 身份**（这是 Nomi 在说话），等待 = **状态**（它在干什么），同一符号扛两义则两义都糊。

**改用「工序图示」**：图标随当前工序变，图标本身即进度。

**阶段词表沿用已有的 Playbook 阶段，不另造**（2026-08-27 修正）。此前本表用的是「读本/拆镜/出图/出视频/上轨」——那是**我自己造的第四套阶段词表**，而系统里已经有两套：

| 词表 | 值 | 位置 | 处置 |
|---|---|---|---|
| 工作区阶段（用户在哪个 tab） | `creation \| generation \| preview` | `src/design/identity.tsx:30` | 保留（它是 UI 位置，不是工序） |
| **Playbook 阶段（干到哪一步）** | `script \| storyboard \| build \| generate \| assemble` | `skills/brand-promo/skill.json` | ✅ **单一真相源** |
| ~~工序图示自造词表~~ | ~~读本/拆镜/出图/出视频/上轨~~ | 本节旧版 | ⛔ 已删，对齐上一行 |

对应关系几乎一一对应，所以对齐是自然的、不是硬凑。**这条修正本身就是本文 §2「同一语义只能有一份定义」的应用**——我自己先犯了一次。

| Playbook 阶段 | 显示名 | 图示 | 动作 |
|---|---|---|---|
| `script` | 读剧本 | 一页纸 + 3 行 | 三行依次亮（1.9s） |
| `storyboard` | 拆镜头 | 3 个横格 | 依次落位（2.1s） |
| `build` | 搭画布 | 取景框四角 + 中心点 | 缩放呼吸 = 对焦（2.4s） |

| `assemble` | 上时间轴 | 3 条轨道 | 短块往左走带（2.0s） |

**同一个阶段值还驱动另外两件事**（一处声明三处用，见 `docs/plan/2026-08-27-skills-knowledge-distribution.md` §2.4）：
- 技能的分阶段可见（当前阶段的技能排前面）
- §6 片场话的分组（说的话必须跟当前工序对得上）

### 5.1 §6 需要开一族新东西

主文档 §6 写死「唯一图标库 `@tabler/icons-react`，其它不许新增」。工序图示不在 tabler 里。

**不是破例，是划一族**：`NomiLoadingMark` 本身就是自画的品牌资产。同理设立 —— **「工序指示器」= 受管动效资产**：

- 只能由 `src/design/` 提供，业务代码不许自己画

- 与通用图标分开：通用图标仍然只能用 tabler
- **长期成本**：每加一道工序要多画一个。加工序前先问「能不能并进已有的一道」

## 6. 文案纪律（片场话）

Nomi 是拍片工具，等待文案用**片场黑话**而非「正在思考中」。四条纪律：

1. **短等待（<3 秒）不轮播** —— 只说真话「正在读第三章」。3 秒的话还没看清就没了，轮播只会闪。
2. **按当前阶段取词，不乱串** —— 「正在架机位」出现在读剧本时就是胡说。句子按 §5 的 5 道工序分组。
3. **花钱 / 失败 / 扣费一律不俏皮** —— 这三个时刻用户在紧张，玩笑显得不靠谱。
4. **必配计时器**「已等 0:12」 —— 俏皮话是陪伴，计时器才是信息。

**文案要为布局让步**（§8 派生）：三等分按钮排里「换个模型重试」会挤，就写「换模型重试」。实现时长文案撑破行 = 设计错误，不是内容问题。

### 6.1 词库（zh-CN）

**分组键 = §5 的 Playbook 阶段**（不另立分组，否则又是一套词表）：

| 阶段 | 句子 |
|---|---|
| `script` | 正在通读第三章 / 正在跟场记对本 / 正在圈重点 / 正在数这场有几个人 |
| `storyboard` | 正在画分镜 / 正在排镜头顺序 / 正在想第一个镜头从哪切 / 正在给每镜配时长 |
| `build` | 正在架机位 / 正在调焦 / 正在给灯师递话 / 正在等演员就位 |
| `generate` | 正在打板 / 正在走位彩排 / A 机开始 / 正在盯回放 / 正在等这条过 |
| `assemble` | 正在压时间线 / 正在对字幕 / 正在垫音乐 / 正在剪掉废镜 |

**英文是已知缺口**（R15 要求走 i18n）：这批不能直译（「正在给灯师递话」直译即废）。英文需**二次创作**一批地道的（"Setting the key light" / "Waiting on the gaffer"…）。在那之前 `en` 回落到朴素版（"Generating…"），**不假装做完了**。

## 7. 动效规范

现状：主文档 §2.7 **只有一条 token**（`--nomi-transition-fast` 140ms）—— 「等待期长什么样」这一层从未定义过。这正是 agent 界面显得死板的根因。

### 7.1 主张

> **每个等待都要有脉搏，每个变化都要有交代。**

| 不做 | 做 |
|---|---|
| 渐变流光、粒子、发光边框、彩虹色（看三次就烦，且与纸感设计打架） | 扫光=还活着在跑 · 呼吸=在想 · 数字滚动=值刚变 · 滑入=这是新的 · 描边勾=成了 · 模糊转清晰=图正在出来 |

**分野纪律**：**等待类动效要慢、要低对比**（1.8–2.4s 循环，用户要盯几小时）；**状态跃迁动效才能快、才能明显**（一次性，值得看一眼）。

### 7.2 token（1 条 → 6 条）

| token | 时长 | 用途 |
|---|---|---|
| `--nomi-motion-tap` | 140ms | 交互反馈（**= 现有 `--nomi-transition-fast`，改名收口，不新增行为**） |
| `--nomi-motion-enter` | 260ms | 进场 / 退场 |
| `--nomi-motion-settle` | 420ms | 一次性跃迁：描边勾、数字落定 |
| `--nomi-motion-breathe` | 1.8s | 呼吸循环（在想） |
| `--nomi-motion-sweep` | 2.2s | 扫光循环（在跑） |
| `--nomi-motion-develop` | 900ms | 模糊转清晰（图在出） |

缓动统一 `cubic-bezier(.2,.7,.3,1)`（沿用现有）；循环类用 `linear` 或 `ease-in-out`。

### 7.3 三条硬纪律

1. **`prefers-reduced-motion` 一次性全关** —— 全部退化成静态。可访问性硬要求，不是选项。现有 `NomiLoadingMark` 已用 `motion-reduce:animate-none`，新组件照办。
2. **同屏最多 1 处扫光** —— 三个任务并行 = 三条进度条同时扫 + 三处呼吸 = 真吵。只有**当前活跃**那条动，其余降级成静态百分比。
3. **暗色模式必须单独验** —— 扫光在白底是「一道亮的扫过」，暗底要反过来。本轮样张只验了亮色。

## 8. 控件规格（尺寸 · 等宽 · 层级）

> 2026-08-27 用户两次点名：「有些按钮很大有些很小」「同行的按钮不能一个大一个小、一个长一个短」。根因是样张里出现了**设计系统里不存在的尺寸**（自造 `xs`=24px / padding 9px），以及**文字链与按钮同排**。

### 8.1 尺寸真相源（全部出自主文档，本节不发明）

| 元素 | 规格 | 出处 |
|---|---|---|
| 动作按钮 | **h-7 = 28px** · `px-3` = 12px · 12px 字 · **圆角 7px** | `WORKBENCH_BUTTON_SIZE.sm`（原注释：「时间线卡片内的紧凑动作」）+ `--workbench-control-radius: 7px` |
| 图标钮 | 28×28 · 圆角 7px · 图标 **16 / stroke-2** | `WorkbenchIconButton` `[&>svg]:size-4 [&>svg]:stroke-2` |
| 选择器 / 参数 pill | h-7 · `pl-2.5 pr-2` · 12px 字 · **药丸** | `NomiSelect` / `InlineParameterBar` 摘要 pill |
| 选项 chip | h-7 · `px-3` · 12px · 药丸 | 与选择器同族 |
| 文字链 | 无高度 · 12px · `--nomi-ink-60` | —— |
| 状态徽标 | 无高度 · 11px · 药丸 · `px-1.5 py-[1px]` · **不可点** | 主文档 §5.5 |
| 卡头语义图标 | **18** | 主文档 §6「弹窗/卡片头部语义图标（付费确认等）18」 |
| 行内小图标 | **13 / stroke-1.8** | 主文档 §6「节点角标内的小图标」 |

**一句话规则：所有可点的东西统一 28px 高。** 不是控件的（文字链、状态徽标）才没有高度。
**形状规则：选择器 / chip = 药丸；按钮 = 7px 方角。** 两者不能互串。

### 8.2 同排按钮四条

1. **同一排的动作按钮等宽均分**（`flex:1`），主次**只用颜色**分：深底(`--nomi-ink`)=主，描边=次。**层级不靠尺寸。**
2. **一排最多 3 个**；再多 → 主按钮 + 「更多」收起。
3. **文字链不与按钮同排** —— 要么单独成行，要么升级成按钮。（此前把次要动作降成文字链，恰恰制造了「一大两小」。）
4. **选项 chip 例外**：按内容定宽（它是**内容**不是动作），但同组高/圆角/字号必须一致。

**单动作最小宽 72px** —— 否则「撤销」会缩成小方块，跟别处按钮看着不是一族。

### 8.3 产物卡的动作归位

改 / 重跑 / 去画布都放在缩略图**外部的就近动作行**；桌面端选中产物后出现，移动端放在选中后的动作行或底部面板。禁止用半透明按钮盖住图像、视频或 3D 预览。调研里「就近改产物」的方向成立，但具体手法必须服从主设计系统 §1.5.3 的「动作不许压在内容上」。

### 8.4 建议加门岗（P2「能 grep 的做成棘轮」）

尺寸一致靠自觉必然再漂（本轮就是我手滑造了 `xs`）。已有 `check:tokens` 拦 hex 与任意 px 字号，但**控件高度没人拦**，这次的毛病正落在那个缝里。

```
check:controls → agent 交互组件内禁止出现 h-6 / h-9 / h-[24px] 等
                 非 h-7 / h-8 的控件高度；baseline 只减不增
```

R17 纪律：**加规则必须先验它会红。**

## 9. 参数条复用（批级 + 单镜两层）

**铁律：不在对话卡里另造参数 UI。** 计划卡/付费卡里的参数条 = **同一个 `InlineParameterBar`**（[InlineParameterBar.tsx](../../src/workbench/generationCanvas/nodes/InlineParameterBar.tsx)）。

它的控件**全由模型档案声明**（`DynamicModelControl` + `useDedupedModelSelect`）—— 换 seedream 出图，控件自动变图片那套；接新模型，卡里自动就有。这就是 P4「档案声明槽，通用系统负责填」。手写一排 chip = 每接一个新模型改两处。

### 9.1 为什么必须分两层

一条完整参数条 ≈ 350px（模型 ≤150 + 变体 + 摘要 pill 110 + 间距），5 行各一条塞不下。更重要的是**真实用法本就分层**：整批统一，个别例外。

| 层 | 位置 | 内容 |
|---|---|---|
| 批级 | 卡顶「这批用」 | 完整 `InlineParameterBar` = 这批的默认 |
| 单镜 | 每行右侧 | 默认显示「同上」；改过显示「已改 10s」+ 可「还原」；点行展开该行自己的参数条 |

**摘要 pill 在这里要 150px，不是节点上的 110px。** 样张真机截图看出来的：110/120px 时「16:9 · 5s · 720p」被截成「16:9 · 5s · 72…」，看着像坏了。节点上 110px 可接受（节点窄、且有 `title` 兜底），对话卡里有横向余量，别沿用。

这刚好咬合 master plan §4 的 v1 刚性「**一批内单 provider，一张卡一次授权一本账**」——批级参数条就是那份合同的可视化。

### 9.2 滚动与窄栏规则

1. **对话内参数使用就地展开，不使用一次定位后不跟随的 portal 浮层。** 展开内容属于原卡片，随消息一起滚动；打开时不冻结整个对话。
2. **320–389px 单列堆叠。** 模型选择器占一行，参数摘要占下一行；摘要可以折成「16:9 · 5s」但不能退化成无文字图标。390px 起允许同排。任何宽度都不横向滚动 composer。

### 9.3 生成提案卡：复用画布图片节点的卡片骨架

Agent 里的图片 / 视频生成提案，不再另造一套“聊天专用生成表单”。它复用画布图片节点下方已经存在的卡片语义和控件：

```text
┌────────────────────────────────────────┐
│ Prompt                                  │
│ 可编辑的提示词 / 当前镜头描述             │
│                                        │
│ [图片模型 / 供应商] [变体] [16:9 · 1K]   │
│                          [确认生成]       │
└────────────────────────────────────────┘
```

- 上半部永远是 Prompt：显示完整可读的当前内容，足够长时在卡内换行 / 滚动，不用一串截断文本冒充已确认内容。
- 下半部是参数区：直接挂现有 `InlineParameterBar`，模型、供应商、变体、比例、清晰度、时长等由模型档案声明；点击选择器或摘要 pill 就地展开并立即更新草稿。
- Agent 卡可以换宿主外壳的颜色、状态徽标和确认文案，但不能改变 Prompt 在上、参数在下的阅读顺序，也不能手写 provider 专属控件。
- 单张卡的主动作只作用于当前这一张；批准前修改 Prompt / 参数会重新计算 `effectiveArgs`、费用和冻结字段，批准后才提交生成任务。

这里的“复用”是交互和数据合同复用，不是把画布节点 DOM 硬搬进对话：卡片宿主可以是 Agent 流内富卡，但参数控件、模型档案、校验、费用和提交入口必须仍由生成画布领域 owner 提供。

### 9.4 框选批量生成：一张批量卡 + 横向三页堆叠

框选后不把 N 张生成卡全部铺在对话流里。Agent 先读取现有选区，生成一张批量提案卡；卡内用横向堆叠承载选中的生成项：

```text
        ┌───────────────┐
   ┌────┤ 3 / 8         │  ← 当前项
   │    │ Prompt        │
   │    │ 参数           │
   │    └───────────────┘
   └────  ← 后两项只露出右侧角 / 页签

本批默认： [图片组模型/供应商] [视频组模型/供应商] [并发数]
                                              [批量生成 8 项]
```

1. 可视层最多露出 3 张：当前卡 + 后续两张，横向错位，后卡只露出可点击的右侧角 / 页签。绝不渲染一长串横向卡片。
2. 点击当前卡右侧角进入下一项；再次点击进入再下一项。当前页用 `当前项 / 总数` 明示，支持键盘左右键和可访问的上一项 / 下一项按钮，不能只靠一个没有文字的角落猜交互。
3. 总数超过 3 时仍只显示三层堆叠；堆叠是视窗，不是把总数截断。翻页后，前一张回到堆叠后方，索引循环到最后一项时回到第一项，并保留当前项的编辑草稿。
4. 点击某项进入编辑态时，仍然遵循“上 Prompt、下参数”；修改只产生该项的显式 override。未修改项显示“同批默认”，修改项显示“已单独修改 / 还原”。
5. 批量卡的公共控制固定在堆叠下方：沿用画布框选工具条的 `CanvasBulkModelSelect` / `BulkModelPicker` 和执行组语义。选区含图片、视频时分别显示图片组和视频组的批量模型 / 供应商选择；不在每张卡重复放供应商选择器。
6. 公共批量参数是默认值；单项 override 只在对应页显示。点击“批量生成”沿用选区范围和现有批量确认 / 费用 / 并发语义，不能把“翻页”误做成逐张提交。

批量卡与多候选卡不是同一个东西：批量卡翻的是多个输入镜头 / 选中节点；多候选卡翻的是同一请求的多个结果。两者都最多露出三层，但状态源、确认语义和“去画布”目标必须分开。

### 9.5 组件与状态合同

建议实现时只增加 Agent 宿主适配层，不复制生成逻辑：

| 责任 | 复用 / 承接 | 不能在 Agent 卡里重新实现 |
|---|---|---|
| 单卡参数 | `InlineParameterBar`、`NodeParameterControls` 的档案声明 | provider 专属参数表、第二套比例 / 清晰度选择器 |
| 框选批量模型 | `CanvasSelectionToolbar` → `CanvasBulkModelSelect` → `BulkModelPicker` | 每张卡一个模型 / 供应商选择器 |
| 批量范围 | 当前选区、`data-batch-scope="selection"`、现有 execution group | 由卡片顺序猜选区，或重新维护一份选中列表 |
| 批量执行 | 现有批量确认、费用和队列入口 | 翻到哪张就自动提交哪张 |
| 翻页 | 批量提案 view 的 `activeIndex`，与草稿映射 | 让 CSS z-index 充当状态，或每张卡自己存页码 |

最小状态形状：

```ts
type BatchProposalView = {
  scope: 'selection'
  itemIds: string[]
  activeIndex: number
  batchDefaults: EffectiveGenerationArgs
  itemOverrides: Record<string, Partial<EffectiveGenerationArgs>>
  executionGroups: Array<{ executionKind: 'image' | 'video'; itemIds: string[] }>
}
```

`activeIndex` 只负责当前页；真正提交的参数必须在确认前由 `batchDefaults + itemOverrides[itemId]` 重新派生、校验、估价和 hash。这样翻页、编辑、返回修改、失败恢复都不会出现“卡面显示一套、实际请求另一套”的第二真相源。

## 13. 输入合同：画布选中、`@` 与附件

### 13.1 不设“引用模式”

用户不用先切换模式再点对象。画布单选 / 多选后，composer 上方的**上下文架**自动出现对应 chip；输入 `@` 或点 `@` 按钮，可补充画布节点、音视频时间段、3D 视角、网页选区与 Skill。两条路径最终都产生同一种结构化引用：

```ts
type ContextHandle = {
  id: string
  kind: 'image' | 'video' | 'audio' | 'document' | 'model3d' | 'webSelection' | 'canvasNode'
  targetId: string
  revision: string
  locator?:
    | { type: 'crop'; x: number; y: number; width: number; height: number }
    | { type: 'timeRange'; startMs: number; endMs: number }
    | { type: 'pages'; from: number; to: number }
    | { type: 'cameraPose'; cameraId: string; poseHash: string; viewName: string }
    | { type: 'web'; url: string; selector?: string; capturedText?: string }
  display: { title: string; subtitle?: string; posterUrl?: string }
  intentRole: 'subject' | 'style' | 'structure' | 'motion' | 'audio' | 'source' | 'target'
}
```

`intentRole` 必须可见且可改。三张图片若只显示文件名，模型不知道谁是主体、谁是风格；chip 要说成「主体 · 角色定妆」「风格 · 低饱和胶片」。自动推断只能给默认值，不能藏起来。

### 13.2 上下文架与附件的边界

| 输入 | 生命周期 | 用户看到 | 规则 |
|---|---|---|---|
| 当前画布选中 | 随选择变化，发送时冻结 | 上下文架 chip | 取消选中前可逐个摘除 |
| `@` 引用 | 本轮草稿，发送时冻结 | 同一上下文架 | 可引用非当前对象和精确片段 |
| 本地附件 | 本轮草稿 | 48px 媒体 tile / 文件 chip | 图片、视频、音频、文档；不自动变项目长期知识 |
| 项目 Knowledge | 跨轮 / 跨会话 | 面板顶部常驻标记 | 需显式加入，不能因一次上传永久污染上下文 |
| Skill | 对后续输出生效直到摘除 | 常驻技能标记 | 展示名称、版本与作用阶段 |

上下文架是 composer 的 L1 输入反馈，不另占工具栏入口；`@` 与附件各保留一个规范入口。图片 crop、音视频 time range 和 3D camera pose 都要在 chip 副标题中可读，不能只藏在 JSON。

### 13.3 发送即冻结

发送生成 `ContextSnapshot`：保存每个 handle 的 `targetId + revision + locator`，同时保存附件、工作方式、批准策略和 Agent 模型。历史消息始终指向该快照。画布对象更新后：

- 历史 chip 显示「引用后已变化」，仍可打开当时快照。
- 用户可点「改用最新版」生成新的草稿引用；旧消息不被改写。
- 对象已删除时保留 poster 与元数据，标「原对象已删除」，不伪装成仍可定位。

## 14. 执行合同：工作方式与批准策略是两根轴

### 14.1 工作方式

| 工作方式 | Agent 可以做什么 | 典型请求 |
|---|---|---|
| `Ask` | 解释、比较、给建议，不写项目 | 「这三个镜头为什么不连贯？」 |
| `编辑选中` | 只对当前冻结的选中范围提修改 | 「把这段 02:10–02:14 的节奏加快」 |
| `Agent` | 跨对象规划并执行允许的多步任务 | 「找参考、拆镜并生成三个候选」 |

### 14.2 批准策略

| 策略 | 默认行为 | 仍会停下的硬闸 |
|---|---|---|
| `逐步确认` | 每个项目写入或外部动作前确认 | 全部硬闸 |
| `自动批准安全动作` | 自动读项目、搜索、创建可撤销草稿；高风险暂停 | 花钱、发布、删除、账号、外部写入 |
| `完全允许（本项目）` | 在当前项目沙箱内自动执行可撤销动作 | 花钱、发布、删除、账号、验证码、外部写入 |

改变工作方式**不能**隐式扩大批准策略；切到 Agent 不等于全权。批准策略也不能扩大 workspace / 项目沙箱。完全允许只减少本地、可撤销动作的停顿，不得绕过硬闸。Codex 桌面端的 sandbox / approvals 两层与 Claude Code 的 permission modes 证明了这种拆分可理解；它们不决定 Nomi 的创作流程。

## 15. 模型合同：Agent 模型与制作模型分层

composer 只选择**负责理解、规划与调用工具的 Agent 文本模型**。图片、视频、音频和 3D 制作模型属于具体产物步骤，在计划卡或画布节点参数中选择。

| 层 | 选择位置 | 自动化 | 必须展示 |
|---|---|---|---|
| Agent 模型 | composer 底栏 | 用户手选，可记项目偏好 | 名称、上下文 / 能力告警 |
| 图片制作模型 | 图片计划项 / 节点 | Agent 按 capability 路由，用户可改 | 模型、比例、数量、单价 |
| 视频制作模型 | 视频计划项 / 节点 | 同上 | 模型、首尾帧、时长、清晰度、单价 |
| 音频制作模型 | 音频计划项 / 节点 | 同上 | TTS / 音乐 / 音效类型、时长或字数、单价 |
| 3D 制作模型 | 3D 计划项 / 节点 | 能力存在才可选 | 输入类型、拓扑 / 贴图档、单价与预计时间 |

Agent 自动匹配制作模型时，计划卡要写明「为什么选它」和备选；用户改的是这一项，不是全局 Agent 模型。模型能力不存在时诚实说缺口，不能用同名伪选项兜底。

## 16. 忙时输入：完整队列，不丢草稿

现状 `busy` 时回车静默丢失是 P0。队列项不是字符串，而是发送瞬间的完整草稿：

```ts
type TurnDraft = {
  id: string
  text: string
  attachments: ComposerAttachment[]
  context: ContextSnapshot
  workMode: 'ask' | 'editSelection' | 'agent'
  approvalPolicy: 'step' | 'safeAuto' | 'fullProject'
  agentModelId: string
  createdAt: number
}
```

- 待执行项可编辑、删除、上移、下移、暂停 / 恢复；当前执行项不可偷偷改写。
- 模式、批准策略或模型切换只影响**新草稿**，排队项显示自己的快照。
- 「纠正当前任务」和「下一条完整请求」分开：前者作为可见 steering 指令，在当前原子动作结束后读取；后者留在队列。
- 队列折叠时仍显示数量和是否暂停；附件与引用用图标 + 数量回显。

Dyad 提供了完整队列操作的开源近邻；AI Elements Queue 提供组合式 UI 壳；Pi 的 `deliverAs: steer | followUp | nextTurn` 说明不同投递语义应成为显式数据，而不是靠时机猜。

## 17. 反馈合同：对话投影，画布承载

### 17.1 多媒体回显矩阵

| 结果 | 对话里显示 | 主动作 | 画布里显示 |
|---|---|---|---|
| 图片 | 缩略图、尺寸、版本 | 去画布 | 可编辑图片节点 / 候选暂存 |
| 视频 | poster、时长、比例、播放状态 | 去画布 | 视频节点与时间范围 |
| 音频 | 波形摘要、时长、类型 | 播放 / 去画布 | 音频节点与轨道入口 |
| 文档 | 类型、页数 / 字数、来源 | 打开 / 去画布 | 文档节点或项目资料 |
| 3D | 当前相机截图、视角名、模型状态 | 去画布 | 完整 3D viewer；窄对话栏不嵌 viewer |
| 网页素材 | 预览、来源域名、作者 / 许可 | 导入画布 | 本地化资产 + provenance |

「去画布」必须实际执行：定位目标、缩放到可读范围、短暂高亮，保留原对话滚动位置；返回 Agent 后仍停在原消息。对象已删时按钮禁用并说明原因。

### 17.2 候选暂存

同一生成请求的多个候选先进入暂存组，拥有 `select / previous / next / accept / discard`；只有 `accept` 后才成为正式画布版本。对话卡只是同一暂存状态的投影，不能另存一套选中结果。InvokeAI 的 staging state 证明该合同可独立建模；ComfyUI 的结果 gallery 证明图片 / 视频 / 音频应共用结果集合，3D 使用独立 viewer。

## 18. 浏览器与外部素材：先读、再选、后导入

首期不是“让 Agent 随便控制浏览器”，而是四段受约束流程：

1. **取上下文**：当前页、用户选区或显式 URL；网页内容一律是不可信输入。
2. **搜索候选**：浏览器搜索或 Connector（如 Unsplash / 合法音频库）返回结构化候选。
3. **展示来源**：预览、作者、来源 URL、许可 / 未知许可、尺寸或时长。
4. **用户选择后导入**：素材本地化并记录 provenance，再进入画布；未选择的不污染项目。

登录、创建账号、验证码、购买、发布、删除、评论和任何外部写入始终停下。浏览器 Connector 只回答「从哪里拿」，Capability 回答「能做什么」，Skill 回答「怎么判断 / 怎么做」，Workflow 负责组合步骤，Agent 负责本次计划；权限与生命周期继续引用 #226，不在本文再造一份。

## 19. 可扩展 UI：借 Pi 与 AI Elements 的壳，不借权限

插件可以贡献受管的 `ComposerAction`、`ContextHandleResolver`、`ConversationItemRenderer` 与 `ResultPreviewRenderer`，但必须注册进宿主 registry，由宿主决定位置、权限、审批和卸载。禁止插件直接向 composer 注入任意 DOM、绕过 `SpendConfirmRequest`，或把自有模型选择器塞进常驻底栏。

Pi 固定提交 `853a80d` 的 extension 合同有两个值得吸收的实现细节：工具执行用稳定 `toolCallId`，渲染上下文显式带 `isPartial / expanded / isError`；消息投递显式区分 `steer / followUp / nextTurn`。不吸收的部分同样明确：Pi 官方说明扩展默认拥有宿主进程完整权限、内建 permission system 不负责 OS 级隔离；Nomi 插件不能照搬这个信任模型。

AI Elements 固定提交 `6a9d5b1` 的 Conversation 用 `role="log"`，把内容、空态、回到底部按钮拆为组合件；Queue 将 item、attachment、actions 拆为 slots。Nomi 可复用这种拆分与测试思路，但 visual tokens、图标、按钮和安全状态都以 Nomi 为准。
