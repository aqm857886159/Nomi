> 日期：2026-08-31
> 状态：设计提案，尚未进入生产实现
> 范围：Agent 主栏、composer、对话流、任务反馈、生成提案、Skill / App / 模型发现、跨工作面连续性
> 依据：用户提供的 2026-08-31 竞品截图、PR #194、目标分支 `codex/project-agent-host-phase1-20260827`、Nomi 设计系统与 Phase 6 真实用户验收合同。

## 0. 结论先行

Nomi 的 Agent 不应该被设计成一个“更大的聊天框”，也不应该复制竞品的 Skill 大厅、模型选择器和工具日志。它应该是同一份创作工作的控制层：

```text
用户说目标
  → Agent 读取当前现场
  → 给出最小可审阅计划
  → 在正确的领域 owner 中执行
  → 把任务、产物、费用、失败和下一步投影回对话
  → 用户回到画布 / 时间线完成专业复核
```

一句话产品主张：

> **对话是任务的索引与回执，画布和时间线是作品的真相源。**

最重要的设计取舍是：

> **Agent 要足够主动，把用户从“我想做什么”带到“下一步是什么”；但所有会改变作品、消耗额度或影响外部世界的动作，都必须能在副作用发生前看懂、改正、确认和撤销。**

这条取舍决定了本方案的形态：默认一行，必要时卡片；默认读现场，必要时行动；默认复用领域 UI 和 owner，不在聊天里再造一套生成器、时间线或账本。

### 1.1 证据分级

| 标记 | 含义 | 本文用法 |
|---|---|---|
| **Observed** | 截图或代码中直接可见 | 说明“现在看到了什么” |

### 1.2.3 竞品优点、Nomi 采用方式与明确不采用项

|---|---|---|

### 1.2.4 对原方案的具体增补

基于逐张复核，原方案需要把以下细节从“原则”落实为组件合同：

1. **ProposalCard** 必须有固定四段：头部费用/状态、可展开 prompt、参数条、右下动作；确认后的视觉状态不能继续保留“确认”按钮，避免用户误以为还未生效。
2. **OperationSummary** 必须先显示阶段摘要和当前动作，再提供“查看技术细节”；失败不能只是一行红字，要提供影响、是否扣费、重试/修改/停止后续三个明确分支。
3. **QuestionCard** 必须支持编号单选、自由文本、附件和忽略，但同一事实要有 factId 与版本，Host 在追问前检查已确认事实，阻止重复询问。
4. **SkillDetail** 必须把“示例效果”与“可执行边界”放在同一详情里：输入、输出、涉及的阶段、所需能力、版本、更新时间、额度风险、失败边界缺一不可。
5. **ContextChip** 必须标明作用域和快照版本：Agent model、Production model、Skill、Reference、Attachment 不能只靠同一种 pill 外观区分。
6. **模式选择** 必须由一个小菜单进入、由一个持续 banner 反馈、由设置页管理默认值；三处共享同一 policy，不允许出现截图 66 与 85 那种词汇漂移。
7. **空间预算** 必须按 320px、340px、390px 三个真实宽度检查：菜单不裁切、参数能堆叠、问题卡不产生大块无意义空白、Composer 不被 banner 覆盖。

这一节是后续 HTML mockup 的逐项验收表：mockup 不能只做“默认展开”一张图，至少要演示 62→63→64、70→71、81→82→84、88→89→92 四条状态链。

### 1.2.5 Beautiful UI 的借鉴边界

补充参考 [Beautiful UI](https://www.beautifului.dev/) 后，借鉴重点确定为“AI-native 原语的组织方式”，不是复制它的页面皮肤。它把 Loading State、Thinking、Streaming Text、Approval Card、Tool Chips、Task Rows、Prompt Bar、Recommendation Card、Context Cards、Diff Table、Records Table、Filter Table、Sidebar Nav、Search、Flowchart、Insight Cards、Code Block、Fine-tune Card 和 Selection Actions 拆成可组合的交互单元。

对 Nomi 直接有效的吸收是：

- **Thinking / Tool Chips / Task Rows** 对应 Nomi 的思考摘要、操作账本和队列；默认呈现阶段摘要，展开才显示证据。
- **Approval Card / Recommendation Card** 对应生成提案和下一步资产卡；增加推荐度，但推荐度只解释排序，不代替用户授权。
- **Prompt Bar** 对应 Composer 的 @ 当前对象、/ Skill、模型、引用和执行方式；这些是输入上下文，不是另一套任务状态。
- **Context Cards / Diff Table** 对应资产标准件、文档变更和版本回执；结果必须可追到 owner 与 revision。
- **Sidebar / Search / Filter** 对应 Skill、模型和任务历史发现；发现层可以丰富，常驻工作面仍要控制 L1 功能簇数量。

不照搬的部分也要固定下来：Beautiful UI 的示例是通用 AI 业务数据，Nomi 的画布、时间线、资产库才是作品真相源；它的轻量演示 loading 不能替代 Nomi 的真实状态；任何“Accept”都要先过 Nomi 的参数冻结、费用估算、权限和可恢复性契约。后续动态 HTML 样张应作为以上原则的验证物，但不纳入本次 PR 文档提交。

## 2. 设计方向：Nomi 应该让人第一眼看到什么

### 2.1 目标用户与任务

核心用户是正在制作视频的创作者，而不是来管理 Agent 的管理员。用户在 Agent 面前通常只有三种真实需求：

1. “看懂我现在的现场，并帮我推进一步。”
2. “把一个模糊目标拆成我能检查的剧本、分镜、素材和生成任务。”
3. “我不想学习 Nomi 的内部格式，但我希望每次自动化都不偷改作品。”

### 2.2 第一眼信息层级

打开 Agent 主栏后，用户按这个顺序理解页面：

```text
1. 我现在在哪个工作面？当前对象是什么？
2. Agent 正在做什么 / 是否等我确认？
3. 结果在哪里？能否打开、修改、重试或撤销？
4. 我下一步最应该做什么？
5. 只有我主动展开，才看技术细节。
```

页面不应第一眼展示供应商、工具名、JSON、result hash 或一大串机器操作。

### 2.3 视觉方向

- **基调**：密集、克制、暖中性、工作台感；不是营销式 AI 面板。
- **主层级**：对话文本保持最轻；正在等待的任务保持中性；需要用户行动使用强调色；完成使用成功色；失败使用危险色。
- **重点**：真正需要判断的地方才用卡片、媒体缩略图或参数条。
- **动效**：等待用低对比、慢节奏的工序指示；状态跃迁才有明显反馈；同屏最多一处扫光。
- **反装饰**：不使用品牌 Logo 代替状态、不使用粒子或渐变流光模拟“智能”、不把状态颜色做成 8 种彩色。

### 2.4 反模式清单

| 不采用 | 原因 |
|---|---|
| 自动模式下删除 Tapies / 历史 | 不可逆、损害可追溯性，与本地优先和可恢复原则冲突 |
| 每个模型一套参数卡 | 违反通用性，接模型就要改两处 UI |
| 聊天中另造一套时间线或生成队列 | 会产生第二份真相，无法与领域 owner 对账 |
| 把 Skill 当权限开关 | Skill 只决定方法；权限由 Host / capability / owner 决定 |
| 一条消息下面展示所有底层工具调用 | 过程噪音挤走用户任务；改为阶段摘要 + 展开细节 |
| 只提供“批准 / 拒绝” | 用户无法修正模型、提示词、参数和引用，审批不是真正的最终提案确认 |
| 让动作盖在图片、视频或画布内容上 | 用户正在看的内容被遮挡，且容易误点 |
| 只验证截图或按钮存在 | 无法证明状态迁移、持久化、真实生成和失败恢复 |

## 3. 页面总结构

### 3.1 外层布局：保留 Workbench，Agent 做统一投影

目标分支已经在 `src/workbench/WorkbenchShell.tsx:343` 使用一个 `ProjectAgentResidentShell`，通过 portal 投影到 Creation、Generation、Preview 的各自 dock；这正是正确的结构。继续保持：

```text
Workbench Host
├─ Creation / 文稿工作面
├─ Generation / React Flow 画布工作面
├─ Preview / 播放器 + 通栏时间线
└─ 一个 Project Agent Host
   ├─ 同一 Thread / Turn / Item / Queue
   ├─ 当前 surface 的 Context Adapter
   └─ 当前 surface 的定位与高亮
```

不做四个面板相互同步标题、消息和草稿。面不同，引用对象不同；Agent 身份、历史、审批、任务和产物引用必须相同。

| 项目 | 建议值/规则 | 依据 |
|---|---|---|

| Dock 收起 | 不占列，右上显示 36px 高状态胶囊 | PR #194 / 目标分支已有走查 |

### 3.4 Header 控件与 icon 规格

Header 只保留跨任务的控制，不把当前操作对象的按钮放在这里：

| 控件 | 图标 | 层级 | 用户看到的语义 | 交互 |
|---|---|---|---|---|

## 4. Composer：把复杂性放在“可见上下文”，不放在表单里

### 4.1 Composer 的四层

```text
上下文架   当前选中对象自动出现 + 用户可摘除
附件架     本轮本地文件，显示上传状态和移除
输入区     自然语言目标，Enter 发送，Shift+Enter 换行
操作行     添加 / 引用 / Skill / 模式 / Agent 模型 / 发送
```

### 4.2 上下文架

当前选中的文稿选区、画布节点、预览帧、时间线区间自动出现在输入区上方；用户不需要先切换“引用模式”。`@` 用来补充非当前对象。

每个 chip 必须显示三件事：

```text
[主体 · 老钟表匠 / 角色定妆 / v3]
[风格 · 低饱和胶片]
[时间线 · 00:06–00:14]
```

内部合同建议继续沿用 PR #194 的 `ContextHandle`，至少包含：`targetId`、`revision`、`locator`、`display`、`intentRole`。其中 `intentRole` 不可隐藏：三张参考图必须能区分“主体、风格、结构、动作、来源”。

发送时创建不可变 `ContextSnapshot`：

- 保存目标 revision、裁剪区域、时间区间、3D camera pose 或网页选区。
- 原对象后来改变时，历史消息显示“引用后已变化”。
- 用户可选择“改用最新版”，但不能偷偷改写旧消息。
- 原对象删除时保留缩略图和元数据，标明“原对象已删除”。

### 4.3 操作行：推荐的 L1 / L2 分层

竞品把很多东西平铺在底部；Nomi 应按频率和作用域分层：

| 控件 | 默认层级 | 原因 |
|---|---|---|
| `+` 添加附件 / 本地上传 / 项目素材 | L1 | 输入新素材是高频行为；同一个入口展开来源 |
| `@` 引用现场或对象 | L1 | 直接决定本轮作用对象 |
| Skill | L1（已选时持续显示） | Skill 会改变后续输出，必须让用户看得见 |
| 模式 / 授权 | L1 | 会改变副作用边界，不能藏起来 |
| Agent 文本模型 | L1 但低视觉重量 | 是理解/规划模型，不应和制作模型混淆 |
| 提示词预设 | L3 | 只改变表达方式，不应占据常驻位；可收进 Skill / 方法菜单 |
| 麦克风 | L2 | 有语音能力时显示；不可用时说明原因并禁用 |
| 发送 / 停止 | L1 | 唯一主动作；发送禁用只能发生在没有任何可执行草稿时 |

不把“图片制作模型、视频制作模型、比例、时长、清晰度”塞进 Composer；它们属于具体生成提案或节点参数。

### 4.4 附件与引用的区别

| 输入 | 生命周期 | 用户看到 | 不允许 |
|---|---|---|---|
| 本地附件 | 本轮草稿 | 媒体 tile / 文件 chip / 上传状态 | 一次上传自动变项目知识 |
| 当前选中 | 随选择变化，发送时冻结 | 上下文架 chip | 历史消息跟着当前选中漂移 |
| `@` 引用 | 本轮草稿，发送时冻结 | 同一上下文架 | 只显示文件名而不显示作用 |
| 项目 Knowledge | 跨轮、需显式加入 | 面板顶部常驻标记 | 因一次附件上传永久污染 |

### 4.5 输入队列

Agent 忙时允许继续输入，不能静默丢弃。每条排队项保存完整 `TurnDraft`，而不是只保存文字：

```ts
type TurnDraft = {
  id: string
  text: string
  attachments: ComposerAttachment[]
  context: ContextSnapshot
  workMode: 'ask' | 'guided' | 'balanced' | 'auto'
  approvalPolicy: 'step' | 'safeAuto' | 'fullProject'
  agentModelId: string
  createdAt: number
}
```

队列可编辑、删除、上移、下移、暂停 / 恢复；正在执行的当前 Turn 不可被偷偷改写。“纠正当前任务”与“下一条完整请求”分开建模。

## 5. 对话流：三种视觉层级，八种状态

### 5.1 三种视觉层级

| 层级 | 用途 | 示例 |
|---|---|---|
| 一行 | 不需要用户做决定的过程 | 思考、读现场、工具摘要、排队、进度、写入回执、上下文用量 |
| 可展开的一行 | 可能需要追查的过程 | 工具调用、压缩提示、计划摘要、失败诊断 |
| 卡片 | 用户要决定或需要查看产物 | 反问、执行计划、付费确认、失败恢复、多候选、媒体产物、偏差对账 |

增加新 UI 前先问：它是否需要用户做决定？它是否就是产物？两个答案都不是，就只能做一行。

### 5.2 状态词表

沿用 PR #194 的统一状态：

| 状态 | UI 文案 | 颜色组 | 用户动作 |
|---|---|---|---|
| `drafting` | 规划中 / 正在输出 | 中性 | 等待或停止 |
| `proposed` | 等你确认 | 强调色 | 查看、编辑、批准、拒绝 |
| `declined` | 已拒绝 | 中性 | 继续对话 |
| `queued` | 排队中 | 中性 | 编辑、取消、暂停 |
| `running` | 进行中 | 中性 + 单处动效 | 停止、查看任务 |
| `done` | 已完成 | 成功色 | 打开产物、定位、撤销 |
| `failed` | 失败 | 危险色 | 编辑并重试、换模型、查看日志 |
| `stopped` | 已停止 | 危险/中性 | 继续或重新计划 |
| `retryable` | `failed` 的附加标志 | 不独立着色 | 允许定点重试 |
| `deviated` | `done` 的附加标志 | warning | 查看批准值与执行值差异 |

### 5.3 过程行

过程行回答“现在在哪一步”，不展开 schema：

```text
[工序图示] 正在读取当前画布 · 2 个对象 ✓
[工序图示] 正在准备 3 个镜头 · 预计费用待确认
[工序图示] 进行中 · 镜头 2 / 3 · 已用 00:18   停止
[工序图示] 已加入 3 个镜头卡 · 定位查看 · 撤销
```

工具行展开后才看到：作用对象、可读参数、结果引用、失败原因。隐藏 capability id、hash、原始 JSON 和内部路径。

### 5.4 思考与等待

不用 Nomi Logo 代表等待；Logo 是身份，工序图示才是状态。阶段值必须来自已有 playbook 阶段：`script / storyboard / build / generate / assemble`，不另造“读本 / 拆镜 / 出图 / 上轨”第四套词表。

动效规则：

- 短等待不轮播多句俏皮话，直接说真实动作。
- 等待类动效慢、低对比；状态跃迁才明显。
- 同屏最多一处扫光；并行任务其余只显示静态状态。
- `prefers-reduced-motion` 下所有循环动效关闭，保留文本和几何变化。
- 暗色模式单独验对比度和扫光亮度。

### 5.5 反问卡

一次最多合并 3 个真正阻断执行的问题；能用当前现场推断的内容不要问。每个选项必须是可点击的结构化值，也允许“自定义”。用户提交后，问题、回答和确认状态留在同一 Turn 中，不能再次问同一字段。

推荐卡结构：

```text
需要你补一个决定
目标：为“老钟表匠”制作角色标准件
已知：主体、三视图、16:9、生成模型已默认
请选择：
  [角色职业 / 表演内容] [输出比例] [跳过并使用项目默认]
```

## 6. 生成提案卡：把“批准”升级成最终提案确认

这是这批截图与现有实现之间最需要继续补齐的部分。

### 6.1 生成前的可读合同

在任何图片、视频或付费动作前，卡片必须把下面内容作为同一份提案展示：

```text
目标：生成老钟表匠角色标准设定图
引用：主体·角色定妆 v3
输出：图片 · 16:9 · 1 张
制作模型：由图片能力档案匹配，可改
关键参数：分辨率、质量、风格/模式、参考权重
预计费用：¥X.XX / 未定价需确认
执行边界：创建节点 / 提交生成 / 写入资产 / 加入时间线
```

关键字段按三种状态标注：

- **发送后仍可改**：提示词、部分构图描述、非冻结文字。
- **批准时冻结**：镜头数、制作模型、时长、清晰度、引用、预计费用对应的请求值。
- **执行后只能撤销/重做**：已提交的 provider job、领域 owner 已写入结果。

### 6.2 参数条复用

计划卡和付费确认卡都复用现有 `InlineParameterBar`，控件由模型档案声明；不在 Agent 卡里手写第二套模型参数 UI。

```text
批级： [制作模型] [比例] [质量] [时长] [数量] [预计费用]
单镜： 镜头 01 · 同上
       镜头 02 · 已改 5s · 还原
```

批级参数是默认值，单镜可以覆盖。单镜覆盖必须显式显示，不能让用户猜某个镜头是否继承默认。

#### 本次补充：生成卡必须长成画布图片卡，批量用三层堆叠

用户对“生成卡”的具体要求进一步收口为：

```text
单张：Prompt（上）
      参数选择：图片/视频模型、供应商、变体、比例、清晰度、时长（下）
      主动作：确认生成

批量：同一张批量提案卡
      ├─ 当前项 Prompt + 参数
      ├─ 后两项横向叠放，只露出右侧角 / 页签
      └─ 公共批量模型/供应商、并发、批量生成
```

这不是视觉上的“像画布”而已，而是复用同一交互合同：Agent 宿主可以有自己的状态徽标和确认文案，但参数控件必须继续来自 `InlineParameterBar`；框选批量的模型选择必须继续来自 `CanvasSelectionToolbar` 现有的执行组和 `CanvasBulkModelSelect` / `BulkModelPicker`。如果选区同时包含图片和视频，底部按现有 execution group 分别显示图片组与视频组的批量选择，而不是把供应商选择复制到每一项。

批量堆叠的可观察行为：

- 最多露出 3 层，当前项 + 后续两项；不把全部卡片铺开。
- 点击右侧露出的角 / 页签进入下一项，并显示 `当前项 / 总数`；支持左右键和有文字的上一项 / 下一项辅助入口。
- 翻页不提交生成，只改变 `activeIndex`；当前项修改 Prompt / 参数才写入该 item 的 override。
- 未改项显示“同批默认”，改过显示“已单独修改 / 还原”。批量生成只在公共动作处一次提交整批，并沿用现有选区、费用、确认、并发和队列语义。
- 批量镜头堆叠与同一请求的多候选结果堆叠分开建模：前者翻输入项，后者翻结果项；不能共用一个 selected index。

因此，批量卡的首要取舍不是“能不能看到所有卡”，而是“用有限视觉空间保留逐项可编辑性”。默认让用户快速扫过整批，只有当前项进入编辑态；公共参数放在下方一次调整，避免 N 张卡重复制造选择器和认知噪音。

### 6.3 审批行为

批准不是 boolean，而是：

```text
用户打开提案
  → 修改 effectiveArgs
  → Host 重新 prepare / validate / hash
  → 展示更新后的费用与冻结字段
  → 用户批准
  → domain adapter 执行
  → receipt / artifact / task 回写
```

拒绝不得写入现场。参数校验失败应回到可编辑态并指出字段，不要只显示“执行失败”。

### 6.4 多候选与暂存

同一生成请求的多个候选先进入候选暂存组：

- 默认最多并排 3 版，更多折叠。
- 支持上一版 / 下一版、接受、丢弃、重新生成。
- 只有“接受”后才成为正式画布版本。
- 对话卡与画布候选区投影同一份 staging state，不各自保存 selected index。

### 6.5 生成后的产物卡

图片：缩略图、尺寸、版本、来源、模型；动作放在媒体外部：`改`、`重跑`、`去画布`。
视频：poster、时长、比例、播放状态、镜头引用；不在窄 Dock 内嵌完整编辑器。
音频：波形摘要、时长、类型、播放 / 去画布。
3D：当前相机截图、视角名、模型状态；完整查看回到 3D viewer。

“去画布”必须真的定位、缩放到可读范围、短暂高亮，并保留对话滚动位置；不是只切换一个 tab 或改标题。

## 7. 下一步卡：让 Agent 主动但不替用户拍板

竞品截图里的“资产审查与下一步”是值得吸收的模式：它把长流程压缩成用户下一次可做的选择。Nomi 的版本应绑定项目阶段和真实资产状态。

### 7.1 卡片结构

```text
ASSET REVIEW · NEXT STEP                         1 / 4
老钟表匠标准件已通过一致性检查
主体特征、三视图、背景规范已满足角色锚点要求

[推荐下一步 · 生成古董黄铜怀表道具]
 [生成道具设定图 ↗]

[第二角色 · 年轻女子]
 [生成角色图 ↗]

[核心场景 · 钟表铺内景]
 [生成场景概念图 ↗]
```

规则：

- 只保留一个推荐主动作；备选最多 2 个。
- 卡头显示项目进度，但进度必须来自真实资产/任务数，不可用“AI 觉得完成了”。
- CTA 发送结构化 intent，继承当前项目的角色锚点、风格和引用关系。
- 允许用户先查看细节，再继续；不能用一键 CTA 直接跳过需要确认的费用或危险操作。
- 完成一个资产后，卡片原位更新为下一阶段；不重复追加一整张旧卡。

### 7.2 不同阶段的下一步模板

| 阶段 | 推荐下一步 | 备选 |
|---|---|---|
| `script` | 检查冲突与节奏 | 改写一段、进入分镜 |
| `storyboard` | 生成关键帧 / 角色标准件 | 调整镜头顺序、检查引用 |
| `build` | 查看画布关系与参数 | 批量修改、删除未使用节点 |
| `generate` | 检查候选并接受 | 换模型重跑、修改单镜参数 |
| `assemble` | 去预览检查节奏 | 检查字幕、导出候选 |

## 8. Skill、App、模型：三种东西，三种入口

竞品的 Skill 发现、详情和导入体验很直观；Nomi 需要吸收它的发现性，但必须把能力、方法和外部连接拆开。

### 8.1 定义

| 对象 | 是什么 | 能否改变权限 | 入口 |
|---|---|---|---|
| Capability | Nomi 允许做的原子动作 | 由 Host / policy / owner 决定 | 不直接作为用户“插件”选择 |
| Skill | 解决一类任务的方法、检查表、表达风格 | 不能 | Composer Skill 菜单 / Skill Library |
| App / Connector | 外部素材或服务的受约束连接 | 不能绕过授权 | App / Connector 管理与 `@` 引用 |
| Agent 模型 | 理解、规划和调用工具的文本模型 | 不改变领域权限 | Composer 模型 chip |
| 制作模型 | 图片、视频、音频、3D 的具体执行模型 | 由能力和费用门控制 | 生成提案 / 节点参数 |

### 8.2 Composer 的 Skill 菜单

默认只显示：

```text
技能
├─ 自动匹配（当前项目阶段）
├─ 最近使用
├─ 项目已启用
└─ 查看全部技能…
```

选中 Skill 后，composer 上方持续显示：`按 分镜规划 · v1 方法执行 ×`。Agent 自主载入 Skill 时在对话中出现一行“已载入……”，可展开查看摘要；Skill 对后续所有输出生效，直到用户摘除或 Turn 结束，生命周期必须明确。

### 8.3 Skill Library

Skill Library 可采用截图里的结构：通用 / 收藏 / 我的、搜索、创建、导入、详情预览。但每个卡片必须额外显示：

- 适用阶段：剧本 / 分镜 / 生成 / 剪辑 / 审校。
- 输入与输出：例如“文稿 → 分镜计划”。
- 方法版本和更新时间。
- 使用的能力范围；明确“不会新增权限”。
- 来源与信任级别；外部导入必须可查看文件来源。

创建与导入属于管理动作，不挤进 composer 的常驻工具栏；管理面板支持详细预览，但“添加 Skill”后要回到原对话并显示持续 chip。

### 8.4 App / 外部素材

首期只做四段受约束流程：

```text
读取当前页 / 用户选区
  → 搜索结构化候选
  → 展示预览、作者、来源、许可
  → 用户选择后本地化导入
```

登录、验证码、购买、发布、删除、评论和外部写入必须停下；网页内容是不可信输入，不能变成隐式项目知识。

### 8.5 模型选择

Composer 只选 Agent 文本模型；制作模型出现在具体生成提案或节点参数中。Agent 自动选择制作模型时必须写明“为什么选它”和备选；模型没配置时显示可行动的配置入口，不能给同名假选项。

## 9. 工作方式与 Agent 设置

### 9.1 两根轴，不合并成一个模糊开关

工作方式回答“Agent 怎么推进”；批准策略回答“哪些动作必须问我”。UI 可以在一个菜单中呈现，但数据和文案要分开。

| 工作方式 | 适合 | 默认行为 |
|---|---|---|
| Ask | 先讨论、先看计划 | 读操作可直接做；写入、生成、导出先给提案 |
| Guided | 专业制作 | 每个关键阶段停一次；同批安全动作合并确认 |
| Balanced | 日常创作 | 已知安全且预算内的动作自动继续；付费 / 删除 / 外部写入仍停 |
| Auto | 长任务 | 按项目策略连续推进；保留历史、预算、停止、任务回执和所有副作用边界 |

不要使用“自动模式会自动删除 Tapies”这类不可逆提示。对应 Nomi 文案应是：

> 自动模式会按项目策略推进；每个生成、付费、删除或外部写入仍遵守预算与授权门。所有任务和回执保留，可随时停止。

### 9.2 Agent 设置面板

设置面板采用竞品的分组方式，但改成 Nomi 语义：

```text
Agent 设置
├─ 当前额度 / 本月用量 / 价格未知提醒
├─ 协作模式：Ask / Guided / Balanced / Auto
├─ 预算策略：本项目上限、单次提醒阈值
├─ 副作用策略：生成、写入、删除、导出、外部连接
├─ 通知：浏览器通知、声音、后台任务
└─ 完成
```

“完成”只保存设置；不因为打开设置就改变正在执行的 Turn。设置变化只影响新 Turn，排队项保留自己的快照。

## 10. 跨工作面连续性

### 10.1 何处必须连续

从 Creation → Generation → Preview 切换时，以下必须保持：

- 一个项目 Agent 身份和 active Thread。
- 历史消息、当前 draft、附件、引用、Skill、模式、批准策略和 Agent 模型。
- 活动 Turn、队列、审批、任务、产物和错误状态。
- 稳定的 `taskRef`、`artifactRef`、`ContextSnapshot` 和 receipt。

### 10.2 何处允许变化

| 工作面 | 就近上下文 | Agent 需要提供 |
|---|---|---|
| Creation | 当前文稿、选区、章节 | 读 / 改文稿、剧本分析、分镜计划 |
| Generation | 当前画布节点、边、生成参数 | 读 / 建卡 / 连线 / 生成提案 / 资产审查 |
| Preview | 当前帧、选中时间线区间 | 检查节奏、提出时间线计划、定位片段 |
| Browser | 当前页、选区、来源候选 | 读取、搜索、展示来源、用户选中后导入 |

聊天不为了“看起来同步”而重建画布或时间线；专业工作面是状态真相源。

### 10.3 `回到现场`

“去画布”“去时间线”“查看变更”都应调用同一类 `focusContext`：

1. 定位到真实对象。
2. 缩放到用户能读懂的位置。
3. 短暂高亮，不遮挡内容。
4. 保留对话滚动位置。
5. 返回 Agent 时仍停在原消息。

如果目标不再存在，按钮禁用并解释原因；不能点击后什么都不发生。

## 12. 实施顺序

### Phase 0：冻结设计和证据

**产出**：本文、页面 mockup、状态与控件清单、证据矩阵。
**不改代码**：确认用户体验方向、确认入口位置、确认未覆盖边界。
**门**：用户看 mockup 后再进入生产 UI；不要先写完再让截图倒推设计。

### Phase 1：统一 Host 投影与布局

**范围**：Workbench portal、Creation / Generation / Preview 同一 shell、收起态、Dock 宽度、时间线几何。
**文件锚点**：`WorkbenchShell.tsx`、`GenerationWorkspace.tsx`、`PreviewWorkspace.tsx`、`workbenchStore.ts`。
**验收**：一个 Thread；切换面不丢 draft / queue / context；收起不抢工作面列宽；时间线宽度通栏。

### Phase 2：Composer 与上下文合同

**范围**：自动上下文架、`@`、附件、Skill chip、模式 / 授权、Agent 模型、完整 TurnDraft 队列。
**验收**：当前选中自动可见；发送即冻结；忙时输入不丢；队列编辑不改变当前 Turn；最坏宽度下关键字段不截断。

### Phase 3：对话状态与过程投影

**范围**：一行 / 可展开行 / 卡片三层；8 态 + 2 标志；原位进度；工具摘要；失败可行动恢复。
**验收**：一项任务不会把排队、进行中、完成刷成多条；失败显示是否计费和下一步；工具细节按需展开。

### Phase 4：计划、生成提案和候选暂存

**范围**：计划卡、参数条复用、批级 / 单镜覆盖、最终 effectiveArgs、费用、候选暂存、产物卡。
**验收**：批准前能修改每个已声明关键字段；Host 重新 prepare / validate / hash；拒绝不写入；候选 accept 后才成为正式画布版本；真实 loopback 记录完整参数。

### Phase 5：跨面现场定位与 Preview Agent

**范围**：`focusContext`、Preview read / plan / apply、时间线检查、导出入口。
**验收**：从 Creation 目标推进到 Generation，再到 Preview 检查和导出；真实领域 owner 持久化；拒绝、停止、stale revision 都能恢复。

### Phase 6：Skill / App / 模型中心

**范围**：Skill Library、导入 / 创建、Connector 候选、Agent 模型与制作模型分层、项目 Agent 设置。
**验收**：Skill 不改变权限；外部素材未选中不污染项目；模型缺失可行动；排队项保留自己的设置快照。

### Phase 7：视觉与可访问性收口

**范围**：token、icon、间距、tooltip、portal layering、暗色 / 窄 Dock / reduced motion。
**验收**：设计系统逐项对账；菜单不被裁切、不穿透、不挡内容；所有 icon button 28px；键盘、ARIA、禁用原因和焦点路径完整。

## 13. 真实用户任务验收

不能用“点击了某个按钮”替代真实任务。至少跑下面四类自然语言目标：

### J1 新手：从模糊目标到一个角色标准件

```text
帮我做一个老钟表匠的角色标准设定图，之后还要用于分镜。
```

断言：Agent 读取当前现场；反问不超过必要字段；生成前展示角色引用、模型、比例、费用和执行边界；批准后真实生成；结果回到画布；资产卡提供下一步。

### J2 专业分镜师：先建卡，不生成

```text
根据当前剧本拆 5 个镜头，先把镜头卡和引用关系建好，不要生成。
```

断言：计划可展开；批级 / 单镜参数清晰；创建节点和生成是两个可观察阶段；只批准建卡；没有 provider job；可整批撤销。

### J3 预算敏感：修改最终提案再执行

```text
用当前角色做 3 个候选关键帧，但总费用不要超过项目阈值。
```

断言：费用未知不会显示 0；用户可改模型、数量、分辨率和引用；超预算停下；最终 effectiveArgs 与 provider 请求、asset、receipt 一致；失败不自动重复扣费。

### J4 成片审校：从预览到时间线回执

```text
检查 00:06–00:14 的节奏，指出问题；如果需要改时间线，先给我计划。
```

断言：时间区间冻结；先读后计划；不偷偷修改时间线；批准后调用唯一 timeline owner；结果有 revision、定位、撤销 / 回滚入口。

### J5 跨面连续性

```text
在 Creation 写好角色设定 → Generation 生成参考图 → Preview 检查成片 → 返回修改角色描述。
```

断言：同一 Thread / queue / refs；历史引用不漂移；每个 surface 的就近定位正确；返回时不丢 draft、Skill、模式和预算。

## 15. 最终不变量清单

### 用户可见

- [ ] 用户只说目标，不必学习 Nomi 内部格式。
- [ ] 当前现场、引用、Skill、模式和模型在发送前可见。
- [ ] 发送后上下文冻结，历史不偷偷漂移。
- [ ] Agent 忙时输入不丢，队列有完整快照。
- [ ] 过程默认一行；只有决策和产物升级为卡片。
- [ ] 每个需要用户行动的卡片只有一个主推荐动作。
- [ ] 价格未知明确显示未知；不会用 0 或假进度安慰用户。
- [ ] 失败说明原因、是否计费和下一步；不会静默重试。

### 工程与状态

- [ ] 一个项目只有一个 Agent Host、Thread、Queue、权限和费用账本。
- [ ] 画布、时间线、ProductionRun 和资产库仍是各自 owner 的真相源。
- [ ] Agent 不直写 store、不复制 provider 调用、不自建时间线。
- [ ] 审批使用最终 `effectiveArgs`，批准后再次校验。
- [ ] 工具调用有稳定 id，完成 / 失败 / 停止是同一任务的原位状态变化。
- [ ] 领域新增字段必须同步 schema、审批编辑、adapter、回执和真实任务测试。
- [ ] 插件只能注册受管的 composer action / renderer / resolver，不能注入任意 DOM 或绕过授权。

### 视觉与可访问性

- [ ] 只用 Nomi token、Tabler 图标和现有设计 primitives。
- [ ] icon button、动作按钮、chip 的尺寸和圆角按设计系统统一。
- [ ] 不在媒体内容上叠加动作按钮。
- [ ] tooltip、`aria-label`、键盘路径、禁用原因完整。
- [ ] 菜单有统一 portal / stacking contract，不因外层 `overflow` 被裁掉。
- [ ] 暗色、窄栏、键盘焦点和 reduced motion 都有真实截图证据。
