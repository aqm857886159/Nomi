# 页面设计流程 · 可搬运版（Nomi Page Design Process）

> 日期：2026-08-20 · 适用：想把 Nomi 这套「设计一个页面」的流程整体搬到**另一个产品**去用的人。
>
> **这份文档不讲 Nomi 长什么样，只讲 Nomi 怎么把一个页面从「想法」做到「敢说完成」。**
> 颜色值、组件名、旅程名这些是 Nomi 的皮，可以整套换掉；**流程的骨架和它防的那些事故是通用的**。
> 每一节都写清三件事：**为什么有这一步（防哪个真实事故）→ 具体怎么做 → 产出物长什么样**。
> Nomi 内部真相源：`CLAUDE.md`（原则）+ `docs/engineering-rules.md`（细则）+ `docs/design/nomi-design-system.md`（设计系统）。本文是这三份的**流程切片 + 去 Nomi 化**。

---

## 0. 一句话 + 全景

**一句话**：页面设计不是「画出来然后写代码」，是**七道闸的流水线**——每道闸挡住一类「看起来做完了、其实没做完」的事故。

```
① 摸现状          ② 判层级          ③ 出样张          ④ 定规范
  不准脑补     →    控件住哪一层  →   可体验+拍板   →   token/组件/契约
  (防拍脑袋)        (防越堆越杂)      (防返工)          (防手搓)
                                                            ↓
⑦ 真实任务闭环  ←  ⑥ 真机走查     ←  ⑤ 机器门岗      ←  实现
  才算完成          眼见链四问        棘轮只减不增
  (防半成品)        (防假绿)          (防慢性腐烂)
```

**七道闸各自防的事故（都是真栽过的，不是假想）：**

| 闸 | 不做会怎样（真实事故） |
|---|---|
| ① 摸现状 | 样张连画三版都错位——因为没看真实布局就在脑子里拼，整个底部输入区都漏了 |
| ② 判层级 | 十个界面各自发明十套摆法：一条工具栏横铺 15 个按钮跨 4 类心智，画布左缘 8 个平铺竖条 |
| ③ 出样张 | 实现完了才发现方向不对，返工；或「我以为你要的是这个」 |
| ④ 定规范 | 每个文件抄一段相似 JSX，半年后「东西完全分割，什么都不一致」 |
| ⑤ 机器门岗 | 靠自觉记不住：小图跑得飞快、大图才冻死，写代码的人手里多半是小图 |
| ⑥ 真机走查 | 五门全绿、3634 个单测全过，但那个下拉点了**完全没反应**（语法对、语义错） |
| ⑦ 真实任务闭环 | 每一步都没报错，但用户想干的那件事**根本办不成** |

## 1. 闸① 摸现状 —— 不准脑补，先看它真实的样子

### 为什么

这是**最便宜也最常被跳过**的一步。跳过它的代价是后面全错：样张画歪 → 拍板拍的是错的东西 → 实现照着错的做。

Nomi 栽过 3 次同一个错（`.claude/hooks/violations.log` 里排第一）：**改现有 UI 时，没看它真实长什么样就开始拼布局**。最典型一次是给画布节点加 3D 能力，连画三版样张都错位，根因是没看真实「生成节点」是「上工具条 / 中预览 / **下提示词输入区**」三段结构，把整个底部输入区漏了。

**这和「凭记忆讲框架」是同一类错：拿部分当全貌，用脑补代替观察。**

### 怎么做

改/扩现有页面，动笔前必须做完这四件：

1. **读完整外壳组件**——是整个 `XxxShell` / `BaseXxx`，不是某个 body 片段。片段拼不出整体排版。
2. **或者看真实截图**——跑一次 app 截图，或翻 `docs/ui-designs/` 里的存档图。
3. **Explore 一遍：这个动作在别处是不是已经有家了**（见闸② 的「一功能一个家」）。这一步能砍掉一半的"新功能"。
4. **碰三方库先查官方文档**——不查就写 = 工作错误。库/框架的能力和 API 半年换一轮，凭记忆判断「这个库能不能做 X」会翻车。Nomi 用 Context7 MCP 查；没有的话 WebFetch 官方站等价。**选型时额外要 web 扫一眼「现在最现役的框架是哪个」**——栽过：凭记忆把一个现役框架当过时的挡回去了。

### 产出物

一段「现状盘点」，**带 file:line**：这个页面现在由哪几个组件渲染、每块归谁管、我要动的那块和谁相邻。没有 file:line 的盘点等于没盘。

### 搬运提示

这一步和技术栈完全无关，原样照搬。唯一要换的是「读完整外壳组件」在你的产品里对应哪个文件——先找到你们产品**每个页面的根渲染组件**，把它记在设计系统文档的速查表里。

## 2. 闸② 判层级 —— 这个控件住哪一层

### 为什么

这是**这套流程里最值钱、也最容易被别的产品直接受益的一节**。

Nomi 2026-08-02 做过一次全 App 控件盘点：10 个界面、约 620 个可点位。结论是**十个界面各自发明了十套摆法**——画布左缘 8 个平铺竖条、剪辑页一条工具栏横铺 15 个按钮跨 4 类心智、3D 视图四面包围、节点四面包围再叠 hover 浮条。

**根因不是「设计师手抖」，是缺一条「新控件该住哪」的判定规则。** 没有这条规则，每来一个新功能就往最近的那条工具栏上贴一个按钮，一年后必然长成上面那样。补上它，新功能进来才不会又长回去。

### 怎么做

#### 一个判定问题

> **「用户在这个面上，10 次里有几次会用它？」**

| 层 | 频次 | 住哪 | 预算 |
|---|---|---|---|
| **L1 主干** | ≥7/10 | **常驻**，视觉最重 | 每个面 **≤5 个功能簇** |
| **L2 情境** | 3–7/10 | **选中 / hover 才出**，贴目标就近浮现 | 不限，但不许挤进常驻条 |
| **L3 收纳** | 1–3/10 | **一次点击可达的二级**：▾ 菜单 / 参数面板 / 抽屉 | 不限 |
| **L4 溢出** | <1/10 | **⋯ 菜单 / 设置 / 仅快捷键** | 不限 |
| **L0 删** | 0 | 死码、占位、重复入口的第 2..N 个 | — |

**「≤5」按功能簇算，不按按钮个数算。** 播放 / 上一帧 / 下一帧 / 时间读数 / 音量 是一个「播放器簇」，算 1 不算 5。

**它是观察指标，不是硬门。** 为了凑数把中频控件收起来是净负收益（见下面反例）。

#### 三条硬规则

1. **一功能一个家** —— 同一动作只保留 **1 个规范入口**，其余全删。**快捷键和手势不算入口，算加速器**（可以多，因为不占视觉预算）。
2. **常驻位有预算** —— 要加第 6 个功能簇，必须先降级一个。
3. **情境控件不许挤常驻条** —— 选中才出的东西不能塞进常驻工具栏，否则布局会抖。

#### 手法有优先级：先分组 → 再去重 → 再归位 → 再就近 → **最后才收纳**

**「杂」的主因是没秩序，不是数量。** 按代价从低到高选手法，收纳永远是最后一招：

| 手法 | 做什么 | 可达性代价 |
|---|---|---|
| **分组** | 控件一个不少，只是有了边界和名字 | 0 |
| **去重** | 同功能的多个入口收成一个 | 0（减的是真冗余）|
| **归位** | 放错地方的搬回它该在的地方 | 0 |
| **就近** | 情境控件搬到它作用的那个对象旁边 | 0（且常驻条不再抖）|
| **收纳** | 收进 ▾ / ⋯ | **+1 次点击** |

配套两条：

- **动作不许压在内容上。** 半透明浮层按钮盖在图/视频/画布上 = 永久遮挡用户要看的东西。动作归浮条（浮在卡片*上方*）、归工具栏，别归内容角落。
- **分段要有名字。** 一条工具栏塞了多类心智时，光加 1px 分隔线不够（真机上淡到看不见）——要有底色或标签。尤其**作用域不同的控件**（改整片 vs 改当前这一段）必须视觉可分。

#### 反例（真栽过，别重来）

| 反例 | 为什么错 |
|---|---|
| 为了把常驻位压到 5，把中频操作收进 ▾ | 「≤5」是观察指标不是硬门，凑数凑出来的清爽是假的 |
| 把已经是二级菜单的 `切图▾` / `变换▾` 再包进一个 `编辑▾` | **为了少一个按钮让用户多点一次 = 净负收益。** 已经在 L3 的不要再降级 |
| 想把「下载」加进卡片右上角 | 那个角落的按钮是半透明**常驻压在图上**的。往内容上加动作，方向反了 |
| 想把「模型 + 变体 + 参数」合并成一句话 | 模型是用户最看重的一等决策，合并等于把它埋了 |

> **改任何 UI 前先 grep 该组件注释里的「用户拍板」记录。** 写着拍板的形态默认不动，要动必须先说清为什么它不再成立。

### 产出物

一张 **before → after 表**：每个控件现在在哪层、应该在哪层、用哪个手法挪、挪完常驻还剩几个功能簇。

### 搬运提示

**这一节 100% 通用，可以整段复制进你新产品的设计系统文档。**唯一要做的本地化：把「每个面 ≤5 个功能簇」的数字按你产品的信息密度调（Nomi 是密集型工作台；如果是消费级 App，3 更合适）。

## 3. 闸③ 出样张 —— 可体验的，不是静态图；样张是验收合同

### 为什么

样张不是"参考图"，是**验收合同**。实现完了要拿着它逐项对账，差一处补一处。

两条铁律的由来：

- **可体验 > 静态图**：静态截图说不清「拖起来顺不顺」。凡涉及交互（可拖/可点/可调/有状态切换），样张必须做成**用户能亲手拖点调的东西**。
- **样张 = 真实布局 + 你的改动**：见闸①。样张是对现状的忠实 diff，不是从零散片段脑补整体。

### 怎么做

1. **先读完设计系统**（token 全表 / 组件库 / 规范），再画。样张里的每个数值都用 token，**禁非 token 的 px / hex / 圆角**——样张里写 `h-[34px]` `text-[12.5px]`，实现时就会照抄进代码，门岗才发现来不及了。
2. **样张里出现品牌就用真品牌**——真 logo、真字标、真配色。别拿通用羽毛/火花图标占位（栽过，用户当场纠）。
3. **有取舍就给多方案**：A / B / C 并排或用切换器，配一张对比表：

   ```
   | 方案 | 用户看到什么 | 代价 |
   |---|---|---|
   ```
   **不要单方面「我建议 A」然后开干。**
4. **多角色评审**（Nomi 是 6 个：CTO / 设计师 / 产品 / 前端 / 后端 / 真实用户，并行审一遍再汇总改）。
5. **用户本人拍板后才进实现。**
6. **样张里出现两条互相冲突的拍板 → 停下上报，不许自己挑一条实现。**

### 产出物：一份自包含的 HTML 样张

Nomi 的样张是**单文件 HTML，双击就能看，不依赖构建**。骨架（可直接复制）：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8" />
  <title>样张标题 · v3（2026-08-20）</title>
  <!-- 图标用真库的 webfont CDN，别画假图标 -->
  <link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@tabler/icons-webfont@3.31.0/dist/tabler-icons.min.css" />
  <style>
    :root {
      /* ← 设计 token 的内嵌副本。样张和产品共用同一套值，改样张 = 改产品 */
      --ink: oklch(0.22 0.01 80);
      --paper: oklch(1 0 0);
      --line: oklch(0.91 0.004 80);
      --accent: oklch(0.55 0.13 250);
      --accent-soft: color-mix(in oklch, var(--accent) 12%, var(--paper));
      --r-sm: 6px; --r: 10px; --r-lg: 16px;
    }
    * { box-sizing: border-box }
    /* 所有组件样式贴真实 token，不写一个硬编码色值 */
  </style>
</head>
<body>
  <!-- 多方案对比：切换器（可选） -->
  <div class="switcher">
    <button aria-selected="true">方案 A</button><button>方案 B</button><button>方案 C</button>
  </div>

  <!-- 或者：现状 vs 改后 并排 -->
  <div class="pair">
    <div class="pane"><div class="pane-hd">现状 · 15 个控件</div><div class="pane-bd">…</div></div>
    <div class="pane"><div class="pane-hd">改后 · 4 组 / 5 簇</div><div class="pane-bd">…</div></div>
  </div>

  <script>
    document.querySelectorAll('.switcher button').forEach((btn, i) => {
      btn.addEventListener('click', () => { /* 切 .screen.active */ })
    })
  </script>
</body>
</html>
```

**关键是 `:root` 那段 token 内嵌副本**——它让样张和产品用同一套值，样张上量出来的间距就是实现时该写的间距。

### 配套：设计交付要配齐四份参考

样张只是「理想态快照」，单给样张会导致实现卡死/跑偏。必须同时交付：

1. 设计系统的 token / 组件清单
2. 三方库的官方文档链接（闸① 查到的）
3. 数据与代码现状（闸① 的 file:line 盘点）
4. **实现规范**：精确 token + DOM 结构 + 每个状态 + 数据绑定

### 额外：用户路径图

讲一个新功能「在用户旅程的哪一步出现、在界面哪几处露出」时，**默认出一张可视路径图**，别用大段文字让用户在脑子里拼。铁律三条：① 钉到真实界面位置（哪个面板/侧栏），不抽象；② **每个触点标当前真实状态（通/半通/断）**，状态必须先实查代码、不拿旧记忆当现状；③ 诞生点 vs 消费点分清。

### 搬运提示

样张骨架照搬即可。要换的只有 `:root` 里的 token 值和图标库 CDN。**如果你的新产品还没有 token，闸③ 就是建立 token 的最好时机**——先在样张里把值定下来，再搬进代码。

## 4. 闸④ 定规范 —— token-only + 组件复用 + 交互契约

### 4.1 值只有一个来源

**铁律：所有数值来自 token，一个 hex / 一个任意 px 都不许写进组件。**

Nomi 的三层（这个分层本身是通用的）：

| 层 | 谁该新增 | 例 |
|---|---|---|
| ① 规范底层（**唯一该新增的地方**）| ✅ 新颜色/圆角/阴影只在这里加 | `--nomi-bg` / `--nomi-radius-*` |
| ② 领域语义映射 | ✅ 业务语义色 alias 到 ① | `--workbench-danger` / `--workbench-hover` |
| ③ 遗留并行命名 | ❌ 不要再用、不要再加 | 早期主题残留 |

**两个真实的坑，值得在新产品里提前避开：**

- **不存在的 token 会静默失效。** Nomi 的灰阶只有 `ink-80/60/40/30/20/10/05`，**没有 ink-70**。写 `text-nomi-ink-70` 是个不存在的类，不报错、静默回退继承色。同类：`text-bodySm`（驼峰）不存在，实际类名是 `text-body-sm`（连字符）——一次抓出全仓 19 处，全都静默回退到 16px。
  → **对策**：加一个门岗扫「引用了但未定义的 token」（Nomi 的 `check:dangling-tokens`）。
- **文档 ≠ 运行时真相源。** Nomi 的 token 文档写着「改 `nomi-tokens.css`」，但实际那个文件**没有被任何地方 import**，运行时真源是 Tailwind config 编译出来的 CSS。结果一批 token 在运行时是 undefined，好几个页面在用空颜色。
  → **对策**：写文档时**实际验证一次哪个文件真的被加载**，别信历史说法。

### 4.2 组件先查再造：「新增协议」

任何「在设计系统里找不到的新视觉元素」必须走三步：

- **Step 1 是真的找不到吗？** 90% 的情况它已经存在。特别留意「我以为它不一样，其实只是文案不同」——**已有按钮 + 不同文案 ≠ 需要新按钮组件**。
- **Step 2 能用 token + 现有组件组合出来吗？** 「右上角带 X 的提示卡」= 卡片组件 + 图标按钮组件，不是新组件。是组合就不用登记。
- **Step 3 确实是新东西**：**先写进设计系统文档（同一 commit 内），再写代码。** 禁止「先写代码看效果再补文档」、禁止「小改动不用登记」。

新组件的登记模板（抄这个）：

```markdown
### X.X `ComponentName`
文件：`src/path/to/Component.tsx`
视觉：1 句话描述
规格：| 背景 | 文字 | 字号 | Padding | 圆角 | 阴影 | 行为 |（每格填 token 名，不填数值）
何时用 / 何时不用：用：…… ／ 不用：…… 改用 [另一个组件]
可访问性：aria-label / 键盘行为 / focus ring
```

### 4.3 全局一次的东西别 per-component 写

例：**键盘焦点环**。Nomi 曾经散在 6 个文件里写了 13 处 `focus-visible:outline-*`，症状是「漏一个就冒系统橙环」（macOS 默认 outline 跟系统强调色走）。根治法是**一条全局规则**：先全局 `:focus-visible { outline: none }` 杀掉浏览器默认，再统一给所有交互元素一个 token 化的焦点环。

**判据**：任何「每个组件都要写一遍」的样式，都是全局规则的候选。写第三遍时就该抽走。

### 4.4 控件交互契约（C1–C4）

> 闸② 管「控件住哪一层」，这一节管「控件**说到做到**」。

起因：一个下拉的 handler 写成 `onChange={(v) => { if (targetId) doSomething(...) }}` 但没有 `disabled`。目标不存在时点它 → if 短路 → **完全没反应、界面也不解释**。它活过了七道门岗、3634 个单测、多轮人眼走查——因为**「语法对、语义错」**：纯函数全对，错的只有「界面承诺可点、实际什么都不做」这一层契约。同类在 Nomi 至少出现过 5 次。

| # | 契约 | 怎么落 |
|---|---|---|
| **C1** | **可点即有效，否则禁用并说明为什么** | handler 里有「目标守卫」（拿不到目标就不做事）→ 必须①守卫为假时 `disabled`；②用 `title` 说清为什么现在点不了。注意：**禁用的 `<button>` 自己不触发 title**，要外层包一层 |
| **C2** | **作用域跟「选中」走，不跟播放头/hover 悄悄漂** | 对象级控件的作用对象必须来自用户显式选中。结构保证：把作用域抽成纯函数，签名里根本不出现那个会漂的变量——**在类型层堵死** |
| **C3** | **不同作用域不混排** | 整体级与对象级控件不得在同一条无标签的行里长成同款。跨作用域必须分组、每组带名字，对象级那组要**写出当前对象名**、没对象时整组禁用 |
| **C4** | **禁用不做沟通死路** | 任何 `disabled` 都要能让用户知道为什么。这条没做成硬门（全仓 100+ 处 `disabled={readOnly}` 语境自明，硬拦必成噪音），靠走查断言兜 |

**C1 是可以机器拦的**（见闸⑤）。C4 刻意不做硬门——**被习惯性忽略的门岗等于不存在**。

### 4.5 分层与文件大小

写码前先想清楚：这块逻辑该放哪一层（UI / 状态 / 领域逻辑 / runtime / 持久化——别混一个文件）。Nomi 的硬上限是**单文件 800 行**，现存超限的列白名单 + 基线行数，**棘轮只减不增**。

### 搬运提示

4.1–4.4 全部通用。4.5 的 800 是 Nomi 拍的数，你可以拍别的数——**关键不是数字，是"白名单 + 基线 + 只减不增"这个棘轮机制**（见下节）。

## 5. 闸⑤ 机器门岗 —— 棘轮，只减不增

### 为什么

**因为有些写法当场看不出毛病，靠自觉记不住。**

Nomi 最贵的一课：「九宫格切图卡死半小时」。根因是三种写法——同步图像编码（`canvas.toDataURL()`）、base64 塞进状态 store、尺寸常量有两份真相源。这三种**小图上跑得飞快，大图才冻死**，而写代码的人手里多半是小图。写文档提醒过，没用；改成门岗之后再没复发。

**判据：如果一个规则「当场看不出违反、要到极端条件才炸」，它必须是门岗，不能是文档。**

### 棘轮机制（这是核心，照搬这个）

```
1. 定规则（一条正则或一条 AST 判据）
2. 全仓扫一遍，把存量数量写进 baseline
3. 每次 CI：当前数 > baseline → 红牌；当前数 < baseline → 黄牌提示「基线可以下调了」
4. 存量慢慢清零，新增当场报红
```

关键三点：

- **黄牌也要报。**「低于基线」要提示下调，否则基线永远不降，变成永久豁免。
- **补了却不删白名单也要报错。** 防「补了一条又留着豁免」。
- **别做「按日历过期」的门岗。** Nomi 明确否掉了「文档检查时间超 6 个月就红灯」：文档不常变，超期红灯会变成噪音、被习惯性跳过——**被习惯性忽略的门岗等于不存在**。复核由改动驱动，不由日历驱动。

### Nomi 实际在跑的门岗（挑与页面设计相关的）

| 门岗 | 拦什么 | 判据类型 |
|---|---|---|
| `check:tokens` | 任意 px 字号 `text-[13px]`、任意 px 圆角、硬编码 hex `bg-[#fff]`、框架默认色板 `text-red-500`、色相漂移 | 正则 + 色相计算，基线已清零 |
| `check:dangling-tokens` | 引用了但没定义的 token（防上文「ink-70 静默失效」）| 交叉比对 |
| `check:filesize` | 单文件 > 800 行 | 行数 + 白名单基线 |
| `check:i18n` | 新增硬编码可见文案（含 `title` / `aria-label` / toast / 确认框 / 空态 / 错误态）| **TypeScript AST**，零容忍不设基线 |
| `check:heavy-path` | 同步图像编码 / base64 进 store / 尺寸双真相源 | 正则 + 上下文窗口，JSON 基线 |
| `check:controls` | C1 违约：handler 有目标守卫但控件没 `disabled` | **TypeScript AST**，刻意收窄到零误报 |
| `check:walkthroughs` | 走查脚本本身的假绿（详见闸⑥）| 正则 + 源码交叉验证 |

**`check:controls` 的判据值得单独讲**，因为它示范了「怎么让门岗零误报」。它同时要求四条成立才算违规：

1. JSX 元素上有 `onClick/onChange/...`，值是箭头函数
2. 函数体只有一条无 else 的 if，或首句是裸 return 早退
3. 守卫条件**不来自 handler 自己的参数**（排除 `event.target === event.currentTarget` 这种事件判定）
4. **守卫的那个变量被当参数传给了动作**（`if (id) doSomething(id, …)`）——这条是关键，它把「目标守卫」和「模式守卫」（`if (splitMode) return`，另一个模式自有处理）区分开

**收窄到零误报比覆盖率更重要**：一个会误报的门岗，三次之后就会被人加白名单绕过，等于不存在。

### 串成一条命令

把所有门岗串成一条 `gates` 脚本，**push 前必须全过**。Nomi 的 `gates` 跑完会往**本 worktree 自己的 git dir** 盖一枚戳（`$GIT_DIR/nomi-gates-ok`），push 钩子核对它——**没跑门岗就 push 会被拦住**。

```
gates = check:filesize && check:tokens && check:dangling-tokens && check:i18n
      && check:heavy-path && check:controls && check:walkthroughs
      && lint:ci && typecheck && test && build
      && node ./scripts/stamp-gates-ok.mjs   # 盖五门戳
```

戳里必须带 **worktree 路径**和 **HEAD sha**，不能只是个时间戳文件：并行多 worktree 时，「固定路径 + 时间新鲜」的戳会**互相顶用**（A 树盖的戳把 B 树没过门的代码放上远端），也会在**盖戳后又提交**时继续放行。三维身份 = 三项都对才算数。

戳只有一个书写者（`scripts/stamp-gates-ok.mjs`），路径与字段名都只在那里定义一次。但写戳方（`gates`，JSON）和读戳方（pre-push hook，shell）**不可能互相 import**，所以由 `check:hook-behavior` 把「两边仍然一致」钉成门岗——而且是**实际执行 hook** 判退出码，不是读它的源码文本。

这两步各补一类**两边都不报错**的失效：① 只升级读戳方、写戳方仍写老戳，于是 `gates` 全过也推不上去，而 gates 说盖好了、hook 说没有戳；② 门岗若只 grep hook 源码，会被 hook **注释里**的同名字符串骗出假绿（实测过），也会把等价的 shell 改写误判成漂移。

`lint:ci` 也是棘轮：`eslint . --max-warnings=98`——**新增 1 个 warning 就红**。

### 搬运提示

**门岗机制照搬，规则内容重挑。** 落地顺序建议：
1. 先上 `check:tokens`（正则，半小时能写完，收益最大）
2. 再上 `check:filesize`（十行代码）
3. `lint --max-warnings=N` 棘轮（改一行配置）
4. 等你踩到第一个「当场看不出、极端条件才炸」的坑，**当场把它做成第 4 个门岗**——这才是这套机制真正的用法：**门岗清单是被事故喂大的，不是一次设计出来的**。

## 6. 闸⑥ 真机走查 —— 眼见链四问，防假绿

### 为什么

**全绿 ≠ 完成。** CI 只证代码健康，证不了体验对不对。

但走查本身也会假绿。Nomi 两类真实事故：

- **验证物 ≠ 用户所见物**：一个 bug 修在 Windows 分支上，在 Mac 上截图验证——当然看不出变化；截图还躺在盘里没人看就把结果交付了，用户当场抓到「和原来一样」。
- **在不可能出错的现场断言没出错**：断言「专职模式下不浮某张卡」，但用的项目本来就不会浮那张卡；断言「下拉里没有『N 家』折叠行」，但那个目录里本来就没有多家同款模型。**两次都报绿，功能却完全没被验证过。**

### 眼见链四问（缺一环 = 没走查）

走查的本质是**证据链从改动一路连到我的眼睛**：

1. **截图存在吗** —— 跑了脚本、产出了文件。
2. **我亲眼看过吗** —— **产出验证物 ≠ 消费验证物**。截图必须真的被打开看过。
3. **它来自用户所见物吗** —— 同构建（不是 stale chunk / 僵尸实例）、同入口（生产构建不是 dev）、**同平台分支**（改哪面就验哪面；有平台分叉的 UI 先 grep 清点所有分叉）。
4. **它拍得到改动区吗** —— 截图手段对改动区不是盲区（栽过：某种截图 API 拍不到子视图；打开态/弹层要逐个打开拍）。

Nomi 把这条做成了机械闸：**Stop hook「查眼不查嘴」**——改了源码又宣布"完成/交付"时，近期上下文里必须有真实的图片读取痕迹，否则直接 block。

### 走查旅程怎么写

**必须是真实创作目标，每条要有「任务成功标准」。**

| ❌ 错误示范（功能探索）| ✅ 正确示范（创作目标）|
|---|---|
| 「查看生成配置面板」 | 「为商品图选好模型，准备生成」|
| 「探索 AI 面板」 | 「用 AI 把故事稿拆成镜头」|
| 「添加新节点」 | 「在画布上补加一个空镜头，填好提示词」|

构建格式：`我有 [输入]，我想得到 [输出]，成功标准是 [可验证的结果]`

Nomi 固定了 5 条核心旅程（J1–J5），发布前必须全过一遍。**你的产品也该有这样一组 3–5 条固定旅程**——它们是产品的"生命体征"。

### 工具形态：常驻驱动，不是一次性脚本

**这是个反直觉但很重要的经验。** Nomi 一开始每步都 `launch → 操作 → close`，结果：① 每步闪屏，② 迭代 12 轮之后桌面上十几个僵尸进程。

改成**常驻驱动 + 命令行客户端**之后：app 启动一次保持开着，逐步发命令。

| 命令 | 作用 |
|---|---|
| `snap` | 列出当前所有可点元素（标签/文字/aria/中心坐标）——**据此决定点哪，不靠提前盲猜选择器** |
| `shot [名]` | 截图到文件，再打开看 |
| `click "文字"` | 也支持 `aria:` / `css:` / `text:` / `xy:x,y` |
| `fill <css> <值>` / `setfile` / `drag` / `eval <js>` / `wait` | 操作 |
| `probe-latency` / `fps-start`/`fps-stop` / `density` / `contrast` | 体验探针：点击→首反馈延迟、帧率、同屏可点位密度、对比度 |
| `quit` | 关 app + 停驱动 |

**循环 = snap/shot 看真实界面 → 判断 → click/fill 操作 → 再 shot 看结果**（感知→决策→行动→再感知）。

一次性脚本只在「固定流程的最终验证」时跑一两遍，且 `finally` 必须有强杀兜底（`close()` 竞速 8s → 超时 SIGKILL 整棵进程树）。

### 断言 API：把「防假绿」写进签名

这是 Nomi 最巧的一手，**强烈建议照搬**。

问题：全仓 33 处「断言某东西不存在」里 94% 没有任何基线。**没有基线的「没看到」= 空洞的通过——它和「探针根本没生效」在观测上完全一样。**

解法：**在函数签名上硬卡，让人写不出没基线的版本。**

```js
// ① 先证明这个探针测得到东西（在它该出现的场景里，至少找到 1 个）
const proof = await proveProbe(card, '通用模式下拆镜头卡会浮')

// …切到专职模式…

// ② 才允许断言它不存在。没有 provenBy 直接抛错，写不出来
await expectAbsent(card, { provenBy: proof, message: '专职模式下不该浮' })
```

`proveProbe` 返回一个带 Symbol 标记的证明对象，`expectAbsent` 校验这个 Symbol。**文档和提醒挡不住第三次，所以改成写不出来。**

配套的几个断言纪律（都被 `check:walkthroughs` 门岗强制）：

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| `expect(count).toBe(0)` 裸用 | 没基线的空洞通过 | 走 `expectAbsent` + `proveProbe` |
| 扫 `document.body.innerText` | 全页文本污染，页面任何角落有那个词都算命中 | 限定容器：`scopedText(locator)` |
| `waitForTimeout(2000)` 当完成信号 | 真实耗时从 2 秒到 2 分钟不等 | 等一个**明确的状态转换**（如「停止」按钮出现→消失）|
| 选择器写了但源码里根本没有 | 永不匹配 = 恒真 | 门岗扫源码交叉验证 |
| 用「文本连续几次不变」判完成 | 加载态气泡的文本恒为作者名，模型还没吐第一个字就满足了 | 同上，等状态转换 |

### 设计保真断言：把规范写成 computed-style 断言

样张对账不能只靠肉眼。Nomi 有一条 `design-fidelity` 测试，把设计规范写成**浏览器算完之后的实际值**断言——它能抓到肉眼看不出的隐藏覆盖（如 class 合并工具吞掉字号、UI 库覆盖样式）。

```js
const start = await win.evaluate(() => {
  const cards = [...document.querySelectorAll('.action-card')]
  const primary = cards.filter(el => el.dataset.variant === 'primary')
  const rect = primary[0]?.getBoundingClientRect()
  return { cardCount: cards.length, primaryCount: primary.length,
           w: Math.round(rect.width), h: Math.round(rect.height) }
})
assert(start.primaryCount === 1, '主入口恰好 1 张 primary（一页一主操作）')
assert(start.w === 280 && start.h === 88, 'primary 动作卡 280×88（尺寸区隔于普通按钮）')
```

注意第一条断言：**「一页恰好一个主操作」这种设计原则，是可以写成机器断言的。**

### 有「打开态」的 UI 有额外要求

任何有打开态的 UI（弹层/面板/菜单/下拉/picker/modal），交付前必须：

1. 真机**逐个打开每一个交互态**截图，以真实用户视角看「能不能看全 / 会不会被挡」
2. **几何实测**：`getBoundingClientRect` 对照祖先 overflow 容器 + 视口，确认不被裁、不溢出、不重叠（含元素在容器边缘等极端位置）
3. 把结果落成可复跑的回归断言

> 一个真实案例：用户群里连着报「改不了 API 地址 / 没有删除按钮」，两次都被当成功能缺失。实查发现**功能一直都在**，根因是那个控件被 overflow 容器裁出了视口——**「坏了」在群里往往意味着「找不到」**。这就是为什么几何实测要做成断言。

### 搬运提示

- 眼见链四问、旅程构建铁律、`proveProbe/expectAbsent`、断言反模式表 —— **全部通用，照搬**。
- 常驻驱动：Nomi 是 Electron 所以用 Playwright `_electron`。Web 产品换 Playwright browser，移动端换 Maestro / Detox，**驱动层换掉，命令集（snap/shot/click/probe）的设计原样保留**。

## 7. 闸⑦ 真实任务闭环 —— 才算完成

### 为什么

五门只证代码健康；**一次性走查只证「这一条路当时能走」**。一个功能真正好不好用、闭不闭环、体感对不对，只有拿真实任务从头走到尾才暴露——多数体验/设计/UI/UX/产品感问题不在单测里，在「用户真的想干成一件事」的完整流程里。

### 怎么做（做一件功能，收尾必走）

1. **建测试系统，不是跑一次**：为这次功能设计 **≥2–3 条**「真实用户任务」场景（主路径 + 边界/降级），是**创作目标**不是功能探索。**固化成可复跑的脚本/清单**，不是一次性手点。
2. **带真实任务跑通闭环**：用闸⑥ 的走查法（真机/真构建/真入口 + 眼见链）把每条场景**从起点走到用户真正拿到结果**。闭环 = 用户那件事真办成了，不是「中间某步没报错」。
3. **过程中主动挑问题**：跑的时候戴产品/设计/用户三顶帽子，专门找——体验问题（卡顿/多余步骤/看不懂）、设计问题（信息层级/入口）、UI 问题（越界/错位/暗色不可读）、UX 问题（流程绕/反直觉/无反馈）、**产品感问题**（这功能到底解不解决摩擦、值不值得存在）、功能问题（做错/漏做/边界崩）。
4. **全修掉，不挑拣**：发现的问题**全部**按根因修完（不是记 backlog 甩给用户）。修完**重跑**直到闭环干净。
5. **才算完成**：半成品、留尾、「还剩 N 项」都不算。

**适用范围**：功能类交付（尤其用户可见/体感）必走；纯内部重构 / 文案 / 脚本改动按常规走查即可。

### 搬运提示

原样照搬。唯一要定的是你产品的「闭环终点」是什么——Nomi 是「用户真拿到一份能播的初稿」，你的产品要有一个同样具体、同样可验证的终点。

## 8. 贯穿全程的四条原则

这四条不属于某一道闸，是每一步都在用的：

| 原则 | 一句话 | 在页面设计里怎么体现 |
|---|---|---|
| **加新必删旧** | 引入新实现时**同 commit** 删旧实现，无并行版、无 fallback、无逃生口 | 新样式只写在组件上，迁移即删旧 CSS；全局 CSS 只可减不可增 |
| **修根因不修症状** | 修完必再问一层：「这个病只在这个功能上，还是**别的功能也可能有**？」 | 是通用的就①全仓实扫同类入口给 file:line（扫，不猜）②能 grep 的做成棘轮门岗 ③存量进基线慢慢清零 |
| **通用第一** | 能力/组件按「通用场景」设计，不为两个相似情况写两套 UI | 那是并行版，违反第一条 |
| **想清楚再动手** | UI 改动先读设计系统再画、先出样张再实现；多文件改动先写 plan 文档 | 就是闸①–③ |

## 9. 配套文档模板

### plan 文档（多文件/多步改动，动手前写）

```markdown
# [标题]（日期）
> 起因：[为什么现在做这个] · 做法：[执行路径] · 范围：[边界]

## 0. 一句话结论
## 1. 盘点结果        ← 现状，带 file:line。不带 file:line 的盘点等于没盘
## 2. 根因分析        ← 根因 1 / 2 / 3，不是症状列表
## 3. 定法            ← 判定标准 + 具体规则 + 约束条件
## 4. 逐面落点        ← before → after 对照表
## 5. 样张 / 参考物
## 6. 落地进度 / 验收门
## 7. 不动什么 + 回滚策略
```

**「不动什么」是最容易漏、也最重要的一节**——它划清边界，防止改动无限扩散。

### audit 文档（周期体检）

```markdown
# [标题]（日期）
## 分级总表           ← P0/P1/P2 + 一句话
## A 类问题
### A1 [标题]（P0 · 分类）  ← 现象 + file:line + 根因 + 修法
## B 类问题
## 横切观察（机制层共因）    ← 跨多个问题的同一个根本模式，这节最值钱
## 疑点（未决，后续验证）
## 附录（截图位置 / 相关引用）
```

**触发时机**：距上次审计 ≥25 个提交 / 发版前 / 巨壳逼近上限 / lint 基线明显上涨。Nomi 用一个 `check:audit` 脚本自动提醒。

## 10. 搬到新产品：落地顺序

**别一次全上。**按「收益/成本」排，一周能落到第 4 步：

| 顺序 | 做什么 | 成本 | 为什么先做它 |
|---|---|---|---|
| **1** | **抄第 2 节「控件层级判定」进你的设计文档** | 半天 | 零技术成本，立刻改变每次讨论的语言。「这个按钮该不该常驻」从吵架变成算数 |
| **2** | **定 token 三层 + 上 `check:tokens` 门岗** | 1 天 | 正则就能写。晚一个月上，就多几百处 hex 要清 |
| **3** | **样张 HTML 骨架 + 「样张 = 验收合同」的约定** | 半天 | 立刻减少返工；token 内嵌副本顺便逼你把 token 定死 |
| **4** | **`lint --max-warnings=N` + `check:filesize` 棘轮** | 1 小时 | 十行代码，止住慢性腐烂 |
| **5** | **走查驱动（snap/shot/click 那一套）** | 2–3 天 | 需要选驱动层。做完之后闸⑥⑦ 才有地基 |
| **6** | **`proveProbe`/`expectAbsent` + 走查门岗** | 1 天 | 有了走查才需要防走查假绿 |
| **7** | **`check:controls` 这类 AST 门岗** | 2 天 | 等你真踩到「点了没反应」再做，那时判据才收得准 |
| **8** | **固定 3–5 条核心旅程 + 真实任务闭环** | 持续 | 产品的生命体征，跟着产品一起长 |

### 哪些照搬、哪些要换

**照搬（与技术栈无关）**：控件层级 L1–L4 + 三硬规则 + 手法优先级 · 一功能一个家 · 样张 = 验收合同 + 逐项对账 · 棘轮门岗机制 · 眼见链四问 · 旅程 = 创作目标 · `proveProbe`/`expectAbsent` 签名硬卡 · 交互契约 C1–C4 · 新增协议三步 · plan/audit 骨架 · 真实任务闭环。

**要换**：token 具体值和命名 · 组件库名字 · 驱动层（Electron/Web/移动端）· 旅程内容 · 文件行数上限 · 常驻预算的那个数字 · 门岗的具体规则清单。

### 最后一条，也是最重要的一条

> **这套流程不是一次设计出来的，是被事故一条条喂大的。**

Nomi 的每一条门岗、每一条契约、每一条铁律，背后都有一次具体的翻车：三次样张脑补 → 「先看真实布局」；一次切图卡死 → `check:heavy-path`；一个点了没反应的下拉 → `check:controls`；两次假绿走查 → `expectAbsent` 硬卡签名；一次 620 个控件的盘点 → 控件层级规则。

所以搬到新产品时，**别指望一次性把清单抄全**。抄走骨架（七道闸）和已被验证的那几条通用规则，然后**每踩一个坑，当场判断：这是"这一次"的问题，还是"这一类"的问题？是这一类，就当场把它做成机器能拦的东西。** 这个动作本身，才是这套流程的真身。
