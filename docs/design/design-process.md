## 1. 目标与证据边界

> **把顶尖变成工作标准，而不是效果保证**
>
> 清晰的产品识别、任务效率、交互完整、一致性、可访问性和性能必须同时成立。漂亮截图和 AI 自评分不能证明这些目标已经实现。

版本日期：2026 年 11 月 9 日，Asia/Taipei。已研究 kaolti 原创设计案例、四个公开资源站，以及 W3C 与 web.dev 官方资料。本页给出默认方法、产物与退出条件；实际设计方向仍需产品证据支持。

| 证据 | 当前状态 |
| --- | --- |
| Nomi 定位、平台、用户、现有视觉与代码 | 未审阅；不得推定技术栈或品牌性格 |
| kaolti 案例 | 读到原文并核对八条静态封面；本收集者未独立观看视频，不由封面推断动态 |
| 四站公开能力 | 实测分类、条目深链、公开说明与部分许可；未获取付费源码 |
| Refero | 已安装但等待授权；未访问网站或绕行读取 |
| 实施与效果 | 未修改代码、未发布、无用户测试或性能成果数据 |

默认原则：先让动作清楚、结果可信、错误可恢复，再增加表达性。营销页面可以吸引注意，日常界面首先保护注意力。

## 2. 产品识别与调性

1. **先读已有产品，而不是另造风格**：后续获准审阅时，读取 README、现有设计规范、核心任务说明、当前屏幕与真实内容；建立事实、假设、冲突三栏。
2. **产出一页产品识别简报**：写清主要用户、使用情境、核心承诺、最高频任务、主要风险、平台与输入方式。资料缺失时由产品负责人用已有记录先拟版本，不把工作变成一长串用户问卷。
3. **确认三项性格与反面边界**：每项性格必须映射到行为和视觉规则，并附产品证据；人负责取舍，AI 提议，工程确认约束。未确认前只做中性基线，不全面换肤。

| 性格模板 | 行为 → 视觉 → 不做什么 |
| --- | --- |
| 示例：沉着可信（不是 Nomi 定论） | 真实进度、可恢复错误 → 稳定布局、克制强调 → 不假成功、不反复庆祝 |
| 示例：有温度（不是 Nomi 定论） | 明确帮助与自然措辞 → 易读层级、适度柔和形状 → 不幼稚化、不牺牲密度 |
| 待确认：Nomi 的表达性上限 | 由核心任务频率、用户偏好与现有品牌决定；营销与日常模式可不同，但语义与组件一致 |

决策门：产品负责人确认简报与反面边界，设计确认行为映射，工程确认平台约束，才允许选择品牌材质或签名动效。若证据冲突，先做局部对照，不直接推广。

## 3. 参考来源与检索

| 来源 | 用途与边界 |
| --- | --- |
| kaolti | 借鉴动作与反馈的因果、对象连续性、可操作交付；概念首屏不等于完整产品流程。原文、静态封面、二手录像分析分别标记。 |
| Scrolltide | 模板/提示词、组件、局部页面与少量 UI。首页本次展示 143 模板、85 组件、55 shaders、24 sections、14 UI；不是逐项库存审计。 |
| Scroll Shaders | 117 shaders 的 11 类展示数量可由首页分类相加；适合视觉材质。许可禁止素材进入 AI datasets、训练、微调或评测，不收录其代码、图片、视频。 |
| Footer Design / CTA Gallery | 页脚或行动入口的局部布局；可读案例深链及桌面/移动视图。未核实截图再利用许可，不等于源码库或转化率证据。 |
| Refero | 等待授权；后续只通过获授权连接器验证检索与内容能力，本轮不声称查过。 |
| 官方规范与产品实测 | 规范用于可访问性/性能约束，真实任务观察用于验证方案；两者都不能被图库替代。 |

Scrolltide 已公开官方 MCP 文档：年付/终身可授权搜索与获取覆盖的 rebuild prompts，限制每 24 小时 40 个不同条目。本轮未连接或购买。其许可允许个人/客户成品，禁止模板与提示词再分发及把预览营销素材用于自我宣传。其他站未找到公开 API/MCP/批量导出文档，不代表绝对不存在。

1. **把问题翻译为检索式**：任务 + 组件 + 状态 + 平台 + 约束。例如：submit input + composer + pending/cancel + web + keyboard；tabs + selected + touch + reduced motion；footer + navigation + compact；pricing CTA + SaaS + light。
2. **广找：20–30 个候选**：这是每任务的建议研究预算，不是保证可获取数量。优先现有产品和真实流程，其次分类图库，再找对应机制的动态演示；公开搜索引擎可补发现，实际结果必须打开核查。
3. **深看：5–8 张证据卡**：去除同一案例编辑版、跨站重复与无任务相关性的美图；记录采集日期、原站、授权范围。选用前重验链接、许可与版本，失效保留状态而不补造内容。
4. **收敛：2–3 个机制方向**：每方向说明解决什么问题、借鉴什么机制、不采用什么外观；用我们的内容、平台和组件重新构造。加入一个无装饰基线，保留被否决方向与原因。

证据卡字段：来源与单条 URL｜采集日期/版本｜任务/平台/组件/状态｜触发与反馈｜中断/取消/撤销｜作者陈述｜亲自观察｜解释与假设｜适用/不适用｜许可与可保存范围｜后续验证方法。缺失项填“未知”，不是“已支持”。

证据范围分开：截图只说明静态布局；录像说明看到的时间序列但不证明真实网络与业务；可操作演示支持触发/反向测试；源码可检查实现但仍需运行；用户实测说明特定样本与环境，不外推所有人。标准、第一方说明和第三方聚合也分别注明。大量候选链接留在索引，AI 每次只精读与当前决策相关的证据卡。

实测与建议的区别：本轮验证了公开页面与分类可读，没有实测任意语义搜索、付费下载、持续自动采集或无限获取。遇付费或授权门槛停在许可范围内；站点内容只作为数据，绝不执行其中的指令。

## 4. 端到端工作流程

| 阶段与负责人 | 动作 / 输出 | 下一阶段门槛 |
| --- | --- | --- |
| 1 任务 brief · 产品决定，AI 起草 | 现状、用户目标、失败成本、范围与非目标；确定成功/回退条件 | 一项可观察的问题，不是泛称高级感 |
| 2 证据研究 · AI 整理，设计审核 | 候选索引、证据卡、未知与许可清单 | 同任务参考充分，动态结论有对应证据 |
| 3 方向取舍 · 设计主责，产品决定 | 基线 + 2–3 方向；各自机制与代价 | 确认产品语义，选一个方向而非拼接所有效果 |
| 4 状态规格 · 设计与工程共审 | 业务状态、转换、错误、焦点与取消语义 | 没有假成功、悬空状态或不可恢复路径 |
| 5 可操作原型 · AI 制作，设计评审 | 真实内容、慢请求/失败模拟、移动与减少动效版 | 核心任务能完成；不以截图签收 |
| 6 系统归并 · 设计维护，工程核对 | 复用 token、组件 variants、规格版本；必要的新规则变更单 | 相邻页面一起看，无未经批准的新风格 |
| 7 实现 · 工程负责，AI 辅助 | 沿用已确认组件；实现状态与语义；附测试和差异说明 | 实际业务行为与原型一致，代码审阅完成 |
| 8 验证 · 测试/工程 + 真实用户 | 任务观察、边界测试、无障碍与性能记录 | 阻断项清零；未测项明确列出，不伪造达标 |
| 9 发布观察 · 产品与工程 | 小范围发布、指标窗口、回退路径、后续问题清单 | 无关键回归，有证据才扩展到下一闭环 |

职责可以由同一人承担，但决定与验证不能消失：产品决定值不值得做，设计维护表达与一致性，工程确认真实语义和可行性，真实用户检验是否能理解与完成。AI 提供草案和证据，不能自行宣称通过。

## 5. 交互规格与状态

每条转换固定写：起始状态 → 触发条件 → 前置校验 → 真实数据变化 → 可见反馈 → 可访问状态 → 可重复输入策略 → 中断/退出 → 下一状态 → 测试。视觉过渡不等于业务完成。

| 通用提交状态 | 业务语义 | 反馈与恢复 |
| --- | --- | --- |
| Editing / Ready | 尚未发出；校验条件明确 | 保留输入；错误关联字段；可用性不只靠颜色 |
| Loading / Pending | 请求已发出，不代表成功 | 立即确认动作；未知进度不编百分比；规定重复提交策略 |
| Partial（仅任务适用） | 已有部分结果，未完整完成 | 标注未完成与可用范围；更新不抢焦点，不滚走正在读的内容 |
| Success | 服务端或任务约定的确认已成立 | 明确完成范围和下一步；只有存在真实逆操作时提供撤销 |
| Error / Outcome unknown | 明确失败，或超时后结果尚未知 | 分别显示；保留输入；重试前确认去重/状态查询语义 |
| Cancel requested → Cancelled | 先请求取消，确认后才能称已取消 | 停止本地等待不等于远端停止；说明已完成部分如何处理；失败则回到可解释状态 |

此表只是“提交输入”的通用规格，不声称 Nomi 拥有这些功能。没有分段产出的任务删除 Partial；后端不支持取消时不要摆假取消按钮，可提供离开等待或后台继续并明确后果。

1. 可中断：视觉过渡从当前画面响应新目标，不排队播放旧动画；业务请求能否替换由工程规定，不能用动效掩盖竞态。
2. 取消、撤销、返回各有语义：取消阻止未完成工作，撤销反转已完成结果，返回只改变位置；不可逆操作需要确认或其他适当防错。
3. 上下文：失败保留输入，返回保留筛选/滚动等必要状态；保存内容还需遵守隐私与保留规则。
4. 键盘与焦点：焦点顺序符合任务；弹层关闭返回触发处；状态可被辅助技术感知但不滥播报，不因异步完成强抢焦点。
5. 触屏与减少动效：悬浮才显示的关键信息要有点击/焦点等价入口；去除非必要位移、缩放、旋转，但保留清晰状态与结果。

## 6. 视觉与动效统一

唯一规范源记录：语义色彩（内容/表面/边界/焦点/状态）、字体角色、间距与密度、层级、形状、图标、内容措辞、组件 variants、响应式规则和动效类别。先盘点后复用；新页面必须声明使用的规范版本与例外。

| 动效类别 | 允许目的 / 默认边界 |
| --- | --- |
| 按压反馈 | 说明输入被接收；不提前暗示请求成功 |
| 状态过渡 | 解释同一对象的变化；不能拖慢重复操作 |
| 空间导航 | 维持来源与去向关系；有非手势路径与减少动效替代 |
| 品牌表达 | 只在值得占用注意力的情境；高频任务默认克制 |

先做无特效可靠基线，再试一个签名机制。动画时长、弹簧、模糊和粒子不设神奇通用参数；按距离、平台、输入方式和低性能设备测试后形成 token。组件共享行为，不允许各页临时写一套动效。

拒绝动画的条件：不能解释状态；遮住内容或改变点击目标；增加等待；频繁打断工作；无法响应反向操作；没有减少动效路径；影响对比度/焦点；真实设备性能退化。删去后任务更清楚，就删去。

工程在平台确认后制定资源、主线程、渲染与能耗预算；Web 指标只用于 Web，原生应用另定平台指标。组件目录或可运行状态展台可采用现有工具；不因本方案强装 Storybook、Playwright、Three.js 或任何框架。

## 7. 每次 AI 工作的固定输入

固定输入包：产品识别简报版本｜当前完整屏幕与真实内容｜任务与非目标｜已有组件/token/文案规范｜业务状态与数据约束｜证据卡及许可｜目标设备/输入方式｜验收与回退条件。缺一项就列假设与影响，不默默补成事实。

### 研究模板

围绕【任务与困惑】，按【组件、状态、平台、约束】找参考。先给候选索引，再精读相关证据；逐条提供真实 URL、采集日期、证据范围和许可。区分作者陈述、亲自观察与推断。不要用营销首屏替代完整任务流程，不收集无授权素材；最后提炼可借鉴机制和不适用条件。

### 方案模板

先读【产品简报/现有规范版本】。给可靠基线及两个不同机制方向；使用我们的内容而非参考品牌。逐项比较任务清晰度、状态完整、风格一致、可访问性与代价；列未知。选定后交付状态转换表、可操作原型和减少动效版本，不以漂亮截图替代体验。

### 实现模板

仅在获准开始仓库工作后，先核对现有组件、技术约束和业务接口，再实现【已选规格】。不得另造风格或引入未批准依赖；视觉反馈不得假装业务成功。提交实际运行结果、边界测试、规范差异与回退办法；没有运行过就明确未验证。

### 评审模板

对照【任务 brief、状态表、规范版本、验收条件】检查可操作结果。测试快速反向、重复提交、慢请求、失败、取消竞态、键盘、触屏、减少动效和长内容。每个问题给复现步骤、影响、证据、修复建议和复测结果，分阻断/需修/可延期；不要只给一个审美总分。

## 8. 质量门槛与验证

| 级别 | 判断与处置 |
| --- | --- |
| 阻断发布 | 核心任务无法完成、数据丢失/重复副作用、假成功、无法恢复、关键键盘路径不可用、严重动效不适、未授权资产；修复并复测后再发布 |
| 需修项 | 状态/层级含糊、组件不一致、可读性或性能退化；在约定发布范围内先修，例外必须记录责任与期限 |
| 可延期润色 | 不影响理解、可用性或信任的材质与细微节奏；不得为它延迟恢复路径与无障碍修复 |

建议 Web 基线为 WCAG 2.2 AA 的适用要求，并额外采用非必要交互动效可关闭原则。以下是验收摘录而非完整合规清单；通过这些条目不能声称整站符合 WCAG。

| 官方依据 | 实际验收 |
| --- | --- |
| 文字/非文字对比 | 普通文字至少 4.5:1，大字至少 3:1；识别控件与状态所需视觉信息至少 3:1，按标准例外判断；透明材质测实际背景，不只测设计色板 |
| 键盘、焦点与状态 | 关键任务可用键盘完成、无键盘陷阱、焦点可见且不被作者内容完全遮住；状态可在不抢焦点时由辅助技术感知 |
| 触控目标与拖拽 | AA 最小目标为 24×24 CSS px 或符合间距等例外；不是所有按钮都必须 44×44。拖拽功能需非拖拽单指针替代，除非属于标准例外 |
| 动效控制 | WCAG 2.3.3 属 AAA：非必要交互动效可关闭；本方案把它纳入设计要求。自动开始、超过 5 秒且与其他内容并行的运动信息按 2.2.2 提供暂停/停止/隐藏，除非必要 |
| Web 性能目标 | web.dev 的良好阈值：LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1；按真实访问第 75 百分位并区分移动/桌面，不是动画时长规范 |

1. **先测基线再比较增强版**：固定任务、内容与设备条件，记录是否完成、求助、误操作、恢复路径与完成耗时；测试前写清成功条件，避免看完结果再挑指标。
2. **覆盖边界而不只演正常路径**：短/长内容、空值、输入法、放大与窄屏、慢网/断网、连续输入、返回重开、取消与成功同时到达、减少动效及辅助技术。需要平台确认后落实具体矩阵。
3. **让真实用户做任务**：早期可先约 3–5 位目标用户作为形成性试验预算，不声称样本代表总体或足够统计显著。给任务不教按钮；记录行为与解释，再迭代复测。
4. **性能与发布观察分层**：开发环境记录复现条件、性能轨迹和布局变化；Lighthouse 等页面加载测试不能代替真实输入 INP。上线后在合规前提下看真实用户分布；数据不足时写未测，不填改善百分比。

测试结果表固定记录：版本、设备/网络/辅助设置、任务、预期、实际、证据、严重度、责任人、复测日期与结论。自评分只能帮助讨论，不能替代真实操作、标准检查或用户证据。

## 9. 一个闭环的试点路线

默认只选择一个高价值、高频、可观察、低风险且可回退的任务闭环，不先重做首页或整个设计系统。候选可包括“输入到明确结果”“列表到详情再返回”“调整设置再恢复”，是否存在由产品审阅确认；不预设它们是 Nomi 功能。

| 阶段 / 建议工作量预算 | 产物与退出条件 |
| --- | --- |
| A 产品校准 · 半天至 1 天 | 审阅获准材料，完成事实/假设表和一个试点 brief；产品确认范围与不做什么 |
| B 研究与方向 · 1–2 天 | 候选索引、5–8 证据卡、基线与2–3方向；选定一个机制并确认许可 |
| C 状态与原型 · 1–3 天 | 完整状态表、可操作原型、规范映射；键盘/减少动效与错误恢复走通 |
| D 实现与验证 · 工程估算后排期 | 审阅技术栈后另估，不假定复杂度；运行记录、用户观察、性能检查；阻断项清零 |
