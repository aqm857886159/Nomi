# 方向检查：走查网络放行名单（2026-10-10）

触发：`electron/testNetworkGuard.ts` 近 14 天已有 2 个 fix，PR #1148 评审后的这一刀是第 3 个；概念「测试模式主进程出站网络门」同样命中。

## 0. 一句话根因

同一份放行语义在走查闸和产品自带测试网闸里两处各写，连接层少判端口、两份各漂各的——缺的是「判定只有一个 owner」这一层。

## 1. 归类表：bug → 直接原因 → 类

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 付费走查静默挂 615 秒（#1148 第一刀） | 没有任何处自动设放行名单；账本没人读；产品闸先拦且不记账 | 隐性前提无 owner |
| 评审 B1：精确 origin 换端口绕过 | 走查闸连接层只比 hostname，不看端口 | 同一语义多处各写 |
| 评审非阻断：通配子域诊断归类错 | 诊断另写了一套主机匹配 | 同一语义多处各写 |

## 2. 为什么这一类会一直出现

放行语义（写法、缺省端口、通配范围）被写在四层 + 产品闸 + 诊断里，每处自己解析环境变量、自己比对。改一处另一处不会红。落到铁律：不适用（测试基础设施，不涉及模型选择与点击预期）。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 下一次加语义（如新增协议、通配范围）会只改一处，另一层放行或误拦 | 同一张用例表对两道闸跑，看答案是否一致（`electron/testNetworkGuard.test.ts`） |
| 新的供应商结果域名需要登记，漏了仍会被挡 | 已有「被挡立即失败」点名 host，补 `VENDOR_RESULT_DOMAINS` 一行 |

## 4. 靶子独立性检查

闸与测试是同一条线写的；用例表覆盖端口、通配、形似域名、CI。没有「修对反而掉分」的先例。靶子（用例表）本身经评审人独立读过。

## 5. P0：这些是我们独有的吗

不是。出网放行只是通用的 allowlist 匹配；但走查闸是本仓走查专用、无现成库能直接挂进 Electron 主进程四层，匹配函数 20 行内，不值得引入依赖。自写登记不命中。

## 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 无合适库（见 5） | | | 否 |
| A 补：并行两份 + 一致性测试兜 | 产品闸留拷贝 | 小 | 违反 P1「不许并行版」，仍会各漂 | 否决 |
| B 删产品闸放行：付费走查关 `NOMI_TEST_NETWORK_GUARD` | 只剩走查闸一份 | 要给 `promptLibraryStore` 加关后台刷新开关 | 后台刷新被走查闸挡下，账本多无关 blocked，走查误红 | 否决 |
| C 单一正本，删拷贝 | 判定挪到 `electron/shared/walkAllowlist.cjs`，两道闸都 require；构建原样拷进 `dist-electron/shared/` 并由产物检查把关 | 一个新文件 + 构建一步拷贝 | 产品闸惰性 require，只在测试闸开且设了名单时才加载，正式包启动不依赖 | 采纳 |

## 7. 用户要权衡的核心

放行判定是否只许有一个 owner，哪怕要为它让构建多拷一个文件。

协调会话 10-10 裁定 C：单一正本，删拷贝。
