# 老项目只读打开时的项目写入

核对基线为当前源码`ac7126cf9`、`v0.24.1` 冻结项目 H0 与任务 S 在 `77ffa8221` 采得的项目差异和请求流水。只读检查，没有改动冻结项目。交接图见 `docs/engineering/seams.json` 的 `draft-save`、`result-to-project`（都尚无图），本案补出来的链条为：`项目读盘 → 内存迁移、事件尾部重放、运行状态展示 → 用户浏览／明确编辑／真实运行结局 → 项目保存队列、事件日志、预览缓存各自的写入者`。

## §0. 一句话根因
缺的是「什么事实已经发生、应由谁写回」的边界。当前打开生命周期把兼容解释当成升级提交，关闭把采样当编辑，事件与缓存也把一次观看写进同一项目目录。

## §2. 复发原因
最早能拦在设计／验收边界。旧门 `tests/ux/project-open-stages.e2e.mjs:271` 只拒 `fsync`，少一次 `fsync` 或只靠 `append` 的路径都能通过。用户的⑫「点击打开」对应项目目录哈希、原任务号、真实编辑可重读三项同时成立。门图实测 `persistActiveWorkbenchProjectNow` 有 11 个调用文件、13 处调用，既有回库／普通关窗／重载／失焦，也有 Agent 明确提交、删资产和真实结果需要回执；单改某一退出入口会漏掉兄弟入口。

## §3. 三个可验证预测
1. 只去掉 hydrate 中的 save，A 的预览、本地媒体请求、返回库仍会产生事件或清单写入。逐项目对照路径集合与逐文件 SHA-256，冷缩略带缓存也算。
2. 只拦 genesis，媒体 GET/播放状态仍往事件日志 append。只拦所有打开后写入，B 已确认终态不能入账或会在编辑后被撤销。分别测持续 `processing`、成功、确定失败及重启后再次读取，按原运行号验 0 新 POST。
3. 只按退出时的全量载荷与原盘作深比较，换窗口宽度或启动后自动 fit 仍可使快照不同；只排空现有防抖队列又会漏掉当前未 bump `persistRevision` 的手动缩放。分别操作自动 fit、手动 fit/滚轮并验证次启回读；连做编辑、撤销、再退出，用最新有效编辑验回执。

## §4. 靶子独立性
冻结样本、SHA 和请求流水来自任务 S，独立于当前实现。S 把 B 的 `recoverable` 落盘列为预期，原始数据只证明 UI 可以这样显示，GET 仍是 `processing`，不足以证明真实结局。H0 三个快照后的原始尾部均只有非画布事件，故这三份不能证明崩溃尾部重放；另用含真实未入快照编辑的尾部检验，需保住重放顺序与之后首次编辑的撤销、重做。无证据表明本线有过修对却掉分的回滚。

## §5. 这一整块归谁（P0）
这一整块：Nomi 项目会话的编辑提交、崩溃恢复与生成结局持久化。

归谁：src/workbench/project/workbenchProjectSession.ts:253 负责项目保存订阅与排空，持久内容投影归 `src/workbench/project/workbenchProjectContent.ts:13`；已提交运行归 `src/workbench/generationCanvas/runner/runProjectDelivery.ts:118`，观测结局按提交身份归回该项目。

我们哪里绕开了它：`projectPersistenceService.ts:228` 打开时直存；`workbenchProjectSession.ts:72`、`:312` 将打开或拿回执变成写因；`localProtocol.ts:193`、`videoPlaybackTelemetry.ts:41`、`extractVideoFrame.ts:276` 另有三个输出口。未发现可替换这些领域语义的第三方库，现有队列、运行账本与撤销主人继续使用。

## §6. 三条路对比

| 选择 | 改动与代价 | 同类风险 | 建议 |
|---|---|---|---|
| **路 1：沿原方向修** | 给 `renderKind`、`scale`、`recoverable` 分别加相等比较例外，做法最省事。 | 新的展示字段、日志与缓存仍会复发，忽略字段还会吞掉用户真的改动。 | 放弃 |
| **路 2：换一种做法（推荐）** | 打开只建立本项目的内存基线、重放已有尾部；仅明确编辑和原运行的真实结局交现有保存主人提交。回库、关闭、重载、失焦只为已欠的保存拿回执。把自动 fit／播放与手动意图在入口区分，第一笔真编辑一并落盘兼容迁移与收敛值；画布在首次真实画布写前按项目一次性补「重放后的基线」并保证顺序；预览诊断分流到应用诊断日志（派活单允许新增 filmstrip JPG）。 | 保留重试、跨项目身份、未结任务免费 GET、明确失败及成功保存；一次封死读路径三处写因。实施范围跨保存会话、缩放入口、事件缓冲与日志分流四处边界。 | **推荐** |
| **路 3：删掉** | 只删掉 hydrate 主动写迁移与每次打开入账的 genesis；已有快照／尾巴继续读。 | 单删无法覆盖退出采样与预览事件；删 genesis 不补首编前基线会破坏依赖日志重放的撤销/消费者（如 `tests/ux/remove-node-lock.walk.mjs:92`）。 | 放弃 |

## §7. 用户要权衡的核心（一句话）
想让创作者「只打开旧片看一眼再关掉」时盘上项目字节原封不动（放在同步盘也不触发无谓同步和冲突），就要接受老格式迁移与未结任务收敛在「只看不改」时只留在内存、等第一次真编辑或真实结局到达时才一笔写盘。

## 拍板结论

D-1127-old-project-readonly 选路 2。打开时在内存建立基线，首笔真实编辑或已有运行的真实结局抵达时一次保存完整项目。未收尾项目只显示可取回时保留原档。可重建的胶片缩略图沿用现有缓存位置。
