# 参考放置：把兼容行为写进声明，再收成一个决定点

## 0. 一句话根因

把“意图”和“已编码参数”当成两套输入语言，却只收拢了函数入口，没有统一落点与编码声明；兼容约束要求保留差异，验收却把“同一文件”与“所有分支都随同一个槽探针变化”当成唯一主人。

## 1. 归类表：bug → 直接原因 → 类

| 事实 | 直接原因 | 类 |
|---|---|---|
| 首次验收：普通 Run、显式参数在函数外选键写值 | 只迁移合并槽，非合并另有目标选择 | 同一事实多份规则 |
| 再验收：外部写口已删，槽改键/形状而 Run 两例不红 | `lowerGenerationIntent.ts:142–173`：槽与原值保留分别决定；后者的 `kind` 甚至不参与选键 | 两种表示未归一 |
| 守卫漏 `Object.assign`、误报普通元数据 | `referencePlacementOwnership.test.ts:153–159` 按语法而非请求边界判定 | 防线缺对象身份 |

## 2. 为什么这一类会一直出现

`runReferences.ts:137–173` 仅将参与合并的参考变成槽意图，其余带着 `keys/readKeys/selection/value` 入场；显式参数在 `:198–221` 同样如此。放置策略一半在声明、一半在意图里。第一次是决定散在函数外，第二次是同一分裂搬进函数内，属于同一类根因；不能说旧外部写口还在。

原值分支保留：①普通图/视频/音频数组及重复项，body 读到的同组键全部写，没有匹配则组首键；②首尾帧字符串；③显式别名数组、角色对象（含调用者的 role）、帧别名；④已有同组值优先和授权 URL 冲突拒收。合并模式已收的槽不走它；无模式、自写目录、合并未收的视频/音频仍可能走。具体入口见 `runReferences.ts:143–168,203–215`。旧目录无需被改写；兼容规则应从其目录/模板编译成声明，而非默认套内置槽。

离线实测两步（只改道、不重构，跑完即恢复）：A. 让有模式的 63 个原值格直接改走现有模式槽，498 份请求体（画布、Run 各 249 份）与拒发逐字节对照 0 份差异；B. 把全部 109 个原值格（有模式 63、本次 Run 未拿到模式 46）都改走现有槽推导，498 份仍是 0 份改变：请求体转拒发 0、拒发转请求体 0、请求体内容改变 0、拒发细节改变 0。恢复后与原基线字节一致。这两个实验只证明这批内置样本不依赖原值分支；矩阵里显式参数全空、只给图片参考，显式值、合并外的视频/音频不在计数内，也不覆盖任意用户模板与自写目录。所以不能据此删掉旧语义、让旧值直接套内置槽：旧落点规则要原样编译进同一份绑定声明，再由同一个解析写入过程执行。

⑩“说的=摆的”和⑫“点了=以为的”适用：参考角色/张数必须落到真实请求；39 题附表的引用绑定拒收、模式/类型冲突是上游同类表现，不是已证实由这里直接引起。⑪“能选到”不是本轮直接故障，不能据此宣称各入口参数清单已完整。

## 3. 不改结构的话，接下来会冒出什么

| 可验证预测 | 验法 |
|---|---|
| 继续改槽形状，原值路径仍维持旧形状 | 复做槽数组→字符串探针，对照 Run 非合并/显式入口 |
| 再补一种赋值语法，仍可换一种语法绕过 | 同目录依次植入赋值、`Object.assign`、展开/别名；普通元数据应始终绿 |
| 直接改走内置槽可能改动旧请求 | 先运行 498 份逐字节矩阵，再回放旧目录与显式值；未覆盖的保持未验证 |

## 4. 靶子独立性检查

复验为独立线重跑。498 份前后相等是兼容量具，不是“真实付费可用”或“符合官方”的证明；缺夹具格不作官方结论。槽分支探针对“同声明、同编码”的三入口有效，对“无模式原值”与“模式槽编码”混比则过强；最终返回值统一改键又过弱，两套放置逻辑也能通过。应先固定语义等价输入和适用规则，再测公共目标选择/编码各类反例；expected 必须是独立字面量，不读被测返回值。

## 5. P0：现成方案与边界

- TypeScript **5.9.3**：`lib/lib.es5.d.ts:1599` 的 `Readonly` 与 `lib/lib.es2015.core.d.ts:286` 的 `Object.assign`。本机实测只拦直接赋值，assign/展开仍可编译；不能当所有权证明。
- Zod **3.25.76**：`v3/types.cjs:3570–3579` 的 `.readonly()` 直接用 `Object.freeze`，只冻一层。可复用校验/冻结，嵌套数组与新副本仍可写。
- Ajv **8.20.0**：`dist/vocabularies/applicator/additionalProperties.js:12–90` 检查额外键；可复用 schema 闸，不知道哪个模块写了合法键。ESLint **10.4.1** 内置 `no-restricted-imports` 可限制构造器/传输依赖，不能替代数据边界。

因此不用自造通用写操作追踪器。结构封口需要构造器私有持有可写数据，外部只收意图/不透明结果，传输入口只接受其产物；只改类型别名/加浅冻结不够。当前仍有逐键合并、模板渲染、明确在范围外的供应商改形，不能宣称整个请求体已如此封闭。本轮先把参考绑定声明与执行统一，语法门只作辅助，未来若要整个请求体封闭需单独扩展传输合同。领域独有部分是参考角色、用户模板与付费请求的字节兼容；通用校验沿用现有依赖，不升级依赖。

## 6. 三条路对比 + 推荐

| 路 | 保住什么／最小单位 | 代价与付费风险 | 预计轮次／0.25 |
|---|---|---|---|
| 沿原方向再修 | 保留双表示，继续给分支与扫描补探针 | 小；字节风险低，但无法证明一处规则覆盖全部；易第五轮再补 | 至少再 1 轮，成功率未知；不推荐 |
| **换一种做法（推荐）** | 把旧落点组、全部/首个匹配、保留值编码纳入同一绑定声明；意图仅带绑定身份和值；同一个目标解析器/发射过程处理槽与旧值，同提交删双放置实现 | 中；保持 498 份零差异，不统一掉兼容语义。采用现有 TS/Zod/Ajv，领域绑定只写一次 | 用户拍板后 1 次替换 + 1 次独立验收，最多 2 轮；0.25 可作为目标，尚无实现工期收据 |
| 删掉／收窄合同 | 最小删除项是“已达成单一决定点”的交付承诺；只交已集中写口的部分，原值兼容继续保留 | 代码少、现有字节不动；结构债仍在。删除原值分支会改旧请求，不选 | 1 轮改合同；与已批 0.25 必达冲突，须用户重批，不能当本轮完成 |

推荐由下一实现线先锁特征与绑定声明、再一次替换，独立验收只对批准合同；本复盘不启动下一轮。改验收的理由是保证同语义共规则，不是把失败条目删掉。

## 7. 用户要权衡的核心

升级后参考图和首尾帧照旧发、花钱的请求不悄悄变；现在要花一次整理成本把决定收成一份，还是接受下次换模型/模式又走岔路。
