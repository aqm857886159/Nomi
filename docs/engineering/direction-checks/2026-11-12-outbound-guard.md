# 方向检查：发送前按解析地址拦（出网守卫的地址层）

日期：2026-11-12。独立调查由没参与过前几轮的只读线完成（代码基线 main f8a351447）；协调会话抽核 4 处代码属实；本页是调查的一页摘要加用户的决定。设计卡：`docs/plan/2026-11-12-outbound-no-address-block.md`。

涉及的自写登记条目：`network-stack`（`docs/engineering/self-written.json`，状态 under-review）。这一刀为什么还换不了现成库、打算什么时候换，见设计卡 ★0 / ★3。

## 症状

开着本地代理（TUN + 合成解析）的创作者点生成，几秒内被「Nomi 自己的安全策略先拦下了」，重试结果不变。一个 Windows 会话重试 11 次；0.24 周期 263 次视频生成里约 59 次属于本机拦下 / 没发出这一类。界面提示「确认检测到本地代理后重新生成」，照做仍被拦。

## 这一处被修过几次

- 2026-08-28 取回侧加地址层和 IPv6 表。
- 2026-09-06 取回侧把代理假地址当内网，10 条已付费视频取不回 → 加「只认 IPv4 198.18/15、且探测确认」的豁免。
- 2026-09-07 提交侧为了和取回侧对称，也接入地址层。
- 2026-09-18、09-30 密钥目的地绑定、遇跳转即停（另两条规则，不在本次范围）。
- 2026-11 IPv6 假地址（Clash Verge Rev 默认开 IPv6）再次撞墙。

每次都是「又认出一种地址」，下一种代理默认值来了再坏。

## 类根因

1. 提交侧的地址层防的事（域名被解析到内网、密钥被内网机器拿走），在 https 下证书校验已经挡住；而且提交侧判完并不锁定地址，中途换解析它本来就挡不住。它是为对称加的，不是因为出过事。
2. 「本机在用代理」靠枚举地址段 + 进程内探测一次来判断：新地址段、先开应用后开代理、DNS 慢，都会判错，判错的结果是拦。
3. 拦下后只给「重试」，结果不会变；遥测里没有子码，看不出是哪一种。

## 三条路

| 路 | 做法 | 证据与代价 |
|---|---|---|
| 沿原方向补 | 再认几段假地址（含 IPv6） | 改动最小；自定义段、新软件默认值还会撞；探测时机问题全留 |
| 换一种做法 | 提交侧对创作者保存的接入地址不按解析地址判；取回侧在确认合成解析时只判名字，证据不枚举地址段，拒之前当场重探 | OWASP 把「只连已知可信目标」和「连任意外来链接」分开处理，前者不建议拿 DNS 解析做校验；Chromium 对走代理的连接不按地址判；代价是少一层纵深（判断为冗余） |
| 删掉 | 两侧地址层都删 | 取回侧对供应商返回的陌生链接失去防线，这一半是真有用的 |

## 结论

提交侧：删。取回侧：换做法（留防线，改判据）。两处必须同一个 PR：只放开提交侧会重演「扣了钱取不回」。保留不动：密钥只发往保存时确认的地址、地址里直接写内网且不等于接入地址就拒、链路本地永远拒、带密钥请求遇跳转即停。

## 用户的决定

用户 2026-11-12 原话：「重开」；看过四条路的对比后：「这种被拦下的东西 最好能不能删掉 遇到类似的问题 太烦了」。协调会话据此按上面的结论开工；合并前把删了哪几条、留了哪几条、改了哪几句界面文字列给用户看。

## 没验证的

Windows 真机上系统是否真的返回 IPv6 假地址（代码层喂数据成立，把握约 75%）；修后要由创作者或 Windows 那边在真机上发一条并取回。
