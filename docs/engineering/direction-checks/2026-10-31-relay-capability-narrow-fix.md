# 画布错误卡与中性键提示（窄修）：类根因复盘

## 0. 一句话根因

两处都是「测的不是实际走的那条路」：分类测试对着裸文案断言，而画布的提交箱先把花钱前的失败包一层；套件样例只过 schema 校验，不过真实的声明提交。话和路对不上，没有一个测试看得见。

## 1. 归类表

| 症状 | 直接原因 | 类 |
|---|---|---|
| 声明撤掉的模式 / 声明不完整：画布上是泛泛的「这次生成没有发出去」+ 重试，重试还是它 | 创建门两句拒绝没有机器码；提交箱把花钱前的失败包成 `submission_not_sent`，分类器先认包装、后看文案 | 只测裸文案，没走包装链 |
| 运行入口「没有声明的视频通道」同上（主线只给它加了 `Model is not configured` 前缀，画布上到不了） | 同上 | 同上 |
| 模型已退役、登记类型不符的专用卡在画布上够不着 | 它们的专用签名在分类器里排在通用的 `submission_not_sent` 之后 | 同上（次序） |
| 中性键规则让改用 `create.paramMap`，交卡 schema 不收这个键 | 提示和校验各写各的 | 提示与校验漂开 |
| 接入套件自己的同步样例卡过不了登记 | 套件测试只过 schema 校验 | 只测半条路 |

## 2. 为什么一直出现

追到表示层：「花钱前就停下」在主进程里是一类事实，到渲染层只剩一个包装码加一句话，分类器必须同时读码和话；每个新增的拒绝句都要自己想起这件事，测试又都在包装之前断言。铁律落点：⑫ 点了=以为的（卡上写的下一步，要和包装之后实际出现的卡一致）；⑩ 说的=摆的（拒绝信息教的写法，要和校验实际接受的写法一致）；⑪ 不适用。

类检查（结构上拦）：`electron/capabilityCore/canvasRefusalCard.test.ts`（真目录 → 真运行入口 → 真提交出口 → 真 IPC 守卫 → 真分类器，每行断言包装过、没有网络请求、卡是真原因）；`electron/capabilityCore/modelOnboarding/kit.test.ts`（套件每张样例原样交给真实的声明提交；被拒时信息里的写法原样照做就能过，别名表遍历）。

## 3. 不改结构会冒出什么

| 预测 | 验证 |
|---|---|
| 下一句从运行入口抛的拒绝仍只靠文案，画布上又是泛泛的卡 | 去掉矩阵里任一行对应的机器码，该行红（已回退验证） |
| 规则或 schema 再改，套件样例悄悄过不了登记 | `kit.test.ts` 逐张提交样例 |
| 拒绝信息再改措辞又走不通 | `kit.test.ts` 照做一遍，别名表每一项都走 |

## 4. 靶子独立性

矩阵用生产的画布传输、提交出口、IPC 守卫和分类器，不用替身分类；每行还断言撞上的就是要测的那一句。实现与测试同线写，不冒充独立验收，由协调另派验收。

## 5. P0

全是现成机制：`tagNomiError` 机器码、提交箱包装、分类器。没有新增依赖、没有新增自写。

## 6. 方案比较

**件 1：两刀规则矛盾（创建门先拒，主线那句走不到），画布上是泛泛的卡**

| 选项 | 改什么 | 结果 | 代价 | 采用 |
|---|---|---|---|---|
| A | 创建门两句和运行入口那句用 `tagNomiError('model-config', …)`；协议测试第一条正则改成 `/does not publish taskKind/` 并写明原因，其余断言不动；补一格走包装链的矩阵 | 两条路都指去模型接入 | 产品 3 行 + 1 格测试 | 是 |
| B | 只加文案前缀 | 测试绿，画布上不变 | 创作者看到的没变 | 否 |
| C | 不改产品，测试改成认现状，写进已知限制 | 误导的卡继续出现 | 零代码，等于把主线断言改差 | 否 |

附：矩阵量到退役、类型不符也从同一条路抛出，同样被包装盖住。它们没有机器码，改法是把两个专用签名排回通用 `submission_not_sent` 之前（分类器注释里本来就写着「最先判」），不新增码，不动抛出端和既有断言。

**件 2：中性参数键的提示走不通，套件样例自己也过不了**

| 选项 | 改什么 | 代价 | 采用 |
|---|---|---|---|
| A | 提示改成「参数键用中性名，线缆字段读它」，去掉 `create.paramMap`；样例改用中性键；加「每张样例过真实提交」和「照提示做就过」两格 | 产品 2 处 + 2 格测试 | 是 |
| B | 真的支持 `paramMap` | 要改 schema 和 AI 路径，校验器注释写明 AI 路径不产出它 | 否 |
| C | 不修，写进已知限制 | AI 多被拒，可能卡在接入这一步 | 否 |

## 7. 用户拍板与权衡

用户 2026-10-31 批了窄修（两件都按选项 A）。要的是「卡上说真话、AI 被拒后一步走得通」，不是再开一轮大改。编译规则不放松，`paramMap` 继续被拒，schema 不加字段。这是该线的最后一次修补，修完直接独立验收。

热点（`fix-churn --staged`）：`runtime.ts` 11 次、`promotionMeta.ts` 7 次、`classifyError.ts` 4 次、`modelAvailability.ts` 2 次、`modelOnboarding/` 目录 8 次，另命中「声明能力与可执行 wire 的完整发布事实」「错误 → 人话与动作」「参考素材在任务的哪一步交给供应商」三个概念。本刀不加分支、不加特例：分类器只调次序，运行入口与创建门各加一个机器码，中性键规则只改提示文字。

范围外、量到、没动：`Model is not enabled`、`Model is not configured: … (not published …)` 两句也从同一条路抛出，同样被盖成泛泛的卡，没有机器码。留给下一次。
