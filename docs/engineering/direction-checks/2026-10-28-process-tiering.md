# 方向检查：流程分档实现线三轮都往「更严」漂

> 触发：同一条线要派第 3 轮修补。协调会话 2026-10-28 写；用户拍板后入库。
> **用户 2026-10-28 拍板：「流程分档按推荐做：硬线只认登记清单、删关键词，碰过方向检查不单独算严，加『严档数不超过现行规则』的护栏。」**

## 0. 一句话根因

「严档硬线」只有名字没有判据：除了花钱 / 长跑 / 可打断、逃逸账本转 fixed 有现成判据，「安全 / 崩溃 / 数据格式 / 方向检查」从没登记过判定口径；任务书和调研又没写清「核实不了落哪档」。实现线三轮都把含糊处往严里补，结果比现行规则还严，和「按大小和风险分档、减文书」相反。

## 1. 归类表

| 轮次 | 现象 | 直接原因 | 类 |
|---|---|---|---|
| 第 1 轮 | 纯文档改动用旧正文，推送前被拦 | 任务书把纯文档 / 测试 / 配置也要求声明，文件清单本可证明 | 档位输入没定义 |
| 第 2 轮 | 没写声明的产品改动一律严；声明短但核实未知也严 | 「核实必须 fail-closed」被读成「掉到最严」，不是「不给短」 | fail-closed 的落点没定义 |
| 第 3 轮 | 「安全 / 崩溃 / 方向检查」用路径关键词子串匹配 | 硬线没有登记过的判据，实现线自己发明关键词 | 硬线没定义 |

## 2. 为什么会一直出现

- 风险分类是调研和任务书里的一串词，没有 owner、测试和可维护的登记表。
- 没有数字护栏，无法阻止新规则比现行规则更严。
- 遇到含糊处时，默认往严里补，导致文书不断增加。
- 三条体验铁律不适用；这是流程门岗，不是产品行为。

## 3. 不改结构的话会怎样（可验证）

| 预测 | 怎么验证 |
|---|---|
| 严档占六成以上，比现行规则还多，文书变多 | 同一批历史 PR 分别跑两套判据 |
| 只要改过方向检查文档就算硬线，严档长期维持在高位 | 统计历史 PR 的文件清单并比较严档集合 |
| 关键词调一个就会翻一批 PR | 逐词统计命中数量并重跑判定 |

## 4. 靶子独立性

- 标题启发式的短 / 标准 / 严比例不是真靶子。
- 可复核的靶子有两条：现行规则严档集合，新规严档数不能比它多；花钱 / 长跑 / 可打断 / 账本 fixed 的 PR 必须全在严档。

## 5. P0：现成的做法

- 按风险分档批准变更是通用做法：标准变更来自事先批准的清单，不靠关键词猜。
- 敏感路径通常用点名的 glob 清单，例如 CODEOWNERS。
- 仓库已有同一机制：测试路由登记表的类别用路径点名、有 owner、有测试，花钱 / 长跑 / 可打断已经沿用它判定。
- 结论：硬线用同一张表表达，不用正则关键词。

## 6. 选项

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成：硬线全部来自登记清单 + 数字护栏 | 花钱 / 长跑 / 可打断 / 数据格式沿用现有登记；安全类在同一张表点名具体边界文件；删掉路径和正文关键词；账本转 fixed 照旧；方向检查不单独算严；验收加严档数不超过现行规则、必须严名单全保留 | 一轮实现加一轮对抗验收；安全清单需逐条过 | 清单漏列时，危险改动会落到标准；仍由评审和清单 owner 兜 | ★ |
| 补 | 只删几个宽关键词 | 最小 | 还是关键词，下一个词又误伤；没有护栏 | |
| 重写 | 换成风险打分 | 大 | 已选清单方案 | |
| 删 | 硬线只留花钱 / 长跑 / 可打断 / 账本 fixed | 小 | 安全边界靠自报 | |

## 7. 要权衡的核心

严档按点名到文件的清单加不比现在严的护栏来判，准确但需要维护；关键词省事却会把大量 PR 判严。方向检查本身已经要用户拍板，不再叠一层严档。

## 特征测试

同一批历史 PR 的现行严档集合先作为护栏夹具，再验证新规严档数不增加，且花钱 / 长跑 / 可打断 / 账本 fixed 的 PR 一个都不能降档。
