# 声明能力投影：类根因复盘

## 0. 一句话根因

登记、认证晋升和旧目录各自拼能力或 wire，没有一次编译、一次替换的完整声明事实。

## 1. 归类表

| 症状 | 直接原因 | 类根因 |
|---|---|---|
| 视频说明为 chat，控件与实发不符 | kind、参数、槽、模板通道分别落盘 | 发布投影不完整 |
| 缩减卡仍能用旧模式 | 只 upsert，没有声明归属与整份撤销 | 替换生命周期不完整 |
| 升级后旧模型仍残缺 | 没有原卡恢复与显式拒发 | 旧数据绕过新边界 |

## 2. 为什么反复出现

连接和模式发布分别修过，但系统没有检查“说的、摆的、发的”是否同源。两个写门、旧数据和其他模板写法都能绕过局部补字段。共享 promote 的属性调用者还包括原生工作流和集成认证，只有点名符号门图会漏掉这类异形输入；本轮从属性门图追一跳，并把完整原生控件交回同一编译器。

## 3. 不改结构会再出现什么

新模型继续丢控制项；重交卡留下旧路由；升级后仍用残缺声明。尺子分别是登记/认证矩阵、双向缩减矩阵、原 revision 恢复矩阵，不能只检查一种供应商或一个读者。

## 4. 靶子独立性与反例

四条现场复现来自先行调研，先红后改普通测试转绿；本线新增矩阵不冒充独立验收。故意丢参数、保留旧模式都使矩阵红，finally 按字节恢复。矩阵覆盖不透明/撞档案名、跨连接、必需首帧、原生文本三种任务、原子拒绝、独立 wire/合同/模式变体、原卡缺损与重复迁移；未声明尾帧覆盖 params、extras、平铺和空白写法。真窗、线上服务与独立验收各报实际结果。

## 5. P0：复用与领域边界

复用现有能力合同、task-kind 主人、paramMap 依赖、目录事务、原 revision、稳定 JSON 和 Node 哈希，不加包或协议。编译声明、撤销自有模式是 Nomi 的领域约束。旧 wire 的 delivery/abandon、停用模式和 modeId 也先核对归属，不能吞掉用户编辑；原生文本继续走既有聊天通道。

## 6. 方案对比

| 方案 | 代价 / 决定 |
|---|---|
| 两边分别补字段 | 继续漂移，不采用 |
| 一个投影产出合同与 wire，事务整体替换 | 删除晋升另一份组装；迁移复用，采用 |
| 按模型名字套档案或再造中转合同 | 可能虚构能力，不采用 |

系统同时删掉调研走查的手工补控件和常量 wire 补救。演练直接检查声明默认值、实际请求与生成计数的正向探针；槽名复用已有翻译词汇并由矩阵核对英文词典，不改门岗或基线。

## 7. 拍板与执行边界

用户 10-30 原话：“它这个接入方式是我们的那个AI接入的接入方式，不是直接接入接入方式。直接接入接入方式是因为我们那个之前也试过，因为各个中转不一样，直接接入让用户接的话，他其实也接不了嘛。所以我们做的是这个让AI接入的”……“按你的这个思路走去做就好了”。

任务书明确该拍板涵盖热点复盘后继续；协调又将原卡迁移、目录版本一行和 Agent 缺失说明归本刀。AI 交对卡后必须保真；无法证明的旧数据保留并说明缺失，不猜能力、不再试跑。创建前拒绝与已受理结果查询分开；协议/物化、picker/i18n 留原分工。没有新增供应商特例；逃逸按首次推送裁定为 reviewed，独立验收与 fixed 结账由协调处理。
