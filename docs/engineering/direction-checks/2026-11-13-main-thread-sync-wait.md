# 方向检查：主进程「原地等待」冻住（第二刀：保存热路径不再原地睡）

日期 2026-11-13。承接第一刀（`2026-11-12-gen-landing-main-stall.md`）。实现合同见设计卡 `docs/plan/2026-11-13-main-unblock-pr2.md`。

## 用户原话

- 「有没有可能把这种问题的根因都找到并且解决 就是原地等待问题 冻住问题什么的」（11-13）
- 更早：「卡顿 卡死 也得研究一下 这两块都是特别影响用户体验的」（11-12）；卡顿要在用户之前测出来、性能是设计维度（10-30）。

## 事实

- 保存路径上，遇到「文件被别的程序占着」（Windows 杀毒 / 同步盘，EPERM / EBUSY / EACCES）时，同步助手在主进程上 `Atomics.wait` 原地睡着退避（约 400ms 总预算），注册表锁还会自旋。睡着的几百毫秒里，所有要等主进程回话的操作排队。
- 每次保存还多做：整份清单写完再整读回来解析比对、再读一遍算同步基线哈希、注册表每次都写。
- Windows 未验证：占用的实际时长分布没有真实数据，下面的数字都在 Mac 上用注入故障量出。

## 三条路

| 路 | 做法 | 证据 | 结论 |
|-|-|-|-|
| 沿原方向修 | 继续在原地睡，缩短预算或调退避表 | 睡多久都是主进程上的冻结；缩短预算又会让真被占用的保存更容易失败、丢改动提示 | 否：治标，还变脆 |
| 换一种做法 | 把保存整体搬出主进程，或接现成的原子写库 | 保存写在同步的暂存事务里、持清单锁；atomically 异步版放不进这个事务，同步版就是忙等；graceful-fs 只在目标不存在时重试，而我们是覆盖写；write-file-atomic 不重试改名。搬出主进程要先补崩溃恢复回放，波及面大 | 否：这一刀放不下，后续再评估 |
| 删掉 | 保存范围内同步助手不睡（立即再试一次就抛）；上层用定时器重排整次保存（50/100/200/400/800/1000ms，总上限 60s）；保存少读少写 | 暂存事务每个文件都是临时文件 + fsync + 改名，整次重做不会让盘上出现半个文件；不新增任何界面元素 | **选这条** |

## 约束

- 结构上只能同步的调用方（清单锁、同步回调、记账类）逐字保持原行为，不降容忍度；金钱记账（运行记录、提交意图、认证持久化）不动。
- 关窗等待不变长：显式等回执的人最多等 5 秒，与今天持续占用时最坏约 5.2 秒失败用时相当；后台重试继续。
- 崩溃不变差：saveFaultSweep 的真实性 / 恢复断言保持绿。
- 校验改为「写下的字节算哈希」，不再整读回来比对；失败仍由 fsync + 原子改名保证盘上是旧的完整版或新的完整版。
- 已知取舍：更长的重试窗口会增大「渲染层旧快照覆盖同期 MCP / Agent 写入」的窗口；今天同样存在，且 Agent 路径在同一次占用里多半同样失败。

## 自写登记条目（commit 门岗要求写明）

- `ipc-invoke-failure-text`（Electron invoke 失败那句话的读法）：这一刀只在 `projectSaveFailure.ts` 的分类里加一个分支（耗尽重试后的「被占用」错误，类名在契约文件里定义，渲染层按类名认），不碰那句话的读法本身，也不新增它的解析逻辑。现成方案：Electron 的 `ipcMain.handle` 抛错只会把 `Error invoking remote method ...: <错误 toString()>` 当字符串给渲染层，没有结构化错误可接；所以现在换不了。我们走的是已有的 `IpcResult` 返回值（保存口本来就是 `{ ok:false, reason }`），失败原因走结构化字段，这条登记条目的读法只是兜底。复评时间：该条目自己的 reviewBy（2026-11-23）。
- `durable-json`（原子写 JSON 与 fsync 屏障）：这一刀在其下登记新的重试件 `electron/sharingRetry.ts`、`electron/projects/saveRetry.ts`，并把 atomically / graceful-fs 的比较写进它的 alternativesChecked；结论见上文「换一种做法」，原因都是领域约束（覆盖写 + 同步暂存事务 + 持清单锁），不是没查。

## 第 2 轮（独立验收 V-main-unblock-pr2 之后）

验收找到三个真问题：清单锁 owner.json 短暂被占就判锁丢、留孤儿锁目录；整次重排用发起时的旧快照，60 秒窗口里谁最后成功谁赢，会盖掉已回执的 Agent / MCP 写入；提交后步骤撞占用会整次重新提交（修订号 0→4、备份被冲成当前版）。

| 路 | 做法 | 证据 | 结论 |
|-|-|-|-|
| 沿原方向修 | 保留「不睡 + 定时器重排」，把重排的单位切对：清单锁读不到 owner 报可重排的被占用并收掉自己的锁目录；提交前 / 提交 / 提交后分段，只重排没提交的那段；每次重排在锁里核修订号；主进程读改写的重排单位包含读（`updateProject`） | 三个问题都是「重排单位切错」，不是「不睡」这个方向错：修订号核对和分段都在现有事务里能做，不搬进程、不改数据格式；`saveUnderOccupancy.test.ts` 把验收的复现搬成仓库测试，修前红修后绿 | **选这条** |
| 换一种做法 | 保存整体搬出主进程（工作线程 / 子进程），在那边原地等 | 不冻主进程，但崩溃恢复回放、锁所有权跨进程、渲染层回执都要重做，波及面远大于本刀；任务书明确「下一刀」 | 否：留到下一刀 |
| 删掉 | 撤回本 PR 的重排，回到 main 的「原地睡约 400ms 就失败」 | 冻结回来；但三个真问题也一起消失 | 退路：这一轮验收再不过就走这条 |

本轮同时删掉 AsyncLocalStorage 隐式范围层（`runWithoutBlockingWait` / `blockingWaitAllowed`），保存路径上的调用方显式传 `noWait`：谁不睡在调用点上看得见，不会因为异步上下文跟丢而悄悄睡回去。

没解决、照实写：渲染层下一次保存仍会用它手里的整份快照盖掉外部写入（和 main 一样）；被占用重试最长 60 秒期间界面没有「正在保存」的显示（项目页本来就没有保存状态），要不要加留到下一刀和用户一起定；慢盘场景仍待测。

## 第 3 轮结论（I-save-hotpath-safe-subset，走退路）

> 上文第 1、2 轮照 #1500 原样保留作历史；其中提到的设计卡 `docs/plan/2026-11-13-main-unblock-pr2.md`、`saveRetry.ts`、`saveUnderOccupancy.test.ts`、两个性能场景只在 #1500 分支上，**这一轮都没有进 main**。这一轮的设计卡：`docs/plan/2026-11-13-save-hotpath-safe-subset.md`。

两轮验收的真问题（第 2 轮报告 `V-main-unblock-pr2-r2`）：

- 被抢先之后渲染层会整份盖回：Agent / MCP 那次已经回执写成功，下一次编辑或关窗时 ownedPayload 重新入队，盘上又变回旧值；基线是两边都报 EBUSY，Agent 知道自己没写上。
- 保存时注册表 `.lock` 目录的 rmdir 被占 100ms 就留下孤儿锁（不睡分支只再试一次就吞掉），下一次同步注册表操作在主线程卡约 3 秒；基线最多约 400ms、不留锁。

结论：走退路。重排机制（`noWait`、`saveRetry`、修订号核对、「被抢先」错误码、渲染层回执上限）和 `updateProject` 新入口全部不进 main；只落和重排无关的部分：热路径同步文件操作的 lint 规则 + 存量冻结清单、导出收尾改名换成异步重试、`sharingRetry` 的异步助手和退避表。少读少写也不落：量不出时间差，且被占用时和 main 不逐字节相同。主进程原地睡的冻结**没有解决**。下一刀：把保存整体搬出主进程，在那边照旧原地等，主进程不冻（要先写设计）。

重排机制为什么一再出并发问题（读代码后的判断，给下一刀当输入）：

1. 今天的保存是「多个写入方各拿整份或半份、最后写的赢」：渲染层手里有一整份快照，主进程的 Agent / MCP / 生成落盘读盘上的再写回。main 能大致不出事，靠的是一次保存在一个同步调用里从取锁做到放锁，竞争窗口只有几百毫秒。
2. 把等待换成定时器，等于把一次保存的「在飞时间」从约 400ms 拉到最长 60 秒，并且在等待期间放开了主进程，别的写入方正好在这段时间插进来——窗口放大了一百多倍，而快照是等待之前拍的。
3. 修订号核对只能管住「同一次保存的重排窗口」，管不住「渲染层加载 → 下一次保存」这一段，也管不住被拒之后渲染层把同一份旧快照再入队；每补一个窗口就多一个特例。
4. 锁和提交后各步（注册表锁、清单锁 owner.json、同步基线）原本假设「在同一段同步代码里做完」，改成「各试一次、失败交给后台」之后，就出现了半释放的锁和需要后台补收的目录。
5. 所以下一刀不该再在主进程里把等待改成异步，而是把整段「取锁 → 读 → 写 → 放锁」原样搬进单独的执行者（工作线程 / 子进程），让它保持「一次保存一个临界区、原地等」的语义，并且所有写入方经同一个队列排队；主进程只发请求、等回执。
