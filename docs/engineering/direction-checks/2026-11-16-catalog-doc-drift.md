# 方向检查：模型档案与官方文档的漂移（接入时对过一次，之后没人回头）

> 触发：档案 / 目录这一带 14 天内「按官方页对齐」的修补提交已有 18 个（`git log --since=2026-10-01 --grep="对账|整页|官方页" -- electron/catalog electron/shared`），其中 11-07、11-12、11-15 各一轮是整批重对；Muse Video 接入后供应商改了时长与计费，没人发现。属于「同一概念同线第 3 轮修补」，先停点修，写这页。
> 写法说明：本页由实现线（没有参与过前几轮修补）按原始数据独立写成，结构性结论交协调会话转用户拍板。

### 0. 一句话根因

接入是对供应商文档某一天的一次抄写，抄完之后没有任何东西定期回头对：档案里每处来源都记了核对日，但「核对日」只是一个人写下的日期，不是一个会自己变红的信号——文档变了，我们这边没有任何东西能知道。

### 1. 归类表：bug → 直接原因 → 类

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| Muse Video 时长 / 计费（供应商改成 2–10 秒可选、按秒计费，档案仍写「固定约 10 秒」） | 接入时抄的是当天的页面，之后页面变了没人知道 | 接入后无回看 |

| 本次对账另查出的多付钱 / 少选项（可灵 3.0 默认 pro、Seedance 2.5 缺 1080p 与草稿流程等） | 接入时按当时的页面取默认值与选项，之后既没回看、也没有人逐项对 | 接入后无回看 |

### 2. 为什么这一类会一直出现

结构上有三层缺口：

1. **没有「文档变了」这个信号。** 模型雷达每天抓同一份索引，只回答「有没有新页 / 新模型」，不回答「已接入的那页变没变」。供应商改一个默认值、一个取值范围、一个计费单位，对我们来说是静默的。
2. **来源地址只是档案里的一段文字。** 每个档案都有 `sources`（地址 + 核对日），但没有任何东西读它：没有哪一步会拿着这些地址去重抓，所以核对日只会越来越旧，不会触发任何动作。
3. **修补靠人想起来。** 每次对齐都是一批人工重对，发现多少修多少，下一批文档变更又从零开始；这种修法天然是「同一文件第 N 轮」。

落到三条体验铁律：⑪ 能选到——档案里的可选项必须覆盖官方给的全部选项；漂移一旦发生，创作者要么选不到官方新增的选项（Muse 的 2–10 秒），要么选到官方已不支持的组合（Veo quality + 参考图）。这条的最小证据此前只有「档案清单生成物」，没有「档案清单与官方文档一致」的证据。

### 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 下一次供应商改默认值 / 取值范围 / 计费单位，档案仍按旧值发请求，创作者多付钱或被拒，用户先发现 | 看文档指纹表里「变了」的条目：没有这条检查前，同一变化不会被任何东西列出 |
| 接入的模型越多，每次整批重对越贵（本次首轮对账 183 个来源地址，人工逐项对只覆盖了其中一部分） | `pnpm run radar:docs` 摘要里的「未逐项对账」数 |
| 官方新增的选项（编辑 / 延长、草稿预览、GIF / SVG 等）一直不会出现在产品里 | 本次差异清单 B 档 |

### 4. 靶子独立性检查

- 「官方文档」是外部事实，不是我们写的：指纹只回答「它变没变」，不判断「我们对不对」。判断仍要人（或另一条线）逐项对，所以指纹表里有「已核对 / 待修 / 未逐项对账 / 读不出正文」四种状态，**抓不到的、没逐项对的绝不记成已核对**。
- 有没有「修对了反而掉分」的先例：没有；本检查是只读的，不改任何档案。
- 价目：目录里种子模型没有写价（价由用户设置），所以价目接口只用来盯「计费单位 / 标价档位」变没变，没有「声明价 vs 官方价」可比，不能当价格正确性的证据。

### 5. P0：这些是我们独有的吗？现成方案有哪些

「盯一个网页变没变」不是我们独有的。通行做法是内容指纹快照比对：changedetection.io、urlwatch 都是「定期抓页面、归一后比对、变了通知」；OpenAPI 一类机器可读规格还可以用 oasdiff 做破坏性变更比对（本次来源是 markdown / HTML 页，不是 OpenAPI 文件，用不上）。我们没有直接接入这些工具，原因是领域约束：

- 需要把「哪个地址对应哪些模型档案」这层映射接进来（这份映射在档案 `sources` 与目录里，是我们独有的），变更通知要进开工提示、和模型雷达同一个出口；通用工具的通知渠道（邮件 / 推送）接不进我们的会话流程。
- 比对要先按我们的口径归一（去站点样板、价目 JSON 去掉促销 / 会员 / 实付折扣这类每天都变的字段），再给出「参数 / 取值 / 计费相关行的前后差」，否则每天都是噪音。
- 复盘结论：指纹、归一、对比这些通用的部分写得很薄（约 500 行，含摘要与落表），映射与出口是领域部分；自写登记不新增（脚本在 `scripts/`，不在领域目录）。以后若有现成工具能直接吃我们的来源清单并输出到开工提示，应换掉自写的那一层。

### 6. 三条路对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 沿原方向修 | 继续每隔几天派一条线按官方页整批重对、修档案 | 每批都要人逐项对，随模型数量线性增长；已有 18 个这类提交 | 两批之间的变更仍是静默的，用户先发现 | 否 |
| 换一种做法 | 指纹 + 每日比对 + 按全量清单一次对齐：来源地址的内容指纹进仓库，每天重抓比对，变了 / 没查成 / 新缺口进开工提示；首次用差异清单一次性对齐已知的差异 | 每天开会话多等约一分钟（并行抓取，超时单独给）；指纹表要有人在核对后落表 | 页面样板变动会产生噪音（已按样板归一）；公开站点改版 / 限流会让某些地址「没查成」（明着报，不当成没变） | **是** |
| 删掉 | 删掉「档案记来源与核对日」这套机制，不再声称与官方文档一致 | 失去逐项对账的依据，创作者更不知道哪里不一致 | 同一类问题照样发生，只是没人知道 | 否（要保住的结果是「创作者看到的选项与官方一致」，删掉这套机制保不住） |

### 7. 用户要权衡的核心

每天开会话多等约一分钟，换「已接入模型的官方文档一变，第二天就会被点名」；代价是指纹表需要有人在每次核对后落表，否则同一处变化每天都会再报。
