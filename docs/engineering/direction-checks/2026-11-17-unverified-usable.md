# 方向检查：验证只提醒，不决定模型能不能用

独立读码复盘，2026-11-17。触发量具：`scripts/fix-churn.mjs` 判定 `src/ui/onboarding/` 近 14 天已有 2 个 fix、涉及 2 个源码文件，此次是概念目录第三个；`ModelSettingsHome.tsx` 本身为 0 个 fix。两次旧修分别处理弹窗滚动和画布手势，计数命中不代表已经证明它们与本问题同根。本复盘未参与旧修，也未改生产代码。

**这一处的全图**：模型接入 → 目录发布/凭据 → 可用性投影 → 三个选择器/三个首用入口 → 执行回执 → 设置状态与失败提示。该段在交接处表中属表外；范围和现役入口见 `docs/plan/2026-11-17-unverified-usable.md`。既有机器门表为 16 个读门、17 处出现，复验有 3 个调用文件；读门数不能解释成 16 份判据。

## 0. 一句话根因

“是否验证过”和“能否按已存请求格式发出去”被编码进同一组启用/发布标记；诊断失败于是改变使用资格，而失败提示又不随当前事实退役。

## 2. 为什么还会出现

共享可用性入口已经存在：`modelAvailability.ts` → `catalogModelAvailability.ts` → `catalogStore.ts` 的投影。三个选择器读同一投影，但写入方先把验证失败翻成停用，统一读面就只能统一拒绝。`derivePublishedExecution` 还读取认证 revision/modes/publication mask，首用复验又能单独抛错；不能只改菜单，也不能只删这一句 throw。

要守住的是原先“说可用就能取到执行模型”的底线。新的本机条件是请求格式与可用凭据；手动停用、缺请求格式、缺能力声明、凭据解不开和凭据目的地约束仍有各自含义。验证进行中/失败只改变状态字。设置计数只读共享可用性，不能把同一个可用模型又算进待设置。

| 体验铁律 | 本次落点 |
|---|---|
| ⑩ 说的=摆的 | 未改变用户意图或生成参数；仅要求设置“可使用”与可执行解析一致 |
| ⑪ 能选到 | 同一目录逐模型核对默认下拉、画布、助手；角色和模式过滤仍保留 |
| ⑫ 点了=以为的 | 保存、验证、重验、选择、生成各记录点击后的实际结果；失败检查不能让已有可执行模型消失 |

逃逸账本结账挂 `src/workbench/ai/modelAvailabilityAgreement.test.ts` 的类级一致性检查（实现线须扩到三个选择器与三个首用入口），并关联设计卡十一条破坏反例及中英文真实流程；仅有截图或单一中转成功不能结账。

## 3. 不改结构会再发生什么

| 预测 | 量具与应见结果 |
|---|---|
| 新增选择器或发送入口仍会按验证状态各挡一次 | 十一条反例中分别改坏任一选择器和任一首用入口，类检查应红；恢复后绿 |
| 只改新写入，旧的 pending/failed 仍不可选；若每次加载恢复，用户后来关掉的又打开 | 三份 0.24.1 真资料升级；升级后关掉一个带失败记录的模型并重启，应保持关闭 |
| 失败卡按供应商而非模型退役，会隐藏同家另一个未恢复模型 | 一家两个模型：一个已恢复、一个缺格式仍失败；只退役前者的旧失败 |

## 4. 靶子独立性

合同和十一条反例由协调给定，本线独立读原话、写口、读口与上轮碰撞数据后对照。旧测试把“未认证必须不发布”写成正确答案的部分已经过时，应随授权语义更新；缺请求格式、用户停用和钥匙安全的反例必须继续拦住。没有证据证明旧修曾因评测掉分回滚，不作此断言。

上轮生产写口合成回放证实：认证失败后一直停用，和失败后用户手动开过又关掉，能落成完全相同记录，连时间戳也相同；它不是安装包真窗口迁移证据。

## 5. 这些是否独有、已有能力能否复用

逐模型/模式的可选性、执行请求格式及老用户启停语义属于 Nomi 的领域约束，第三方 UI 或凭据库不能替产品决定。现成能力已在仓库：共享可用性/发布判定、现有验证请求、版本迁移链 `migrateCatalogForward`、`snapshotBeforeMigration` 迁移前留底和既有鉴权错误分类。复用它们，不新增依赖、第二份清单或新状态机。同行文档仅继承设计卡中的调研，未在本线另作联网验证。

## 6. 三条路

| 选项 | 做什么 | 代价与风险 | 判断 |
|---|---|---|---|
| 沿原方向修 | 延续“验证决定发布”，逐家放宽或增强探测 | 列表接口仍可能误判；继续增加供应商特例；接入后仍可能无模型可选 | 不选 |
| 换一种做法 | 将验证作为诊断；同一共享判定按已有请求格式和凭据给资格，执行成功统一清标记 | 有坏 key 的模型也能被选择；真实鉴权拒绝交现有错误卡 | 推荐，复用现有 owner，不做第二套实现 |
| 删掉 | 最小单位是“验证失败导致停用/不发布/首用拒发”及脱离当前事实的失败展示规则；保留验证动作与缺格式拒绝 | 不能删整个验证或格式检查，否则没有请求可编的模型会被假称可用 | 与推荐同提交执行；新加必删旧 |

本次结构性方向已由任务书和更新后的设计卡授权。老用户在现有前向迁移入口按只增不改的目录顶层收据修正一次，不升目录版本：pending 连接恢复；停用且有失败记录且有请求格式的模型恢复；无失败记录的停用模型及无请求格式的模型不恢复。**已明示接受的限制**：失败后用户自己开过又关掉的那一类，也会在这一次迁移被启用；以后再关不得因重启恢复。不给模型行加字段，退回 0.24.1 必须仍可读写；旧规则可能重新停用未验证模型，旧版写入若丢标记则再升级可能重做，已由协调接受。更新提醒的版本号不能区分同为 0.24.1 的源码变化，已有修正均绑定目录版本、没有通用修正账本，故使用顶层单调收据；须以已发编译模块和真窗口证实兼容。

## 7. 用户权衡的核心与实施边界

让已有请求格式的模型先能发，代价是推迟发现坏 key，并在一次性迁移中接受少量来源分不开的旧停用模型重新出现；每个都仍可手动关掉。

实施必须在共享 owner 收口：迁移检查请求格式不能先要求旧 `enabled:true`；真实成功清标记须绑定本次凭据/模型，旧请求不能替刚换的 key 转正，缓存命中与排队也不能冒充本次真发成功；旧失败按同一模型的更新成功或当前可用性退役，不能拿同家另一个模型作证。若发现新的独立可用性判据、现有迁移链无法安全留底或旧版无法读写带收据的目录，按任务书停下报；不改接入页面结构或数据上传路径。
