# 方向检查：失败后再发一次只由主进程一处定

全图：画布上一镜失败或没等到结果后，创作者点「再发一次 / 重新生成 / 重试」。系统要定三件事：要不要再问一次花钱、问几镜、确认后放行哪几笔旧单。改前这三件事分在三处：
- 渲染层 `generationRunController.ts` 按节点错误 / 占用自己判要不要问；
- 渲染层 `releaseUnknownSubmission.ts` 在确认后重读全部没收尾的，逐个放弃结果未知的那几笔，再把全部在途名单当许可报回去；
- 主进程 `appIntegrationCanvasShot.ts` 的 `assertNodeIdle` 拿「窗口身份 + 这份名单」放行。

设计卡：`docs/plan/2026-11-20-retry-one-home.md`。
复盘来源：一条没参与过前几轮修补的只读线，在 2026-11-20 基线（origin/main `48ad810e8`）上静态读码写出，再与方案对照。它没跑测试或真任务，下面的行为预测都由实现线的跨层测试来核。

### 0. 一句话根因
重发这一类问题反复出现，根因是主进程没有一份自己持有的决定，说清「确认了哪笔旧单、因此允许哪笔新单」。入口按节点错误和占用自己问，确认后又把名单扩大；主进程拿窗口身份加这份名单当放行依据。缺的不是又一张确认卡。

### 2. 为什么这一类会一直出现：谁在判、读哪份事实
| 层 | 自己判什么；读哪份事实 |
|---|---|
| 渲染：画布单镜 | 读主进程的没收尾清单、当前节点错误、发起方和「要重发」标记：机器发起且有占用就拒，人发起且有占用或说了要重发就问；准入拒绝后最多再问一次 |
| 渲染：分镜 / 批量 / 波次 | 各自按没收尾清单筛掉在途的，只为显示「跳过 N 个」；这是内容和归属保护，不等于重发授权 |
| 渲染：批量通知 / 任务中心 | 通知只排除本机拒绝就给「重试失败的 N 个」，结果未知的也算进去；任务中心无节点时问同一张卡，确认后只放弃旧任务、新提交 0 |
| 渲染：放弃结果未知 | 卡后重新查全量没收尾的，逐个放弃结果未知的，再回报全部在途名单 |
| 渲染 → IPC 透传 | 那份自报名单沿 bridge / taskApi / 任务动作 / 节点执行器一路透传，属运输链，不另算判据 |
| 主进程画布准入 | 读 Run 账本、没收尾索引、节点在途：人手势加外部名单就放行旧在途。确认时究竟是哪几笔，它自己没存 |
| 主进程制作 Run 服务 | 只对「结果未知」收「我查过了，放弃」，并要求人手势；对「核对中」拒，所以渲染层认「核对中」、服务不认 |
| 主进程真人章 | 制作 Run 命令通道按窗口来源盖人手势章；它只证明请求来自窗口，证明不了「那张重发卡批了哪几笔」 |

结果：确认卡打开时只有 A，等待中来了 B，渲染层会把 B 也列进回报的名单，主进程照单放行。这个扩大范围的风险静态可复核，但没有证据表明线上已经双扣。任务中心无节点的分支、渲染层与服务对「核对中」的不同看法，同属「入口先承诺、主进程另判」，跟卡的样子无关。
最早本该拦的地方：概念登记把画布单镜的执行登记成已收口，却允许渲染层另判花钱；ESLint 只拦新的确认调用，不拦名单和放弃。判据漏了跨确认 / 准入的授权范围，不是人没注意。落到铁律「点了 = 以为的」。

### 3. 不改结构的话，接下来会冒出什么
| 预测 | 怎么验证 |
|---|---|
| 只确认 A，后来的 B 也一起放行；换一个入口仍能自报名单 | 卡开着时插入 B 再答 A，数供应商 POST 次数：B 出现后，这次重发在拿到新确认前不得多发；直接传名单不得放行 |
| 「核对中」再发仍卡住；节点删了仍承诺重发却没有新单 | 同一原任务切到核对中，有节点 / 无节点各走一遍，逐项比按钮承诺、真实命令、新单数；不能拿「全拦住」算过 |
| 新通知 / 外部助手入口重新拼「可重试」和放弃逻辑 | 枚举所有新入口，对照主进程的结果；结果未知只能拿到确切的动作或确认；免费取回 0 次新 POST；代码扫描能写出新的自报写口就算失败 |

### 4. 靶子独立性检查
- 现成尺子：`canvasOpenRuns.test.ts` 钉了「后来的 Run 不获旧批准」和 v0.24.0 中断夹具，`canvasOpenRunsRecovery.test.ts` 钉了重启和取回失败，`generationOpenRuns.test.ts` 钉了取消、机器跳过、批量筛选和竞态。
- 它们有分层缝：主进程测试直接喂名单，渲染层测试用 mock 顶替主进程，证明不了卡和旧单的绑定。旧测试把「竞态后再弹一张」钉成期望，迁移后要按新决定的范围重审，不能为了旧断言留第二处判定。
- 没有评测分数当靶子，14 天内也没有「修对反而掉分被回滚」的先例。

### 5. P0：哪些是我们独有的
独有的是「按镜再次花钱」：旧 Run 和新 Run 的范围、整镜依赖、旧产物归属。下面三样已经在仓库里，直接复用，不重写：
- 幂等：同一运行记录号只重放；
- 不盲发：结果未知 / 已提交的意图不再自动发；
- 收据：已有挑战与合同绑定。

普通 HTTP 重试代替不了「要不要再花一笔」。本刀不引库、不新建账本或提交机，不登记新的自写。

### 6. 三条路对比 + 推荐
三条路都保住已定的三件事：重发卡只问是否再花一次，不在卡上改模型或参数；积分单位不改；问法拆分不改。

| 路 | 会发生什么 | 代价 / 风险 | 推荐 |
|---|---|---|---|
| 沿原方向，各入口各补 | 给画布、任务中心、通知、放弃逻辑各补状态和范围，A 确认只传 A | 局部改动少，但多份要长期保持一致；新入口仍可复制「要不要问」和名单 | 否 |
| 换做法：扩现有主进程画布准入 | 在主进程画布准入这一家决定原单事实、问不问、批准范围；入口只报重发意图、显示决定。确认绑定卡前的具体旧 Run / 作业；新增 B 时这次决定不放行 B，本次重发 0 新 POST，重读后再问；取消 0 新 POST。未知旧单可能已扣，明确同意的新单仍可能再扣一次，不承诺供应商只扣一次 | 跨层改动较多，但不添第二本账、不添第二台发送机 | 是 |
| 删掉「未结束旧任务原地重发」 | 删重发卡调用、名单链和用于重发的放弃写口；保住明确失败的普通重试、原单查询和免费取回 | 最省后续防守，但退回到「卡住没出路」；违背「人确认后可再发」的既定结果，需用户改方向 | 否 |

为什么不直接塞进另两处：
- 试跑模型的「一次性下单准入」是一份应用级意图对一次尝试，画布是一个节点上可以并存几笔 Run，身份模型不同。
- 助手出价的「待确认花费」本来就拒收结果未知，硬塞进去会把普通画布重发都变成助手出价。

做法：在现有画布准入里加唯一的重发决定。借「一次性下单准入」那套做法：读和认领用同一份决定，结果未知就冻结。借「待确认花费」那套精确的身份和镜头范围。两处各自的职责不动。
共用人证（可信宿主 / 客户端确认链，即「主进程核对确实问过人」）另有主人。本刀只拥有「这次重发的具体对象、原任务事实和新意图」，不另铸一个布尔真人章。制作 Run 命令通道上「来自窗口即已确认」的旧放行口，要等共用人证接口定下后再随迁移收掉。

### 7. 用户要权衡的核心
「收一处」已经定了，这次拍板的是收在哪、删哪条旧放行路。推荐接受跨入口迁移的成本，把决定放在已有的画布准入，保住「上一单没回音，人同意可能再花钱后，仍能继续做这一镜」。删掉原地重发虽然省事，但未知旧单就只剩等和核对。

### 8. 自写登记 `gate-family`（门岗族）
本刀碰到门岗族：在现有 `check:concept-owners` 的扫描里加一条规则 `resend-owner-bypass`，不新增检查命令。
- 先看了现成方案：
  - eslint-plugin-boundaries、dependency-cruiser：只判「谁能 import 谁」。本刀要拦的是「登记的主人函数之外调用放占用」和「共享表之外列出那一组状态」，import 关系一样也会出事，它们判不出来。
  - eslint 的 `no-restricted-syntax`：能拦字面量，拦不住别名、展开、拼接这些绕法。现有扫描已经用 TS 绑定追这些绕法（`findFailureDecisionBypass`），本刀照它扩。
- 现在换不了的原因：规则判的是 Nomi 自己的主人登记（哪个函数是主人、哪张表是共享表），没有现成工具读得懂这份登记。门岗族「保留 / 合并 / 降级 / 删除」的账本结论还没拍板，现在单独把这一条挪去别的工具，等于先造一个并行版。
- 哪天换：`gate-family` 复审日 2026-11-30。账本拍板后，如果概念扫描整体并进 eslint 自定义规则或别的现成工具，这两个落点跟着一起迁，不单独留。

## 和原方案对照

实现线的方案（设计卡）在复盘之前写成，复盘没读过它。对照后，第一阶段按推荐的路落地；放弃写口迁进主进程需要共用人证，留第二阶段。

| 复盘建议 | 第一阶段怎么做的 | 一致 / 差异 |
|---|---|---|
| 判定放进现有主进程画布准入，不另建通用重发服务，不并进试跑准入或待确认花费 | 主进程画布单镜主人持有唯一一份 `createCanvasShotResend`（`resend.decideResend` 是唯一判定；规则体放在旁边的 `canvasResendDecision.ts`，因为主人文件已到 800 行体积红线），`assertNodeIdle` 只执行决定；试跑准入、待确认花费不动 | 一致 |
| 入口只报意图、显示决定 | 画布 / 节点错误卡 / 分镜单项 / 任务中心只报「要重发」和发起方，读回 `send` / `ask` / `refuse`；渲染层自判分支删掉 | 一致 |
| 决定由主进程私有持有、绑定具体旧 Run / 作业、一次消费 | 决定号只在主进程内存：绑项目、窗口（和节点）；记下卡打开那一刻的在途 Run → 作业号、结果未知那几笔；同一运行记录号只用一次，过期 30 分钟、窗口没了即作废 | 一致 |
| 删公开的名单 / 已批准类许可 | 提交负载里的自报名单整条链删掉，换成决定号；同提交删渲染层两个放弃辅助函数 | 一致 |
| B 冒出来：这次决定不放行 B，重读后再问 | 主进程拒 B，渲染层重新要决定、再问一次；跨层测试数供应商 POST | 一致 |
| 删渲染层的「放弃结果未知」命令，由主进程按决定放弃 | 放弃仍经制作 Run 命令通道，由渲染层按决定里的清单逐条发。主进程核对每一笔都在同一窗口、同一项目的一份有效决定的清单里，清单外的、没带号的、号是编的一律拒 | **差异**：写口还在渲染层，但已不能自报范围。写口迁进主进程要等共用人证落地，属第二阶段 |
| 按状态的「结果未知 / 在途」清单只留一份 | 新增共享表 `productionJobOpenAs`（按全部状态的 Record，漏写一个状态类型检查就红），原来两份清单改读它，逐状态对拍相同 | 一致（复盘未点名，按同一根因顺手收） |
| 任务中心无节点分支要诚实（不承诺重发） | 可见结果不变 | **差异**：诚实版另记待办 |
| 「核对中」渲染层与服务看法不一 | 不动 | **差异**：另记待办 |
| owner 边界接现有门岗；变异「恢复名单 / 第二放弃写口 / 直接 IPC 放行」全红 | `check:concept-owners` 加 `resend-owner-bypass`，登记进推送前 `SCAN_GUARDS`：<br>· 第二份「结果未知」清单 → 红<br>· 主人之外替别的 Run 放占用 → 红<br>· 两个落点各五种绕法改坏全红、复原全绿<br>直接 IPC 放行由主进程的清单核对拦（编造号 / 清单外 → 拒） | 一致；「只有主人能发放弃」这个落点随第二阶段 |
| 正常人确认后每个目标恰好新增 1 个意图，批量 / 机器跳过，不许全拦 | 「永远问」「永远拒」两个没做成版本都有测试变红（D1、D3、确认后 A 真发出） | 一致 |

第二阶段（共用人证落地后的下一刀）要做：
- 放弃写口迁进主进程：只有主人能发，扫描加这个落点；
- 放弃失败后再点能过；
- 老数据（v0.24.0 中断 / 未知夹具）跨版本回放走完整个「决定 → 问人 → 放行 → 发出」；
- 任务中心无节点分支的诚实版；
- 「核对中」的差异。
