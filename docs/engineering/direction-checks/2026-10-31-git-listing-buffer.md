# 方向检查：门岗的文件清单撞上 1 MiB 缓冲

命中：自写登记 `gate-family` 近 30 天第 99 个 fix。要改的文件本身没有命中，改法是换和删（缓冲上限收进一个入口，调用方的选项和私有上限都删掉），按 P1 的例外由协调会话代批，事后报用户。

## 0. 一句话根因

路径列表多长归仓库大小管，上限却留给每个调用方自己定，默认值就成了一条没人看见的仓库大小上限；列表失败和列表为空也没有分开。

## 1. 归类表

| 事件 | 直接原因 | 类 |
|---|---|---|
| 2026-09-17 `check-no-machine-symlinks` ENOBUFS | `ls-files -s` 输出 1,050,944 字节 | 上限归调用方；当时只修了撞上的这一处 |
| 2026-10-31 5 道门 ENOBUFS | `ls-files -z` 输出 1,051,294 字节，`gitPaths` 只在调用方传值时才给缓冲 | 同一类，第二次 |
| 2026-10-31 `check:secrets` 写「扫 0 个，通过」 | `listAllTracked()` 把错吞成 `[]` | 失败读成了空 |

## 2. 为什么这一类会一直出现

仓库只会变大，所以每个写死或继承的上限早晚被撞。09-17 那次修在调用方，别的调用方没变。三条体验铁律不适用：这是门岗脚本，没有用户界面。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 主线只剩 351 字节余量，下一个多加几个文件的 PR 就全红 | `git ls-files -z \| wc -c` |
| 下次溢出时密钥检查再次扫 0 个并放行 | 在超过 1 MiB 的提交上跑 `pnpm run check:secrets` |

## 4. 靶子独立性检查

这次是验收线在 CI 日志和本机独立查出的，实现线没有参与。新测试用真实 git index 造出超过 1 MiB 的列表，不依赖主线当前大小。

## 5. P0：这些是我们独有的吗

列文件不是我们独有的，门岗要守的规则才是。`gitPaths` 只有一个函数，读的是 git 自己的输出，用的是 Node 官方的 `maxBuffer` 选项（https://nodejs.org/api/child_process.html ）。这次的毛病是谁持有上限，换一个 git 库解决不了这件事。

## 6. 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 用 simple-git（https://github.com/steveukx/git-js ）替掉 30 个调用方 | 新依赖，改 30 个门岗 | 不解决失败读成空，换一遍要重验 | 否 |
| 补 | 只给 5 个红的门传缓冲 | 最小 | 09-17 的修法，第三次还会来 | 否 |
| 换和删 | 上限收进 `gitPaths`，删调用方选项和私有上限，直接调用改走入口；密钥检查列不出就红 | 15 个文件，多为删参数 | 低，反例都验过 | **是** |
| 删 | 去掉整仓扫描 | 门岗没了 | 不可接受 | 否 |

## 7. 用户要权衡的核心

没有要权衡的：这次只把上限从 40 处默认值收成一处，并让失败变红，不改任何门岗的判据。
