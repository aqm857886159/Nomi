# 方向检查：发送约价人民币参考汇率单点归属与权威中间价替换（2026-11-23）

> 独立复盘：由未参与 `#1624` 编码实现的协调主管线基于公开供应商接口实测、源码与门岗规则独立撰写。

**这一处的全图在哪**：表外（由 `src/workbench/generationCanvas/spend/sendCostFormat.ts` 单点持有，并由 `sendCostFormat.test.ts` 全仓源码扫描与 `scripts/check-i18n-no-cost-claims.mjs` 词条锁共同守卫）。

### 0. 一句话根因

供应商公开价目与余额接口只返回美元与积分、不提供人民币价格或汇率；此前初版手填了一个未标出处的近似数 `7.25`（比当期人民银行中间价偏高约 8%），且走查脚本又各自抄了一份汇率数字，缺少「唯一主人 + 权威出处 + 日期 + 全仓禁重名扫描」闭环。

### 1. 归类表：bug → 直接原因 → 类

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| `#1624` 初版 `BUILTIN_USD_TO_CNY_RATE = 7.25` 无出处且偏高 | 未先核实中国外汇交易中心当期中间价并在界面明示出处，只写了「内置汇率」 | 参考数据缺权威来源与日期溯源 |
| `tests/ux/send-cost-currency-topup.walk.mjs` 重复硬编码汇率字面量 | 走查直接手抄产品常量而非从唯一 owner 导入 | 同一数值多处各写一份 |

### 2. 为什么这一类会一直出现

涉及金额折算的展示层若只定「给个参考值」而未用单测把「全仓只能有一处定义汇率常量与字面量、且必须写明权威出处网址与日期」钉成结构门岗，后续脚本或新入口很容易随手再抄一份近似数。

#### 三条体验铁律

- 本次属参考汇率数据源与单点归属校准（体验铁律 ⑩ ⑪ ⑫ 不直接适用；面向创作者的约价展示已统一标「约」/`~` 并注明人民银行中间价与日期，不把估算值伪装成实扣账单）。

### 3. 不改结构的话，接下来会冒出什么（可验证预测）

| 1. 后续 Agent 侧或设置页展示人民币约价时，容易在各自模块再写一份 `USD_TO_CNY = 7.x` 导致同屏两处人民币约价不一致 | 运行 `pnpm exec vitest run src/workbench/generationCanvas/spend/sendCostFormat.test.ts` |
| 2. 继续使用无出处的 `7.25` 会让创作者看到的人民币约价系统性高估约 8% | 核对 `https://www.chinamoney.com.cn/chinese/bkccpr/` 当期 `USD/CNY` 中间价（`6.7120`） |

### 4. 靶子独立性检查

- 词条精确门岗 `scripts/check-i18n-no-cost-claims.mjs`（属自写登记 `gate-family`）独立锁死所有涉及金额/积分的面向用户词条；由于 `i18next` 与 ESLint 通用规则无法表达 Nomi 领域特有的「约价文案必须标明公开价与汇率出处、禁止断言零成本」语义，当前仍需保留 `gate-family` 中的词条白名单检查，待后续探索统一 AST 词典契约生成器时再评估收敛（预计 `2026-12-15` 复盘）。

### 5. 这一整块归谁（P0）

这一整块：美元公开价折算人民币展示约价时的唯一参考汇率数据源、出处日期标注与格式化出口
归谁：中国人民银行授权中国外汇交易中心公布的银行间外汇市场人民币汇率中间价（https://www.chinamoney.com.cn/chinese/bkccpr/）及仓内唯一主人 `src/workbench/generationCanvas/spend/sendCostFormat.ts:19`
我们哪里绕开了它：初版在 `src/workbench/generationCanvas/spend/sendCostFormat.ts:9` 手填了无出处的 `7.25`（词条写「内置汇率」），且在 `tests/ux/send-cost-currency-topup.walk.mjs` 重复抄写字面量；已实测供应商 `GET https://api.apimart.ai/api/pricing/models/all`（502 条全为 `usd_*`）与 `GET /v1/balance` 均不提供人民币或汇率字段，故在唯一主人中替换为带出处与日期的 `6.712`（`2026-11-23`）并加全仓唯一性扫描

### 6. 三条路对比表 + 推荐

| 选项 | 做什么 | 代价 | 选了以后同一类还会不会出现、从哪出现 | 风险 | 推荐 |
|---|---|---|---|---|---|
| 沿原方向修 | 保留 `7.25` 只补一句注释 | 极小 | **会**：约价持续高估 8%，别处仍可再抄一份汇率常数 | 中 | 不推荐 |
| **换一种做法（推荐）** | 实测确认供应商无汇率接口后，在全仓唯一主人 `sendCostFormat.ts` 接入中国外汇交易中心 `USD/CNY` 中间价 `6.712`（`2026-11-23`，附官方网址），界面明示「人民银行中间价（日期）：$1 ≈ ¥6.712」并全标「约」/`~`，删除走查中的重复抄写，并在 `sendCostFormat.test.ts` 扫全仓 `src/` 与 `electron/` 禁止第二处汇率命名或字面量（零新增分支或特例；要改的源码文件自身近 14 天均为 `0` 次 `fix`） | 小 | **不会**：全仓产品代码只准 `sendCostFormat.ts` 一处持有参考汇率与出处日期，别处出现即红 | 极低 | **推荐** |
| 删掉 | 删掉人民币展示选项、只留积分与美元 | 小 | 不会出现汇率，但国内创作者失去最直观的人民币单次花费体感 | 中（牺牲已定需求） | 不推荐 |

### 7. 用户要权衡的核心

在供应商接口只返回美元与积分的前提下，人民币约价采用「唯一主人 `sendCostFormat.ts` 钉死人民银行中间价（明示出处+日期+全标『约』）并由门岗禁绝第二处定义」是否满足透明与诚实要求？
