# 方向检查：一次运行给几份就留几份（类根因复盘摘要）

复盘由没参与过前几轮的线独立写（2026-11-09），只拿了用户原话、代码、近 30 天的提交历史和约束，基线是当天的 `origin/main`；用免费的假上游跑了源码级检查，没有付费、没有真窗口。这里是复盘结论的仓库内摘要，实现合同见设计卡 `docs/plan/2026-11-09-multi-result-landing.md`。

触发：画布生成的提交 / 收账 / 恢复这几处文件 14 天内 fix 已到第 3 个以上（`appIntegrationCanvasShot`、`generationRunController`、`productionGenerationSubmission` 等），这次的修法又要碰同一批文件。

## 0. 一句话根因

缺少「同一次运行内的完整产物集合」这一层：按镜头准入给的是一笔运行的身份，却被一路当成「一笔只有一份产物」——供应商提取取第一项、主进程收到第一份收据就算完成、渲染层的运行记录和节点投影都只存一份。

## 2. 为什么一直出现

和 11-07「镜头结果归谁」同属一个上位类：**运行事实与展示投影混同**。11-07 修的是跨运行的准入和归属（主进程给运行号、按运行号收账、显示从记录投影），但没覆盖一次运行**内部**的数量：执行器仍回单个结果、运行记录的结果号仍是单值，11-07 的 22 个场景每次也都只回一份。

至少 7 个单值边界串在一条链上：供应商提取（取 `[0]`）→ 主进程画布提交（先裁成一份再落账）→ 制作提交（第一份收据即完成、多份直接拒）→ 账本重放 / 完成通知（只取第一份）→ Agent 投影（只投第一份）→ 对账（只认第一份）→ 渲染层（单值交给 store）。每一层各自缩成一份，补一层，下一层照样丢。

三条体验铁律：主犯 ⑫（点了 = 以为的：付了四张的钱、上游也给了四张，创作者只看到一张）；⑩（张数意图、出站参数、返回数、保留数要能对上）；⑪（入口按目录枚举，不靠记忆列）。

多份被拒发生在上游已经出完、取片的阶段，挡不住已经花掉的钱。

## 3. 不改结构会冒出什么（复盘时用假上游验证过）

| 预测 | 怎么验证 | 复盘时的结果 |
|---|---|---|
| 只修渲染层的结果解析，Agent、账本重放、批量 / 音频仍漏 | 主进程画布提交预置 4 份本地假素材；Agent 走共用制作提交口，一个任务回 4 份 | 账本只存 1 份、重放 1 份；Agent 0 份落地，报「单镜生成返回了不止一份」 |
| 简单改成循环，同一运行的几份共用结果编号被去重；账本有四份仍只投影一份 | 合成 4 份的账本喂给真实投影 | 每镜只投出 1 份 |
| 同样四张，换供应商 / 换阶段仍少结果 | 真实内置目录的映射解析四份假响应，分 query / result 阶段 | 6 组里 newapi 4、Runway result 4，Higgsfield、Runway query、APIMart 图片、Suno 都只有 1 |

渲染层的画布 / 批量 / 配音 / 音乐 4 例和编号冲突 1 例，复盘时装配失败没跑成，只是源码推断；修复后由实现线在仓库内补成正式测试，先在修复前的代码上跑出旧行为，再在修复后翻转。

## 4. 靶子独立性

判据是「同一笔上游给四份有效产物，四份都有自己的身份、都归这笔运行、不多提交一次」，和现有测试无关。现有的恰好一次测试只证 N=1，11-07 的场景只证跨运行，都不能拿来当修好的证据。复盘线、实现线、验收线三条不同。没发现本类「修对了反而掉分」的先例。

## 5. P0

现成做法（2026-11-09 现查）：

- [OpenAI Images](https://developers.openai.com/api/reference/resources/images/methods/generate)：请求带 `n`，响应是 `data[]`，一次请求不等于一张。
- [ComfyUI 官方路由](https://docs.comfy.org/development/comfyui-server/comms_routes)按 `prompt_id` 查任务，[官方客户端示例](https://raw.githubusercontent.com/comfyanonymous/ComfyUI/master/script_examples/websockets_api_example.py)遍历该任务各节点的 `images[]`。

对决定的影响：任务身份和产物集合分两层，逐份取全，再在上面选「当前」。

复用现有的供应商产物数组、制作账本的产物数组、上游产物编号和素材收据，不加队列、数据库或依赖。按镜头准入和花钱、撤销、旧运行归属、时间轴规则是领域本身（制作运行、画布、目录 / 任务、素材都在领域目录里），外部方案替我们定不了，只有这部分自己写。本次是文件 / 概念热度触发，没有命中具体的通用自写登记条目。

## 6. 三条路

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 沿原方向修 | 各处「取第一个」改循环，各单值改数组 | 初改小 | 7 个边界继续各自漂移；共用编号、第一份即完成、旧账缺份都还在 | 否 |
| 换做法：补全已拍板的按运行号收账模式 | 运行 / 任务管一笔，稳定的产物编号管每一份；冻结返回集合，逐份收据、判完整；共享投影，「当前选中」单列。同提交删「首项当全集」「单份闸」「第一份即完成」「同运行共用结果编号」 | 一次跨层收口（提取 → 耐久收账 / 恢复 → 全部投影），独立线验；跨层兼容有成本 | 投影规则要覆盖部分失败、重启补缺 | **是** |
| 删掉 | 只开放能强制单张的模型 | 收回已开放的能力 | 挡不住默认多份的音乐，也救不了旧账；丢掉多余产物不算成功 | 否 |

推荐方案的硬约束：

1. 保留空集、媒体类型、回显、路径越界这几道校验；不泛抓所有链接绕过它们。
2. 完整 = 枚举到的每一份有效产物都有收据，或者明确标部分 / 失败；第一份落盘不能结束这笔；重启只补缺份，不重发。
3. 身份不能只靠易变的链接。
4. 时间轴仍只用「当前选中」那一份；四个候选不自动变四个镜头；旧运行全部留在历史里，不抢当前。
5. 一张四宫格仍是一份；不夹带拆图、分轨等新功能。

## 7. 用户要权衡的核心

接受一次跨层收账和旧数据兼容的成本，换「这一笔给几份就完整留下几份」；只补显示或藏起张数，后面多首歌、找回、部分失败还会再丢。

## 批准

用户 2026-11-09 拍板『按结构』：沿已拍板的按运行号收账模式补全一次运行内的产物集合。
