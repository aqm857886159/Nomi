# 方向检查：删除最后镜头后的空分镜组

## 0. 一句话根因

节点删除和分镜组生命周期由同一个 store 持有，但删除写口只维护组成员数组，没有声明“因删除变空的组必须随同一次删除消失”的不变量；因此三个删除入口会继续产生空框语义。

## 1. 归类表：bug → 直接原因 → 类

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| L-sbgroup：删除组内最后一个镜头留下空框 | `deleteNode` 只过滤 `group.nodeIds`，不删除变空组；撤销快照虽完整，但保存了错误的中间态 | 共享删除边界缺少组生命周期不变量 |
| `deleteSelectedNodes` / `cutSelectedNodes` 的等价路径 | 入口语义不同，组清理规则未集中到同一删除写口 | 同类状态变更分散 |

## 2. 为什么这一类会一直出现

组是画布领域对象，节点删除是它的唯一成员变更来源之一；目前各动作分别拼接节点、边、组的后态，无法保证所有入口执行同一生命周期规则。应在共享删除边界计算“本次删除后受影响且无成员的组”，并把组删除纳入同一撤销快照与事件批次。用户手动创建的空组属于显式对象，不能由通用空组清理误删。

三条体验铁律：⑩ 不适用（不是意图参数）；⑪ 不适用（不是模型档案清单）；⑫ 适用——删除后画布实际仍显示空框，和用户对“删掉最后镜头即清掉该组”的预期不一致。最小证据是 `src/workbench/generationCanvas/store/generationCanvasStore.test.ts` 的 characterization 测试，以及任务书复现。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 单节点删除和剪切会留下不同数量的空组 | 对同一快照分别调用 `deleteNode`、`deleteSelectedNodes`、`cutSelectedNodes`，比较 `groups` 后态 |
| 撤销后节点恢复但组成员关系可能依赖入口细节 | 每个入口删除最后成员后执行一次 `undo`，断言节点、组及 `nodeIds` 完整相等 |
| 用户新建的空组会被过度清理 | 预置 `group('empty', ..., [])`，删除别的节点后断言该组仍在 |

## 4. 靶子独立性检查

当前已有 `deleteSelectedNodes` 的删除全选测试；本次新增 characterization 只钉住 `deleteNode` 的真实旧行为，未把期望行为伪装成通过。实现后的回归测试需要覆盖三个入口，并由另一条线验收；暂无评测 oracle 冲突证据。

## 5. P0：这些是我们独有的吗？现成方案有哪些

删除快照、撤销栈和数组更新是通用状态管理能力，继续使用现有 Zustand store 与既有 `pushUndoSnapshot`，不引入自写通用框架。唯一自有约束是分镜组在节点删除后的领域生命周期。

## 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 不适用；现有 store 已是唯一状态 owner | 无 | 无法表达本项目组生命周期规则 |  |
| 补 | 在共享删除写口统一计算并删除“因本次节点删除变空”的组，保留用户原有空组；沿用单次 undo | 小范围改动，需同步事件 | 需覆盖所有删除入口 | **推荐** |
| 重写 | 抽出新的画布文档 reducer | 大，触碰并行删除手势线 | 合并冲突和行为漂移 |  |
| 删 | 删除分组能力或空组持久化 | 破坏现有用户数据和交互 | 不可接受 |  |

## 7. 用户要权衡的核心

是把“空组是否存在”当成用户显式创建的对象，还是当成节点删除后的派生残留；推荐只清理由本次删除造成的空组，并保留用户主动创建的空组。
