# 设计图流程：探索 → 组件搭建 → 清单 → 实现

日期：2026-10-10（用户拍板）。适用：新界面、改布局。只改单个元素样子的，跳过探索，直接「组件搭建 + 清单」。修 bug：改前改后有看得见的差异就走（2026-11-02 用户：修 bug 时带出的看得见的改动也要先出图；和 `CLAUDE.md` P5 短档的判法同一个口径）。

## 为什么有这套

「拍板图有、产品没做」已经发生 4 次（底部加节点条、缩放簇、顶栏居中、分组框头），全是用户自己发现的。
根因：拍板图只是一张画，没人把它拆成「这张图一共有哪几个东西」，漏了没有任何东西会红。
清单把图变成会红的东西：图上每个看得见的元素都有一条记录，每条都要有去处。

10-16 补记：这套流程两头都要——探索在 Claude Design 上放开画，才跳得出现有组件的框；落地用我们的组件搭，才能按标准实现。本文 10-10 初版第 1 步写成「可以手画」，漏了 Claude Design（规则正本 `docs/engineering/rules.json` P5 一直写着），这一轮权限两档因此没出画布就实现了；用户追问「不是要用我们的 claude design 吗」，已补回。

用户原话（2026-10-10）：「两个问题 只考虑原组件会导致探索跳不出原来的框 只考虑新的东西又不能标准实现 核心是 1.先探索出设计图 2.然后用我们的组件搭建出来 最后形成清单 里面要考虑各种状态和情况 不能因为设计把功能消失了 然后做实现」。

## 四步

0. **出样张前先问一句（2026-10-22 用户拍板，`docs/design/nomi-design-system.md` §1.0）**：「这个东西在工作台里有没有家？」判法：它有没有一份自己的数据、一套自己的编辑入口（画布节点、创作区文稿、时间轴片段、项目库条目）。有家 → 样张里聊天只画指向元素（长得和家里一样、点一下定位过去），要改去家里改或跟 Agent 说一句，聊天里不画小编辑器和完整预览；没家 → 先给它安家，再谈聊天里怎么指。必要请示（花钱、覆盖、不可撤销）每次只问一件事，不顺带改参数。
1. **调研 + 探索**：改现有界面时，出图前先做旧功能普查（这屏每个按钮和操作：它帮创作者做什么、以前定过什么、留 / 搬到哪 / 删），摘要放画布探索图旁边。

   - 收进菜单或二级入口的控件，逐个写两件事：创作者多久用一次（有数据写数据，没有写不知道），最接近的成熟同类产品把它放在哪。常用的直接摆；写不知道的，按同类产品的摆法当默认。（2026-11-14 用户拍板）普查每项写去处属于哪种（直接摆 / 收进菜单或二级入口 / 删掉），留下来的每项写一句「删掉它创作者会做错什么」（设计系统 §1.5.2 第 5 条），都进清单 `functionCensus`。
   - 每块板附「以前定过什么」：查到哪几条、现在还算不算数；没查到写查了哪里。进清单 `priorDecisions`。

   先调研再出图（2026-10-18 用户拍板；GOV.UK discovery 的做法：先了解用户、现有做法和已有服务，调研结论和图一起交出去）。调研 ≥3 条先例，每条「出处 · 它怎么做 · 对哪个设计决定的影响（改了 / 确认了）」，覆盖同类产品的交互、别人踩过的坑（论坛 / issue / 事故复盘）；摘要放在画布上探索图旁边，用户拍板时同屏看到，清单 `priorArt` 收同样的条目（`check:board-parity`，2026-10-19 起的板必填）。

   - 探索图的先例里，必须有一条是最接近的成熟同类产品同一处的真截图；和它不一样的地方，逐条写理由。它没有这个东西时，写明查了哪里。（2026-11-14 用户拍板）这一条放 `priorArt` 第一项；同类产品的截图不进仓库，清单只记产品名、截图文件的 sha256 和看的日期。
   - 同类是谁只看 `docs/design/peers.json`（同类产品登记表，用户拍板）：按 Nomi 的定位选（AI 视频创作工具），不按好不好打开选；表里「不算同类」的一类（自己填 Key 的开发者聊天客户端等）不能拿来当先例。先收公开的——官网、帮助中心、新手引导、更新日志，公开的不够再请用户登录或开权限，看不到就写查了哪里，不换一个好打开的顶替。要加一家或借一次「不算同类」的，先请用户拍板（2026-11-21 用户：「我觉得不应该看这几个 他和我们的产品定位不一致吧」「为什么你会看这些 修复底层系统」）。
   - 同一个东西出现在几处，就是一套设计、一个组件。出图前先数清它出现在哪几处，每处各出一张图。（2026-11-14 用户拍板）「几处」包括设计实验室里复用同一个组件的屏：清单 `components` 写这块用到的生产组件文件，`check:board-parity` 按「谁直接引用了这些文件」列出引用方，每个引用方要么写进 `appearsIn`，要么写明不算的理由。
   - 出图前在真画布的截图上自查：图标盖住文字还认不认得、中英文最窄宽度、间距量一遍。（2026-11-14 用户拍板）

   出图前还要先查这一块以前报过的排版问题（证据图、修复提交、反馈、待办），每个问题对应一张图；探索图必须带边界表（`docs/design/nomi-design-system.md`「会被数据撑开的地方」）和对应的最大值图，没有不进拍板。再在 **Claude Design 画布**（Artifact「Design」类型）按设计系统（`Design.md`、`docs/design/nomi-design-system.md` 的 token 与组件规格）出高保真设计图：用真实内容，关键屏要有光 / 暗、中 / 英。由协调会话出图并逐张对过设计系统，再交用户拍板。**跳过这一步、直接拿组件拼出来的屏不进拍板**（2026-10-08 用户：「是没用你的 claude design 设计吗，因为这个设计很重要」）。其它手写 HTML / 交互 widget 只准标 `exploration`，不能当实现合同。画布链接只有仓库主人能打开，所以拍板后把画布的截图和源码落进 `docs/design/boards/<日期>/preview/`、`source/`，清单从这里抽。
2. **派工前对照 + 组件搭建**：照拍板图实现，开工前由不写实现的线把本轮认领元素的每种状态对应到图、组件和断言，任务书与断言只从这张表取，交回同次提交的逐态并排图和索引，由另一条线核过才标已实现。（2026-11-16 用户拍板）
   对照表是「本轮认领元素 × 状态 → 批的图上哪一块 → 生产组件 → 断言量什么」，作为下面清单的一部分；为搭建而修改生产组件也算照图实现。任务书和断言不另写一份口径；实现线不改表里的拍板要求，发现冲突交协调处理。
   表中每行写明源图版本与区域、状态和造数条件（语言、主题、窗口与边界数据）、复用或拟建的组件、断言文件/名字及具体判据；条件相同的多个元素可共用一张源图。来源是用户定过的图和原话，不是当前实现。图上未画但明确沿用的，指向旧批准图或原话及改前真图；没有依据的先记未定，不从实现倒写要求。图和已定文字矛盾时只停受影响项，交用户定，不自己挑。
   再用生产组件（设计实验室的真组件 + 真实宿主数据）照表搭出来，每个元素交代三选一：
   - 用现成组件搭成；
   - 要改或新建组件；
   - 样子变了，要用户点头。
   不许悄悄去掉。
3. **清单**：探索图一拍板就生成清单（见下面格式），第 2 步逐态对照表随清单核准。每个元素的状态从组件登记的状态表带出（阶段 B 自动化，阶段 A 手填），核对空、加载、失败、选中、禁用、悬停、窄窗、长文字、中英、暗色及边界表条件。第 1 步的普查转进清单 `functionCensus`，每项必须有去处（保留、归位，或经拍板删除），否则清单红。
4. **实现与交回**：清单是实现合同。实现线按对照表自验；交回时，本轮每个认领元素、每种状态都交同一次实现提交的「拍板图 | 真截图」并排图及索引，图的语言、主题、窗口、数据和交互状态按表对应。索引逐行指到两边的区域、构建提交、图文件、断言结果与核对结论；同一张同态图可被多行引用，不重拍相同证据，不用总览顶替未出现的状态。截图留足宿主上下文；悬停、点击、聚焦由真实输入产生，不把预置状态当真操作。
   独立验收线按对照表逐态核对分镜、真窗断言和并排截图。图标、文案、样式和实际点击结果齐全后把该元素标为 implemented。缺状态或有偏差时保留原状态与责任人。起表线可兼验收线。
   验收时每个控件真点一次，并写下点完之后创作者看见什么。（2026-11-14 用户拍板）并排图不替代真实任务闭环、旧数据、时序与花钱验证。
   小改（只改一个元素的样子，或修 bug 带出可见差异）仍走上述核对，只补该元素和受影响各处的状态行，可引用原表、原图和原断言，不重出整张表/整套图；共享组件须先数清受影响各处。未认领、明确未实现的项不追交实现图。没有可见差异沿用设计卡原分档，不能自称小改来免核。

## 另两个决定（用户全选推荐）

- **偏差拍板**：用户只看「差异清单 + 两版并排截图」点头，不重看全图。
- **分档**：新界面 / 改布局走完整四步；只改单个元素样子跳过探索、直接组件搭 + 清单；修 bug：改前改后有看得见的差异就走。

## 清单格式

清单位于 `docs/design/boards/<日期>/<板名>.board.json`。批准稿与预览在同目录的 `source/` 和 `preview/`。

```
{
  "board": "Main", "approvedOn": "2026-10-08", "stage": "explored" | "built",
  "priorArt": [{ "url": "https://…", "takeaway": "它怎么做", "decisionImpact": "对哪个决定的影响：改了 / 确认了 …" }],  // 2026-10-19 起的板必填，≥3 项
  "boundarySheet": [{ "where": "哪里", "max": "最大值", "source": "最大值的出处", "layout": "怎么排", "board": "对应哪张图（同目录里的板名）", "element": "清单里的元素 id" }],  // 2026-11-13 起的板必填
  // 这一屏确实没有会被数据撑开的地方时：
  // "boundarySheet": { "none": "原因" }
  "elements": [{
    "id": "group.header.title-inside",   // 元素 id
    "label": "分组框头：框内左上组名与计数",
    "anchor": "[data-board=\"group.header.title-inside\"]",
    "assertions": ["分组标题的文案", "分组框头的内边距"],
    "status": "implemented" | "in-progress" | "missing" | "deferred" | "dropped",
    "owner": "I-groupheader",             // missing / in-progress 必填（PR 号或交接任务名）
    "states": ["empty", "narrow", "dark", ...],
    "userDecision": { "quote": "...", "date": "..." }      // deferred / dropped 必填
  }],
  "functionCensus": [{ "function": "...", "before": "...", "after": "<元素 id>",
    "placement": "direct" | "menu" | "dropped",     // 2026-11-15 起：直接摆 / 收进菜单或二级入口 / 删掉
    "frequency": "创作者多久用一次（有数据写数据，没有写「不知道」）",   // menu 必填
    "peerPlacement": "最接近的成熟同类产品把它放在哪",               // menu 必填
    "ifRemoved": "删掉它创作者会做错什么" }],                         // direct / menu 必填
  // 以下 2026-11-15 起的板必填（出图依据，不是实现合同；补它们不算界面差异）
  "components": ["src/…/组件.tsx"],       // 这块用到的生产组件文件（仓库相对路径）
  "appearsIn": [{ "place": "产品里的面或设计实验室的屏", "files": ["引用组件的文件"], "board": "同目录的板名", "element": "本清单的元素 id" }],
  // 只有一处、也不复用任何生产组件时："appearsIn": { "none": "原因" }
  "appearsInExcluded": [{ "file": "引用了组件、但不算一处的文件", "reason": "为什么不算" }],
  "priorDecisions": [{ "what": "定过什么", "source": "出处（用户原话日期 / PR / 文档）", "stillValid": "现在还算不算数" }]
  // 没查到时："priorDecisions": { "notFound": "查了哪里" }
}
```

2026-11-15 起 `priorArt` 第一项是同类产品同一处，长这样（截图不进仓库，只记指纹和日期，图由协调存在仓库外）：

```
{ "kind": "same-surface", "product": "产品名", "screenshotSha256": "截图文件的 sha256（shasum -a 256）", "seenOn": "看的日期",
  "differences": [{ "what": "哪里不一样", "why": "为什么" }] }      // 至少 1 条；完全照它做也写一条说明
// 它没有这个东西时：{ "kind": "same-surface", "product": "产品名", "absent": "查了哪里" }
```

这一项不再要求 `url / takeaway / decisionImpact`（差异逐条写理由就是「对哪个决定的影响」；`url` 写了照样查格式），但照样算进 ≥3 项先例里；第 2 项起照旧要求三个字段。

## 门岗

在生产组件与对应的批准分镜上写同一个 `data-board="<元素 id>"`。走查先打开真实功能，再选本次的分镜和真窗区域。例如引导板在 `#O1a-canvas` 内读取「连接模型」，并在选中节点的生成框内核对。调用 `tests/ux/_boardAnchorAssert.mjs` 的 `assertBoardAnchor`，传入分镜 locator、真窗 Page、生产区域 locator、清单元素、语言、主题，以及要比的文案或 CSS 属性。每个分镜单独执行。真窗语言取自根元素的 `lang`，主题取自 `data-mantine-color-scheme`。文案保留数字，计算样式按批准值逐项比。交互由所属走查实际点击核对。

历史清单中无法确认的锚点写「未定」。已有的走查说明保存在可选字符串数组 `assertions` 中。迁移保留各元素原状态、责任人和用户决定。确认对应组件后即可补入锚点。

- `check:board-parity` 校验每张清单。R2、R3、R5–R8 检查元素身份与状态、缺项主人、推迟或放弃的用户原话与日期、旧功能去处、状态词表和 PR 正文认领。R9 要求 2026-10-19 起的板填至少三项先例，每项写出来源、做法与对决定的影响。
- 边界表 R10（`boundarySheet`）：日期目录 ≥ 2026-11-13 的板必须有。是数组时至少 1 行，每行 `where / max / source / layout / board / element` 六个字段都非空，`board` 是同目录里存在的板名，`element` 是本清单里存在的元素 id；是 `{ none }` 时原因非空。更早的板不查，但写了就按同样的规则查。状态词表加了 `max-count`（元素要覆盖「最大数量」时用）。
- 设计流程输入 R11–R15（2026-11-14 用户拍板的几句的执行）：只查日期目录 ≥ 2026-11-15 的板（目录名带后缀按开头日期算，取不到看 `approvedOn`），更早的板不追溯、写了也不查。
  - R11 同类产品先例：`priorArt` 第一项是上面的 `same-surface` 一项。
  - R12 出现在哪几处：门岗列出直接引用 `components` 里每个文件的源文件（`src/`、`electron/` 下，测试文件和只取类型的引用不算，设计实验室的屏算；桶文件 `export { X } from` 不算一处，换成从桶里取了 X 的文件；更远的间接引用不追），每个都要在某行 `appearsIn.files` 里，或在 `appearsInExcluded` 里写理由。`components` 里的文件互相引用不算一处。
  - R13 普查加列：`functionCensus` 每项有 `placement`；`menu` 要 `frequency` 和 `peerPlacement`；没删的要 `ifRemoved`。
  - R14 以前定过什么：`priorDecisions` ≥1 行，或 `{ notFound }`。
  - R15 边界表覆盖：`states` 里有 `max-count` 或 `long-text` 的元素，必须被边界表某一行的 `element` 指到；边界表写 `{ none }` 却有这样的元素也红。它查不到「这个元素会变多却没标 `max-count`」——那一步还是出图的人数。
- R16 同类产品登记表（日期目录 ≥ 2026-11-22 的板；2026-11-21 用户要求修底层）：`priorArt` 第一项的 `product` 必须是 `docs/design/peers.json` 的 `peers` 里的一家；任何一项（按产品名、链接、摘要里的名字或别名）命中 `notPeers` 就红；这一项带 `userApproved: { quote: 用户原话, date }` 才放行。登记表本身也查：`approval` 要有用户原话和日期，每家要有 `why / surfaces / access`，同一家不能两边都在。它查不到「登记表里漏了一类不算同类的」——新出现的那类，发现时补进登记表。
  - 合同差异口径（`compareBoardManifests`，短档核实「base/head 清单有没有差异」用）：`components / appearsIn / appearsInExcluded / priorDecisions` 和普查的四个新列是出图依据，不算差异；`priorArt` 照旧算。
- 合并前：`scripts/merge-preflight.mjs` 读 PR 正文的 `## 拍板图`（一行一板：`- Main: 元素id, 元素id`），这些元素在 PR 头上必须是 implemented，或带用户原话的 deferred / dropped，否则红。

拍板清单的状态、主人与用户决定属于 Nomi 交付流程，由 `scripts/check-board-parity.mjs` 维护。浏览器定位、样式与文案断言归 Playwright。按日期目录和板名校验每一张板。门岗随 `gate-family` 于 2026-11-30 复评，依据见 [第三轮独立方向检查 §5](../plan/2026-11-27-direction-check-board-diff-r3.md)。
