# 设计图流程：探索 → 组件搭建 → 清单 → 实现

日期：2026-10-10（用户拍板）。适用：新界面、改布局。只改单个元素样子的，跳过探索，直接「组件搭建 + 清单」。修 bug 不走这套。

## 为什么有这套

「拍板图有、产品没做」已经发生 4 次（底部加节点条、缩放簇、顶栏居中、分组框头），全是用户自己发现的。
根因：拍板图只是一张画，没人把它拆成「这张图一共有哪几个东西」，漏了没有任何东西会红。
清单把图变成会红的东西：图上每个看得见的元素都有一条记录，每条都要有去处。

10-16 补记：这套流程两头都要——探索在 Claude Design 上放开画，才跳得出现有组件的框；落地用我们的组件搭，才能按标准实现。本文 10-10 初版第 1 步写成「可以手画」，漏了 Claude Design（规则正本 `docs/engineering/rules.json` P5 一直写着），这一轮权限两档因此没出画布就实现了；用户追问「不是要用我们的 claude design 吗」，已补回。

用户原话（2026-10-10）：「两个问题 只考虑原组件会导致探索跳不出原来的框 只考虑新的东西又不能标准实现 核心是 1.先探索出设计图 2.然后用我们的组件搭建出来 最后形成清单 里面要考虑各种状态和情况 不能因为设计把功能消失了 然后做实现」。

## 四步

0. **出样张前先问一句（2026-10-22 用户拍板，`docs/design/nomi-design-system.md` §1.0）**：「这个东西在工作台里有没有家？」判法：它有没有一份自己的数据、一套自己的编辑入口（画布节点、创作区文稿、时间轴片段、项目库条目）。有家 → 样张里聊天只画指向元素（长得和家里一样、点一下定位过去），要改去家里改或跟 Agent 说一句，聊天里不画小编辑器和完整预览；没家 → 先给它安家，再谈聊天里怎么指。必要请示（花钱、覆盖、不可撤销）每次只问一件事，不顺带改参数。
1. **调研 + 探索**：改现有界面时，出图前先做旧功能普查（这屏每个按钮和操作：它帮创作者做什么、以前定过什么、留 / 搬到哪 / 删），摘要放画布探索图旁边。先调研再出图（2026-10-18 用户拍板；GOV.UK discovery 的做法：先了解用户、现有做法和已有服务，调研结论和图一起交出去）。调研 ≥3 条先例，每条「出处 · 它怎么做 · 对哪个设计决定的影响（改了 / 确认了）」，覆盖同类产品的交互、别人踩过的坑（论坛 / issue / 事故复盘）；摘要放在画布上探索图旁边，用户拍板时同屏看到，清单 `priorArt` 收同样的条目（`check:board-parity`，2026-10-19 起的板必填）。出图前还要先查这一块以前报过的排版问题（证据图、修复提交、反馈、待办），每个问题对应一张图；探索图必须带边界表（`docs/design/nomi-design-system.md`「会被数据撑开的地方」）和对应的最大值图，没有不进拍板。再在 **Claude Design 画布**（Artifact「Design」类型）按设计系统（`Design.md`、`docs/design/nomi-design-system.md` 的 token 与组件规格）出高保真设计图：用真实内容，关键屏要有光 / 暗、中 / 英。由协调会话出图并逐张对过设计系统，再交用户拍板。**跳过这一步、直接拿组件拼出来的屏不进拍板**（2026-10-08 用户：「是没用你的 claude design 设计吗，因为这个设计很重要」）。其它手写 HTML / 交互 widget 只准标 `exploration`，不能当实现合同。画布链接只有仓库主人能打开，所以拍板后把画布的截图和源码落进 `docs/design/boards/<日期>/preview/`、`source/`，清单从这里抽。
2. **组件搭建**：用生产组件（设计实验室的真组件 + 真实宿主数据）照图搭出来。每个元素必须交代三选一：
   - 用现成组件搭成；
   - 要改或新建组件；
   - 样子变了，要用户点头。
   不许悄悄去掉。
3. **清单**：探索图一拍板就生成清单（见下面格式）。清单里每个元素带状态表：空、加载、失败、选中、禁用、悬停、窄窗、长文字、中英、暗色。第 1 步的普查转进清单 `functionCensus`，每项必须有去处（保留、归位，或经拍板删除），否则清单红。
4. **实现**：清单是实现合同。实现时逐条把元素的 status 推到 `implemented`，并给出走查断言。

## 四个子决定（用户全选推荐）

- **清单在探索图拍板时就生成**；第 2 步搭建时每项必须交代去向（上面三选一）。
- **偏差拍板**：用户只看「差异清单 + 两版并排截图」点头，不重看全图。
- **状态全覆盖**：每个元素的状态从组件登记的状态表带出（阶段 B 自动化，阶段 A 手填）；外加旧功能普查。
- **分档**：新界面 / 改布局走完整四步；只改单个元素样子跳过探索、直接组件搭 + 清单；修 bug 不走。

## 清单格式

路径：`docs/design/boards/<日期>/<板名>.board.json`。板源放同目录的 `source/`、`preview/`，候选抽取结果是 `<板名>.candidates.json`（`node scripts/board-extract.mjs` 生成，确定性）。

```
{
  "board": "Main", "approvedOn": "2026-10-08", "stage": "explored" | "built",
  "priorArt": [{ "url": "https://…", "takeaway": "它怎么做", "decisionImpact": "对哪个决定的影响：改了 / 确认了 …" }],  // 2026-10-19 起的板必填，≥3 项
  "boundarySheet": [{ "where": "哪里", "max": "最大值", "source": "最大值的出处", "layout": "怎么排", "board": "对应哪张图（同目录里的板名）", "element": "清单里的元素 id" }],  // 2026-11-13 起的板必填
  // 这一屏确实没有会被数据撑开的地方时：
  // "boundarySheet": { "none": "原因" }
  "elements": [{
    "id": "group.header.title-inside",   // 元素 id
    "label": "分组框头：框内左上组名与计数",
    "candidates": ["046-span-..."],       // 认领的候选（板上的文字 / 按钮 / 图标 / 条 / 卡）
    "status": "implemented" | "in-progress" | "missing" | "deferred" | "dropped",
    "owner": "I-groupheader",             // missing / in-progress 必填（PR 号或交接任务名）
    "assertion": "board:Main/group.header.title-inside",  // implemented 必填，且断言名要在 tests/ux 走查里出现
    "states": ["empty", "narrow", "dark", ...],
    "userDecision": { "quote": "...", "date": "..." }      // deferred / dropped 必填
  }],
  "decor": ["..."],                       // 纯装饰候选（说明文字、占位框），不算产品元素
  "functionCensus": [{ "function": "...", "before": "...", "after": "<元素 id>" }]
}
```

## 门岗

- `pnpm run check:board-parity`：先跑单测（`scripts/check-board-parity.node-test.mjs`，每条规则一个反例），再跑清单规则。**默认模式不起浏览器**（CI 的 Contracts job 没有 Playwright 浏览器）：
  - 每张板的 `<Board>.candidates.json` 记着抽取时板源的 sha256（`sourceSha256`，覆盖亮 / 暗预览、画板源码和 `source/canvas.json`，算法在 `scripts/board-source-hash.mjs`）。
  - 默认模式只比哈希：板源哈希 ≠ 记录的哈希，或文件里缺哈希，就红，提示「板改了，重跑 `node scripts/board-extract.mjs`」。
  - 候选 id 与清单的认领关系，照 `candidates.json` 里的候选检查。
  - 真重抽比对是显式开关 `node scripts/check-board-parity.mjs --reextract`：会动态加载 Playwright 真抽一遍、逐字节比对候选文件。只在本机或装了浏览器的环境跑，**不进 gates**。
  - 改了板源：本机跑 `node scripts/board-extract.mjs` 重抽，把新的候选和哈希一起提交。
  - 已挂进 `gates:contracts`，并在推送前门（`scripts/pre-push-contracts.mjs`）里跑默认模式。
- 清单规则（R1–R8，外加 `priorArt`：日期目录 ≥ 2026-10-19 的板必须有 ≥3 项 `{url, takeaway, decisionImpact}`，三个字段都非空，更早的板不查）：每个候选恰好被一个元素或 decor 认领；status 合法；missing / in-progress 有 owner；implemented 的断言名真在走查里；deferred / dropped 有用户原话和日期；旧功能的去处是存在的元素；states 来自词表；PR 认领的元素在合并前有去处。
- 边界表 R10（`boundarySheet`）：日期目录 ≥ 2026-11-13 的板必须有。是数组时至少 1 行，每行 `where / max / source / layout / board / element` 六个字段都非空，`board` 是同目录里存在的板名，`element` 是本清单里存在的元素 id；是 `{ none }` 时原因非空。更早的板不查，但写了就按同样的规则查。状态词表加了 `max-count`（元素要覆盖「最大数量」时用）。
- 合并前：`scripts/merge-preflight.mjs` 读 PR 正文的 `## 拍板图`（一行一板：`- Main: 元素id, 元素id`），这些元素在 PR 头上必须是 implemented，或带用户原话的 deferred / dropped，否则红。

## 阶段

- **阶段 A（2026-10-10 已做）**：流程写进仓库、清单格式、抽取脚本、门岗与单测、12 张板的对账（手填 status，状态来自生产字样探测，待真 App 核）。

## 方向检查（自写登记 gate-family）

这份流程新增的门岗 `check:board-parity`（`scripts/check-board-parity.mjs`、`scripts/board-extract.mjs`）属于自写登记条目 `gate-family`（门岗家族，状态 under-review）。按 P1，碰这个家族的修补要写清「为什么现在换不了现成方案、哪天换」：

- **查过的现成方案**：视觉回归类工具（Playwright 截图比对、Storybook / Chromatic 这类）比的是「同一个组件前后两次渲染的像素」；它们回答不了这里要答的问题——「拍板图上的这个元素，在产品里有没有主人、有没有断言、推迟有没有用户原话」。这是 Nomi 自己的交付流程约束（拍板图 → 清单 → 认领 → 合并前对账），没有现成件可接。
- **为什么现在换不了**：对账门岗只做清单的结构检查（候选是否都被认领、状态是否合法、断言名是否存在、板源哈希是否漂移），不含任何通用能力；真正通用的那一步（无界面浏览器抽元素）已经用 Playwright，不自写。
- **哪天复评**：随 `gate-family` 登记的 `reviewBy`（2026-10-31）一起复评；届时若门岗家族整体迁到现成的策略引擎，这道门岗作为其中一条规则跟着迁。
- **这一刀修的是什么**（2026-10-10）：门岗默认模式在 CI 上起浏览器失败——改成比对板源哈希，重抽比对留给显式的 `--reextract`。不是同一个 bug 的反复修补，是新门岗上线当天发现的环境假设错误（Contracts job 不装浏览器）。
- **2026-10-16 又碰了一次（`gate-family` 第 2 次）**：门岗与合并前扫描只认 2026-10-08 那 12 张板（`BOARD_NAMES`），之后新建在别的日期目录里的板对两边都不可见——门岗不查它，PR 正文 `## 拍板图` 认领它时合并前扫描只会报「不存在」。这不是同一个 bug 的反复修补，是「清单格式 / 板目录按日期分」与「门岗写死 12 张板名」两个决定之间的缺口，第一次有板（AgentPermissionTiers，只有文字拍板、没有画布）要走 `## 拍板图` 时才暴露。改法只放宽「找得到」：`loadManifests` 能按名找到任何日期目录的板，只有清单的板按 R2–R7 照查；有候选文件的新板的哈希核对没有并进来（现有两张新板的哈希对不上，归各自的线）。现成方案的结论同上一条：视觉回归 / 截图比对工具回答不了「拍板元素有没有主人、有没有断言」，没有可接的；随 `gate-family` 的 reviewBy（2026-10-31）一起复评。
- **2026-10-16 同日第 3 次（独立验收 V-1203 F2）**：上一刀让门岗「找得到」新日期目录的板，但只把「只有清单」的那一种放进校验循环，带候选文件的新板落在两个循环之外——发现集合与校验集合不是同一份，这是上一刀自己引入的缺口。改法：发现到的每张新板都跑完整规则；`board-extract` 抽取的候选核板源哈希，人工普查（`extractor: manual-*`）免哈希但照认领规则查，两样都不是就红。门岗单测补三条反例。仍然没有可接的现成方案（同上），随 reviewBy 复评。
- **2026-10-16 复验 R1（同一方向内的最小修复）**：上一条把「发现到的每张板」放进了校验，但校验仍按板名查表，跨日期同名板只查了第一份。改成按「日期目录 + 板名」逐张读它自己的清单；重名（彼此或与固定 12 张）本身报红，PR 按板名认领重名板也报红。
- **2026-11-12 加 R10（`boundarySheet`）**：新增的是一条规则，不是修补；清单结构是我们独有的，没有现成工具能校验它，理由同上，随 `gate-family` 一起复评。起因是同一块界面按「最大数量」坏过四次，流程里没人要求出图前查最大值。
