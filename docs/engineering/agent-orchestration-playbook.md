# 多智能体编排手册 — 派工 / 收货 / 接力的机器化纪律

> **谁读这份**：任何在本仓调度多个执行体（Codex / Opus 子 agent / 后台命令）替自己干活的会话。这是把 2026-08~09 一连串实战事故（合并列车连折六班、cutover-transplant 607 文件误植、ponytail ENOBUFS 撞钩子）反推出来的**编排者纪律**，一手来源沉在会话记忆里，这里提炼成仓库级、可照抄的做法。
>
> **一句话心智模型**：活会话会死，盘上现场不死。编排者的全部本事是「把判断留在自己手里、把执行和状态外化到 git/PR/docs、用机器（哨兵/门岗/延迟数）代替信任」。凡靠「我记得」「agent 说它做了」的地方，迟早翻车——本手册每一节都是某次翻车的疤。
>
> 相关：`CLAUDE.md` R27（本手册索引）、R11/R19（可交付才叫解决）、R17（重活门岗）、R18（测试等待门岗）。

## 1. 双池 / 多执行体调度：干活的不给自己打分

**原则**：谁的方案谁实施（上下文优势），**验收必派另一池**——干活的执行体不给自己的活打分，跨池互检是质量结构不是流程装饰。

- 两个独立额度池（Codex / Opus）+ 两种模型视角。方案是谁写的谁主实施，验证 / 走查 / 合并 / 门禁交给另一池。
- 两池都空闲时按任务性质分：长编码 → Codex 或 Opus 皆可；审查 / 走查 / 多路侦察 → Opus（Agent 工具生态最全）。
- **编排者本人两端不可委派** —— ① **进端 · 方案把控**：需要出推荐 / 拍板支持的方案·架构·产品决策件，核心文本编排者**亲读原文**再给判断；班组只做交叉验证，不是替读。
- ② **出端 · 交付对账**：交付回来后，交付 vs 冻结方案的逐项对账由编排者亲做——方案每条承诺（边界归属 / 删旧 / 验收门 / 停止条件）必须在交付里指得到对应证据（diff / 测试 / 文档 file:line）。
- 分工线：结构性承诺编排者亲核；机械面（测试计数 / CI 状态）才交给交叉班；班组报告降级为导读 + 证据索引，不是判断来源。
- 「只判断不动手」的边界：读决策件、对账交付 = 判断本身，不是动手；纯机械交付（合并列车 / 门禁收口）无方案可背离，照常委派。
- **架构岔路先测再裁**：多个合理解的岔路，裁决前派一个 ~20 分钟可行性探针（空证明 / 成本测量），**禁纯类比裁决**（「这个像 X，就照 X 办」= 先裁后测）。班组有权停在岔路上用证据推翻编排者——这是制度设计，不是抗命。
  - **反例**：某路线按类比裁给方案 ②，实施班在空证明里量到 176 个类型错，当场推翻回方案 ①；25 分钟纠偏，比按错的方案做完再返工便宜一个量级。

**反例**：某架构方案三次拍板推荐都基于评审班转述，补读 1100 行原文后才多抓出「双轨滑坡」风险——转述链确实滤掉了东西。

## 2. 派工纪律：任务书发行权独占 + 开工三行头

**原则**：任务书的发行权归编排者独占（班组只产建议清单，不产可执行任务书 / chip）；每份任务书写死**开工三行头**；一个分支一个主人。

- **发行权独占**：班组 / 执行体自发 spawn 的执行类 chip **必须先经编排者审分支唯一性**再放行。建议清单 ≠ 任务书。
- **开工三行头**（缺一不发工）：
  - ① **新鲜底座** —— 从最新 `origin/main` 起新 worktree；沿用旧 SHA 必须在任务书里写明理由。
  - ② **唯一分支名 + 绝对工作路径 + 禁触分支清单** —— 一份任务书只授权一个分支。
  - ③ **改动预算** —— 预估文件 / 行数量级；超预算必须逐类解释（607 文件的 transplant 本该在这一行就爆掉）。
- **一个分支一个主人**：同一子系统的大收尾优先单班顺序做，并行只留给真正不相交的文件面。保关键信息 > 堆并行度。
- 任务书正文固定带：等待语义（见 §4）、红线 / 禁触清单、报告格式、总限时。

**反例**：M1 三线撞车——两个核账班 chip 都指向同一 `-r2` 分支，用户点开后互相踩掉对方的 commit。

## 3. 收货三查：采纳任何分支 / 底座前的第一动作

**原则**：采纳（合并 / 继承底座 / 复用产物）任何分支前，**跑三查、缺一不收**。结构断言（"我加了测试"）不作数，只认延迟数字。

- **查一 · 底座 behind 数**：`git rev-list --count <branch>..origin/main`。落后就先并线（§6），别在陈旧底座上验收。
- **查二 · 两点 diff 回滚检查**：`git diff --stat origin/main...<branch>` 是三点、会掩盖过期分支对 main 的大回滚。
  - **必须用两点** `git diff --stat origin/main..<branch>` 看真实增删；对 main 的删除量必须解释得通（删了门岗 / 删了别人的功能 = 立即拒收）。
- **查三 · 全套件失败 delta vs main = 0**：在分支和 `origin/main` 上各跑全套件，失败集合逐条对比，delta 必须为 0。「结构上加了断言」≠「套件真没多红」。
- 样张门只验长相，**底座工程体检是编排者采纳前的独立第一动作**；终装班的 before/after delta 法升格为标准收货动作（机器化为 `check:handoff`，在尾巴单）。

**反例**：cutover-transplant 事故——只看样张没跑工程体检就采纳底座，误植 607 文件、带进 47 处套件回归；三病（旧底座 / 宽泛回滚 / 结构假绿）当时全无机器拦。

## 4. 等待语义：sleep 轮询 + 哨兵文件，禁一切「挂起等唤醒」

**原则**：后台执行体没有「挂起等唤醒」的能力——它的心智是「最终文本 = 报告 = 终局」。派长任务（CI / 构建，本仓 Desktop Linux ~20-25 分钟）必须**写死等待语义**，否则模型会各自发明一种错误等法。

- 任务书必带这句：「你是一次性后台 agent：最终文本就是报告；不存在『等通知再继续』；**禁 `--watch`、禁 Monitor、禁『run_in_background / 后台任务 + 交卷』**。」
- **哨兵文件法**（超 10 分钟的长命令这样跑）：
  - `run_in_background` 启动时把退出码写哨兵：`(cmd; echo $? > /tmp/<名>.exit)`。
  - 然后**原地** `sleep 60` 前台轮询哨兵文件直到出现，读真实退出码再继续。**轮询封顶 25 轮**，超时 = 如实报告、不恋战。
  - **哨兵文件启动前必删**——后台通知里的 exit code 是假的，`| tail` 之类管道的退出码是 tail 的、会把红门洗成绿。
- 每个工作单元给总限时（如 50 分钟），到点跳过 + 记录。**每完成一个单元即 commit**——盘上现场比会话命长。
- **这条同样管编排者自己**：派完后台班就结束回合裸等通知 = 犯同一个错。托管后台班期间必须挂一个定时巡查（~1500s 唤醒）兜底，巡查动作 = 外部面判活（§5）→ 死班发接力 / 交付跑收货三查（§3）再派下一棒 / 活着不打扰，每轮用同一 prompt 续排下一轮，战役收官才撤。**通知只是快路径，不是保障**——班和通知都会跟着会话一起死。
  - **反例**：某画布性能班派出后主会话结束回合裸等通知，会话压缩把后台班 kill、完成通知变死信，编排者恢复后也失忆，班死无人接力，直到用户来问「推进得怎么样」才发现。

**反例**：合并列车连折——v1 挂死在 `gh pr checks --watch` 的无限等待（CI 有 check 永久 pending 时不返回）静默 1 小时；v2 学会不用 `--watch`，却把结果交给一个 Monitor 通知然后结束了自己的回合，通知无人接收；第三班 brief 已写「禁结束回合等通知」，仍把 gates 丢进 `run_in_background` + 挂 Monitor 交卷，死后孤儿 vitest 继续空转还污染别的 worktree 的耗时测量。

## 5. 活性与接力：判活看外部可观测面，接力靠盘上现场

**原则**：判断一个 agent 死没死，**看外部可观测面**（CI 活动 / worktree 时间戳 / commit 流），不读它的输出转录（会爆上下文，且转录会骗人）；死班 = 备份现场 + 带清单接力，一切状态外化到 git / PR / docs。

- **活性探测三面**（三面都断流 = 死了）：
  - `gh run list` 看相关分支 CI 是否持续有新活动；
  - worktree `git log -1 --format=%cr` 时间戳是否还在推进；
  - `gh pr list` 记分 / 评论区是否有变化。
- 静默死亡的 agent 用 `TaskStop` 停不到（id 已不在）就**直接发接力班**。接力 brief 给足盘上现场：worktree 绝对路径、停在哪个分支、未 push 的 commit（`git log origin/main..HEAD`）、已完成 / 待办清单。
- **一切交接强制走 git / PR / docs 外化**（不靠 agent 记忆、不靠转录）：分支 = 代码现场、PR 评论区 = 最新裁决、`docs/handoff` / `docs/plan` = 冷启动接手点。开局让接力体先 `gh pr view <n> --comments` 取最新状态。

**反例**：一晚死六班；能救回来全靠「commit 已进分支、方案已进 docs」——凡只活在某个会话内存里的进度，随会话一起蒸发。

## 6. 远落后分支：服务端并线，别在本地追平 push

**原则**：远落后 main（几十到近千 commit）的分支上车，用 **`gh pr update-branch` 服务端并线**，别在本地 `git merge origin/main` 后 push——追平 merge 的巨 diff 会撞本地钩子上限。

- **病因**：打捞类分支落后 main 45~944 commit 时，本地 merge 后 push 的 diff 高达 15-88MB，远超 ponytail pre-push 评审的 1.5MB 上限（`execFileSync` 默认 buffer 也炸）→ `spawnSync git ENOBUFS` 挡 push。
- 根因是量具错配：追平 merge 的 push 内容 99% 是 main 已有的 commit，本地钩子却要整包评审。
- **上车流程**：`gh pr update-branch <n>`（服务端把 main 并进分支，不经本地钩子）→ CI 在 merge tree 上跑验证 → 全绿 `gh pr merge <n> --merge`。
- 需要补小修（如 docs 索引）时：先 `update-branch` 让 remote tip ≈ main，再只 push 那个小 commit（几个文件，ponytail 安全）。
- **验证在本地、并线在服务端**：本地五门（`pnpm run gates`）照跑，只是并线动作交给远端。合流模型注意：2026-09-02 起本仓 `strict` 已关（PR 凭自身绿即合，见 §12），`update-branch` 从「合并前强制」降级为「工具」——远落后分支要提前拿 merge tree 的 CI 结论、或本地钩子撞 ENOBUFS 时仍用它。

**反例**：此前至少三个班都撞过 ponytail ENOBUFS，反复试「本地 merge 再 push」反复被挡，直到改用服务端 `update-branch` 才通。

## 7. 验收锚：红灯用固定复现命令一字不改

**原则**：判某个红灯是不是真回归、真修复，**用固定的复现命令，一字不改地重跑**——防「移靶」（改命令 / 改参数 / 改预算，让红灯变绿，实则没修根因）。

- 红灯的复现命令写进任务书 / 记忆，验收时原样重跑：同一命令、同一参数、同一入口、同一平台分支。**移靶被抓**：把 canvas perf 预算 / 段长挤松让门岗变绿，是 P2 症状级修法，不是根因——正解是平台感知预算或降 advisory，不是改尺子。
- **样张门只验长相，工程体检另跑**：用户可见改动过样张对账（R8 / R13），但样张对不上 ≠ 工程健康；底座 / 套件 / 门岗的健康是另一条独立验收线（见 §3 收货三查），两条都过才叫完成。
- 验收物必须 = 用户所见物：同构建、同入口、同平台分支；截图必须编排者亲眼 Read 过才算数（眼见链，R13）。

**反例**：CI 门岗红被误判成回归——实为 perf 预算按 macOS 校准、CI 在 xvfb 软渲染下慢 1.3-2x；若当时改预算「让它绿」就是移靶，真相是量具没对平台校准。

## 8. Codex 执行体专项：full clone + 结构护栏

**原则**：给 Codex 派码活用 **full clone 不用 git worktree**（worktree 的 `.git` 元数据在主仓路径下，Codex 的 cwd 沙箱写不了）；护栏不靠沙箱靠结构。

- **禁 worktree**：worktree 的 `.git` 是指向主仓的引用文件，Codex 沙箱在主仓路径下连 `index.lock` 都写不了、代理端口也不通——它只能把活存成 patch，逼出「假 commit / 补丁接力 / fetch 反转」三类弯路。**给 Codex 一个独立 full clone 目录**。
- **沙箱与护栏**：`--sandbox workspace-write` 连 clone 内 `.git` 都拦（疑似 VCS 硬保护）→ 码活默认 `--sandbox danger-full-access`；护栏改由**结构**兜：分支保护挡 main、push 五门闸、跨池核账后才合并。任务书仍写死「只在指定 clone 目录工作、只推 feature 分支」。
- **派工姿势**：`codex exec --cd <clone> --sandbox danger-full-access "<中文任务书>"`，用 Bash `run_in_background`（不阻塞主会话，完成有通知）。默认 **fresh 会话 + 盘上外化现场**，开局先 `gh pr view <n> --comments` 取最新裁决。
- **resume 只用于恢复中断现场**：需要它「回忆当时设计动机」才 `codex exec resume --last` 或 `fork`（会话存 `~/.codex/sessions/`）；常规派工一律 fresh。沙箱会拦 push 外的 fetch 类操作（如 `delivery:preflight` 的 `FETCH_HEAD` 写）——非实质红，验证侧补跑。

**反例**：M1 给 Codex 配 worktree，它 commit 全被 `index.lock` 拦，只能交 patch；改 full clone + `danger-full-access` 后一路通到 push。

## 9. 解冲突三查：禁整文件盲选边

**原则**：merge / 装配时冲突落在**别的在途或近期战役碰过的文件**上，必须跑解冲突三查；禁 `--theirs` / `--ours` 整文件选边——一把梭会把对面战役的成果连根撞掉，而且当场看不出。

- **查一 · 对面意图**：`git log <merge-base>.. -- <file>` 看对面分支在这个文件上的提交意图。冲突标记里只有两段文本，commit message 才写着「为什么这么改」；不知道对面为什么改就选边 = 盲选。
- **查二 · 逐 hunk 裁**：冲突逐 hunk 裁决，两边都要的改动手工合成；禁 `git checkout --theirs/--ours <file>` 整文件收编。文件级选边的隐含断言是「对面在这个文件里的所有改动都不要」——冲突文件恰好是多条战线交汇处，这个断言几乎必错。
- **查三 · 减号行扫尾**：解完冲突对热点目录跑 `git diff origin/main HEAD -- <热点目录>`，逐条审**减号行**，找丢失的保护性代码。重点盯「memo 稳定化 / 性能选项 / 撤销·持久化隔离」一族——这类代码删了功能照常、review 和全绿套件都看不出，只有对应门岗才拦得住。
- 编排者收装配货时把「冲突文件清单 + 每个文件怎么裁的」当验收项：报「冲突已解」而说不出逐文件裁法 = 按盲选边处理，退回重解。

**反例**：2026-09-02 M1 终装配对冲突文件盲选边，撞掉 #311 刚合入的 React.memo 稳定引用与媒体尺寸持久化隔离（`src/workbench/generationCanvas/nodes/BaseGenerationNode.tsx:164` 一带）→ media-reveal 场景长任务回归到 185ms；性能门岗拦下后 Codex trace 定位根因，恢复保护代码后长任务归 0（PR #301 终轮）。人工 review 和全绿套件都没看出来——被撞掉的代码不改变功能正确性，只有性能预算红了。

## 10. 谁优化谁上锁：战役成果必须同 PR 落回归锁

**原则**：谁做的优化谁负责上锁——战役成果（性能优化 / 行为修复 / 结构保证）必须**同 PR** 落回归锁（性能预算 / 断言测试 / 棘轮门岗）。没锁的优化 = 等着被后续 merge 静默撞死：它被撞掉时功能照常、套件照绿，没人知道。

- 锁的形态按成果选：性能成果 → 基准场景 + 预算门岗（如 canvas perf 的 media-reveal 预算，`tests/ux/canvas-performance-benchmark.e2e.mjs`）；行为成果 → 断言测试；「本地看不出、线上才炸」的写法族 → 棘轮门岗（`check:*` + baseline 只减不增，R17）。
- **为什么必须同 PR**：优化和锁分两个 PR，中间窗口任何 merge 都可能把优化无声撞掉；同 PR 落锁 = 优化从合入那一刻起就有自动防线。这也是 §3 收货三查的镜像——收货时只认延迟数字，那交付时就必须把「能产生延迟数字的锁」一并交出来。
- 编排者验收「优化完成」时索要锁的 file:line：指不出锁在哪 = 交付不完整，按未完成处理。

**实证**：§9 那次事故里，#311 同 PR 带上的 media-reveal 预算锁是**唯一的自动防线**——盲选边撞掉优化后，人工 review 没看出、全绿套件没红，只有这道预算门岗把 185ms 回归拦在合入前。若 #311 只交优化不交锁，这次回归会静默进 main，直到某天用户抱怨「大图拖不动」才追得回来。

## 11. 大件上车：忙碌 main 上没有大 PR 的安稳座位

**原则**：合并交通的默认解是**切小片**；大 PR 挂在忙碌 main 上会被小件车流反复罚考——main 每前进一次，大件就要重新并线重跑全套 CI（本仓 Desktop 一轮 ~20-25 分钟），而小件因为 CI 快天然插队，大件结构性吃亏。切不动的真大件，申请**静止窗口**：编排者暂停放行小件，让大件独占并线直到合入。

- **罚考是结构性的，不是运气**：`strict` 分支保护要求合并前必须 up-to-date，任何小件先合入都会作废所有在途 PR 的绿；CI 时长差让小件永远先到站、大件永远在重考。怪大件「写得慢」是错误归因。
- **切小片为主**：大战役默认拆成串行小片（M 线切片制），每片独立可合。这同时服务 §2 的改动预算与 §3 的收货三查——小片的两点 diff 人读得完。
- **切不动才申请静止窗口**：真正不可拆的大件（如底座终装），窗口期内编排者不放行任何同 base 小件，大件一次并线一次考试直达合入。占道登记走 `docs/engineering/active-lanes.md`。
- 2026-09-02 起 `strict` 已关（§12），机械罚考消失；但大件长挂的另两笔账还在——冲突面随 main 前进持续扩大（正是 §9 事故的弹药）、占道阻塞别的战线——**切小片仍是默认解**。

**反例**：M1 终装 PR #301 挂上忙碌 main 后连吃六轮 CI 重考，每轮 ~20-25 分钟全在重复验证同一份改动；这笔墙钟学费直接催生了 §12 的合流裁决。

## 12. 合流保护带：strict 关闸，main push CI 兜底（2026-09-02 裁决）

**原则**：本仓合流模型自 2026-09-02 起为 **strict=off + main push CI 兜底**：PR 凭自身绿即可合入（不再强制先追平 main），组合树的健康由合入后 main 的 push CI 验证；防线不靠「合并前重考」，靠回归锁（§10）+ 解冲突三查（§9）。

- **为什么不是 merge queue**：官方 merge queue 只开放给组织所有的仓库，个人仓不够格；**迁组织仓 = 待拍板项**，拍板前用本节模型。
- **strict=off 的含义**：分支保护仍在（必需 check + review 照旧），只是去掉 up-to-date 强制。PR 的绿证明「它对自己的 base 成立」；「它和最新 main 组合仍成立」交给合入后 main 的 push CI（R22 按真实 `before..after` 分类跑）。
- **押的风险与对冲**：语义冲突（两个各自绿的 PR 组合后红）会在合入后才暴露。对冲三件：① 战役成果必须同 PR 落回归锁（§10）——组合树上锁会替你叫；② 冲突落在别人战场必跑解冲突三查（§9），禁盲选边；③ main push CI 红 = 组合树坏了，最高优先级处置（修复或 revert），不许带红挂着。
- 远落后分支的 `update-branch`（§6）从「合并前强制」降级为「工具」：想提前拿 merge tree 的 CI 结论、或本地钩子撞 ENOBUFS 时仍用它。

**实证**：M1 终装 PR #301 的六轮罚考（§11）暴露 strict=on 在单人多执行体高吞吐下的墙钟成本，权衡后落本裁决。现状可核验：`gh api repos/:owner/:repo/branches/main/protection` 应见 `required_status_checks.strict=false`。

## 13. 纵切开工前先审链：问题清单就是红灯弹药

**原则**：每片纵切（或任何「收敛/重构一条既有链路」的战役）动工前，先对目标链做一次 **#202 式真走查审计**——真进程真客户端走完整链，产出带 E-ID 的问题清单（现象 / 证据 file:line / 影响 / 修法一句）。审计只记录不修码；清单直接充当该片的**红灯弹药**：切片第一步拿它们「先红证明缺失，再绿」。

- **为什么先审再切**：切片方案写在想象的现状上必翻车——链路的真实现状（哪些工具真的可达、回归网是不是活的）只有真走一遍才知道。审计把「实施中途才撞见的惊吓」前置成「开工前的已知弹药」，切片计划直接锚到 E-ID。
- **两条腿都要真**：真客户端全链（如 MCP stdio 起真 Electron server）+ 内核真语义驱动；诚实记分——没走到的标出来，不冒充覆盖。
- **回归网自身是首查项**：先确认「这条链的既有测试在 main 上是绿的」；网破了修网优先于切片，否则切片收货的失败 delta=0（§3 查三）没有基准。

**实证（连续两链首跑必中，不是运气）**：
- M2 slice-2（剪辑纵切）开工前的剪辑链审计 PR #321（`docs/research/2026-09-02-mcp-editing-chain-audit.md`）首跑即中两 P0——E-01：剪辑族 14 工具在 MCP 面 100% 缺席，切片的「收敛」对象实为「从零投影」，方案前提当场改写；E-02：`pnpm run test:mcp`（J-MCP1 旗舰旅程）在 main 上本来就是红的，回归网在开工前夜已断。两件任何一件拖到实施中途才发现，都够切片返工一轮。切片计划照此锚定（`docs/plan/2026-09-02-m2-editing-semantic-slices.md`：「先以 E-01/R1 红灯证明缺失，再绿」）。
- slice-3（画布纵切）开工前的画布链审计 PR #353（`docs/research/2026-09-02-mcp-canvas-chain-audit.md`）首跑再中三 P0——C-01：三族三个世界（剪辑已语义化 / 画布仍 5 个旧直投 / 文档族 MCP 面 0 工具），「收敛」在文档侧又是「从零投影」；C-02：未知 kind 静默落盘再被渲染层静默蒸发（两个只读面对同一画布讲两个事实）；C-03：权限倒挂——读画布强制租约、写画布裸 projectId 直通，整套授权体系恰好把破坏性操作放在门外。三件全是「切片方案若写在想象现状上绝不会预料到」的结构级前提改写，并直接产出 slice-3 的 8 条红灯锚（R1-R8）。
