# 方向检查：外壳重设计 + 画布底部控件（2026-10-10）

触发：`node scripts/fix-churn.mjs` 命中 `CanvasToolbar.tsx`（14 天第 3 个 fix）和 `src/ui/app-shell/shell/`（第 6 个）。任务书（协调会话第四条消息）已预见本次要带 Direction-Check trailer，这份即复盘；结构性结论交用户拍板。

### 0. 一句话根因

不是同一个 bug 反复冒，而是同一份拍板稿（Main 板）被拆成多个 PR 交付，每个 PR 只对了自己那一片，没人拿整板对账；缺的是「合并前对着拍板稿逐项对账」这一层。

### 2. 为什么会一直出现

拍板稿是整屏，交付是按概念切片；切片之间的接缝（谁负责加节点条的位置）没有结构化的归属，只在 PR 正文里用自然语言写了「后续再做」。铁律 ⑩⑪⑫ 均不适用（不涉及意图 / 模型参数 / 点击预期），类根因是流程层：延期承诺无落点。

### 3. 不改结构会冒出什么

| 预测 | 验证 |
|---|---|
| 下一个拆分交付的 PR 又留下无落点的延期话 | `git grep -nE "后续提交|后续 PR|合入后"` 在 PR 正文里；merge-preflight 现已判红 |
| 走查再因控件换位大面积悬空 | `pnpm run check:walkthroughs` 的 raw-shell-anchor 规则拦手抄选择器 |

### 4. 靶子独立性

尺子是拍板稿 Main 板图 + 走查里的几何测量（分段中心 vs 窗口中心 ≤1px），不是实现线自己画的。无「修对反而掉分」先例。

### 5. P0：是我们独有的吗

加节点条、顶栏居中是产品外壳，属我们独有的画布领域；⋯ 菜单用仓库已有 `AnchoredPopover`，缩放用 React Flow 自带 zoom API，没有新写通用能力。

### 6. 接入 / 补 / 重写 / 删

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 复用 #1133 的加节点条组件、AnchoredPopover | 小 | 低 | 已采用 |
| 补 | 在竖排条上再加样式 | 与拍板稿仍不一致 | 高 | 否 |
| 重写 | 就地换成横排底部条，旧样式同提交删 | 中 | 低 | 已采用（换，非补） |
| 删 | 7 控件长条、三列 grid 同提交删除 | 小 | 低 | 已采用 |

### 7. 用户要权衡的核心

要不要把「对着拍板稿逐项对账」从评审习惯变成合并门岗的结构化项（本次只先拦了延期承诺这一半）。
