# 方向检查：设计实验室「基准机版本号」误红（2026-11-06）

命中方式：commit-msg 的热点检查只因自写登记 `gate-family`（门岗家族，近 30 天 88 个 fix）命中；这次要改的文件 `scripts/check-design-lab.mjs`、`tests/ux/design-lab/visualMode.mjs` 近 14 天没有 fix。改法是删掉一条多出来的规则、把判定换成一个纯函数，同提交删旧、不加分支或特例。按 CLAUDE.md P1 的例外（用户 2026-10-22 拍板），由协调会话代批、事后报用户。

### 0. 一句话根因

门岗拿「CI 机器的 macOS 小版本号」当红绿判据，而这个版本号由 GitHub 分批滚动、同一个 `macos-26` 标签下会混着出现；判据应该是门岗真正要守的东西——像素。

### 1. 归类

| 现象 | 直接原因 | 类 |
|---|---|---|
| #1413 派到 26.7，154 张全在容差内仍红（运行 42177144509） | `runner-drift` 跑完无条件退出 1 | 判据绑在不归我们控制的环境标识上 |
| 把登记改成 26.7 后，本 PR 派到 26.6，反方向红（运行 42181884795） | 同上 | 同上 |

### 2. 为什么会一直出现

GitHub 每次换小版本都要分批推几天，期间登记写哪个版本，另一半 PR 都红。10-18 原方案（`docs/plan/2026-10-18-design-lab-macos-ci.md`「残留风险」）只要求「版本不符且像素不符时说清是镜像漂移」，实现多做了「像素对了也拦」。

### 3. 不改会怎样（可验证预测）

- 26.7 推完之前，所有 PR 的 Design Lab (macOS) 约一半概率红，与改动无关。
- 下一次小版本滚动（26.8）再来一遍。

### 5. P0：现成方案

比像素本身用的就是现成的 Playwright `toHaveScreenshot`，自写的只有「哪台机器的结果算数」这一小段。现成的另一条路是 Playwright 官方推荐的固定 Docker 镜像录基线（字体不随托管机换代），代价是基线变成 Linux 字体，和用户在 Mac 上拍板时看到的不一样，150 多张要全部重录重拍板。现在不换：拍板对象是 Mac 上的样子；这次的改法是删规则，不增加自写量。哪天换：换代期两种机器像素真不一样、导致两边总有一边红的情况第一次出现时，重新评估 Docker 方案。

### 6. 三条路

| 路 | 做法 | 结果 |
|---|---|---|
| 沿原方向修 | 再改登记版本 | 已证明不行：混着派活，必有一半红 |
| 换做法 | 登记改成版本列表 | 每次换代仍要手改，换代当天照红 |
| 删掉（推荐，已做） | 红绿只看像素，版本号只用来在不符时点破原因 | 换代不挡人；字体真变照样红并提示重录 |

### 7. 用户要权衡的核心

没有新的取舍：像素拦截强度不变，只是不再因为一个与界面无关的版本号拦人。
