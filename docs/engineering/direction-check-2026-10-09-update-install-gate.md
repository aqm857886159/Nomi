# 方向检查：更新安装「判忙」与「调用库」不同时刻（#1135，第 3 轮修补）

### 0. 一句话根因

「判忙」和「真正调用安装」不在同一时刻（TOCTOU）：每一轮都是判了一次忙，隔着一段会改变世界的步骤（渲染层判、abort 之后判、await 之后装），才去调 electron-updater。

### 1. 归类表：bug → 直接原因 → 类

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 第 1 轮：重启安装打断 queued / 主进程任务 | 渲染层数任务、主进程不核验就 `quitAndInstall` | 判忙与安装隔着进程边界 |
| 第 2 轮：退出时导出被 abort 后照样装 | 更新排空项读「现在忙不忙」时，前一个排空项已把导出计数清零 | 判忙与安装隔着会改世界的排空步骤 |
| 第 3 轮：新进程点重试，`await` 核缓存之后任务开始，照样装 | 判忙只在 await 之前做了一次 | 判忙与安装隔着 await |

### 2. 为什么这一类会一直出现

安装有三条入口（IPC 立即安装、退出排空、续装重试），各自散在不同文件里自己「先判忙、再装」，判忙和调用库之间想插什么就能插什么（异步准备、别的排空项、IPC 往返）。结构上没有「一个唯一入口、入口内部不许 await」，所以每补一处只是把窗口挪到下一个 await 后面。

| 铁律 | 类根因要回答的问题 | 最小证据 |
|---|---|---|
| ⑩ 说的=摆的 | 不适用：不是意图或草稿参数问题。 | — |
| ⑪ 能选到 | 不适用：不是模型档案入口。 | — |
| ⑫ 点了=以为的 | 点「重启以更新」，用户以为只有没任务时才会重启；被拒时界面要如实说「有任务在跑」。 | `UpdateDialog.test.tsx` 的 installBlocked 用例、`autoUpdater.flow.test.ts` 的核缓存期间变忙用例 |

### 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 以后有人加第四条安装路径（比如 Mac 就地装、静默更新），又自己「先判忙再装」，中间再隔一个 await | 结构测试 `installGate.structure.test.ts`：只有 `installGate.ts` 能调 `quitAndInstall` / `install(isSilent…)` |
| 在入口里加一个 await（例如先上报遥测再装）重新打开窗口 | 同一结构测试断言 `installIfIdleNow` 函数体没有 `await` / `async` / `.then(` |
| 判忙读到被前一步改过的世界 | 退出开始快照（`registerQuitStartProbe`）+ `installOnQuit.test.ts` 顺序回归 |

### 4. 靶子独立性检查

评审（Codex 对抗评审）与实现不是同一条线；测试里「核缓存期间任务变忙」是把忙态注入在 `checkForUpdates` 的 await 之内，不依赖实现里某个具体字段。没有评测分数；不存在「修对了反而掉分」的先例。

### 5. P0：这些是我们独有的吗？现成方案有哪些

安装本身用 electron-updater（`quitAndInstall`、`install(isSilent, isForceRunAfter)`，`node_modules/electron-updater/out/BaseUpdater.js`），没有自写更新器能力。库不认识 Nomi 的在途工作（任务缓存、制作流程 Run、导出、画布排队节点），所以「判忙」是 Nomi 领域约束，放在我们自己的单一入口里。自写登记命中：`update-reminder-state`（`docs/engineering/self-written.json`，本分支新增，理由与出处写在条目里）。退出相关沿用 `quitTeardown` 唯一 owner（见本目录 `direction-check-2026-10-07-quit-teardown.md`）。

### 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 继续用 electron-updater 做安装本身 | 无 | 低 | ✓（已是现状） |
| 补 | 在 IPC 处理里把判忙挪到 await 之后再补一次 | 三处各补一刀，窗口仍在 | 高：下一次还会漏 | |
| 重写（限一个模块） | 新增 `installGate.ts`：唯一安装入口，入口内同步判忙 + 同步调用库；IPC / 退出排空 / 续装重试三条路都走它；旧调用点同提交删掉 | 一个小模块 + 结构测试 | 低 | ✓ |
| 删 | 删掉「立即重启」，只留退出时安装 | 用户少一个动作 | 中：丢了拍板的「重启以更新」 | |

### 7. 用户要权衡的核心

宁可偶尔拒绝一次「立即重启」（有任务在跑就让它退出时再装），也不让更新在任何一步里打断正在跑的生成。
