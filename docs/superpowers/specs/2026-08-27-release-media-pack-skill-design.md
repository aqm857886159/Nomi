# Nomi 发版素材包 Skill 设计

日期：2026-08-27

## 目标

把每次 Nomi 桌面端发版的“查版本事实 → 研究公开样片 → 搭故事 → 在 Nomi 里生成 → 本地后期 → 双语图文与文案 → 验证交付”固化成一个随应用打包的多阶段 Skill。

它不是普通品牌广告 Skill 的别名。它解决的是一个更具体的摩擦：发版信息、AI 片段、宣传片、更新图文和社交文案分别散落在不同工具里，容易漏掉事实核验、双语分版、声音、转场、成片 QA 或真实完成状态。

## 用户输入

1. 当前版本与上一个版本的准确标识。
2. PR、提交、发布说明、安装包或其他可验证的版本证据。
3. 已有 AI 片段、产品/品牌素材与链接；没有片段时则提供生成 brief。
4. 发布平台、画幅与时长；缺省为 60 秒内，横版保留中央 9:16 安全区。
5. TikHub 运行时凭据（仅在执行公开样片研究时提供，不进入对话、文件或仓库）。

## 单一工作流

1. **evidence**：先冻结发布事实、安装包身份、上版基线、公开可说与不可说的内容。
2. **research**：通过 TikHub 有界研究公开样片，验证账号身份，只学习钩子、节奏、转场、标题、声音和 CTA 机制。
3. **story**：故事先于功能；先写一句话主张、人物欲望/阻力/转折/回收，再写 3–4 段分镜和声音/转场设计。
4. **build**：在 Nomi 中把获批分镜落成画布节点，锁角色、道具和风格参考。
5. **generate**：用户确认花费后，按波次生成关键帧与视频；先代表镜头，后扩批。
6. **assemble**：把镜头排入 Nomi 时间轴，形成可预览的故事顺序。
7. **handoff**：明确 Nomi 当前还不能完成的 TikHub、音乐/音效、HyperFrames/FFmpeg、本地文件打包和发布动作，输出外部后期清单和状态，不假装完成。

## 素材包契约

每次运行对应一个版本目录，最少包含：

```text
Nomi-<version>-launch-media/
├── 00-intake/release-evidence.md
├── 01-research/reference-index.md
├── 02-story/STORY-BRIEF.md
├── 02-story/STORYBOARD.md
├── 03-generation/task-manifest.md
├── 04-edit/post-production-plan.md
├── 05-video/zh-CN/
├── 05-video/en/
├── 06-social/zh-CN/
├── 06-social/en/
├── 07-copy/wechat-zh.md
├── 07-copy/x-en.md
├── 08-qa/
└── manifest.json
```

`manifest.json` 是状态真相源；不存在的成片不创建空文件。每个产物只能是 `planned`、`draft`、`verified` 或 `published`，整个包只能是 `complete`、`conditional`、`partial` 或 `blocked`。

## TikHub 研究边界

- 凭据只从执行进程的 `TIKHUB_API_KEY` 读取，只做存在性检查，不输出或持久化。
- 官方顺序：搜索账号 → 比较身份 → 选定稳定 ID → 拉取帖子 → 必要时补单条详情。
- 默认最多取 20 条元数据、下载/转写最多 10 条；发布片研究通常精选 6–10 条即可。
- 保存公开 ID、描述、时间、互动、封面和播放 URL；原始下载只留在任务研究目录，不进发布素材目录和 Git。
- 遇到账号歧义、401/403、额度耗尽或 429 时停止；不盲目重试。
- 不复刻完整故事、镜头序列、台词、音乐、人物、Logo 或品牌视觉；只抽象可迁移机制。

## 叙事与设计边界

- 默认 60 秒内，用 3–4 个片段组成有起因、追逐/变化和回收的完整故事。
- 产品更新是剧情变化的原因，不是旁白式功能列表。
- 用户可见的核心迭代必须说清：模型/供应商、ComfyUI 多图或多媒体输入、暂停/恢复/局部返工等；内部地基只在能解释用户体验时出现。
- 核心标题位于中央安全区，用显影、烧片、章戳、形状匹配、虹膜等与故事有关的动词；禁止全片统一淡入淡出和长期底栏字幕。
- 中文版和英文版是两支独立成片，不能做中英混排；品牌和模型官方英文名例外。
- 图文沿用极简、单页一主张、少装饰的更新卡片系统，不做产品总介绍。

## 能力与诚实边界

Nomi 当前能直接执行：读文稿/画布、故事板规划、创建节点与参考边、批量生成、排时间轴。

Nomi 当前不能由该 Skill 直接执行：TikHub 联网检索、音频生成/配音、HyperFrames/FFmpeg 本地后期、文件夹打包、最终导出 QA、上传发布。这些步骤必须在 handoff 中标为外部动作。能力未连接时仍可交付分镜、提示词、节点和后期方案，但状态最多是 `partial`；不得用静态卡片冒充成片。

## 验收

- 每条公开更新可回溯到版本证据，安装包/发布标识与文案一致。
- 故事在前五秒能被理解，功能没有堆成列表。
- TikHub 只做有界机制研究，无密钥泄漏、账号误认或受保护表达复刻。
- Nomi 生成动作必须经过用户花费确认；普通 API 路线不能被 CLI 专属校验误写成全局限制。
- 中文/英文视频与图文独立，标题安全区、转场、音乐与音效有设计。
- 最终视频通过 ffprobe、全量解码、关键帧/转场目检和音频响度/峰值检查。
- 最终交付链接到真实可播放文件；如果未生成、未验证或未上传，状态必须如实降级。

## 基线红测

1. 紧急发版场景：旧流程产生中英混排成片，且没有统一素材包状态契约。
2. TikHub 压力场景：旧流程未锁官方端点顺序和 20/10 默认采集上限。
3. MCP 未接通场景：旧流程虽能诚实降级，但没有 Nomi 工具阶段与外部后期的单一交接协议。

## 非目标

- 不新增 TikHub、音频、HyperFrames 或 FFmpeg 的运行时工具。
- 不替换现有 `brand-promo`；它继续服务通用品牌/产品广告。
- 不把本次 v0.21.0 的故事、标题或模型名单写死成以后每版都复用的模板。
- 不安装或默认调用第三方 GitHub Skill；它们只作为经核验的方法参考。
