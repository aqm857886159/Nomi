# 方向检查：门岗族（`gate-family`）——第一次规则体检

## 0. 一句话根因

门岗各自找文件、读 git、判入口、维护基线并从自由文本抠判据，没有共享运行层、统一数据形状和“我扫到了几样”的自证；因此平台路径、静默空转、正文误判和基线跟着产品改动反复出现。

## 1. 归类表：近 30 天 94 个 fix

| 类 | 个数 | 结论 |
|---|---:|---|
| 产品 fix 顺带改基线 / 豁免 | 18 | 门岗本身没坏，基线写死在代码里 |
| 产品 fix 顺手新增判据 | 25 | 只加不减，fix-churn 永远命中 |
| owner / 文件搬家 | 12 | 门岗写死产品路径和符号 |
| 平台 / 路径 / git 解析 | 8 | Windows、中文路径和输出边界会空跑 |
| 误报 | 15 | 正则无法区分注释、测试和真实语义 |
| 漏拦 / 空转 / 纸面能过 | 12 | 扫到 0 和全合格外观相同 |
| 接线不一致 | 2 | 门岗从 contracts 链掉出或恒红 |
| 其它 | 2 | 注释和提示改坏规则 |

## 2. 为什么这一类会一直出现

98 个脚本里大量重复目录遍历、git 调用、路径归一和正则判定；基线写在脚本里，PR 正文是自由 Markdown，且没有统一扫描计数。门岗在给门岗站岗，修一次只会再长一条例外。

## 3. 不改结构的话，接下来会冒出什么

1. “系统改进”会出现标题变体和一句空话两类红；以真实合并 PR 回放验证。
2. Direction-Check 会被同一身份自己放行；以提交作者和放行来源回看验证。
3. 目录级 fix-churn 会把只改基线的产品 fix 当成门岗修复；以 30 天回放验证。
4. 新门岗继续各写一套入口、路径和 git 解析；统计新增脚本是否使用共享承载层。

## 4. 靶子独立性检查

现有门岗和阳性对照多由同一条线编写，曾出现死代码阳性对照、测试里的 `AbortController` 被判成产品能力、以及文件表静默截断。先修承载层和特征测试，不在错误正文判据上继续补例外。

## 5. P0：这些是我们独有的吗？现成方案有哪些

判据内容（概念 owner、根因合同、逃逸账本、真实素材和四类花钱路由）是领域约束；找文件、AST、import、PR 数据、密钥扫描和棘轮基线不是。成熟承载层是 ESLint + RuleTester、dependency-cruiser、Danger、JSON Schema / AJV、gitleaks / secretlint。本批先做共享自证和基线外置，后续再分批迁移。

## 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 逐道迁移到 ESLint / Danger / Schema | 2–3 周分批迁移 | 迁移期需逐道删旧 | 推荐 |
| 补 | 继续修 39 个坏门岗并加三道判定 | 快 | 同类毛病继续复发 | 不推荐 |
| 重写 | 只给跨文件登记表层写小 runner | 约 1 周 | 重造已有工具能力 | 部分采用 |
| 删 | 删除只为承载层而生的门岗 | 小 | 需先证明无唯一判据 | 仅删 `main-guard`、`git-path-quoting`、旧正文半场 |

## 7. 用户要权衡的核心

规则系统要不要从“每条规则一个脚本、正文里抠字”换成“现成承载层 + 结构化数据”；本批先完成最便宜的共享自证和基线出代码，期间暂停新增门岗。
