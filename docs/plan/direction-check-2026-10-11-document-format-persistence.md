触发：`fix-churn.mjs` 对 `src/workbench/common/useNomiRichTextEditor.ts` 报「14 天第 3 个 fix」。本刀是否该停：下面第 1 节逐条看前两个 fix 与本刀是不是同一类，结论是**不是**，但仍写成一页留档。

### 0. 一句话根因

文稿的「编辑器里长什么样」与「落盘 / 回流的写法」是两份各自维护的事实，中间的对账（归一化白名单、受控内容的字符串比较）都是手写的，没有拿编辑器 schema 当唯一考官。

### 1. 归类表

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 链接保存后丢（本刀） | `workbenchTypes` 的 mark 白名单手写，漏了 schema 里的 `link`、`underline` | 白名单与 schema 两份事实 |
| 同类：有序列表起始号、代码块语言、表格单元格合并 / 列宽落盘即丢 | 归一化对节点属性一律不带 | 同上 |
| 点加粗后要按两次撤销（本刀） | 回流的是同一文档的另一种 JSON 写法（键序 / 空段落），字符串比不等，被当成外部改写，`setContent` 压进一条等价历史 | 受控内容按字符串比较，判据与载体不对齐 |
| 前一个 fix：react19 编辑器生命周期 | 渲染与事务耦合 | 生命周期（与本刀无关） |
| 前一个 fix：助手聚焦时保留选区 | 焦点切换丢选区 | 选区（与本刀无关） |

前两个 fix 属于生命周期 / 选区，本刀属于「内容对账」，不是同一类的第三次补，所以不触发「同线第 3 轮」。

### 2. 为什么这一类会一直出现

白名单每加一个编辑器扩展就要有人记得同步，没有任何东西拦。铁律归属：不适用三条体验铁律，属于数据保真（保存了就该原样回来）。

### 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 以后给编辑器加新扩展（新 mark / 新节点）又会保存即丢 | `workbenchTypes.schemaRoundTrip.test.ts` 的覆盖断言：schema 里有而样例表没有就红 |
| 受控内容别的写法差异（如新增节点属性默认值）再触发等价历史 | `tests/ux/document-format-persist-undo.walk.mjs` 的 B 项 |

### 4. 靶子独立性

考官是编辑器真实 schema（`getSchema`），不是手写清单；走查是真 Electron 点工具条。

### 5. P0

Tiptap / ProseMirror 的 schema、`Node.eq` 都是现成能力，本刀只接它们，没有新自写。

### 6. 对比表

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 归一化改为直接用 schema 的 `nodeFromJSON().check()` 做，彻底删手写白名单 | 要把 `workbenchTypes.ts` 约 150 行手写归一化重写，并让持久化层依赖 tiptap | 读盘行为会变（空文本、非法结构的处理差异） | 后续单独一刀 |

| 重写 | 同第一行 | | | |
| 删 | 不可行，归一化还承担脏数据清理 | | | |

选「补」的理由：重写会改读盘行为，需要单独评估；本刀先用测试把「手写名单与 schema 漂移」变成构建期就红。

### 7. 用户要权衡的核心

要不要后续把手写归一化换成按 schema 校验（一次性消灭白名单这一类，代价是读盘行为要单独验）。
