# 设计卡 + 方向检查：撤销 / 重做不再撤掉已落地的生成结果

```
改动名：撤销只回退用户编辑，生成结局落地原样保留      线/负责人：L-undo      类别：[花钱]
```

来源：10-06 版本卡片线顺查——在画布上改了参数（或拖了节点）、之后生成结果落地，按 Ctrl+Z 想撤掉刚才那一下编辑，结果把刚出的图也撤没了（钱已经花了）。协调会话按用户已拍板的原则定产品规则：撤销 / 重做只管用户自己的编辑；生成结果落地是系统事实，撤销不能把它撤掉；撤销「删节点」时，节点在删除前落地的结果一起回来；不加任何界面元素和提示文字。

「花钱」：碰的是付费生成的结局怎么留在节点上（不碰发起、确认、扣费）。「画布」：改的是画布 store 的撤销 / 重做。

## 待拍板（产品取舍，本线没擅自决定）

撤销「建这个节点」本身，而这个节点在建好之后已经落了付费结果，怎么办？现状（本 PR 保持不变）：第二次 Ctrl+Z 把节点连同结果一起拿掉，Ctrl+Y 能拿回，但之后再做任何编辑，重做栈清空，结果就从画布上没了。同一类：Agent 一笔提议建了节点、节点随后出了图，一次 Ctrl+Z 撤整笔。

| 选项 | 撤销「建节点」时 | 代价 |
|---|---|---|
| A 维持现状 | 节点和它的结果一起拿掉 | 撤销语义最干净；付费结果可能丢（只剩重做能找回） |
| B 有落地的节点不被撤销拿掉（推荐） | 这一步里其他东西照撤，带着落地结果的节点留下 | 钱不会丢；用户偶尔会觉得「撤了一下，这个节点怎么还在」，得手动删 |
| C 拿掉节点，但结果另存 | 需要一个「找回」去处 | 要加界面，违背「不加界面元素」 |

推荐 B：和「落地是系统事实、撤销不撤事实」同一条规则——节点存在本身成了结果的容器。核心权衡一句话：**撤销要不要为了不丢付费结果，让「撤掉建节点」这一步在有结果时不完全生效。**

## 方向检查（14 天三次规则）

触发：`events/canvasUndoJournal.ts` 14 天 3 个 fix（这是第 4 个）、`store/nodeRunOutcome.ts` 与 `store/canvasStoreTypes.ts` 各 2 个、概念「画布媒体节点的固有尺寸」3 个。

### 0. 一句话根因

画布节点是一个对象，里面混着两层东西——用户编辑层（位置、提示词、参数、连线）和系统事实层（生成结果、版本、运行记录 / 状态）——而撤销历史按整个对象回退，没有任何一处声明「哪一层归撤销管」。

### 1. 归类表

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 18c7ac300 / ab78d10b3 延迟删素材绑到撤销历史 | 删素材是事实层动作，被撤销后要能复原，位置要用绝对位置 | 事实层 × 撤销的边界没声明 |
| 058f6fa03 版本卡片 V1 返工 | 删最新一版后复用编号 | 版本（事实层）编号规则被各处手抄 |
| 2d5f987ea 导演台「撤销这批」 | 整份放回节点时覆盖后续改动 | 撤销按整对象回写，覆盖了之后的事实 |
| 本次 | 前缀重放把撤销点之后落地的结果一起丢掉 | 同上 |

### 2. 为什么会一直出现

撤销 = 「把节点整个回到某一刻」。只要节点上同时存在「用户改的」和「系统写的」字段，每个新功能都要重新想一遍这个字段撤销时该不该回退，而没有地方强制回答。落到铁律 ⑫：用户按 Ctrl+Z 以为撤的是自己的编辑，实际撤掉了系统事实。

### 3. 不改结构会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 新的落地写口（比如以后的放大 / 抠图走付费模型）如果绕过 `addNodeResult` / `landNodeContent` 直接 `updateNode` 写结果，撤销又会撤掉它 | 新写口不在 `undoKeepsLandedResults.test.ts` 的门表里就没被覆盖；`door-map addNodeResult landNodeContent` 对照 |
| 撤销「建节点」丢付费结果（见「待拍板」） | 本卡探针：建节点 → 改提示词 → 落地 → 撤两次 → 节点没了 |
| MCP 外部写画布（读整张图 → 主进程算 → 整张写回）与结果落地并发时，整张写回会盖掉刚落地的结果（不是撤销问题，同一层次的混层） | 构造：MCP 读图后、写回前落一次结果，写回后看结果是否还在 |

### 4. 靶子独立性检查

测试走真实写口（`deliverRunOutcome`、`attachShotResult`、真实撤销 / 重做），只把「运行所属项目是否正打开」固定为是；断言的是用户能看到的东西（主图、版本列表、参数、位置、连线），不读实现内部。四个变异各自变红。

### 5. P0：这些是我们独有的吗

撤销栈本身是通用能力，仓库已用会话日志前缀重放实现（S5-b-2，已登记）。「哪些字段是付费生成的结局、撤销不回退」是领域规则（按镜头的花钱语义），只能自己写；本次没有新增通用能力。

### 6. 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 现成撤销库（如 zundo、Yjs UndoManager 的 trackedOrigins）按「来源」过滤可撤操作 | 换掉现有日志重放，牵动 Agent 提议事务、延迟删除等多处 | 大改动，和在途的版本卡片 / 编组线冲突 | 否（Yjs 的「按来源只撤自己的」思路就是本次做法，机制不必换） |
| 补（本 PR） | 撤销 / 重做在唯一的读边界上把目标位置之后的落地重新叠回，运行态取此刻的 | 小；落地写口要走两个 store 动作之一 | 新写口绕过就漏（预测 1） | **是** |
| 重写（限画布节点模型） | 节点拆成「编辑层 + 事实层」两块，撤销只碰编辑层 | 节点类型、持久化、所有读者都要改 | 大 | 留作结构性结论交用户拍板 |
| 删 | — | — | — | 不适用 |

### 7. 用户要权衡的核心

现在用「落地记账 + 撤销时叠回」把规则钉在撤销边界上就够用；要不要以后把节点拆成编辑层 / 事实层，让这类问题从结构上消失（代价是一次画布数据模型大改）。
