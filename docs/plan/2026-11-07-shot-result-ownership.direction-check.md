# 方向检查：镜头结果归谁（类根因复盘摘要）

复盘由没参与过前几轮的线独立写（2026-11-04），只拿了验收原话、复现、代码和约束；协调会话补查了后端做法；用户 2026-11-04 拍板「先合，再单独修」。这里是复盘结论的仓库内摘要，实现合同见同名设计卡 `2026-11-07-shot-result-ownership.md`。

## 0. 一句话根因

画布生成没有一个跨进程一致的「这次运行归谁、结果记到哪次」的边界：渲染层在主进程准入之前就把这次点击写成节点的最新运行，结果、进度、状态又都按「第一条记录」判归属，被拒后再按开始时的快照回滚。

## 1. 归类表

| bug | 直接原因 | 类 |
|---|---|---|
| 先发成功、后发被拒，图进不了镜头，一直生成中 | 后发那次准入前写成第一条；先发的结果被「只认第一条」过滤丢掉；被拒后恢复成开始时的「生成中」快照 | 归属由渲染层数组顺序决定 |
| 前台旧进度写进新记录 | 进度并进第一条记录，不看进度自己的运行号 | 同上 |
| 不带号的结果记到最新那次头上 | 结果并进第一条记录 | 同上 |

## 2. 为什么一直出现

每补一个出口，另一种先后顺序（成功先到 / 被拒先到、前台 / 后台、删节点再撤销）又会把结果吞掉：判据是「第一条记录」，而第一条记录在准入之前就可能被一个尚未成立的尝试占走。三条体验铁律里属于 ⑫（点了 = 以为的）：创作者点了生成、钱也花了，看到的却是一直在生成。

## 3. 不改结构会冒出什么（复盘时三条都已验证为红）

| 预测 | 怎么验证 |
|---|---|
| 后台盘上投递同样丢先发的结果 | 盘上副本：结果（旧号）→ 被拒（新号），节点无结果 |
| 旧进度把旧任务号写进新记录 | 前台进度（旧号、旧任务号）→ 新记录的任务号变成旧的 |
| 不带号的结果把新记录记成成功 | 不带号的结果 → 新记录的结果号是旧图 |

## 4. 靶子独立性

验收线、复盘线、实现线三条不同；特征矩阵在修复前的代码上先跑红再改。

## 5. P0

这是领域本身（按镜头的花钱语义、运行与结果的归属），没有现成库替我们决定「哪次付费替代哪一镜、旧图能不能改时间轴」。做法参考 Temporal（Run Id 由服务端准入给）、围栏令牌（先后由授予方定）、事件溯源（记录是正本、显示是投影、补偿而不回滚）、Stripe 幂等（结果绑在意图上）、TanStack Query 乐观更新（乐观层不进正式缓存）；不引入新依赖，复用已有 Zustand / Immer、主进程 Run 账本、画布写边界（自写登记 `canvas-undo-journal-write-boundary` 的系统事实重放保持不变）。

## 6. 三条路

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 沿原方向修 | 过滤加暂存、拒绝时重放 | 又多一层缓存和交错分支 | 下一种先后顺序继续吞结果 | 否 |
| 换模式 | 主进程准入给身份 → 按运行号收账 → 节点显示从记录投影；同提交删「只认第一条」和快照回滚 | 一次收敛前台 / 后台 / 取回 / 制作投影 / 升级测试 | 显示规则要覆盖所有状态 | **是** |
| 删掉 | 删过滤，所有结局直接落节点 | 不增加界面 | 晚到的旧图盖新图、改时间轴，违反已定规则 | 否 |

## 7. 用户要权衡的核心

付出一次归属迁移和交错验证的成本，换掉「每补一个出口、另一种先后顺序又吞结果」的结构。

## 硬约束（协调补查后端做法后加）

1. 「当前运行」只由主进程准入给出，渲染层不得自封。
2. 被拒、取消只追加「这次结束」，不恢复快照，节点显示从记录重算。
