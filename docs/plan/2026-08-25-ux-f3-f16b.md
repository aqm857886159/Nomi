## 2026-08-26 follow-up · F16b 收口（PR #177 review blockers）

### Blocker 1 — 旧卡路径其实还活着（P1）

**问题的真实形状**：上面第 4 条把旧卡留成了「兜底」，靠一个条件挡着：

```ts
if (options.assetUploadConsent !== 'allow' && !(await requestAssetUploadConsent(consentNode)))
```

这不是删除，是**按条件绕过**。`runGenerationNode` 当时有 7 个调用点，只有 3 个传了
`assetUploadConsent: 'allow'`。剩下 4 个——尤其是 agent 与 MCP 能力路径——每次生成照弹第二张卡，
正是 F16b 要根除的那张，而且偏偏落在这个产品最要紧的自动化路线上。

坏就坏在**「忘了传参数」这件事完全没有信号**：编译过、测试绿，只有真用户会撞上。

**修法（不是补条件，是把「谁问用户」变成编译期必答题）**：

1. **删掉 `requestAssetUploadConsent`**（连同它的 `confirm` 依赖、`generationCommon.assetUploadConsent.*`
   zh+en 文案、以及只为守护它而写的 `tests/ux/hosting-consent-dialog.walk.mjs`）。
   解析（`resolveAssetUploadConsent`，不弹 UI）与呈现（花钱卡里的披露块）从此分离。
2. **`assetUploadConsent` 改成必填**，类型 `'allow' | 'not-needed'`；同时去掉
   `runGenerationNode(id, options = {})` 的 `= {}` 默认值——那个默认值正是让调用点能省略它的逃生口。
   于是每个调用点都必须在编译期回答「这次的托管同意是谁给的」。
3. **两条没有确认面的路线各自接上真实来源**（不是重新塞回一个 fallback）：
   - MCP 能力路径 → 新增 `resolveAutonomousUploadConsent`：复用同一个策略真相源，
     策略允许 / KIE 已配 / 本地 ComfyUI → 放行；**还需要问一次 → 诚实拒发**，
     把「去配 KIE（免费）或改托管策略」的人话回给 agent。自动化不替用户把素材传上公共托管（D4）。
   - agent 批量受理（`applyCanvasToolCall` 的 `run_generation_batch`）→ 同上，逐节点解析后整批带下去。

**顺带清掉的两处死代码**（P1：留着就是下一个人把它接回去的现成零件）：

- `generationCanvasTools.execute` 里的 `generate_image` / `generate_video` 两个工具：
  **全仓无人调用** `generationCanvasTools.execute`，却各自绕开花钱卡直接跑 `runGenerationNode`。
- `rerunGenerationNodeAsNewNode`：除了自己的定义和一句注释，全仓零引用。

### Blocker 2 — 走查的否定断言盯错了元素

原断言是 `expectAbsent([data-hosting-disclosure])`——那是**新卡自己的披露块**，卡一关它必然消失。
所以「确认后不再弹第二张卡」这句话**从来没有被测量过**：哪怕 Blocker 1 完整存在，这条走查也是绿的。

修法：
- 否定断言改盯**旧卡的身份**：`[data-confirm-dialog-surface="confirm"]` + 标题文案
  「KIE 视频上传 / 公共托管确认」。
- 补**阳性对照**：旧卡代码已删、没法让它真弹一次，故用 `proveProbe` 的第 ② 种用法——
  经同一个 `__nomiConfirmDialogE2E` 桥造一张同构的卡，证明这两个探针在这一屏是活的，再关掉、再断言它没了。
  没有这一步，`expectAbsent` 和「探针根本没生效」在观测上完全一样。
- **改走真实漏斗**：原来那腿用 `__nomiSpendConfirmE2E` 塞手写的 title/message/hostingDisclosure，
  把策略解析、KIE 探测、`resolveHostingDisclosure`、i18n 键**全绕过去了**。现在挂出生产入口本尊
  `__nomiConfirmAndRunPlan = confirmAndRunPlan`，由它自己去解析策略、自己决定弹什么；走查一个文案字符串都不手写。

#### 修 Blocker 2 的过程里又挖出一个假绿（值得单记）

改完否定断言后我**用变异测试验了一次**：在点完「生成」之后注入一张假的旧卡，看走查会不会报红。
**它照样报绿。**

根因是 `expectAbsent` 的语义 —— 它内部是 Playwright 的 `toHaveCount(0)` **自动重试**断言：
- 对「稍后才异步冒出来的坏东西」→ 它会抢在坏东西挂载前采到 0，**直接通过**；
- 对「已经稳定存在的坏东西」→ 它又会一直等到坏东西消失为止。

两头都能给假绿。也就是说，**光把否定断言的目标改对还不够**，断言的时机与语义同样会让它变成空话。

最终写法：① 先 `await` 生成那一轮跑完（旧路径该弹的都弹过了）；② 再造一次探针卡证明此刻探针仍是活的；
③ 真判据换成**连续观察 3 秒、期间一次都不许出现**的轮询计数，而不是 `expectAbsent`。
变异测试复验：注入假卡 → **报红**（`unexpected value "1"`）；去掉注入 → 绿。这条断言现在是真的承重的。
- **补单测**（走查覆盖不到的那一半）：
  - `hostingRememberPersistence.test.ts`——用**生产自己组装的** `onRemember` 验证「记住我的选择」
    真的把 `anonymousAssetHosting` 写成 `'allow'`，且不冲掉其它策略字段。此前两处覆盖用的都是
    测试/E2E 桥各自另写的 `onRemember`，生产那份写坏了照样全绿。
  - `assetUploadConsentRouting.test.ts`——结构不变量：旧函数已删、旧 i18n 键已删、
    每个 `runGenerationNode` 调用点都显式带 consent、runner 自身不再持有任何弹卡能力。
    判据是「整棵源码树里还有没有能弹第二张卡的东西」，不是某一次调用的返回值。
