# 应用内反馈：发得出去、带得上日志、收到了有人记（设计卡）

改动名：一键反馈的送达、日志尾巴、反馈雷达的待分诊账。类别：[长跑][可打断]（由路径和超时信号推出，流程按严档走）。实现线和验收线分开，验收线编号见 PR 正文。

## 查到的事实（只有汇总数字，原始反馈不进仓库）

来自接收端已有的 29 份反馈包（只读清单和时间戳）：

- **日志**：29 份全部 `logs/tail.txt = logs-unavailable`，Windows 和 Mac 都一样。直接原因：`readLogTail` 把只有文件名的结果交给 `readFileSync`，按当前工作目录找，必然 ENOENT，又被 `catch` 吞成 `null`。走查和单测都注入了假的读取函数，所以从没红过。
- **送达**：按「创建时间 + 摘要」去重后是 26 份，其中 10 份（38%）晚到半小时到 7 天，也就是第一次发送失败、排队等到下次启动才补发。有 1 份报告被送达了 4 次（创建时间完全相同，编号不同）：接收端已经收下，客户端 8 秒超时没等到回答，留在队列里反复重发。
- **体积**：反馈包 345–454 KB，其中模型目录占 95%，目录里接口映射又占 85%（配了 key 的厂商通常只占其中几十 KB）。带内容不会超过 2 MB：组包预算 1.2 MB，勾选内容只多几 KB（见下一条）。
- **勾选内容**：`redactLogValue` 自带 200 字上限，所以「也附带提示词和文稿」实际每段最多 200 字；文稿根本没有；没有对话的失败面（生成、导入、设置入口）勾了也什么都不带，而 29 份里有 16 份勾了。
- **卡在「正在发送…」**：等网络有 8 秒上限，但前面的 `readTrajectory` 没有上限，而且跑在同一个 `await` 上（对话还在跑时要排在派生视图写入之后）。它不返回，界面就永远停在发送中，报告也还没落盘，用户关窗就真丢了。从线上数据证明不了当时卡在哪一步（那份报告没到，也没有日志），这里修的是所有能卡住的地方。
- **雷达**：`reports/<UTC 日期>.md` 同一天第二次运行就覆盖第一次。10-31 那条反馈 19:45Z 被记为新增，22:45Z 的运行把报告盖成「新增 0」；10-29 也一样。更根本的是：每日 hook 只留输出最后 14 行，10-29 加进去的版本健康块正好占满这 14 行，**「新增反馈 N 条」这一行从那之后就没进过会话**（`daily-radar.json` 里实测没有这几个字）。新增数一被看过就清零，没有任何东西记着「这条还没人处理」。

## 先查别人（★0）

1. [Sentry JS 离线传输源码](https://github.com/getsentry/sentry-javascript/blob/develop/packages/core/src/transports/offline.ts) · 发送抛错才入队，重试从 5 秒开始翻倍、封顶 1 小时，一次只取一条；Replay 这类丢不起的数据是先入队再发 · **改了**「失败后要等下次启动才补发」和「固定 60 秒重试」：改成失败当场排重试、翻倍退避；**确认了**「先落盘再发」只用在丢不起的货物上，用量事件的发件箱不动。
2. [Sentry SDK 传输规范（develop docs）](https://github.com/getsentry/sentry-docs/pull/15571.patch) · 网络错误可以重试；服务端明确回 4xx / 5xx 就丢弃并记原因，不当网络错误处理 · **改了**「所有失败一律留在队列头」：400 / 413 这种重发同一份字节也不会变的回答不再堵队列。**有意不同**：401 / 403 / 404 / 5xx 我们留着重试，因为令牌随版本轮换（README 第 1 条），更新 App 后还能送达；用户点过发送，不能丢。
3. [Linear Triage](https://linear.app/docs/triage) · 外部来的条目进 Triage，必须被接受、拒绝、标重复或暂缓才离开 · **改了**雷达「看过就算处理过」：新反馈进待分诊账，只有明确出账才离开；重复的折叠到原件上。
4. [OWASP 日志备忘单](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) · 日志里不放令牌、密钥、敏感个人数据，文件路径要特殊处理；用户没同意的不记 · **确认了**自动出机的日志不能只靠黑名单。没有找到直接比较白名单和黑名单的权威说法，白名单是工程判断：黑名单只挡得住想到过的字段名，而仓库里已有 `firstLine`、`detail`、`message`、`lane` 这些名字无害、值是自由文本的字段。
5. `electron/telemetry/trajectoryProjection.ts` · 轨迹出门前做字段白名单投影，再过第二道网 · **确认了**日志尾巴用同一个做法，不另起一种。

## ★1 用户怎么用

当我卡住了、点「反馈这个问题」时，我想点一下发送就走，不用守着，也相信它最终会到，以便开发者能查到原因。

1. 失败面上点「反馈」，或设置 → 关于 → 反馈。
2. 看一行摘要和「附带」那一行，想看就点「查看」。
3. 有对话的话决定带不带内容；可以补一句。
4. 点发送。最多十来秒，看到编号，或看到「已存在本机，之后自动重发」。
5. 窗口自己收起，可以继续干活。

不做什么：不加状态页、重发按钮、设置项；不做回复闭环；不新收任何数据（日志本来就写在清单上，只是一直没带上）；不改接收端（改了要先部署，新旧版本还要互相兼容）；不把生成失败节点的提示词接进来（这是新的数据流，单独提）。

已知坑：响应丢了会重发，所以接收端可能收到重复，由雷达按「创建时间 + 摘要」折叠；原话文本的字段留在本机日志里（诊断包是用户自己看过再发的），只在一键反馈这条路上过滤；自建连接的地址不再出门，排查中转问题少一条线索，换来日志和目录说同一句话。

真实任务：
- Windows 用户弱网，勾了内容点发送，接收端不回：十来秒内界面告诉他已存本机，窗口收起，稍后自动送达。
- Agent 还在跑时点反馈：轨迹读不出来也不卡，报告照发，清单写明这一项这次没带。
- 协调会话同一天跑两次雷达：第一次的新增不丢，开会话时看得到还有几条没记。

指标和量具（目标 → 信号 → 指标）：
- 主指标：首发直达率 = 去重后「接收时间 − 创建时间 ≤ 60 秒」的比例。基线 16/26（62%），新版目标 ≥ 90%。量具：`pnpm run intake:radar` 报告的「送达」一节（本 PR 新增，只看本版本）。样本：新版发布后的真实反馈，发布前只能由走查证明链路。
- 质量指标：日志尾巴带上率 = 清单里有 `logs/tail.txt` 的比例。基线 0/29，目标 ≥ 99%。量具：同一节；走查 `tests/ux/feedback-delivery.walk.mjs`。
- 护栏指标：出机内容敏感命中 0。量具：`electron/feedback/feedbackLogTail.test.ts` 夹具矩阵 + 走查对真报文的扫描。
- 护栏指标：雷达漏件 0（新反馈到被明确出账之间，每次开会话都看得到）。量具：`scripts/intake-radar.node-test.mjs`、`scripts/daily-radar-session.node-test.mjs`。
- 护栏指标：重复送达率。基线 3/29，目标不上升。量具：雷达「送达」一节。

## ★1b 连带界面

- 四个失败面的「反馈」钮、设置 → 关于 → 反馈：同一张卡，一起变。
- 「查看」清单：文案随界面语言（之前 `what` 全是中文，`why` 全是英文机器码）；模型目录那一行改说自建连接不带地址。
- 设置 → 关于 → 反馈这个入口没有失败：摘要从「这一步没成功」换成中性的一句，发出去的也是这一句。
- 「帮 Nomi 变好」同意卡、设置 → 隐私与诊断：说的是用量统计，不是一键反馈，不动。设置 → 导出诊断包：是用户自己保存的 zip，包的内容不动；上面那段说明改一句，照实说日志里可能有工具出错时留下的一小段原话。
- 每日雷达提示（开发侧）：多一行待分诊；版本健康判停不再说成「今天没查成」。

## ★1c 老用户

- 旧版没发出去、留在本机的反馈：队列文件形状不变，升级后照常补发。里面没有日志尾巴的不补。
- 退回旧版：队列文件形状不变（只多一个可选字段），旧版照常读。
- 用惯的入口、设置、项目都不碰，没有迁移。
- 雷达（开发侧）：旧缓存没有待分诊账，第一次运行把缓存里已有的都记进账（宁可多看一眼，不能漏），协调会话一条命令出账。旧的 `reports/<日期>.md` 留着不动。
- 旧版排队的报告按当时的样子补发，不重新投影：里面的模型目录还带着自建连接的地址，那一版的清单就是这么写的。新版组的包才走新投影。

## ★2 谁说了算

- 「反馈必须送达」归 `electron/telemetry/intakeQueue.ts` 的 `submitIntake`：唯一先落盘再发的入口，主进程其他地方不再各写一遍「发不出去就入队」。门：`submitIntake` 1 扇（`feedbackSend.ts`）；`flushIntakeQueue` 2 扇（启动时、队列内部重试）；`postIntake` 2 扇（队列、用量发件箱）。
- 「出门的日志长什么样」归新文件 `electron/feedback/feedbackLogTail.ts`。`listLogFilesForBundle` 的读入口从错用的那一处换到这里。
- 「出门的模型目录长什么样」归新文件 `electron/feedback/feedbackCatalog.ts`，门 1 扇（`feedbackReport.ts`）。「这一家是不是内置」和日志尾巴用同一个判据 `builtinVendorOf`，所以两边不会说两句话。诊断包用的 `redactModelCatalog` 不动。
- 「这条反馈记没记」归 `scripts/lib/intake-radar/inbox.mjs` 的待分诊账（仓库外缓存目录的 `inbox.json`）。事实只存一份，hook 现读，不抄进摘要。
- 没有靠「东西不见了 / 状态变了」猜意图：出账是显式命令。

## ★3 一致与复用

- 复用 `listLogFilesForBundle`、`redactLogValue`（第二道网）、`writeJsonFileAtomic`、`redactModelCatalog`、`DiagnosticsBundleEntry/Exclusion`；代码登记过的 host 不另抄一份，从 `applyBuiltinSeeds` 算出来。
- 不碰 `electron/logging/`（`node scripts/fix-churn.mjs` 判它是热点）：读日志和投影放在 `electron/feedback/`。
- 不引库：退避是一行翻倍；Sentry 的离线传输绑在它自己的信封格式上，接不进来。
- 自写登记：`electron/feedback/` 之前没有登记，这次的两个新文件被 `check:self-written` 拦下。它和用量事件是同一条出站管线、同一句承诺（数据只去我们的端点），所以并进现有的 `telemetry-pipeline` 条目，不另开一条。
- 概念登记：送达（`feedback.report-delivery`）、出门的日志尾巴（`feedback.outbound-log-tail`）、待分诊账（`intake-radar.triage-inbox`）各一条，同一个提交登记。

## 5 中途表（不涉及花费）

| 状态 | 关窗 / 关卡 | 断网 | 重启 | 连点 | 主进程卡住 |
|---|---|---|---|---|---|
| 组包中（≤5 秒） | 组包继续，落盘后发 | 进入排队 | 没落盘，这份没了；用户没看到任何回执 | 按钮禁用，点不了 | 20 秒后卡解锁，可再点 |
| 发送中（界面等 ≤8 秒） | 已落盘，继续发 | 进入排队 | 已落盘，下次启动补发 | 同上 | 同上 |
| 后台补发中 | 无影响 | 下次重试 | 下次启动补发 | 同一条只有一个请求在飞 | 恢复后继续 |
| 已排队 | 无影响 | 等下次重试 | 下次启动补发 | 又发一份是另一份报告 | — |

回执都在卡上那一行；排队的报告送达后不再回显编号（用户拍板⑥：只给编号，不做回复闭环）。

## 6 外部数据与失败

- 接收端（`infra/feedback-worker`）：2xx 收下；413 / 400 重发也不会变，413 去掉附件再发一次，400 丢弃并写日志；401 / 403 / 404 / 429 / 5xx / 断网 / 超时留在队列重试。**偏差**：不认 `Retry-After`，因为接收端不发；不做幂等键，因为接收端没有，靠雷达折叠。
- 上传超时：8 秒 + 体积 ÷ 16 KB/s（350 KB 约 30 秒，1.2 MB 约 83 秒）。同一个数对用量事件几乎不变（小报文仍是 8 秒多）。
- 本机日志：可能是旧版本写的、可能很短、可能有滚动的 `.1.log`、可能读不了。默认拒绝：认不出形状的行整行不要，认不出的词不要。
- 模型目录：用户可以改地址、映射和脚本。默认拒绝：字段表外的不要，host 不是代码登记过的 URL 换成标记，不认识的形状整份不带，只排除这一项。
- 时钟：用户机器时钟可能不准（线上见过差 45 秒），送达统计以 60 秒为界，不算精确值。

## ★7 性能

不是新功能，但路径推出了性能类。新增操作：无（还是点发送）。登记场景：`tests/perf/scenarios/feedback-send-main-stall.json`，跑法 `pnpm run perf:scenarios`。

指标是发送期间主进程往返最慢的一次（`mainRoundTripMax`），也就是这段时间别的 IPC 最多要等多久。点发送到卡上变「正在发送」不经过主进程，这个数卡上看不到，别的面板看得到。

| 规模 | 中位数 | 最慢 | 预算 |
|---|---|---|---|
| 今天的日志 299 行，再读一份 4 MB 滚动日志；目录约 450 KB，映射全算相关；队列是空的 | 19.3 ms | p95 22.1 ms | 100 ms（默认的操作到反馈预算，`budgetStatus: proposed`，由协调定） |
| 队列里已有 50 份约 450 KB，再发一份（只留在原始结果，不判预算） | 82.2 ms | 93.8 ms | — |
| 这 50 份一起补发（同上） | 104.6 ms | 109.6 ms | — |

5 轮，Apple M5，跑之前机器 5 分钟负载低于 8。同一轮里什么都不做时的最慢往返也有 6–27 ms，所以第一行和这台机器的底噪差不多。队列攒到 50 份是离线很久才会有的规模，补发时主进程被占 100 ms 上下，没有单独优化。弱设备和 Windows 没有量（`unverified`）。原始结果：`docs/evidence/2026-11-01-feedback-delivery/perf-feedback-send-main-stall.json`（第一行）、`docs/evidence/2026-11-01-feedback-delivery/perf-all-samples.json`（全部样本）。
