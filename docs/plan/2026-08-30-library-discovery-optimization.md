# Nomi 资源库发现与检索统一方案

日期：2026-08-30
状态：🚧 进行中（第一阶段工作流库生产闭环已落地，其他资源库按风险分层推进）
范围：项目库、提示词库、技能库、素材库，以及已确认的跨项目工作流库

## 1. 先定结论

Nomi 不做一个把项目、提示词、技能、素材和工作流混成一张卡片网格的“超级库”。这些东西的使用动作不同：项目是打开，提示词是预览/送到画布，技能是启用，素材是拖拽/预览，工作流是完整复制。混在一起会让用户每次都重新理解卡片上的按钮。

采用“**各自有家，共用找东西的规则**”：保留现有左侧栏的四个领域入口，每个库使用统一的搜索、范围、最近使用、收藏、分类和空态约定；以后再提供一个只负责搜的全局快速入口，结果按资源类型分组，不改变各领域的主操作。

## 2. 用户价值与真实场景

用户打开库不是为了浏览更多内容，而是为了完成一个当下任务：

| 当下任务 | 他要找的东西 | 找到后的动作 | 现在的主要摩擦 |
| --- | --- | --- | --- |
| 新项目继续使用旧做法 | 工作流 | 完整复制到当前画布 | 只能在项目内找，或记不住流程名称 |
| 当前节点需要一条已验证提示词 | 提示词 | 预览后送到画布/节点 | 只能按图/视频和全文搜，标签没有成为入口 |
| 想让 Agent 按自己的方法工作 | Skill | 在创作区启用 | 只有名称/描述搜索，不知道是否需要当前已有的模型能力 |
| 找上一项目的参考图或视频 | 素材 | 预览、拖到画布或导入当前项目 | “全部素材”能列跨项目素材，但当前动作语义不够明确 |
| 回到上次的项目 | 项目 | 打开继续创作 | 搜索只覆盖项目名称，来源/最近状态分散在卡片和筛选里 |

核心验收不是“库里有多少项”，而是用户能否在 10 秒内从“我知道大概要找什么”走到正确资源，并且看懂下一步怎么用。

## 3. 当前基线与证据

现有库入口集中在 `ProjectExplorerSidebar` 的 `ProjectSidebarTab` 和四组懒加载面板：`src/workbench/explorer/ProjectExplorerSidebar.tsx:42,142-158,320-331`。入口位置已经是左侧栏，问题不在再增加入口，而在每个库的发现规则没有对齐。

| 库 | 当前搜索/分类 | 代码证据 | 缺口 |
| --- | --- | --- | --- |
| 项目库 | 受控搜索只匹配 `project.name`；来源筛选为全部/本地/文件夹 | `src/workbench/library/ProjectLibraryPage.tsx:132-153,327-333` | 没有最近/收藏等统一排序，项目元数据线索有限 |
| 提示词库 | 来源“我的/Nomi 精选” + 图片/视频；关键词匹配标题、正文、来源 | `src/workbench/promptLibrary/PromptLibraryPanel.tsx:58-71,239-249`；`src/workbench/api/promptLibraryApi.ts:117-126` | `tags` 已存在于数据形状，但没有成为筛选或卡片线索；用户库与精选的动作层级不同 |
| 技能库 | 来源“我的/内置”；关键词只匹配 `label` 和 `description` | `src/workbench/skillLibrary/SkillLibraryPanel.tsx:44-59,235-244` | 没有按 playbook/assistant、所需模态、兼容状态分类；用户技能不能编辑资料 |
| 素材库 | 全部/当前项目来源 + 图片/视频/音频多选过滤 + 文件夹；关键词只匹配素材名 | `src/workbench/assets/AssetLibraryPanel.tsx:136-193,526-667`；`src/workbench/assets/assetTypes.ts:214-225` | 跨项目素材可见但默认是预览语义，复制到当前项目的动作需要更明确；文件夹只在项目素材范围生效 |
| 工作流库 | 方案中的全局跨项目条目；名称/描述/标签/结构和素材封面 | `docs/superpowers/plans/2026-08-30-canvas-workflow-plugin.md` | 需和其他库共享检索约定，但复制语义保持独立 |

### 3.1 “概览”不是当前产品入口

代码核对后，当前 `ProjectExplorerSidebar` 的 `ProjectSidebarTab` 只有
`categories | prompt-library | skill-library | asset-library`
（`src/workbench/explorer/ProjectExplorerSidebar.tsx:42`），没有 `overview`。项目库也不是这个侧栏资源 tab，而是 AppBar 的独立“返回项目库”入口（`src/workbench/NomiAppBar.tsx:123-140`）。

因此原型早期出现的“概览”只是为了比较“一个统一入口”与“各自有家”两种布局的演示脚手架，不对应真实功能，也不应作为长期导航项。当前方案明确删除它：用户从已有资源入口找东西；需要跨库快速找时，未来再做一次性的搜索入口，不增加一个空泛的“概览”页面。项目库的返回入口位于 `src/ui/app-shell/NomiAppBar.tsx`，实际页面由 `src/workbench/library/ProjectLibraryPage.tsx` 提供。

## 4. 统一信息架构

### 4.1 入口不合并，检索规则合并

左侧栏仍保留“素材 / 项目分组 / 提示词 / 技能”等现有领域入口。不要再添加一个长期常驻的“所有资源”面板；它会与每个库重复，且在窄侧栏里无法同时表达五种主操作。

每个库统一使用同一个工具区顺序：

1. 搜索框（默认聚焦能力由调用场景决定）
2. 范围：我的 / 内置 / 当前项目 / 所有项目（只显示该库有意义的范围）
3. 高频筛选：最近、收藏、类型/分类
4. 高级筛选：通过“更多筛选”收纳低频字段，不把长尾选项平铺

搜索范围必须始终可见。用户输入关键词后，结果计数、空态和清除搜索动作必须同步变化，禁止出现“看起来能搜但结果不变”的假搜索。

### 4.2 统一卡片信息层级

卡片只回答四件事：这是什么、有什么识别线索、是否可用、下一步是什么。

- 预览：项目/工作流用封面或结构缩略图；提示词用图片/视频封面；技能用能力图标和状态；素材用真实缩略图/首帧/波形
- 标题：名称优先，最多一行，溢出显示完整 tooltip
- 次信息：来源、最近使用、类型、数量或兼容状态
- 描述：可选一行；不要求用户为每个条目填写说明
- 主动作：每张卡只有一个（打开 / 送到画布 / 在创作区用 / 拖拽或导入 / 复制到画布）
- 其他动作：收藏、编辑资料、导出、删除进入 `⋯`，不和主动作争夺视觉权重

### 4.3 画布分组是工作流内容，不是第五个资源库

画布分组已经是 React Flow 画布里的真实组织原语，不能在资源库里另造一份“分组库”。当前实现由 `CanvasGroupProjectionLayer` 投影普通组框和折叠卡片（`src/workbench/generationCanvas/components/CanvasGroupProjectionLayer.tsx:14-67`）；点击组框会选中成员并支持整体拖动，折叠卡片只显示封面/成员数（`src/workbench/generationCanvas/components/GroupFrame.tsx:16-42`；`src/workbench/generationCanvas/components/useCanvasSelectionDrag.ts:191-209`）。选择多个节点后，已有浮条同时提供“创建分组”和“保存为流程”（`src/workbench/generationCanvas/components/CanvasSelectionToolbar.tsx:84-107`），所以用户不需要先进入“概览”再找分组。

设计上的关键是：保存流程时，分组要随工作流快照一起复制，而不是把它当成独立可搜索条目。`NodeGroup` 当前已包含 `name / categoryId / nodeIds / frameBounds / collapsed / inputLinks / outputLinks` 等结构信息（`src/workbench/generationCanvas/model/generationCanvasTypes.ts:186-213`），并且分组的创建、移动、折叠、解组和成员迁移都已经是文档写入（`src/workbench/generationCanvas/events/canvasWriteBoundary.ts:23-29`），有撤销和持久化边界。

第一阶段已经兑现了其中的分组部分：`CanvasWorkflowTemplate` 现在记录完整选中分组、成员关系和相对 frame bounds，实例化时只重建新 id 并把写入交给统一 store action。跨项目素材 bundle 仍未宣称完成：当前 app-level 索引保存的是受校验的画布快照和素材引用，真正的素材物化必须继续沿用主进程资产所有权边界，不能把路径直接交给 renderer。

部分选区的行为需要在实现前锁定：推荐默认只保存用户实际选中的节点及内部边；只有当一个组的全部成员被选中时才携带该组的组框、折叠状态和组端口声明。这样不会因为误选一两个节点就复制出一个残缺分组，同时仍支持用户框选整组后原样复用。若产品希望“选中一个成员也自动带整组”，这是另一条明确的交互合同，不应隐式发生。

### 4.4 详情与素材库的布局调整

详情是对当前条目的确认，不应该把画布或库永久挤窄。因此点击卡片后使用带遮罩的**居中详情对话框**：保留当前库和画布的上下文，关闭只需点右上角、遮罩或 `Esc`；主动作仍在对话框底部，且与卡片主动作一致。只有需要连续对比多个条目时才回到列表，不建立右侧常驻详情栏。

素材库不再使用“一行一个、缩略图统一裁剪”的列表。真实素材按自身比例进入响应式网格：图片/视频保留原始宽高比，音频使用横向波形卡；卡片只保留媒体、文件名和必要的类型线索，点击/拖拽就是主路径，不在每张卡上重复描述、标签、收藏、导入和更多按钮。第一阶段只露出一个与现有 `AssetKind` 一致的类型分类（图片 / 视频 / 音频），不宣称尚未建立索引合同的“人物 / 场景”等语义分类。需要确认时使用现有居中媒体预览，不增加常驻详情栏。

## 5. 各库的分类与搜索合同

分类必须是确定性的索引，不调用 AI 进行猜测。用户可以加标签，但不需要学习 Nomi 的内部格式。

### 项目库

- 默认排序：最近打开
- 筛选：全部 / 本地项目 / 文件夹项目；后续可加收藏
- 搜索字段：项目名、来源路径、用户描述（若未来加入）
- 主动作：打开项目
- 卡片补充：最近打开时间、缺失/不可用状态；不要在卡片上堆模型和成本信息

### 提示词库

- 默认排序：最近使用（精选库仍可按来源保持稳定顺序）
- 筛选：我的 / Nomi 精选；图片 / 视频；已有标签
- 搜索字段：标题、提示词正文、来源、标签
- 主动作：预览后送到画布；我的库保留编辑/删除
- 标签来源：沿用现有 `LibraryPrompt.tags`，不另造第二套分类表

### 技能库

- 默认排序：最近使用
- 筛选：我的 / 内置；Playbook / 助手；文本 / 图片 / 视频能力；可用 / 缺少模型
- 搜索字段：显示名、稳定 `name`、描述、manifest 声明的 provider/type
- 主动作：在创作区用
- 卡片状态：直接显示“可用”或缺少的模态，不让用户点进去才发现不能用
- 编辑边界：第一阶段只编辑名称、描述、标签等资料；技能正文继续通过现有 AI 创建、导入/导出合同管理

### 素材库

- 默认排序：最近添加或最近使用，保留现有确定性时间排序
- 筛选：全部项目 / 当前项目；图片 / 视频 / 音频一个类型分类入口；文件夹仍只在当前项目范围生效
- 搜索字段：文件名、文件夹、来源项目、媒体类型，以及已存在的用户标签
- 主动作按上下文决定：画布侧拖入/预览，时间轴侧追加，跨项目资产在选中状态明确为“导入到当前项目”；不把导入按钮平铺到每张卡
- 跨项目规则：现有 `useAllProjectAssets` 已能枚举所有项目资产（`src/workbench/assets/useAllProjectAssets.ts:89-125`），下一步只需把“预览”和“物化到当前项目”分成两个明确动作，不把项目来源偷偷改掉

### 工作流库

- 默认排序：最近使用
- 筛选：全部 / 最近 / 收藏；节点类型/媒体类型作为确定性分类
- 搜索字段：名称、描述、标签、节点名称、插件 type、来源项目
- 主动作：复制到画布
- 预览：有素材使用素材封面并叠小结构图；无素材退回结构图
- 内容合同：完整节点、边、分组、参数、插件状态和本地素材快照；仅重新生成 id 并重写引用

## 6. 编辑、收藏与版本边界

统一提供 `⋯` 菜单，但不同资源的编辑含义不同：

- 项目：重命名，不改变项目文件
- 提示词：编辑标题、正文、类型、标签
- 技能：编辑资料；正文仍受 skill 包校验和来源权限约束
- 素材：编辑名称、文件夹、标签；删除继续经过现有确认/撤销边界
- 工作流：编辑名称、描述、标签、封面；节点内容必须复制到画布后明确另存或更新

收藏和最近使用应先成为一个**统一的索引字段**，不把所有资源迁进同一个存储。各领域原有存储继续是真相源，库层只维护轻量索引：`itemKind + itemId + favorite + lastUsedAt + tags`。这样可以统一搜索体验，又不会破坏提示词、技能、素材和工作流各自的持久化与权限模型。

## 7. 技术落地边界

### 第一阶段：统一发现，不重做数据层

1. 新建只读的 `LibrarySearchResult` 视图模型和各领域 adapter；它只负责把现有数据投影成 `title / description / tags / kind / scope / updatedAt / capability / primaryAction`，不替换现有 store/API。
2. 抽出搜索归一化、排序、分类计数、空态原因等纯函数，每个库用自己的字段 adapter；保持 renderer 侧轻量过滤，避免把完整 skill 正文或二进制素材塞进全局索引。
3. 抽出共用的搜索框、范围 tabs、筛选菜单、最近/收藏状态和空态交互；外壳复用 `src/design` 现有组件，token-only。
4. 将“当前项目/所有项目”的范围写进卡片和结果状态，尤其修清素材跨项目的“预览 vs 导入”语义。

### 第二阶段：全局快速找（可选）

在四个库的本地检索稳定后，再增加一个 `⌘K`/顶部搜索入口。全局结果按“项目 / 工作流 / 提示词 / 技能 / 素材”分组，每组只显示一个领域主动作；不把五种卡片混成无上下文的单一列表。Agent 若要调用，必须复用同一查找和写入边界，等待 #223 的能力合同稳定后再接入。

## 8. 分层测试与验收

### 纯逻辑单测

- 每个库的 query + scope + category + sort 组合都返回正确结果和计数
- 关键词匹配字段与用户可见字段一致；空结果能区分“库为空”和“筛选无命中”
- 收藏/最近使用索引幂等，删除原条目不会留下可点击的死索引
- 资源类型的主动作映射不会串库（提示词不能误走素材拖拽，工作流不能误走单节点插入）

### 真实用户旅程

- 新项目中搜索并复制一个跨项目工作流，节点/素材出现且可一次撤销
- 在节点里搜索一条提示词，预览后送到画布并能继续编辑
- 搜索一个缺少图像模型的技能，用户在卡片上直接看到不可用原因
- 从全部素材中找到上一项目的参考图，明确导入当前项目后再拖到画布
- 项目库输入关键词、切来源筛选、清空搜索，结果和空态始终正确

### 风险分层

本方案先改检索和 UI 信息架构，不改变生成、媒体编码或大图处理路径，因此不机械执行全量性能基准。若后续全局索引触及跨项目资产扫描或持久化格式，再单独留下索引耗时和内存基线。

## 9. 不做与回滚

- 不做一个常驻的超级资源库页面
- 不把所有资源搬进一套新数据库
- 不用 AI 自动猜分类，不要求用户按 Nomi 格式重写资料
- 不增加任意脚本、远程加载器或宽泛 Electron API
- 不改变 Agent/MCP/Skill 的能力准入边界

第一阶段可以按“搜索/筛选纯函数 → 共用工具栏 → 各库卡片信息 → 索引持久化 → 全局快速找”的顺序逐步落地。任何一步回滚都只撤该库的 adapter/UI，不影响原有资源文件、画布数据和项目存储。

## 10. 与工作流方案的关系

工作流库是本方案中的一个资源域，但它的“复制到画布”是唯一不可泛化的主动作：完整快照跨项目物化、插件占位、撤销/重做和素材所有权继续遵循 [原生画布插件与固定流程 ADR](../superpowers/specs/2026-08-30-canvas-workflow-plugin-adr.md)。本方案只统一它的发现和资料编辑体验，不改变复制语义。

本轮的代码盘点、分组关联 ID、现有模板缺口、资产所有权和定向测试记录见 [画布分组与工作流库代码盘点](../research/2026-08-30-canvas-group-and-library-code-audit.md)。它是实现前的基线证据，不是生产实现承诺。

本轮设计与用户旅程复审见 [资源库样张设计复审](../research/2026-08-30-library-design-review.md)：素材库收敛为“看图、认出、拿走”，只保留真实媒体、文件名和少量分类入口；详情在需要时居中打开。

- `?variant=1&library=workflow`：独立资源页，用于一次整理或批量浏览。

可点击验证：点击卡片看详情，素材详情只保留媒体预览和一个上下文动作；其他库可点击 `⋯` 编辑资料或收藏。搜索 / 最近 / 收藏 / 类型会立即改变对应库结果，素材改为分类 chips。工作流的主按钮会反馈“节点和素材保持不变”。样张只验证信息架构和交互语言；分组随工作流快照复制、素材物化、撤销/重做等行为仍以生产代码合同和测试为准。

## 12. 方案、原型、生产实现的边界

这三件事分别回答不同问题，不能相互冒充：

| 交付物 | 要回答的问题 | 本轮对应内容 |
| --- | --- | --- |
| 方案 / ADR | 用户为什么需要、数据和所有权合同是什么、哪些事情明确不做 | `docs/superpowers/specs/2026-08-30-canvas-workflow-plugin-adr.md`、本文和代码盘点报告 |
| 原型 | 用户能否看懂入口、搜索、预览、复制和编辑资料；布局是否符合设计系统 | `docs/prototypes/library-discovery.html`，只读、可点击、可切换三种布局 |
| 生产实现 | 真实数据是否经过现有 React Flow/store/bridge、能否保存恢复和撤销 | 第一阶段已开始：工作流库通过左侧侧栏接入，保存写入项目快照与 app-level 本地索引，复制调用统一 store action 并携带分组；素材 bundle 与其他库 adapter 尚未开始 |

因此当前浏览器里看到的页面只证明交互方向。第一阶段生产切片已把工作流库接入真实左侧栏、全局本地索引、资料编辑和 React Flow 的分组/撤销复制；跨项目素材 bundle、其他资源库的统一索引和端到端真机旅程仍需按本文边界继续验收，不能提前宣称已完成。
