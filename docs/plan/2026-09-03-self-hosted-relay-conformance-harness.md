# 自建中转一致性台架：把「用户接入」这条路接上反馈回路

> 📋 方案待拍板
>
> 日期：2026-09-03 · 分支：`claude/relay-real-probe` · 触发：2026-09-03 真中转付费实测挖出四连环（`docs/fixes/2026-09-03-relay-multipart-image-edit-certification.root-cause.json`）
>
> 用户拍板要求：「最大程度上解决用户的问题，除非有些我们完全没法控制」。本方案据此把边界划在**我们能控制的那一侧**，并明确写出控制不了的部分。

---

## 1. 为什么要做：一条没有反馈回路的路径

| | 我们策展的模型 | 用户自建中转 |
|---|---|---|
| 谁在跑 | 我们天天跑、天天看 | **只有用户**，且在我们没有的配置里 |
| 出错多久被发现 | 快 | **可以很久，而且是静默的** |
| CI 覆盖 | 契约测试 + loopback + 走查 | **零** |

2026-09-03 实测证实了这条推论：任何经自建中转接入的 `gpt-image` / `dall-e-2`，**改图通道 100% 是坏的**，而 app 还告诉用户「这个模型没有图生图通道」。四个 bug 串成一条，全部只能靠真人拿真 key 去撞才会暴露。

**这条路径恰好是产品价值的入口**（用户接自己的 API），也恰好是我们自己 dogfooding 的盲区。两件事重合，价值就在无声中流失。

## 2. 先否掉一个更漂亮但没用的方案

曾考虑「让能力声明由认证实测产生」（把成功请求的形状固化成声明）。拿它对四个 bug 逐条检验：

| bug | 该方案能挡吗 | 为什么 |
|---|---|---|
| 1 用错端点族（聊天接口发改图） | ❌ | 请求**从未成功过**，没有实测可 derive |
| 2 漏声明参考参数 → 探针没注图 | ❌ | 探针没注，就没有可观测的东西 |
| 3 multipart 忽略注入的读取器 | ❌ | 基建缺陷，与声明无关 |
| 4 夹具 2×2 被真端点拒 | ❌ | 测试数据缺陷 |

四个都挡不住。**共同点是它们不是「声明漂移」，而是「我们真发出去的请求本身就错」——只有真发一次才抓得住。**方案作废，理由记此以免重提。

（「声明与实测对账」本身仍有价值，但属独立议题，不在本方案范围。）

## 3. 做什么

**在 CI 里起一个严格的假中转，驱动真实的接入 → 认证 → 生成全链路。**

两块现成积木，从未接在一起过：
- `electron/catalog/falLoopback.integration.test.ts` —— 起本地 HTTP server 冒充供应商，驱动**真运行时**
- `electron/providerAdapter/ipc.test.ts` / `existingConnectionIpc.test.ts` —— 从 vitest 直接驱动**真认证 IPC handler**

### 3.1 唯一的关键设计约束

> **假中转必须是「严格的」，不是「配合的」。**

一个宽容的假中转会把这四个 bug 全部放过去——那正是本仓反复栽的「假绿」。**真中转当初怎么拒我们，假的就必须怎么拒。**

四条拒绝规则直接来自 2026-09-03 真机实测（`otokapi.com` / `gpt-image-2`），不是臆造：

| 规则 | 真机证据 | 抓住哪个 bug |
|---|---|---|
| 用 `/v1/chat/completions` 发图像编辑 → 400 | 真机原文 `This model is not supported on the Chat Completions endpoint` | 1 |
| `/v1/images/edits` 收不到图片文件 → 400 | 改图端点必须有 image part | 2 |
| 图片短边过小 → 400 `invalid_image` | 实测 2×2 → 400，256×256 → 200 | 4 |
| multipart 必须真收到文件**字节**（非 URL 字符串） | 真机 multipart 契约 | 3 |

**验收要求（R17）**：每条规则都必须先证明「把对应修复回退掉，这条规则会让测试红」。没验过红的规则不算数。

### 3.2 范围：两步走

**第一步（本方案落地范围）——把已知真机行为固化**
- 假中转实现上述四条严格规则 + `/v1/models`、`/v1/images/generations`、`/v1/images/edits` 三个端点
- 驱动真实认证入口（`nomi:integration-certification:http:configure` → `...:http:existing:start`）
- 断言：认证后 `image_edit` mapping **确实落库且 enabled**；生成时参考图**确实进入报文**
- 立刻获得的回归价值：这四个 bug 任何一个复发，CI 当场红

**第二步（增量，本方案定义边界不实现）——形状矩阵**
覆盖用户可能造出的接法：零 mapping / 无 modeId 单端点 / chat 协议改图 / multipart 改图 / 进程型 transport。每种形状跑同一套断言。

## 4. 我们控制不了的部分（明确写出，不假装覆盖）

- **供应商单方面改契约**：某家突然改参数名/端点，假中转不会知道。→ 缓解：偶尔用真 key 实测（本次已建立该做法）+ 已有的 `radar:models` 雷达。
- **用户中转的私有魔改**：有人自己改了转发逻辑。→ 不可控，但第三闸（发送前拒发）与失败文案已能诚实报错。
- **付费产物质量**：假中转不产出真图，证不了「参考图真的影响了产出」。→ 只能真机封印，已记入各模型认证台账。

**本台架只承诺一件事，但要做到极致：凡是「我们自己写错」的，必须当场红。**——这次四个 bug **全部**属于这一类。

## 5. 不动项 / 回滚 / 验收门

**不动项**：不改任何生产逻辑（本方案纯粹是加测试台架）；不动认证落库契约；不碰真供应商配置。

**回滚**：删测试文件即可，零生产影响。

**验收门（缺一不可）**
1. 四条严格规则**各自**验过红（回退对应修复 → 该条红；恢复 → 绿）。
2. 假中转对「正确请求」放行，全链路能走到 `image_edit` mapping 落库且 enabled。
3. `pnpm run gates` 全绿。
4. 台架**不联外网**（`hardenedFetch` / `networkHostPolicy` 允许 loopback；CI 无外网也能跑）。
5. 运行时间可接受（目标 <30s，与既有 loopback 测试同量级）。

## 6. 为什么这能「以后不再发生」

不是因为我们更细心了，是因为**那条唯一没有反馈回路的路径被接上了回路**：每次提交都以用户的身份走一遍接入，且假中转的严格程度锚定在真机实测上。

声明与现实的任何分歧，当场红。
