- **OpenAI 现行错误码页** · [Error codes](https://developers.openai.com/api/docs/guides/error-codes)（2026-11-22 现场抓过）：429 分三种——`credit_balance_exhausted`（预付额度用完，加额度）、`organization_spend_limit_exceeded` / `project_spend_limit_exceeded` / `organization_usage_limit_exceeded`（限额到了），以及 `rate_limit_error` / `slow_down`（真限流，按 `Retry-After` 等）；原话「For billing-related errors, inspect `error.code` … The broader `error.type` can still be `insufficient_quota`」「Retrying billing, spend, or quota errors won't restore API access」。 · **改了**：429 不等于可重试，`type: insufficient_quota` 这一族必须不重试；「额度用完」和「限额到了」用户要做的事不同，现有词条只有「余额不足」一种（问题 h）。
- **APIMart 自己的说法** · 上传文档（`uploads_images.md:198-206`）原话「Inspect the HTTP status, `error.type` / `error.code`, and `error.message`」，402 的标识放在 `error.type`（`insufficient_user_quota`），429 分 `rate_limit_exceeded`（共享文件额度用完，看 `Retry-After`）和 `rate_limit_error`；文本 402 文档是 `type: payment_required`（`llms-full.txt:93`）。 · **确认了**归一必须读 `type`，只读 `code` 会漏掉 APIMart 的两种形状。
- 出口：new-api `service/billing_session.go:402-412`（余额不足带 `ErrOptionWithSkipRetry`）与 pi `utils/retry.js:4-19`（账单 / 额度类不重试）· 别人对「余额不足」的处理都只是**这一次不重试**，不锁账户、不挡下一次：充值后下一次请求照常 · **确认了**我们的出口：本刀不新增挡人的东西，停只停在本轮——`electron/agentLane/laneTurnBudget.mts:44,65`（#1532 已合入 main `618485aec`，与分支版逐字相同）在用户下一条消息时复位，被停的那一轮由 pi 的 `requestAbort` 收成「已取消」；用户充值或换模型后发下一条消息就照常。

## ★1 用户怎么用

**当**创作者让 Agent 拆镜头、或在画布上点生成，而账户余额不够这次请求被预扣的量，**我想**第一次就看到「余额不足」和能做的事（充值 / 换模型），Agent 不再替我重发，**以便**不去查一把没问题的 Key、不等四倍的时间换同一个结果。（「每次请求都带上限、预扣按这次最多写多少算」是「S4-上限」那一刀的事。）

1. 创作者在面板里发一句话；
2. 余额不够 → 上游回 402 / 403 / 429 + 余额码 → 归一成余额不足，不重试；
3. 面板那一行说余额不足（现有词条）；本轮结束；
4. 画布节点失败卡显示余额不足（不再是「API Key 无效」）；
5. 创作者充值或换模型 → 发下一条消息 / 再点生成，照常；
6. 模型写一条工具调用写到一半撞了输出上限 → 这条半截的调用不执行，本轮以一条失败收尾（面板走通用兜底那句，措辞留给界面文字那一刀）。

## ★2 谁说了算

- 「上游这次失败算哪一类、能不能重试」→ 唯一 owner `electron/shared/vendorFailure.ts` 的 `categorizeVendorFailure`（状态码 + 上游自己给的 `error.code` / `error.type`）；消费者只读 `VendorRequestError.structured`。改前同一事实 4 处在判：`categorizeVendorFailure`（只看状态码）、`detectBalance`（文字）、`detectLegacyErrorKind`（文字）、`laneProviderGuard` 正则表（文字）。本刀后：有 HTTP 结构的失败只由那一张表判；认字的只剩「没有结构」的输入（`laneProviderGuard` 余额那行只管无状态码的失败；`detectBalance` 在 `decideGenerationFailure` 里排在结构类别之前，等 S7 删）。保持「1」的办法：三扇门都把响应体交给同一对取码（`pickUpstreamCode` / `pickUpstreamType`）再交那张表，往外只给结构；上传那扇门不再只把状态码拼进句子（改抛 `VendorRequestError`）。门表：`node scripts/door-map.mjs categorizeVendorFailure` 3 扇、`createNomiProvider` 2 扇（`laneHost.mts:195`、`laneModelCall.mts:34`），存 `door-map.txt`。
- 「pi 重不重试」→ owner 是 pi（`utils/retry.js`），它没有开关；我们唯一的口子是 `errorMessage` 结尾的标记，写标记的只有 `laneProviderGuard.withClassifierMarker` 一处（provider 层按结构调它，守卫按文字调它，结尾已有标记就不再贴）。
- 「这条回复的工具调用能不能执行」→ owner 是 pi harness；我们在 provider 层把「写满上限的半截工具调用」改成失败，判据直接用 pi 的 `isRecoverableLength` 和 pi 判溢出用的同一个数（这次请求的模型 `maxTokens`），不自造第二个阈值。
- 「这一轮停不停」→ owner 是 #1532 的 `laneTurnBudget`，本刀不碰。大脑那一条失败由 pi 自己收尾（它不重试就结束）。

## ★3 一致与复用

- 以前定过什么：见文首「已拍板」「已定」；11-08 方案 S4（本卡核对后的出入在文末）。
- 三条路（余额不重试）：
  - **沿原方向修**：往 `laneProviderGuard` 的余额正则里再加词（`quota`、`pre-consume`…）。不行：403 + 余额码这一族的正文各站不同（中英两模板、one-api 不带数），认字永远追不完，而且会把「403 无权访问」之类误认成余额。
  - **换做法（采用）**：三扇门都读上游自己给的 `error.code` / `error.type`，一张表判类；大脑那条按结构类别贴 pi 认得的标记。
  - **删掉**：删掉余额正则、什么都不贴。不行：pi 会按「500」子串把余额失败重试 3 次（第 16 行实测 4 次请求）。
- 三条路（截断的工具调用）：沿原方向 = 交给 pi（它会执行补全过的半截参数）；换做法 = provider 层改成失败（采用）；删掉 = 不发上限（那是「S4-上限」的事，而且上限总会撞到）。
- 归一：复用现成的 `VendorRequestError` / `categorizeVendorFailure` / `decideGenerationFailure`，不新建分类器；不按供应商写分支，读的是错误对象的通用两格（`code` / `type`），余额词表每个词带出处。
- 不重试：复用 pi 自己的不可重试表（追加它认得的词），不自写重试。
