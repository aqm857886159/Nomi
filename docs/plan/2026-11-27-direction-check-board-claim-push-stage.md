### 0. 一句话根因

门岗在推送档执行了合并档的判据：规矩是「只有不写实现的线才把元素翻成 implemented」，门岗却在实现线推送时就要求 implemented，实现线只剩两条路——自己翻（自盖章）或者绕开门岗。

### 2. 为什么这一类会一直出现

这条判据 10-10 随拍板图门岗第一版写下（`244390b18`），当时实现线可以自己翻 implemented。11-16 规矩改成「另一条线核过才标已实现」，门岗没跟着分档。同一个文件里另外两项「推送时还不可能满足」的判据——独立验收报告链接（`scripts/pr-body-criteria.mjs:142`）、未兑现承诺（`scripts/pr-body-criteria.mjs:434`）——早就是「推送档只提醒、PR Body 检查与合并前扫描判红」，只有这一项漏了。

三条体验铁律：不适用（门岗流程，不碰产品的参数、档案或点击结果）。

### 4. 靶子独立性检查

- 「implemented」就是验收的靶子，应由不写实现的线设。现状逼实现线自己设，等于出题人和答题人是同一条线；这一刀恢复独立。
- 没有「修对了反而掉分」的先例。

### 5. 这一整块归谁（P0）

这一整块：PR 正文判据在推送档和合并档之间的分档。
归谁：我们唯一的主人 `scripts/pr-body-criteria.mjs:497`（`evaluatePrBody` 的 `stage` 参数），分档口径的先例在同文件 `:142`、`:162`、`:434`。
我们哪里绕开了它：`scripts/pr-body-criteria.mjs:542` 调 `checkBoardClaim` 时没有把 `stage` 传进去，`scripts/check-board-parity.mjs:673` 因此在推送档也判红。

自写登记 `gate-family`（under-review）：PR 正文判据管的是我们自己的交付流程（拍板图认领、独立验收、逃逸账本），没有现成的库能接；这一刀不新增门岗，只把一项判据接回已有的分档口径。

### 6. 三条路对比表 + 推荐

| 选项 | 做什么 | 代价 | 选了以后同一类还会不会出现、从哪出现 | 风险 | 推荐 |
|---|---|---|---|---|---|
| 沿原方向修 | 实现线推送前自己翻 implemented，验收不过再翻回去 | 每条照板实现线都自盖章 | 会，每条照板实现线都会 | 没核过的元素以 implemented 进 main | |
| 换一种做法 | `checkBoardClaim` 收 `stage`：推送档只把「还在等验收」的 `missing` / `in-progress` 收进提醒，合并档（PR Body 检查、合并前扫描）照旧判红；其余认领错误（不在清单、空认领、板不存在、缺用户原话的 deferred / dropped、非法状态）推送档照旧红 | 推送档少一道红，CI 的 PR Body 检查红到验收线翻状态为止 | 不会：所有判据都按同一个分档口径 | 低：合并前仍判红 | ✅ |
| 删掉 | 最小能删的单位：删掉推送档的拍板图认领核对，只在合并前扫描查 | 写错元素 id、认领不存在的板要到合并前才发现 | 不会，但早发现的价值丢了 | 中 | |

### 7. 用户要权衡的核心

推送时少一道必然的红，换来实现线不再自盖章；合并前照旧严。
