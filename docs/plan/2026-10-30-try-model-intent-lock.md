# 试跑的持久意图锁：设计卡

负责人：试跑防重实现线。类别：花钱、长跑；纯逻辑修复，无新界面。状态：方向已获批准，产品实现与自动测试已落地；完整门岗与真实应用演练结果见文末。前九格保留动手前合同。

## ★0 先查别人（2026-10-30 实查原文）

| 出处 | 它怎么做 | 对本次决定的影响 |
|---|---|---|
| [支付 API 幂等请求](https://docs.stripe.com/api/idempotent_requests) | v1 执行开始后保存同键响应，包括失败；参数不一致拒绝；键清理后重用会创建新请求 | 确认：未知订单不按超时自动过期；身份与请求指纹分离，改参数不是新意图授权 |
| [云 API client token](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html) | 同 token 重试不再创建资源，参数改变返回不匹配；token 有明确资源作用域 | 确认：宿主名、调用 id、prompt hash 不能当付费意图；作用域应由主进程统一认领 |
| [HTTP Idempotency-Key 草案 -08](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-08) | 在途重复应冲突，完成后应返回一致结果；客户端不能假定服务端支持该头；仍是工作草案 | 确认：本地先落意图再出站，不凭 request-id 或协议名称重发未知 POST |
| [Agent 工具设计](https://www.anthropic.com/research/writing-tools-for-agents) | 返回有意义上下文，并用真实多轮任务测工具选择和结果 | 确认：回执要有 intentId/attemptId/phase/allowedActions，不能只写 nextAction |
| [MCP 分页规范](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination) | 不透明 cursor，缺 nextCursor 才结束 | 不适用分页：本次单订单回执，不新增列表或工具动词；保持原工具注册顺序 |

逐层对照：身份键与请求指纹分离、持久记录先于提交、重复返回原结果与上述合同一致。有意不同：上游无明确幂等契约时本地拒绝再发，而非网络重试；不能承诺远端 exactly-once。没有把上游的键保留时限照搬为本地未知订单释放时限。工具 schema、profiles 和注册顺序不变；结果层新增结构需由同一事实投影给 Agent 与现有用户动作。已读模型可见工具清单及 pi 逐层对照报告；不把工具 UI 状态复制进聊天。

## ★1 用户任务、指标与连带面

当创作者让 AI 接入并试跑模型、提交回执丢失时，我想再次询问仍拿回原单，以便核对而非重复下单。流程：保存声明 → 用户在现有钱闸授权 → 认领稳定意图和 attempt → 持久化后只提交一次 → 超时返回原身份与未知状态 → 再调只读原单 → 有句柄只取回 → 明确拒发证据才给有界重试。

真实任务形态：自定义异步视频模型回包延迟；换 Agent 宿主重问原单；改声明后核对原单。真实账号、素材、付费均未使用，保持 unverified。本次不实现视频协议、二进制取回、新界面或通用工作流框架。

目标 → 信号 → 指标：避免重复提交 → 环回供应商收到的 POST → 同意图重复创建率 0（量具：现有 tryModelSubmitBudget.test.ts 增加重复调用断言）；回执可恢复 → 重启后身份一致 → 原单回收率 100%（计划量具：跨实例/进程隔离测试，尚未实现）；护栏 → 缺证据不放行 → 参数变化、改卡、并发矩阵所有用例 POST ≤1（同上）。当前基线将由红测实测，不编数字。真实模型工具写对率、回合成功率未验证：缺本轮真实模型量具。

★1b：Agent 回执、任务读取、现有恢复按钮必须读取同一个 allowedActions 投影。未知仅核对，有 taskId 才查/取回；不能出现工具禁止但按钮允许重生。现有中英恢复文案复用，禁止仅改英文 nextAction 宣称完成。

## ★2 状态主人

付费意图、attempt、受理事实归主进程耐久 Run/submission 设施；renderer、内部 Agent、MCP 只读投影。试跑缺的是跨调用到耐久身份的认领，不是第二套 outbox。现有 readCatalog 模型身份不包含原单；卡 revision 和参数不应自动换身份。新的用户新单授权必须显式，不能从模型不存在、参数改变、任务失败猜测。

`node scripts/door-map.mjs tryModel`：1 写/0 读/1 总门，dispatch.ts；`createSubmissionOutbox`：2 写/1 读/3 总门，generationSubmission.ts、productionGenerationSubmission.ts、submissionOutbox.ts。该计数是符号直接调用门数，不相加冒充端到端路径数；已向上检查 dispatch、向下检查 runtime 与 Run-owned wrapper。

## ★3 一致与复用

复用 productionRunRepository、productionRunLock、productionRunIntentLog、submissionOutbox 及 runtime envelope；出站失败证据复用 outboundDispatchEvidence，钱闸复用 spendDecisionByPolicy/spendGrant。删掉每调用自动 mint 新 node/grant 的语义，禁止另建试跑 outbox。当前 wrapper 要求已有 Run/job/approval，不能直接拿 vendor/model 填上就视为接入；认领与同源投影尚缺，热点方向复核前不实现分支。

## ★4 全状态合同

| 状态 | 回执和允许动作 |
|---|---|
| 空 | 无订单，沿现有钱闸请求确认 |
| 提交中 | 返回同 intent/attempt，观察；不再创建 |
| 结果未知 | 返回原单，人工核对；不再创建、不以超时解锁 |
| 已受理 / 取回中 / 部分成功 | 返回原句柄，仅查询或取回，不发 create |
| 成功 | 返回原产物；再次有意生成必须显式新授权，不能永久按 prompt hash 合并 |
| 明确拒发 / 从未发出 | 依据共享证据给有界重试；不能无限每调用补一次 |
| 受理后失败 / 取消中 | 原单与证据保留；不得当作从未提交 |
| 过期 | 宿主超时与授权过期均不删除原单锁 |
| 能力不可用 | 保留原单并引导查询/核对；没有句柄则人工核对，不伪造取回能力 |
| 记录读不出来（损坏、形状不认识、缺文件） | 普通调用不下单、不抛裸错；回执 `code=submission_unknown`、`accepted=unknown`、`allowedActions` 只有核对类动作和 `request_new_attempt`、`newAttemptRequiresUserConfirmation=true`、`recordDamage` 写明哪里读不出；不知道有没有扣钱 |
| 坏记录上的显式新单 | 在认领租约内把坏记录整个挪到一边（不删），基于干净记录开新单，`spendDecidedBy` 强制 `user`，走现有确认卡；全自动档绕不过；不需要用户删文件或换连接 |
| 挪走后、新单认领前崩溃 | 「这里有过一笔坏记录」活过崩溃：普通调用仍只回未知，全自动档也不发；显式新单可继续 |
| 上一笔结果不确定时开新单 | 确认卡的 message 写明「上一笔结果不确定，不知道扣没扣钱，再试可能多扣一次」（中英）；记录完好但结果未知时用同一句；安全重试继承这句话 |
| 新单开不出来（磁盘、锁、改名失败） | 回执明说这次什么都没发、原单状态不变、可以再调；不能冒充旧单的未知结果把失败盖住 |

## 5 中途表

所有格的扣费事实均以供应商回执/对账为准，不声称停止或关窗等于退款。

| 状态 | 停止 | 关窗 | 断网 | 重启 | 连点/跨宿主 |
|---|---|---|---|---|---|
| 未授权 | 保留草稿，无提交回执 | 同左 | 同左 | 同左 | 同钱闸 |
| 提交中 | 原单观察，可能受理 | 原单持久，可能受理 | 原单未知，可能受理 | 读原单，可能受理 | 返回原单，可能受理 |
| 未知 | 原单核对，可能受理 | 同左 | 同左 | 同左 | 同左 |
| 已受理/取回中 | 原单留存，受理事实保留 | 同左 | 仅恢复取回，受理事实保留 | 同左 | 同左 |
| 成功/受理后失败 | 回执留存，不自动重生 | 同左 | 同左 | 同左 | 同左 |
| 有未发出证据 | 回执留存，无该次提交 | 同左 | 同左 | 重试预算仍持久 | 同一有界预算 |

## 6 外部失败与依赖

外部来源为上游 HTTP/任务状态和用户声明。按 ★0 标准保留身份；上游未声明幂等则未知不可重发。只接受共享出站证据证明未发出/明确拒发，泛化 Error、HTTP 5xx、无资产、断线都不能释放。依赖生命周期：not-applicable，本修复不增加/升级运行时框架；通用执行选型另行处理，本次只对齐已有耐久门。

## ★9 动手前验收与反例清单

1. 红测：环回服务已收到一次 create 后掐线，工具回 submission_unknown；同参再调，预期 POST 仍 1，当前应红。再用不同 prompt/params 重调同意图也须保持 1。
2. 同进程并发、两个独立宿主、进程重启：同一未结意图返回同 intentId/attemptId，create 总数 1；不是只检验内存 Map。
3. 提交中、unknown、accepted、retrieving、取回失败、成功分别测试；晚到 taskId 持久化到原单，不能留孤儿单。
4. 改参数、taskKind、重交卡、修订号变化、授权过期不清未知锁；旧数据缺受理证据按未知封闭处理。
5. 缺 key、用户拒绝、明确拒发、从未写出证据分别测试有界预算；普通网络错误、5xx、落地失败不得释放；跨重启不刷新预算。
6. Agent code/phase/accepted/allowedActions 与按钮判据逐项对账（⑫点了=以为的）；⑩不改冻结请求；⑪不改模型可选参数。
7. 有意新生成不得被 prompt hash 永久合并；必须显式新单授权，与旧未知单隔离，不由 Agent 换参隐式创建。
8. 删锁反例：临时移除共享认领，原样重跑第 1/2 项必须红；恢复源码后绿。未实现前不能把当前缺锁基线当作已完成 mutation 验证。
9. 根因合同 schema v3、candidate 逃逸账、结构预防闭环；门岗与快检退出 0。独立验收由协调另派，未完成，不伪造验收线。
10. 付费确认：专用工作树构建含字面标记 `try-model-intent-lock` → 共用步骤零费演练 → 单次真实提交 → 强制等待预算先回未知 → 重复调用与换参 → 原单取回 → 核账只有一笔。预计支出只在私有交接报告写；无脚本/标记/演练则不跑。
11. 读不出来不等于没有单子：`run.json`、`events.ndjson`、`runtime.json` × 缺失、截断、乱码、旧形状（缺 `schemaVersion`），普通调用、换参调用、新进程重启后再调都不下单、不抛裸错，回执字段见 ★4，坏记录字节不变。
12. 显式新单走得通：同一批记录 × 确认、拒绝、全自动档、窗口不在，确认后 create 恰好多 1 笔，拒绝和窗口不在时 create 不变；新单 `spendDecidedBy=user`，拒绝后转全自动也绕不过；坏记录挪到一边且字节不变。
13. 确认卡明说：上一笔结果未知（记录坏或完好）时开新单，确认卡 message 有那句话，中英都有；不新增组件、不改布局，只用 `SpendConfirmDialog` 现有 message 行。
14. 给出去的动作走得通：回执里每个 `allowedActions` 在每一种状态下真走一遍，都不能是死路；新单开不出来时回执说清楚，不能拿旧单未知盖住。
15. 崩溃窗口：首次认领、完好未知单开新单、坏记录开新单，每一步读者看得出差别的落盘之后都真杀一次进程（`process.exit(137)`，不跑 finally），重启后普通调用不下单（全自动档也不下；只有还没有任何单子的首次认领可以继续），显式新单还能完成，且只多一笔，坏记录字节还在。
16. 并发：两个进程同时对同一条坏记录开新单，只成一个，另一个看到新单；同时做首次认领也只成一个。认领租约不在要挪的目录里。
17. 挪走的目录不再被 `read` 读到；新 attempt 不和被挪走的撞名；旧 approvals 留存不触发 `Approval id conflict`，也不能变成绕过确认或多发。
18. 反例（都真跑、都按字节还原）：① 只删 `if (previous && !explicitNew && !retry) return { owned: false as const, receipt: previousReceipt! };`，矩阵防重格红，两个独立意图阳性对照绿；② 把读不出来当成没有单子，矩阵坏记录格红；③ 挪走改成删除，字节格红；④ 显式新单不强制 `user`（认领和 `tryModel` 两处一起去掉，只去一处另一处还兜着），全自动格红，拒绝后转全自动的安全重试会直接下单。
19. 真付费路径同样先回未知：共用步骤强制第一笔先回未知，断言不分演练和付费；零费演练走同一段步骤。真 Electron 演练：先弄坏记录 → 普通调用不下单 → 显式新单 → 中文确认卡看得到那句话，确认后 create 1 笔；英文确认卡同样，取消后 create 不变。

## 裁定后的实现合同补充

用户批准按推荐实现。应用级试跑按连接 + 模型认领同一 Run（不含 prompt、模式、参数或卡修订）；应用设置根内的 app-executions 使用原 productionRunRepository 的 .nomi/runs 布局，没有另建 outbox。先落 job 与冻结请求，再异步问人/出站；已存在的 authorized job 也不自动接管重发（覆盖崩溃窗口）。

newAttemptOf 必须引用当前 attemptId；重复引用旧 attempt 不再创建。新单的真人确认标记由共享认领边界强制持久保存，安全重试继承它，不能在拒绝新单后转用全自动绕过。未发出/明确拒发每条谱系最多一次跨调用重试；试跑把共享 outbox 的内调用安全重试关闭，防止预算分散计数。Agent allowedActions 与是否允许再次走确认卡来自同一持久记录及 submissionActions。

删认领反例已实跑；同参、换参两项及共享矩阵重新失败。最终数量和恢复校验随最后一轮复核记录，不能用早期数量替代。两份源文件已按字节恢复，SHA-256 记录在私有交接报告。无产品截图新增需求；确认卡复用原组件，零费演练核中英文及重启，不用新 UI 替代。


## ★9 执行矩阵（补齐跨边界验收）

| 持久状态 / 反例 | 同调用在途 + 后续调用 | 独立宿主并发 | 服务重建 / 进程重启 | 判据 |
|---|---|---|---|---|
| authorized（认领后崩溃窗口） | 保留原 attempt | codex / claude / restart 三子进程 | 同一磁盘根恢复 | 不接管出站 |
| submitting（40 秒预算先返回） | 原单、晚到句柄写回原单 | 同上 | 同上 | create ≤1 |
| submission_unknown | 同参、换 prompt/params/taskKind 不解锁 | 同上 | 同上 | 原 intent/attempt，禁止 retry |
| accepted / retrieving | 仅 GET 查询或取回 | 同上 | 同上 | 原句柄、原冻结请求 |
| materialized | 返回原产物 | 同上 | 同上 | 不计第二笔 billable request |
| 从未发出 / 明确拒发 | 同一谱系最多一次安全重试 | 预算耗尽后子进程仍拒开 | 预算落盘不刷新 | 第三次无新 job |
| HTTP 503 / 409 / 已带 taskId 的失败 | 不放行 | 共享持久判据 | 共享持久判据 | 不出现 retry |
| 受理后落地或下载连接失败 | 保留 accepted | 共享持久判据 | 共享持久判据 | 不因最后错误解锁 |
| 已交 POST 后抛 RendererUnavailable 字样 | 保留 unknown | 共享持久判据 | 共享持久判据 | 用整次交接账，不匹配文案 |
| 卡修订、模式变更、参数变更 | 原单先于卡和参数验证返回 | 身份不含宿主 | 身份不含修订号 | 原始 POST 总数 1 |
| 显式 newAttemptOf | 新 job 强制真人确认 | 旧引用重放返回当前单 | 新单确认谱系落盘 | 拒绝后也不能切全自动绕过 |
| 存储损坏 / 缺记录 | 封闭，不推断新意图 | 共用同一记录 | 重启仍封闭 | 不新下单 |

主量具：submissionIntent.test.ts 的真实子进程 + tryModelSubmitBudget.test.ts 的真实环回 POST；独立 Electron 演练通过两个真实 MCP 连接、既有中文确认卡、原产物导入和应用重启核实。脚本宿主不是实际模型，工具选择正确率仍未验证；真付费、Windows 和独立验收交协调。

## ★9 类级清单与首次交付补验

|---|---|---|---|---|
| same-arguments | 已受理 | 同参再调 | 1 | 原 intent/attempt |

## 恢复出口合同（2026-10-31，第 1 次独立验收不通过后；用户原话「修完再合」）

**类根因：** 安全封闭只想到挡自动重发，没给人工留出口。试跑身份是「连接 + 模型」算出的固定路径，记录一坏，这条路径就永远读不了；`tryModel` 和共享认领都在任何异常处理之前先读旧单，所以连显式新单也到不了真人确认。

**类合同：**

1. **读不出来，不等于没有单子，也不等于可以自动发。** 判定放在意图层：记录损坏、形状不认识、缺文件时，普通调用（没有 `newAttemptOf`）不下单、不抛裸错，回执见 ★4。
2. **显式新单走得通。** 坏记录挪到一边，不删，留作诊断；新单基于干净的记录，`spendDecidedBy` 强制 `user`，走现有确认卡；全自动档（direct）绕不过；不靠用户手工删文件或换连接。
3. **确认卡要明说。** 上一笔结果不确定时开新单，确认卡 message 写「上一笔结果不确定，不知道扣没扣钱，再试可能多扣一次」，中英都有；记录完好但结果未知时开新单用同一句。只用 `SpendConfirmDialog` 现有 message 行，不新增组件、不改布局。
4. **给出去的动作一定走得通。** `allowedActions` 里每个动作，在每一种状态下真走一遍都不能是死路；新单开不出来要明说，不能拿旧单的未知盖住失败。

**怎么落：**

| 决定 | 做法 | 为什么 |
|---|---|---|
| 什么算读不出来 | `events.ndjson` 解析不了、形状不认识、比快照或任务目录旧（尾部丢行）或缺失；`run.json` 在但校验不过；最后一笔的 `runtime.json` 坏或缺；`approvals.ndjson`、`budget-ledger.ndjson` 解析不了；数据全没了但还有 `quarantine`、开单痕迹或旁账残留 | 下一次认领和提交要读的东西，一处读不了就走不通。`run.json` 单纯缺失不算：它能从事件重建，崩溃窗口里本来就可能缺 |
| 锁文件坏了算不算 | 不算记录坏。`claim.lock`、`claim.lock.epoch`、`repository.lock` 再也解析不了且已过一个租约，认领时改名留底、换掉，原单照常核对；还在租约内的按占用处理，回「这次没开成」 | 锁不带任何订单事实。把它算成记录坏，一个写到一半的锁文件就会把查得到的原单变成「不知道扣没扣钱」（崩溃扫描第一次跑出来的就是这个）。判据放在 `productionRunLock.ts` 只读，`acquire` 自己仍然封闭，制作 Run 不受影响 |
| 回执身份 | 事件读得出就用真实 `attempt-N`；读不出来用合成身份 `unreadable-r<n>`，它接受任何非空 `newAttemptOf`（只会多弹一张确认卡，不会多发） | Agent 手里拿的旧 attemptId 不能因为记录坏了就走不通 |
| 坏记录挪到哪 | 整个记录目录原子改名到 `<root>/.nomi/intent-claims/<runId>/quarantine/r<n>/` | 一次改名没有中间态；不在 `.nomi/runs` 下，任何列举都读不到 |
| 认领租约放哪 | 从记录目录移到 `<root>/.nomi/intent-claims/<runId>/claim.lock` | 挪目录不会把正持有的锁挪走；锁文件也活过整个记录目录被删 |
| 「这里有过坏记录」怎么活过崩溃 | `quarantine/r<n>` 存在且当前没有任何 attempt，就只回未知（`awaiting_new_order`）；数据全没了时，认领目录里的 `issued.json`（开单前落盘，活过记录目录）或旁账残留同样算有过记录 | 落盘的事实，不靠内存。原来想用 `fencingEpoch > 1`，实现时发现只认领过一次再丢目录时围栏号也是 1，全自动档会借机再下一单，所以换成开单前写的痕迹 |
| 谁来判定能不能开单 | `submissionIntent.ts` 里只有一个判定 `admission`，`tryModel` 先于校验问的 `observation` 和认领本身都问它 | 两份判定会漂移；也只有这样，反例删掉那一行时所有防重格才都会红，不被另一份盖住 |
| 判定和挪动时别人在写怎么办 | 显式新单持仓库自己的 `repository.lock` 判定和挪动；被活着的写手占着就回「这次没开成」，什么都不动 | 写手写到一半的那行不能被当成坏记录，也不能写到挪走的目录外面。锁跟着目录走，挪完删掉，被挪走的记录逐字节不变 |
| 新 attempt 命名 | 挪过 n 次后叫 `attempt-r<n>-<k>` | 不和被挪走的撞名；旧 `newAttemptOf` 重放对不上当前单，只回当前单 |
| 上一笔不确定的事实 | 冻结请求里带 `priorOutcomeUnknown`，安全重试继承 | 确认卡的那句话和 Agent 回执来自同一份持久记录 |
| 那句话怎么到确认卡 | 这笔走现有的 `confirmSpendAndMintGrant`，带专用 intent；渲染层在 `spendCardByIntent` 表里加一行，卡本身不变 | 表就是为不碰热点文件留的；`taskSpend.ts`、`capabilityApplyHandler.ts` 都是文件级热点 |
| 旧 approvals 为什么会撞 | `approvals.ndjson` 是按 `approvalId` 记的旁账，事件丢了以后 job 编号从头来，同名 approval 指纹和时间不同，于是 `Approval id conflict`。这是读不出来的一种表现：approval 指向不存在的 job 就算 `journal_behind`，显式新单把它连目录一起挪走；普通调用根本走不到记 approval 那一步 | 不绕过确认、不多发 |

**不改：** `productionRunRuntimeEnvelope.ts`、`productionRunRepository.ts`；普通调用不下单的语义；`SpendConfirmDialog` 的结构和布局。

**有意不做：** 制作 Run 自己的 `run.lock` 坏了也会永远 busy，这是同一类问题在别的调用者上的表现，但本轮只在意图层处理，已在交付报告里交回。

**量具：** 矩阵接在 [try-model-intent-matrix.json](../../tests/fixtures/try-model-intent-matrix.json) 上，记录 × 动作、共享认领、窗口都从清单取数；oracle 仍是环回服务器收到的 POST 数。真窗走现有零费演练。

★7：这条路径不新增用户操作和列表。认领多读几个固定路径的文件（快照、事件、approvals、预算账、任务目录一层），仍是单意图常数次 IO，不扫历史。

★8：Windows 上目录改名可能被占用文件挡住，挡住时走「新单开不出来」的回执，下次再调；未在 Windows 实测。
