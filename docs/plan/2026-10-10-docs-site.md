## 接入方案落地（对照 R-docs-framework 第六节 1–8 条）

1. **孤儿清理**（先修）：`build-marketing-site.mjs` 的「应有页面」集合改读全部页面（含教程页）。红绿证明：把清单挪走，`--check` 立刻报 5 个教程页是孤儿。
2. **sitemap 与页面清单**：`sitePages()` 并入 `docsPages()`；`/docs`、`/en/docs` 归「库首页」一档。`site.page-list` 概念登记已补说明。
3. **描述门岗**：判据不改。`Head.astro` 补 `twitter:description`、og 图、robots；canonical / hreflang / og:url 去掉 Starlight 在 file 格式下带的 `.html`。
4. **`check:site`**：新增两项：`docs-site (tests)`、`marketing docs`（重建一遍和入库产物逐字比对）。
5. **SEO 巡检**：`docs/seo/config.json` 的 `publicPaths` 是手写短清单，本段不改；巡检已读 sitemap（含教程页）。
6. **`_headers`**：加 `/_astro/*`（immutable）与 `/pagefind/*`（必须重新验证）。
7. **工作流**：不用改。`build-marketing-docs.mjs` 自己按 `marketing-docs/pnpm-lock.yaml` 冻结安装依赖（已装则跳过），所以 `site-data-sync.yml` 里的 `pnpm run build:site` 和 CI 的 `check:site` 都不需要多一步安装。
8. **`wrangler.json` 的 `run_worker_first` 加 `/*.webm`**：官网的服务契约（`scripts/marketing/serving-contract.test.mjs`）规定所有媒体类型都走站点 Worker 才有 Range（206），新媒体类型没路由就红。起初我以为 webm 不走 Worker，那是错的；后果是 webm 的缓存头由 Worker 响应决定，`_headers` 对它不生效。

## 2026-10-12 补：入库产物的哈希为什么随环境变（#1186 的 CI 红）

- 实测根因：Vite 从 `marketing-docs/` 往上找 PostCSS 配置，会吃到仓库根给 App 用的 `postcss.config.js`（autoprefixer，给 CSS 加 `-moz-column-break-after` 之类前缀）。有没有这份配置、能不能解析到它，决定了 `print.*.css` / `common.*.css` 的内容和哈希——产物就不只由教程站自己的源码和锁文件决定。对照实验：不带仓库根的副本构建出 `print.ehPL0gv-.css`（无前缀），本机在仓库里构建出 `print.BcLXvclU.css`（有前缀）；CI 报的正是前一个。
- 修在源头：`marketing-docs/astro.config.mjs` 里 `vite.css.postcss.plugins = []`，挡住往上找配置。修后本机在仓库里构建与另一路径下的干净检出构建，哈希一致（`common.KRJgqbup.css`、`print.ehPL0gv-.css`）。
- 第二层防线：「重建 vs 入库」的比对抹掉打包器自己的哈希（`_astro/<名>.<哈希>.css|js`、`astro-<哈希>` 作用域类），页面文字 / 结构 / 链接 / 元数据仍逐字比对（`normalizeBundlerHashes`，有单测）。理由：这类哈希是构建工具内部产物，我们无法在本机（Windows，不用 Docker / WSL）证明它在 Linux 上也一致；它本身不是页面内容。入库产物内部引用得上由 `check-site-links` 守。
- 「入库构建产物」本身没改：官网其它生成页同样入库、由门岗比对，Cloudflare 直接服务 `marketing/`，改成部署时构建会让部署多一个构建步骤，且协调会话手动部署的流程要变——不是这次的病根。若 CI 上仍对不上，下一步推荐改为「门岗只比源码到页面文字」。
- `lint:ci`：`marketing-docs/.astro/` 与 `marketing-docs/dist/` 加进 `eslint.config.mjs` 的 ignores（`.astro/` 早已在 `.gitignore`）。本机先 build:docs 再 lint:ci：0 error、78 warning（≤79；忽略前多出来的是 `.astro/types.d.ts` 带来的）。

## 2026-10-16 补：postcss 只是一半，门岗改核「逻辑文件」（#1186 Contracts 第二次红）

- 事实：d7f8d4780 之后，CI（Linux）重建的 `print.*.css` 已和入库的一致，`common.*.css` 仍然不同（CI 是 `common.y1p1JTPO.css`，本机是 `common.KRJgqbup.css`；两轮 CI 里 CI 的哈希同为 `y1p1JTPO`，不随根目录 postcss 变）。所以上一节「根因是根目录 postcss」只解释了 `print`，`common` 的差异另有环境因素；本机（Windows，不用 Docker / WSL）拿不到 Linux 产物，无法定位到字节，标 `unverified`。
- 不再追哈希：门岗的目的是「入库的教程页和源码对得上、页面引用的文件都在」，不是「在每个平台上位对位打出同一个哈希名」。`build-marketing-docs.mjs --check` 现在：`_astro/` 文件按逻辑名（抹掉 8 位哈希）核在不在、磁盘上多出来的也报；新增 `missingAstroReferences`——入库教程页引用的每个 `_astro/…` 必须在磁盘上。页面文字 / 结构 / 链接仍逐字比对（上一节）。两条都有单测与红绿证明（改名换哈希仍绿；页面引用的文件不在 → 红；逻辑文件缺失 → 红）。
- 这是同一条线（产物哈希）的第 3 轮。不再有下一轮的理由：门岗已不依赖哈希本身，剩下的环境差异只会改文件名不会让门岗红。

## 2026-10-16 再补：换行符假设被实验推翻；Pagefind 索引名同样随平台变（#1186 Contracts 第三次红）

- 新头上 CI 报：`pagefind/index/en_235b578.pf_index`、`pagefind/index/zh-cn_30c119e.pf_index`、`pagefind/pagefind.en_ea867f7b82.pf_meta` 磁盘上没有（本机分别是 `en_cdcf5a8`、`zh-cn_7be9267`、`pagefind.en_b0fff2f2d8`）；`common` 样式 CI 为 `y1p1JTPO`、本机 `KRJgqbup`。
- 换行符假设（Windows 的 `core.autocrlf` 把 LF 转 CRLF）：**已排除**。`.gitattributes` 是 `* text=auto eol=lf`，`git ls-files --eol marketing-docs` 22 个文件全是 `i/lf w/lf`；更直接的实验——把 marketing-docs 的源文件全改成 CRLF 再构建，产物名与 LF 时完全相同（`common.KRJgqbup.css`、`en_cdcf5a8`、`zh-cn_7be9267`），所以输入字节里的行尾不影响这些哈希。依赖版本两边按同一份 lockfile 冻结安装（astro 7.3.8、starlight 0.42.6、pagefind 1.5.2、lightningcss 1.33.0），版本也一致。
- 现有证据指向的方向（unverified，没有 Linux 机器可以验证）：每一个「逐页的」产物两边一致——页面 HTML（抹掉哈希后逐字一致）、`print.*.css`、Pagefind 的 `fragment/*`（内容哈希）；每一个「跨页汇总」的产物两边不同——合并样式 `common.*`、Pagefind 的 `index/*`、`pagefind.*.pf_meta`。汇总类产物依赖页面被处理的先后顺序，而目录枚举顺序 Windows（NTFS 按名字排序）和 Linux（文件系统自带顺序）不同。要在 Linux 上证实：在 CI 里临时把 `marketing-docs/dist/check` 当 artifact 传上来，和本机 diff（协调会话做，需要推送）。
- 因此不能靠「改输入字节」让两边相同。做法：把 Pagefind 的 `index/*.pf_index`、`pagefind.<语言>_<哈希>.pf_meta` 也按逻辑名核在不在、多出来的报；新增 `missingPagefindReferences`：`pagefind-entry.json` 点名的每种语言元数据文件必须在盘上。`fragment/*` 仍逐字核。单测加 2 条，红绿证明：索引改名 → 绿；索引缺失 → 红；元数据与入口对不上 → 红。
- 「按真实文件名核」要不要恢复：不恢复。两边字节本来就不会一致，除非能在 Linux 上构建并入库；这是同一条线的第 4 次，门岗已经只核有意义的东西。
