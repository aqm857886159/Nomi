# Nomi 增长运营闭环

> 状态：🚧 进行中
> 日期：2026-09-02
> 目标：把 SEO、内容分发与公开增长数据接成一个每周可复盘、可继续执行的闭环。

## 现状与根因

- 官网技术 SEO 可抓取，但 sitemap 只有 4 个页面，缺少承接具体搜索意图的案例内容。
- `download-stats.yml` 从 2026-08-17 起每天生成数据后直推受保护的 `main`，因此连续失败。
- `seo-radar.yml` 可以生成报告，但仓库禁止 GitHub Actions 创建 PR，因此报告没有进入可观察路径。
- 当前只有下载量时间序列，没有 stars、仓库访问、来源站点、克隆量与内容发布记录，无法判断哪类内容带来有效访问。
- 已有中英文宣传片、竖版素材、海报与渠道文案；主要缺口是发布单元、归因台账和持续复盘，而不是继续做一批泛功能截图。

## 方案取舍

| 方案 | 结果 | 代价 | 决策 |
|---|---|---|---|
| 放开 Actions 创建/批准 PR | 旧 SEO 流程可继续 | 扩大仓库级自动化权限，仍未解决下载任务直推 | 不选 |
| 每日向 `main` 开数据 PR | 数据能合入主线 | 每天制造 PR 噪音，合并不及时仍会断序列 | 不选 |
| 单一观测任务写专用数据分支 | 不绕过主分支保护，公开数据可持续保存 | 数据分支需要显式读取，主线只保留脚本与初始基线 | 采用 |

## 执行范围

1. 用一个 `growth-observatory` 定时任务替代失效的下载与 SEO 两条 workflow。
2. 每天记录安装包下载、stars/forks、仓库访问/克隆与公开 referrer；每周一追加 SEO 审计。
3. 数据写入 `automation/growth-data`，不直推 `main`、不自动创建 PR；同日重复运行幂等覆盖。
4. 在主线提交一份 2026-09-02 初始增长基线，证明采集器可用。
5. 以现有真实宣传片与产品证据制作第一批国内外平台发布包，并给每条内容定义假设、主指标与复盘窗口。
6. 更新现有营销执行文档的过时基线，明确后续 SEO 页面必须由真实案例派生，不做关键词堆砌。

## 不做项

- 不加入 App 内埋点，不读取用户项目、提示词、密钥或媒体。
- 不改官网核心主张“把 AI 视频的成本打下来”。
- 不虚构搜索量、客户案例、节省比例或平台成绩。
- 不在首批内容缺少成片/成本/可复现材料时发布 HN、Product Hunt 或 Reddit。
- 不改受保护分支规则，不扩大 GitHub Actions 的 PR 审批权限。

## 验收

- 采集器对同一天重复运行只保留一条快照；无 traffic 权限时明确记录 unavailable，不伪装为 0。
- workflow 不包含对 `main` 的 push，也不依赖 Actions 创建 PR。
- 下载、仓库增长、referrer 与 SEO 报告有明确的数据所有者和保存路径。
- 首批内容包至少覆盖中文短视频/图文、英文开发者渠道与一个 SEO 长文母题；每条都带内容假设、素材清单、CTA 和复盘指标。
- 通过相关 Node 测试、workflow 静态检查、SEO 测试和文档门禁。

## 回滚

删除统一 workflow、恢复原两条 workflow，并删除新增采集脚本即可。`automation/growth-data` 是独立数据分支，不影响产品代码；即使任务失败，官网与桌面 App 均不受影响。
