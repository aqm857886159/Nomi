# 设计卡 + 方向检查：生成中删节点再撤销，结果落回节点（不再永远转圈）

```
改动名：节点不在时到达的生成结局暂存，撤销带回节点时落上去      线/负责人：L-undo（续）      类别：[花钱]
```

来源：#1065（撤销保留落地结果）顺查到的同一类丢钱路径，协调会话 10-07 排进本线。现象：生成中删掉节点 → 撤销删除 → 节点带着「生成中」回来，结果永远不到。要求按根因在两种做法里选：①结果到了落回被撤销恢复的节点；②恢复时如实变成「已中断，可以重试」。

## 根因与选择

- **删节点时生成任务去哪了**：删节点的所有入口（右键删、删选中、剪切、外部写入删）都**不取消**生成任务；上游接着跑。
- **钱扣了没有**：扣了——付费在提交时就发生（单镜 Run 的准入 / 供应商提交），删节点之后不会退。
- **结果去哪了**：运行器照常把结局投给 `deliverRunOutcome`；它在 store 里找不到节点，**什么都不写、直接丢掉**。之后撤销删除，节点按删除前的样子回来（状态「生成中」），丢掉的结局再也不会来。
- 先撤销、结局后到：节点在，正常落地——这个顺序本来就是好的。

**选①**：结果是已经付过钱、真实存在的东西，只是到达时没地方放。把它暂存在撤销日志里（与 #1065 的落地记账同一处），撤销把节点带回来时，由 #1065 的 `reapplyLandedOutcomes` 按顺序落上去。②要用户再点「重试」，而重试是**再花一次钱**（或走找回再拉一次），比①差。失败也一样暂存：节点回来时如实显示失败卡，不转圈。

## 方向检查

与 #1065 同一个类根因（复盘全文见 `docs/plan/2026-10-07-undo-keeps-landed-results.md`「方向检查」）：系统事实（结局）和用户编辑（删节点）混在同一个节点对象里，节点没了，事实就没地方放。本 PR 让「结局到达」与「节点在不在」脱钩：节点不在时结局照样记账。

- **还会从哪冒出来**：制作流程（Run）的镜头节点被删时走 Run 自己的「解除挂接」（`watchDeletedProductionNodes`），结果留在 Run 里——不经本路径；撤销后能否重新挂回未在本 PR 验证，记为遗留。
- **用户要权衡的核心**：误删后撤销能接住这次付费结果；不撤销的话结果仍不回画布（尊重删除）。
