# 镜头结果归谁：主进程准入给身份、按运行收账、节点显示从记录算

实现线写，2026-11-07。四类（花钱 + 长跑 + 可打断），9 格全填。方向不是这条线定的：上一轮验收发现「两个入口几乎同时点，先发那次付了钱的图进不了镜头」，独立复盘线（没参与过前几轮）写了方向检查，推荐「换模式」；协调补查后端做法后加了两条硬约束；用户 11-04 拍板「先合，再单独修」。方向检查原文的要点抄在同目录 `2026-11-07-shot-result-ownership.direction-check.md`。这张卡是这一刀的实现合同和验收合同。

## ★0 先查别人

1. Temporal「Workflow Id 与 Run Id」（https://docs.temporal.io/workflow-execution/workflowid-runid ）· 服务端保证同一个 Workflow Id 同时只有一个在跑；第二次启动被拒，或者直接拿到正在跑那次的 Run Id；每次运行各有自己的 Run Id · 影响 D1、D3：「哪次算当前」只由主进程准入定，被拒的那次从来不是一次运行，所以不进运行记录。
2. Martin Kleppmann「How to do distributed locking」（https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html ）· 围栏令牌由授予方在授予那一刻发，存储按令牌先后拒绝倒退的写 · 影响 D1、D5：先后由准入定，不由渲染层数组第一项定；我们只拿先后裁决「显示哪张、动不动时间轴」，付了钱的结果照样入账，不拒收。
3. Azure 架构中心「Event Sourcing pattern」（https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing ）· 追加写的记录是正本，当前状态是投影；撤销靠补偿记录，不改回旧状态；文档提醒整套事件溯源很重 · 影响 D3、D5：删掉「恢复开始时的快照」，节点显示从运行记录算；不引入事件溯源框架，只在运行记录这一处用。
4. Stripe「Idempotent requests」（https://docs.stripe.com/api/idempotent_requests ）· 按幂等键记第一次请求的结果；和正在执行的请求冲突时不产生副作用 · 影响 D2、D3：结果绑在这一次意图（运行记录号）上；被拒的并发尝试不碰原来那次的结果。
5. TanStack Query v5「Optimistic Updates」（https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates ）· 乐观的那一层只在界面上显示，不写进正式缓存，结束时按服务端事实重算 · 影响 D1、D3：点下去到主进程准入之间，只在节点显示上写「排队中」，不写运行记录；被拒就按记录重算，不回滚快照。

## ★1 用户怎么用

**场景一（两个入口几乎同时点）。** 我在画布生成框点了一镜的生成，几乎同时在分镜表又点了同一镜。
1. 后点的那下被主进程拒了（这一镜已经在生成）。先点的那次照常出图。
2. 不管哪次的回话先到，出的图都落到这一镜上，镜头显示成功，不再一直转「生成中」。
3. 点取消能停；停了能重新生成。确认卡只为人亲手的「再发一次」弹（已有规则），不会因为这一下多扣一次。

**场景二（切走了项目）。** 同样两下，点完我切到另一个项目。回来时这一镜有图、是成功，另一个项目一个字没被改。

**场景三（确认过的再发一次）。** 上一次结果不明，我确认「再发一次」。新的那次先出图：新图是当前图、时间轴用新图；上一次的图晚到了：进这一镜的版本历史（在项目文件里），不顶掉新图、不动时间轴。上一次的运行记录记成成功（或失败），不再永远挂着「生成中」。新的那次失败而上一次的图到了：上一次的图成为当前图（钱花了的图要到镜头上）。

**场景四（生成中删了节点，又撤销）。** 先发那次的图在节点被删期间到了、后发那次在被删期间被拒；撤销把节点带回来：图在、成功。

**场景五（重启）。** 生成到一半关掉 Nomi 再打开：还在跑的那次变成可找回（有任务号）或空闲（没发出去），已经结束的运行记录一个字不改。

**不做什么：** 不改花钱规则、确认卡、拒绝的判据（主进程 `assertNodeIdle` 照旧）；不做「第二次点击直接接到正在跑的那次」（Temporal 的 Use Existing，另起一条待办）；不改主进程到渲染层的通道（不新增「准入」推送，准入回执用已有的「提交返回」）；不改项目文件格式（不加字段、不加状态值）；不改任何界面元素、布局、文案。

**已知坑：** ① 同步出图的模型，「提交返回」就是出图那一刻，所以准入回执要等整张图出完才到；在那之前这一次只在节点显示上，不在运行记录里（重启后靠主进程的开着的运行清单接回，见格 5）。② 被拒那一下如果正好占着节点显示（没有别的运行在跑），显示按记录重算：之前用户手动关掉的失败卡会重新出现（记录里本来就是失败），不再按快照恢复成「关掉」的样子。

**真实任务与量具：**

| 目标 → 信号 → 指标 | 量具 |
|---|---|
| 付了钱的图都到镜头上 → 先发成功 / 后发被拒任意先后，前台后台都落 → 落到的比例（矩阵格数中落到的 / 全部）= 100% | `src/workbench/generationCanvas/runner/shotResultOwnership.test.ts` 特征矩阵 |
| 镜头不卡在生成中 → 终态可动手 → 每格结束后「不忙 + 能再生成一次」比例 = 100% | 同上，每格末尾断言 `isGenerationNodeBusy` 为假并真跑第三次 |
| 不多扣钱 → 每格下单次数 = 预期（被拒的不重发，不自动重试） → 比例 = 100% | 同上，数执行器调用次数 |
| 真实流程里修前红、修后好 | 免费演练 `tests/ux/shot-result-ownership-real.rehearsal.walk.mjs`（修前、修后各一份日志和截图）；真付费 `tests/ux/shot-result-ownership-real.paid.mjs` 协调跑一次 |
| 记录多了显示还快 | perf 场景 `canvas-run-outcome-projection-200x20`（★7） |

真实任务：① 画布生成框 + 分镜表同时点同一镜（用户那条路，见 ★9「真实场景复现」）；② 结果不明后确认「再发一次」，上一次的图晚到；③ 点完切项目。

节点生成中遮罩和失败卡（读 `node.status` / `node.error` / `runs[0]`，改后读到的是同一份投影）；分镜表镜头行和资产卡（`storyboardRowStatus` 读节点状态；`storyboardNodeRunUnclaimed` 比 `runs[0].id`）；生成列表小卡、大详情；任务中心（队列条目：被拒的那次照旧记「已取消、不计失败」）；时间轴（只在当前图换了才对账，批量路径补上同一个判断）；Agent 回执（不变，读同一份结局）。都不新增文字。

### ★1c 老用户

- 项目文件格式不变：不加字段、不加状态值，运行记录仍是新的在前。旧版本打开新版本存的项目：一样的形状，读得懂。
- v0.24.0 真实落盘的数据（`tests/fixtures/old-user-data/runs/v0.24.0-canvas-interrupted/node.json`：旧版把被拒的那次写成了 `runs[0]`，状态 error、原文 `node_generation_in_flight`；同目录 `.nomi` 里有一个提交中的 Run）：升级后什么都不做，节点照原样显示（失败卡，「本机拒绝」那一类，出口「再发一次」）；主进程观察者为 `old-post` 交回的结局按运行记录号记到这条记录上；再点生成被拒时显示按记录重算，等于原样。矩阵里有这一格，用的是这份夹具原文件，不手写形状。
- 旧版本留下的「还在生成中」的旧记录（重启前存的）：收敛只改那条在跑的记录，不再改第一条（以前第一条要是已经成功了也会被改成取消）。
- 没有迁移，没有并行旧路径；退回上一版本打开：形状一样。

### 决定

- **D1 准入身份。** 花钱的那条路（`ledger: 'run'`）点下去时只在节点显示上写「排队中」，进度带这次的记录号；不写运行记录。准入回执到了（第一个带任务号的进度 = 提交已返回；或结果；或除拒绝以外的任何结局）才写这条记录。记录按开始时间插入（新的在前），所以晚拿到回执的老运行排在新运行后面。
- **D2 按号收账。** 结果、进度、状态各找自己的记录。进度只写在跑的记录；对已结束的记录、不认识的号，进度不写记录，也不动显示（除非这次正占着节点显示）。
- **D3 被拒只结束这一次。** 主进程拒了 = 这次从来不是一次运行：不写记录，不恢复快照；它占着节点显示的话，显示按记录重算；队列条目照旧记「已取消、不计失败」。取消、失败、可找回照旧给这次的记录写终态（没拿到回执就先写进来再结束，因为主进程可能已经收下了，记录号要留着对账）。
- **D4 结果去哪。** 结果永远进这一镜（钱花了）。比它新的运行已经成功了 → 只进版本历史，当前图不动、时间轴不动；否则成为当前图。
- **D5 显示投影。** 有在跑的记录 → 最新那条在跑的说了算（排队中 / 生成中 + 它的进度）；没有在跑的、但这次乐观占着显示 → 保持；否则最新那条记录说了算（成功 / 失败 + 原文 / 可找回 + 原文 / 取消 → 空闲）。新落成当前图 → 成功。
- **D6 不带号的结局。** 不带号的结果只结掉在跑的制作记录（`isProductionRunRecord`），别的记录一个字不动；不带号的状态只改最新那条没结束的记录。
- **D7 时间轴。** 只有当前图就是这次的图才对账，批量路径（`runGenerationNodesBatch`）补上这个判断。
- **D8 重启收敛。** 只改在跑的那条记录；没有在跑的记录（这次还没拿到回执就关了），显示按记录重算。
- **D9 批准的输入。** 「正在跑的是哪次」由运行自己报号，不读 `runs[0]`；上游的「这次批准的那次运行」按号找记录。

## ★3 一致与复用

同一个合并规则（`nodeRunOutcomePatch`）给活的画布、盘上副本、暂存重放、撤销叠回四处用，不新造第二份；不新增 store；不新增主进程通道；准入回执用已有的「提交返回」进度（`catalogTaskActions.ts` 不改，另一条线在改它）。乐观显示复用已有的 `node.progress.runId`。自写登记 `canvas-undo-journal-write-boundary` 的系统事实重放保持原样。

## 5 中途表

| 时刻 | 停（取消） | 关窗 / 重启 | 断网 | 连点 |
|---|---|---|---|---|
| 点下去、主进程还没准入 | 取消 → 这次记成取消（写记录，号留着对账），显示空闲；没扣钱或扣了由主进程 Run 记 | 节点显示存了排队中、没记录 → 重开收敛按记录重算；主进程那边要是已经收下，开着的运行清单让节点显示「可找回 / 结果不明」，回执在主进程 Run 里 | 提交失败 → 这次记成失败（写记录），按已有分类给出口 | 第二下被主进程拒：不写记录，不扣钱，不恢复快照 |
| 已准入、生成中 | 取消停这一次（记录取消，交主进程观察者收尾，钱花了的图照样进项目） | 重开收敛：有任务号 → 可找回，回执是任务号；没有 → 空闲 | 轮询失败不重发，到时限落可找回 | 第二下被拒同上；不弹确认，不多扣 |
| 已准入，另一下被拒前出图 | 已结束，取消无效 | 图已存进节点 | 不影响 | 图在，成功 |
| 结果不明，确认再发一次 | 新的那次可停 | 两次各有记录；重开后各自收敛 | 同上 | 确认卡只弹一次（已有规则） |
| 切走了项目 | 回去才能点取消；结局写原项目盘上副本 | 同上 | 同上 | 同上，写盘串行 |

扣不扣钱：只有主进程收下并发出去的那次可能扣钱，回执在主进程该次 Run（任务号、账本）；被拒的那下主进程没建 Run，不扣钱。

## ★7 性能

新增的计算：每个结局落下时按号找记录（最多 20 条）和投影一次。最坏规模：一个项目 200 个节点、每个节点 20 条运行记录。操作：批量跑着时每个节点来一个进度、一个结果；打开项目时收敛 200 个节点。预算：一轮 200 个节点各落一个进度 + 一个结果，纯计算合计 ≤16ms（一帧之内，不产生 >50ms 长任务）；收敛 200 个节点 ≤16ms。场景 `tests/perf/scenarios/canvas-run-outcome-projection-200x20.json`，量具 `tests/perf/node-json-bench.mjs` + 新仪器脚本，基线数字见 PR 和报告（实现线只交冒烟和 5 次的数，基线由协调写）。

### 真实场景复现

- 用户的流程：验收线在 #1413 第 3 次独立验收里走出来的（逃逸账本记「验收发现」）：同一镜从画布生成框和分镜表几乎同时点生成；后发那次被拒；先发那次付了钱的图进不了镜头，镜头一直「生成中」，取消一直转，确认又付一次。
- 我走的：开发构建 + 隔离资料目录 + 假服务商（免费）；画布选中这一镜点生成，假服务商把第一笔的回话压住；切到分镜表对同一镜再点一次（主进程真拒）；放开第一笔回话，让它在第二下被拒前后各走一次；看节点、分镜行、列表三处；点取消；再生成一次。
- 差别：服务商是假的（真付费由协调跑一次）；「几乎同时」靠压住回话造出来，不靠手速。
- 修前看到什么算复现：节点一直是生成中、没有结果（或结果没落到镜头上），取消后不能再生成，或再点又下一单。
- 修后看到什么算好了：图在镜头上、成功；分镜行、列表一致；被拒那下没有多下单；能取消、能再生成。
