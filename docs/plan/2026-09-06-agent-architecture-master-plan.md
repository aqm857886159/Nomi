## 0. 一句话：这份方案在解决哪个真实摩擦

**用户看不出 Agent 在干什么，而且它一遇到小问题就整轮死掉。**

具体到画面上是三件事：
1. 面板先甩一大段文字，然后一排工具收据——读起来像「它想好了全部，再一口气做完了全部」。真实过程是「说一句、做一件、再说一句」。**多步任务（做一条短片要跑 8~24 步）里，这个差别就是「我知道它在干嘛」和「我不知道它卡在哪」的差别。**
2. 一次 429（供应商临时限流）= 整轮失败，用户重发。
3. 面板上的「花费」「推理」两行永远是空的，「上下文用了多少」画不出百分比。

**要权衡的那一个东西**：这些都不是显示层的活，是**接缝形状**——主进程和渲染层之间那条管道现在只能传「一根字符串 + 一个数组」。改它就是改契约，改契约就要动宿主状态机、投影层、走查断言和视觉基线。**所以真正的取舍是：是继续在渲染层用易失的内存登记表打补丁（便宜、但冷重启后历史永远是错的），还是一次把管道拓宽（贵、但从此每个新功能都有地方落）。**

本方案主张后者，并把它压到**一个 P0 阶段 + 三条互不阻塞的支线**，而不是一次大重构。

### 术语先解释（D6）

- **段 / parts**：模型一轮回复不是一整块文本，而是一串有顺序的小块——「说一段话」「想一下」「调一个工具」。pi 原样保留这个顺序，我们在接缝处压平了。
- **接缝 / runtimePort**：主进程里把 pi 藏起来的那道门。门外（宿主）不认识 pi 的任何类型，只认识我们自己定义的一组结构。今天这组结构里没有「段」这个概念。
- **压缩 / compaction**：对话太长时，把前面的历史总结成一段摘要，腾出上下文空间。pi 自带，我们在用。
- **steering**：模型跑到一半时插一句话改方向（「不对，横屏」），不用等它跑完。pi 有，我们关掉了（因为每回合开新会话）。
- **一次写对率**：模型第一次调工具就把参数写对的比例。它直接决定用户等多久、烧多少钱。

#### P1-B · 工具契约不再对模型说谎

**真实摩擦**：模型给分镜表写 24 行，看到的 schema 只说「shots 是一个由任意对象组成的数组」——25 个字段名一个都没告诉它。写错要到渲染层才报错，而报出去的是 zod 的原始错误（`path`/`code`），模型看不懂也改不对。

| 做什么 | 怎么做 |
|---|---|
| **① 门岗：模型可见的 schema 不许是空的** | 任何进 `tools/list` 或 pi `parameters` 的 JSON Schema 里，不允许出现 `{}`、`z.any()`、`z.record(z.unknown())`、或无 `items` 的数组。棘轮，基线只减不增。**这一条同时拦住三处已知问题**：分镜 `shots`/`anchors`、MCP 的 `references: {type:"array"}` 无 items、以及未来被 preprocess override 抹平的字段 |
| **② 把描述搬回活 schema** | `canvasDescriptors.ts` 那份带 `.describe()` 的 shot/anchor schema 是资产。让它成为 `canvasWrite.ts:139-146` 里 `storyboardPlanActionInputSchema` 的真身，然后同 commit 删死文件（P1） |
| **③ 拒绝要能自纠** | `tools.mts:74` 改成 pi 设计的形状：`beforeToolCall` 返回 `{block:true, reason}`，`reason` 是「你少了哪个字段、合法值是什么」的人话。`CANVAS_WRITE_OPERATIONS`（`canvasWrite.ts:283`）已经是为这件事准备的派生名单 |
| **④ 用官方钩子代替 hack** | 需要容忍模型把数组写成 JSON 字符串时，用 pi 的 `AgentTool.prepareArguments`（`pi-agent-core/dist/types.d.ts:346`），而不是 `z.preprocess` + 抹平 schema |
| **⑤ 一次写对率评测** | **等 `docs/agent-tool-layer-audit-20260906` 分支的真实测量数据，不重复做。** 它的结论出来后并进本节，作为「改前/改后」的对照基线 |

- **回滚**：③④ 单独可 revert；①② 一起。

## 3. 关键岔路（R3 对比表）

### 3.1 转录的真相源：放 pi session，还是放宿主 record？

**背后的逻辑（大白话）**：「这段对话到底发生了什么」现在有两份落盘记录——pi 自己的会话快照，和宿主自己的事件溯源存储。两份都在长，谁说了算今天没定。P1-A 要往里加「段」这个概念，就必须先回答加到哪一份。

| 方案 | 用户看到 | 代价 |
|---|---|---|
| **A. 宿主 record 是唯一真相源**（把 parts 加进 `ProjectAgentItem`） | 冷重启后历史完全正确；审批/提案/任务卡与文字段在同一条时间线上 | 宿主契约要扩（`projectAgentContracts.ts`）；migration 要处理旧快照；pi 快照降级成纯粹的「给模型看的上下文」，不再是用户可见历史的来源 |
| **B. pi session 是唯一真相源**（面板从 pi 快照投影） | 与模型看到的历史逐字一致，永不漂移；pi 的压缩/分支/统计能力可以直接用 | pi 快照今天**不过 IPC**（是主进程侧的不透明 blob）；要新建一条投影通道；宿主的审批/任务/失败条目在 pi 快照里没有位置，会变成两条时间线要 join |
| **C. 双真相源 + 同步**（今天的事实上状态） | — | **已经在付代价**：同一段文字有两处独立推导且互相覆盖（`:128-157` 增量 vs `:684` 整覆盖），reducer 只在两者不一致时 bump 修订号——分歧被容忍且不可见 |

**推荐 A**。理由：宿主已经有完整的修订号/命令账本/幂等机制，而且用户可见的历史里有一半东西（审批卡、任务卡、失败条）**pi 根本不知道**。B 会把「用户看到的历史」和「模型记得的历史」强行绑成一件事，而这两件事本来就该不同（模型不需要看到审批卡）。C 是今天的状态，它正在产生 §2.2 表里那两行漂移。

### 3.2 工具收敛到多少个？

**背后的逻辑**：工具越多，模型每次请求要读的 schema 越长（占上下文、占钱、增加选错的概率）；工具越少，每个工具的参数就越复杂（一个 `operation` 枚举带十几个分支），模型要在参数里做二次选择。MCP 侧已经做过一次 42→15 的收敛，内部侧没做。

| 方案 | 用户看到 | 代价 |
|---|---|---|
| **A. 内部也收敛到按对象归并（~15）** | 与 MCP 词表一致；prompt 更短更省 | 内部要跟着做一遍 MCP 的手写再展开逻辑；`agentPanelV4ActionFamily` 的 icon 家族表要重做；**一次写对率可能下降**（多态工具的参数分支更难写对）——这条要用工具层审计的真实数据判 |
| **B. 内部保持 35 个细粒度工具，MCP 保持 25 个归并工具** | 各自最优 | 两套词表长期并存；渲染层要按两套名字对表（`agentPanelV4ActionFamily.ts:6` 已在这么做）；每加一个能力要在两处各表达一次 |
| **C. 收敛只做「按 capability 分档后实际暴露的数量」，不改工具名** | 单次请求里模型看到的工具数从 22 降到 6~8 | 已经在做（意图正则 + sticky profile，`agentChatPolicy.ts:126-180`），但**正则路由本身是个猜**：「帮我做一条 20 秒短片」命中 `PRODUCTION_INTENT`，一旦那个档里有任何一个工具名不合法，整轮发不出去（这正是 `layout.read` 那次事故的放大器） |

**推荐 B + C 的加固**，**但把决定推迟到工具层审计的一次写对率数据出来**。理由：A 的收益（prompt 短）可以用 C 达到，而 A 的风险（多态工具降低一次写对率）恰恰打在我们最痛的地方。在没有真实数据前收敛工具是拿一次写对率赌 prompt 长度。

### 3.3 MCP 与内部 Agent 是否共用同一套能力调用路径？

**背后的逻辑**：外部 AI（比如 Claude Code 当 MCP 宿主）和 Nomi 自己的 Agent，最后要不要走同一条路进入 Nomi 的能力？

| 方案 | 用户看到 | 代价 |
|---|---|---|
| **A. 完全共用（同一批工具定义 + 同一条校验链）** | 外部宿主能做的 = 内部能做的，用户不用记两套 | **做不到**：MCP 的每个工具必带 `leaseHandle`（显式租约），内部 agent 是环境绑定的。这条形状差异是安全设计的一部分，不是历史包袱 |
| **B. 共用能力契约与领域实现，各自派生入口**（今天的方向） | 行为一致，名字不同 | 今天「派生」只做了别名一半，**分解方式仍是两边各手写**——这就是 P2-3 要收口的东西 |
| **C. 各自独立** | — | 已被否定：会长出两份领域实现（`ARCHITECTURE-NOW` 已记「两套入口合同，一套领域实现」） |

**推荐 B，并把 P2-3 的口收到「分解方式也从契约派生」**。同时**明确保留一条不对等**：内部 agent 永远不能自开付费闸和启动付费生成（`modelToolSurfaceManifest.ts:236-240`）——这是有意的信任边界，不是缺口。

## 6. 必须先拍板的三条

按 CLAUDE.md「才问用户：产品方向 / 不可逆取舍 / 需要用户独有资源」，其余全部按 P0 自主推进。

### Q1 · LLM 目录新鲜度：要不要用真实 key 跑一次带鉴权的模型列表探测？

- **摩擦**：Agent 自己的脑子是全产品唯一没有自动新鲜度检查的模型类。目录里五个 DeepSeek id 来自 2026-08-21 的一次手动探测，其中三个仓库自己已标 `legacy` 但仍完全可选；退役靠用户撞到报错才发现。
- **需要你的**：一次带 APIMart key 的 `GET /v1/models` 探测（一次性，额度极小），以及「探到的退役 id 要不要直接下架」的决定。
- **推荐**：探一次；退役 id 直接从可选列表移除（不是只降分层），并把 LLM 加进日常雷达。

### Q2 · 思考（thinking）打不打开？

- **摩擦**：现在 `thinkingLevel:'off'` + `Model.reasoning:false`，思考在系统里结构性不存在。面板上那条「思考中 · 4s」量的是**等第一个 token 的时长**，不是模型在推理；契约里的 `reasoningTokens` 字段永远填不上。
- **要权衡的那一个东西**：**推理 token 是要额外付钱的**（它算在 output 里）。打开 = 复杂任务（分镜、剪辑计划）质量可能明显变好 + 面板上那条线名副其实；不打开 = 便宜，但要把「思考」改名成「等待模型」、删掉推理那一行（D4：不给用户看一个永远空的行）。
- **推荐**：**按能力分档打开**——`storyboard` / `production` 这类多步规划开 `medium`，`creation-chat` / `canvas-refine` 保持 `off`。先用一条真实任务对照测（同一句话、开与不开各跑一次）再定档位。

### Q3 · `skill.write`（让 Agent 写技能）这条能力，是恢复还是删掉？

- **摩擦**：`author_skill` 工具在 `documentDescriptors.ts` 里，而那个文件已死；`agentChatPolicy.ts:85-86` 那条找它的分支恒空。净效果：**`skill.write` 能力从任何入口都够不着**，`creation-chat` 实际只有一个只读工具。
- **要权衡的**：「让 Agent 把这次学到的方法写成一个技能」是经验沉淀闭环的一环（`ARCHITECTURE-NOW` 里有整段设计），但它今天没有 UI、没有审批卡、也没有任何人用过。
- **推荐**：**先删**（连同死文件一起，P1），把它记进 `docs/plan` 的远期项。理由：一条够不着的能力不是能力，是一条会让下一个读代码的人误判现状的假线索。要恢复它需要的不是把工具接回去，是先设计「Agent 写的技能怎么被用户看到、审批、撤销」——那是一件独立的活。
