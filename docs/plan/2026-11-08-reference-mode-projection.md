# 已选择模式的参考图投影与容量

## 设计卡

★0 查过 APIMart Vidu Q4 官方页（generation.md，15 张合计限制，决定超量反例），Wan 2.7 官方页（角色数组区分角色参考，决定同类覆盖），Seedance 2.0 官方页（首尾顺序和角色词，决定测试从创建请求走到 fetch）。出处和字段见本分支各模型档案的 sources 及官方页，证据在 apimartDocsAlignRunPath.test.ts。

★1 同一批参考在两条生成入口发成选中模式的同一组字段，每张只出现一次。量具是实际生产请求函数出口的 fetch 捕获。老用户不改项目存储；无模式的调用与自定义连接继续按有效载体解析。

★2 模式档案拥有容量和输入角色；两个调用者把所选模式传给主进程共用的判据。档案已经放置的同一 URL 不再投到第二个键。

★3 保留现有模板、角色声明与真实 fetch 捕获。逐个移除或更改供应商模板会漏同类；删除落位推断会破坏无档案自建模型。选择复用模式声明，并删两条重复的 URL 遍历。

★4 仍由现有确认卡批准。超出 Agent 合同容量在付费调用之前拒绝；取消、查询、重启恢复和结果落盘继续走已有主人。

5 现有数据仍按原选中模式读取；未选模式维持当前兼容逻辑。自定义 Comfy 槽继续按绑定身份生效。

6 不引入存储字段，无后台任务；同步投影以单次请求中的参考数和槽位数为界。

7 复杂度随参考项数量线性增长，不新增网络操作。

8 两条入口的发图都经主进程，使用已授权参考；测试捕获发出请求，评测不产生真实订单。真实样本另由协调登记。

★9 Vidu Q4 的参考 1、8、15 张各出现一次；16 张画布只取合法槽内的 15 张，Agent 拒发。Seedance 2.0、2.5、Wan 3.0 首尾图只落各自角色；Wan 2.7 单参考不变首帧。原有无模式、自建中转、混合媒体测试继续通过。

## 方向检查

2026-11-08 已拍板的生成请求链 S3 方向是按所选模式放参考且只放一次。方向检查指出重复的键和同一 taskKind 被错误当成单一容量。此 PR 验证角色槽与容量；完整 S3 清单包括无档案声明迁移、全格对照和真机样本，需另逐项核实。

## 官方案例复验

- Vidu Q4 生成页面明确两个数组按总数计；参考 1/8/15 张走两个入口时每个地址只应出现一次。16 张的画布按槽位容量进入提交，原始 Agent 合同携带 16 张会在出网前拒绝。样本表的临时挂起已解除，付费入口也断言只有一条创建请求、一个 reference_image，并拒绝扁平键和首帧键。
- Veo 3.1 的选中方式决定 generation_type；Wan 3.0 用同一键表达 2 张首尾帧或 10 张参考。投影保留公共可调参数的默认值，方式固定字段按所选模式重算；旧请求没有 modeId 时仍采用原来的主模式默认值。KIE 的 GPT Image 2 档案保留 16，APIMart 依据该供应商的实际合同最多 15；模型商之间的差异只在声明槽的供应商上限写一次。Gemini 3 Pro 的改图模板消费 reference_image_urls，两个发送入口复用目录现有别名表。
- 修前在真实画布构造→runTask 和 Agent 运行入口捕获请求。原有官方字段已知失败表已在 11 月 8 日重放。原 26 个型号、60 种方式，按当前合法上限的 125 组输入通过官方事实的全部判定；旧上限硬塞 16 的 GPT 样本单列，保留旧判据，避免把 UI 的第 16 张写成已发。
- 真实 App 执行记录另由协调验收。本案没有迁移项目文件、没有生成新的供应商订单，其他 S3 结构改造不作为这次完成依据。
