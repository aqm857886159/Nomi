# Nomi 综合体验验收体系：从“功能通过”到“真实创作者完成任务”

状态：方案 PR，尚未实施生产代码

关联任务：PR #1014 任务板（分镜方案问题暴露出的综合验收缺口）

## 1. 结论

Nomi 目前不是缺少测试数量，而是缺少一条以真实创作者任务为中心、把功能、参数、视觉、交互、性能、Agent 决策、异步状态、真实素材和恢复能力放在同一条链上验收的机制。

本方案把现有的 `full-walk`、storyboard 表格覆盖矩阵、Agent eval、真实 Electron journey、feel observer、canvas 性能基准和生产 Run 账本组合成一份“体验验收包”。指标只并入设计卡 ★1 / ★9；不另设指标卡或常驻规则。以后新增或修改功能，按设计卡分档并用真实任务验收，不能只用单元测试、静态 mockup 或合成性能夹具报告完成验收。

## 2. 这次暴露的问题与类根因

用户实际使用分镜方案时发现（七个问题）：

- 参数控件无法找到或无法选择；
- 比例显示错误或与实际出站比例不一致；
- 只能逐镜生成，批量生成剩余时没有等待跨镜一致性或前置镜头完成；
- 参考图没有自动引用；
- Agent 起草分镜容易出错，需要反复创建多个方案；
- 表格点击行为与用户预期不一致，点击选择后反而隐藏；
- 真实任务中的性能问题没有在测试中出现。

这些不是七个互不相关的 bug。当前类根因是：

1. 验收单位按组件、函数或单一状态切割，没有按“创作者完成一条分镜并继续生成”的完整任务切割。
2. 测试主要证明“入口存在、状态能转移、代码合同成立”，没有证明“用户知道下一步、能选到参数、看得懂比例、操作结果与预期一致”。
3. Agent eval 主要检查产物结构，未把错误率、返工轮数、方案收敛时间和最终采用率作为一等指标。
4. 性能测试的输入规模和素材分布与真实用户工程不一致，合成夹具掩盖了导入、解码、布局、媒体预览和长任务联动成本。
5. 通过标准没有统一的基线、留出集、最小可行动提升和停止条件，导致局部绿灯被误报成综合完成。
6. 意图抽取的期望没有和草稿参数做确定性对比，模型说过的约束可以在方案落地时悄悄丢失（铁律 ⑩「说的=摆的」）。
7. 模型档案的参数清单没有自动生成并覆盖每个入口，导致参数存在于档案却无法在实际入口选择（铁律 ⑪「能选到」）。
8. 可点击目标只记录了动作名称，没有把用户预期和实际结果成对落盘（铁律 ⑫「点了=以为的」）。

## 3. 体验验收包的五个面

每条真实用户任务都从以下五个面同时验收；任一面阻断任务，整条任务不通过。

三条新增铁律贯穿五个面：⑩「说的=摆的」核对意图抽取期望与草稿参数；⑪「能选到」要求模型档案参数清单自动生成并覆盖各入口；⑫「点了=以为的」要求 `catalog.mjs` 的每个可点目标都有用户预期与实际观察的对照记录。

| 面 | 要回答的问题 | 典型指标 |
|---|---|---|
| 任务结果 | 用户是否完成了真正想完成的事 | 任务完成率、最终采用率、返工轮数、从输入到可继续编辑的时间 |
| 交互与可理解性 | 用户是否知道在哪里点、点了之后发生什么 | 参数可发现率、可操作控件命中率、错误操作率、关键状态理解率、隐藏内容率 |
| 视觉与信息 | 用户看到的内容是否完整、清楚、比例正确 | 中英双轨截图、裁切/溢出、对比度、比例一致性、表格密度、可见状态覆盖 |
| Agent 与流程 | Agent 是否一次做对并遵守生产顺序 | 首次方案通过率、平均方案数、返工轮数、工具参数正确率、引用命中率、前置依赖阻断率 |
| 性能与可靠性 | 真实输入下是否足够快、不会丢状态或错误花费 | 首次打开、导入、预览、拖动、批量生成调度、重启恢复、错误率、重复提交率、token/成本 |

## 4. 分镜方案的第一套真实任务矩阵

第一阶段只做 storyboard / creation plan，不同时扩张整个产品。

| 任务 | 真实用户动作 | 必查问题 |
|---|---|---|
| S1 从 brief 起草 4 镜 | 输入一句产品 brief，接受 Agent 方案 | Agent 是否一次创建正确方案、是否反复重建、镜头是否覆盖 brief |
| S2 修改一镜参数 | 在表格中选择模型、比例、时长、画面类型 | 控件是否可见、可选、保存后仍显示同一值，显示值是否等于发送值 |
| S3 自动引用跨镜主体 | 为角色 / 场景设置参考，再查看各镜 | 引用是否自动带入、引用数量和类型是否正确、用户能否移除或替换 |
| S4 单镜生成 | 只生成当前镜头 | 是否只提交当前镜、其他镜头状态不被改变、失败可重试 |
| S5 生成剩余 | 前一镜仍在生成时点击生成剩余 | 是否阻止违反顺序的提交；“剩余”是否明确指未完成镜头；不会重复提交或跳过跨镜依赖 |
| S6 表格行交互 | 点击行、缩略图、选择框、更多菜单 | 点击目标是否符合用户心智；选中、展开、隐藏、开始操作不可混淆 |
| S7 中英文与小窗口 | 中文 / 英文、最小窗口、窄表格 | 参数、比例、按钮、错误和弹层不溢出、不遮挡、关闭可达 |
| S8 真实媒体与恢复 | 导入真实图片 / 视频，生成后 reload / restart | 解码、预览、导入、保存、恢复是否仍成立，失败能否解释和恢复 |

S1–S8 不是八个孤立脚本，而是一条任务链：同一个项目先起草，再编辑，再引用，再单镜生成，再批量生成，再重新打开。每个里程碑记录截图、用户动作、界面反应、工具轨迹、落盘状态和耗时。

## 5. 评分与判定

### 5.1 硬门

以下任一项失败，不能用平均分覆盖：

- 用户无法完成关键动作；
- UI 显示的模型、参数、比例、引用与实际发送不一致；
- 批量生成绕过跨镜依赖、重复提交或发生未授权花费；
- Agent 产物无法继续编辑，或需要重复创建方案才能收敛；
- 真实素材导入、预览、保存或重启恢复失败；
- 关键控件在中英文或最小窗口不可见 / 不可点击；
- 出现无限等待、丢状态、错误归因或不可恢复的失败。
- ⑩「说的=摆的」：意图抽取写下的期望与画布 / 分镜草稿参数逐项不一致，或没有确定性对比收据；
- ⑪「能选到」：模型档案声明的参数没有自动生成清单，或任一用户入口无法选到该参数；
- ⑫「点了=以为的」：`catalog.mjs` 的可点目标缺少 `userExpectation` / `actualObservation` 对照，或点击后的实际结果偏离预期。

### 5.2 结果指标

每轮报告按设计卡 ★1 / ★9 所选档位收集必要字段；体验验收包的结果字段包括：

- 任务完成率；Agent 改动另报 pass@k / pass^k；
- 首次方案通过率；
- 平均方案数、平均返工轮数；
- 参数 / 引用 / 比例的 shown-equals-sent 通过率；
- 真实用户从开始到完成的时间；
- 真实素材导入、预览、reload、restart 的成功率；
- p50 / p95 延迟、长任务数量、最大帧间隔；
- token、重试、供应商请求数和花费收据（未知就标 `unverified`）。

这些字段是报告内容，不另开指标卡。留出集、pass@k 和单变量爬坡只用于 Agent 改动；其他改动只记录对应真实任务的基线、结果和逃逸项。

### 5.3 质量评分

开放式结果仍使用校准后的 analytic judge，但 judge 只能补充确定性检查不能检查的质量：

- 是否忠实用户 brief；
- 是否能直接生成画面；
- 是否保持叙事 / 镜头连续；
- 是否保持角色、产品和画风一致；
- 是否让用户少读、少配、少返工。

judge 在人工标注达到约定一致性前，只作 advisory，不得把结果变成通过。

## 6. 测试分层与工具归属

| 层 | 工具 | 作用 | 不能证明什么 |
|---|---|---|---|
| 合同层 | Vitest / node tests / schema gates | 类型、边界、状态和数据不变量 | 用户是否理解交互 |
| 真实 Electron 层 | `tests/ux` journeys、full-walk | 真页面、真点击、真状态和截图 | 真实供应商画质，除非付费实跑 |
| Agent 层 | `evals` run / score / judge | 起草、工具选择、产物质量、成本 | Windows / 真实供应商全平台行为 |
| 体验层 | feel observer、双语截图、人眼复核 | 发现遮挡、不可见、层叠、误导、错误心智模型 | 单靠 DOM 断言无法替代的人类判断 |
| 性能层 | 真实媒体 + scale / task profile | 真实导入、预览、交互和恢复成本 | 未校准平台上的绝对门限 |
| 生产层 | paid / provider journey | 真实供应商、扣费、回执和落地 | 零花费夹具不能升级为真实供应商通过 |

已有工具继续复用：`full-walk` 的九条铁律负责跨任务不变量，storyboard coverage 负责状态矩阵，`evals` 负责 Agent 质量与成本，feel observer 负责界面体感，性能基准负责可重复读数。需要新增的是编排层和统一报告，不是第二套平行测试框架。

## 7. 每次功能开发的设计卡与分档流程

### 开始前：指标卡

在设计卡 ★1 / ★9 中补齐（不新增指标卡）：

- 用户任务和不做什么；
- 主指标、质量指标、护栏指标；
- 真实任务样本和样本来源；
- 评分器和人工复核方式；
- 基线、目标、最小可行动提升（只在该改动需要时填写）；
- 失败时回滚或停止条件。

### 实现中：先基线、后改动

- 先在当前提交跑出基线；
- 留出集、pass@k、单变量爬坡只在 Agent 改动中使用；
- 每轮只改一个可归因表面（Agent 改动才要求单变量爬坡）；
- 失败必须按根因分桶，不按单个 case 打补丁；
- 真实素材、真实页面输入、真实工具轨迹和真实状态落盘必须保留证据。

### 合并前：综合验收

- 普通 PR 只要求设计卡 ★1 / ★9；
- 花钱、长跑、可打断改动运行中英文真实任务链；新界面再加一条 AI 创作者任务；
- Agent 改动增加意图准确率，并按 Agent 档位跑留出集 / pass@k / 单变量爬坡；
- 发版前运行全套体验验收、AI 创作者任务和逃逸报告；
- 逐步截图并由独立验收线人眼复核，按设计卡所选字段对比基线、成本和延迟；
- 任何硬门失败或只改善训练集的改动不得合入；
- 未覆盖的平台、供应商或真实媒体明确标 `unverified`。

### AI 创作者任务规格

新界面任务由一句 brief 加一份人设组成，人设至少覆盖新手和老手。每一步先写用户预期，再记录实际结果；不一致立即写入 `tests/ux/full-walk/escapeLedger.json` 的候选项，人工复核后才能转为正式回归项。图片任务只使用当前可用的最便宜模型，并在报告中记录实际花费。

## 8. 分阶段实施

### Phase 0：小范围治理基座

- 只补设计卡 ★1 / ★9 的指标与验收字段；
- 新增 `tests/ux/full-walk/escapeLedger.json` 及方案第 2 节七个问题、2026-10-05 四个真实测试的种子；
- 在 `catalog.mjs` 约定每个可点目标的 `userExpectation` / `actualObservation` 列；
- 把铁律 ⑩「说的=摆的」、⑪「能选到」、⑫「点了=以为的」写进类根因复盘与硬门规格；
- 不改产品逻辑、已有门岗判据、常驻规则或新增指标卡。

### Phase 1：storyboard 综合体验包

- 为 S1–S8 补真实 Electron playbook；
- 把参数、比例、引用、批量依赖、表格点击语义纳入监视器；
- 增加 Agent 首次通过率、方案数、返工轮数的 eval 输出；
- 增加真实媒体导入 / reload / restart 证据；
- 建立 train/test 与基线对比。

### Phase 2：性能真实化

- 采集脱敏的真实用户工程规模、素材尺寸、编码和操作轨迹；
- 真实素材与合成素材成对跑，单独报告两者差异；
- 以同机对照、p50/p95、长任务和最大帧间隔为主要指标；
- 未取得跨平台样本前，未校准阈值只作 advisory。

### Phase 3：扩展到 ProductionRun / 导出 / 恢复

- 把授权、批量、失败恢复、保存、重启、导出纳入同一套真实任务链；
- 付费任务与零花费任务分开，所有真实花费保留收据；
- 用用户结果和重复失败类驱动下一轮优先级。

## 9. 设计卡

### ★1 用户怎么用

真实创作者从一句 brief 起草分镜，修改模型 / 比例 / 时长，设置跨镜引用，先生成一镜，再生成剩余镜头，最后 reload / restart 并继续编辑；新界面任务另带新手 / 老手人设。每一步记录预期和实际，验收必须覆盖真实页面输入、真实素材和真实工具轨迹，并把指标写在本格而不是另开指标卡。

### ★2 谁说了算

体验验收编排由 `tests/ux/full-walk`、`tests/ux/journeys` 和 `evals` 的现有 owner 负责；各产品能力仍由生产代码的现有 owner 决定。新指标不得在测试脚本中复制业务真相。

### ★3 一致与复用

复用现有 full-walk 铁律、storyboard coverage、eval run/score、feel observer、性能启动器和真实媒体 fixture；只新增统一任务目录、指标卡和报告编排，不新建第二套状态机、第二套网络闸或第二套性能夹具。

### ★4 全状态

必须覆盖：空白、起草中、方案可编辑、参数展开、引用已连接、单镜生成中、部分完成、生成剩余被依赖阻断、批量进行中、失败、可重试、暂停、reload、restart、英文、最小窗口、真实素材导入和导出前后。

### ★9 验收与回滚

本 PR 的验收是设计卡字段、逃逸账本种子、catalog 预期列约定和三条铁律规格通过文档 / 索引 / diff / preflight 门禁，且 PR #1014 收到协调会话确认。后续 Phase 1 需由另一条验收线在真实 Electron 上跑 S1–S8，报告截图和原始轨迹。回滚为 revert 本 PR；本方案不宣称任何尚未执行的真实媒体、Windows、供应商或付费证据。

## 10. 完成标准

只有以下条件同时满足，才可以说“综合体验验收体系落地”：

1. Phase 0 的设计卡 ★1 / ★9、逃逸账本、catalog 预期列约定和三条铁律规格齐全；
2. storyboard S1–S8 每条都有真实 Electron 入口、状态矩阵、指标和证据路径；
3. Agent 改动才要求留出集 / pass@k / 单变量爬坡，其他改动不借此扩张门槛；
4. 结果、交互、视觉、Agent、性能五个面都能在报告中逐项对账；
5. 独立验收线发现的问题能回写到任务目录、根因或逃逸账本，而不是只留下口头反馈；
6. 报告明确区分已观察、已实现、已验证、未验证和被跳过的范围。

## 11. 方法依据

- [Anthropic：Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)：生产任务分布、人工校准 grader、train/test 留出集、单变量改动、噪声与回滚。
- [Google Research：Measuring the User Experience on a Large Scale](https://research.google/pubs/pub36299/)：指标必须从用户结果出发，而不是只统计系统内部事件。
- [web.dev：Web Vitals](https://web.dev/articles/vitals)：性能指标应覆盖加载、交互和视觉稳定性，并用分位数描述真实用户体验。
- Nomi 现有 [全功能走查纪律](../engineering/full-walk.md)、[storyboard 表格覆盖矩阵](2026-09-25-storyboard-table-coverage.md) 和 `tests/ux/full-walk`：本方案优先收拢现有资产，不复制第二套测试框架。
