# 设计卡：删结果时「文件还有没有人用」改成整份项目内容扫描

改动名：素材文件存活判定改为整体保守扫描　　类别：[其他]（会丢用户文件的修复；不碰花钱 / 长跑 / 可打断 / 新界面）

## 来由（症状 / 直接原因 / 类根因）

- **症状**：创作者把一张生成图选去当分镜镜头的参考图（或另一个节点的参考、或贴进助手输入框），再回画布把原来那个结果删掉。到撤销窗口过去、切换或关闭项目时，这张图的文件被移进系统废纸篓；分镜 / 节点 / 助手里的引用还指着它，文件没了。已发 0.24.0 / 0.24.1 都是这个判定，更早版本有同型遗漏（分镜参考绑定自 0.22 起就有）。
- **直接原因**：`src/workbench/assets/assetResultDeletion.ts:73` `isProjectFileReferenced` 只读四处：节点白板图层、节点当前 / 历史结果的地址与封面（含结果里的白板）、时间轴片段地址与封面。分镜方案 `storyboardDesignsByDocumentId[].plan.shots[].referenceBindings`、普通节点 `meta.referenceImageUrls`、助手输入 `projectAgentAttachments` 都不在里面。
- **类根因**：「谁引用了这个文件」靠手工逐项列举位置。每加一种引用位置就得有人想起回这里加一行；没人想起来，就丢文件。门岗也拦不到：判定的输入是一个手写的形状 `{ nodes, timeline }`，新字段天然不在里面。

## ★0 先查别人

- Obsidian 论坛「Where did some of my pics (attachments) in a canvas go?」（https://forum.obsidian.md/t/help-where-did-some-of-my-pics-attachments-in-a-canvas-go/88038）· 一个「附件被笔记用着就不删」的插件只认笔记里的链接，后来加入的画布文件不在它的名单里，画布里的图被删、找不回 · **确认了**类根因判断：按位置列举的引用表一遇到新的引用载体就漏，和我们漏分镜参考同一型；因此不再列举位置。
- Obsidian 插件 Clear Unused Images Plus（https://community.obsidian.md/plugins/clear-unused-images-plus）· 扫整库的 Markdown、wikilink、画布文件、frontmatter 做引用全集，再和磁盘文件比；「引用扫描没跑完，附件目录一律保留」· **确认了**两件事：判定用「整份内容扫描出引用全集」；读不全 = 保留（本卡第 3 条要求「拿不到完整内容一律保留」照此）。
- git gc 文档（https://git-scm.com/docs/git-gc）· 标记清扫：凡是从分支、标签、index、reflog、`refs/*` 任何一处能到达的对象都保留，不可达的还要再过宽限期（默认两周）才删；并明说「和别的进程并发时有误删风险，靠宽限期降低」· **确认了**「根集合要全、宁可多留」的取向；**改了**一个细节：我们已有的「撤销窗口过去才真删」就是宽限期，不再另加计时；但撤销栈本身是不是根，要按会话还活不活着分（见 ★2「会话撤销材料」）。
- 出口：不涉及：这次没有新增、扩大或挪动会挡住人的保护——判定只会把更多文件判成「有人用、保留」，删结果、撤销、关项目的操作本身都照旧放行，界面上没有新的拒绝或等待。

## ★1 用户怎么用

- 当我把一张生成图挂到分镜镜头 / 别的节点参考 / 助手输入框里，再删掉产出它的那一版结果时，我想要被挂着的那张图一直在，以便分镜和后续生成还能用它。
- 步骤：①画布上出图 A；②在分镜镜头的参考格「＋选图」选 A（或拖进另一个节点的参考列表、或贴进助手输入框）；③回画布在版本卡片上删掉 A 那一版（或在素材库删）；④继续干活、撤销日志滚过 80 步，或切换 / 关闭项目；⑤重开项目；⑥分镜 / 节点 / 助手里 A 还在、能打开。
- 不做什么：不做 Nomi 内的回收站 / 还原入口（新界面，另议）；不改素材的导入、身份、来源；不承诺找回已经进了系统废纸篓的文件；不改存储格式。
- 已知坑：①整份扫描会把被删那一版自己的回显也扫到——扫描前必须先把要摘的结果摘掉、并把待删清单本身排除，否则什么都删不掉；②会话撤销材料（时间轴撤销栈等）在关项目那一刻不能再算「有人用」，否则文件永远删不掉；③素材库列表也问这个判定，列表每一项各扫一遍会卡死，必须一次扫描建索引、逐项查。
- 真实任务：三条都是查证线已在真画布 store + 真删除入口 + 真存盘上实跑证实会丢的流程——（a）分镜镜头参考绑定；（b）普通节点参考列表；（c）助手输入框附件；外加对照（d）时间轴片段（今天就保留）和（e）真的没人用了的文件（必须照旧被回收）。
- 指标：主指标「被引用文件在 引用 → 删结果 → 关项目释放 → 重开清扫 之后仍在原路径的比例」，目标 3/3 情形 100%，量具 `src/workbench/assets/assetLiveness.realStore.test.ts`（新）；护栏指标「真的没人用的文件仍被回收的比例」目标 100%，量具同上对照组 + 现有 `assetDeletionMatrix.test.ts`；性质指标「往项目持久内容任意字段放一个文件地址都判保留」，量具新的性质测试；性能见 ★7。用户侧真实丢失率：未验证：缺量具（没有遥测记录文件被回收后又被引用）。
- ★1b 连带界面：素材库删除后的提示里「还被用着、没删」的计数（`keptInUseCount`）会比以前多，现有文案「被别处用着」已覆盖，不改文案；素材库列表里「已删待回收」的隐藏规则读同一个判定，被分镜等引用的文件以后不会被藏起来。没有新回执、新通知。
- ★1c 老用户：升级后判定只会比以前留得多（旧的四处都还在扫描范围内，扫描是超集），不扩大删除范围；项目文件里已有的待删清单 `pendingAssetDeletions` 不迁移，释放前（撤销挤出 / 关项目 / 重开清扫）照旧逐条判，判的就是新判定，所以旧清单里还被分镜等引用的条目会被「只销账、不删文件」；已经进了系统废纸篓的不管、也不承诺找回；退回上一版打开不受影响（存储格式不变）。证据：旧版本数据 `tests/fixtures/old-user-data/` 里带 `pendingAssetDeletions` 的项目重开清扫一次（没有带这一栏的旧夹具就写明，并用 0.24.1 存出的项目形状补一份）。

## ★2 谁说了算

- 概念：`asset.deferred-file-deletion`（owner 符号 `isProjectFileReferenced`）与 `asset.library-deletion`（owner 符号 `planAssetDeletion`），沿用现有两条登记，不新建概念；只更新 notes。

  - `collectProjectFileReferences(nodes, rest)`：对「摘掉这次要删的结果之后的画布节点」和「其余整份内容」整体走一遍（显式栈，对象的键、Map、Set 也走；节点的 `runs` 不走——它回显的是那一次落盘的文件），把每个字符串规范化后收进引用索引（规范化见下）；
  - `isProjectFileReferenced(target, references | null)`：查索引；`null` = 拿不到完整内容 → 一律 `true`（保留）。
- 「项目内容」只有一个装配口 `src/workbench/assets/projectLivenessContent.ts`（`readLoadedProjectLivenessContent(projectId, moment)` / `closedProjectLivenessContent(payload)`；写盘投影抽到 `src/workbench/project/workbenchProjectContent.ts` 的 `readCurrentWorkbenchProjectContent()`，写盘与扫描共用）：
  - 已加载项目：`readCurrentWorkbenchProjectContent()`（就是写盘用的那个函数——写盘多一个字段，扫描自动多一个字段）去掉 `pendingAssetDeletions`、并把画布节点换成「摘掉这次要删的结果之后」的那份；外加不进项目文件、但属于这个项目会话的「还没发出去的输入」：助手输入框附件 / 引用、找回的未发草稿；外加「会话撤销材料」（时间轴撤销 / 重做栈、删节点摘下的片段），只在会话还活着时算（关项目那一次释放不算——撤销栈马上清零）。画布撤销日志不进扫描：它已经由「撤销窗口过去才真删」的日志位置机制管着，进扫描会让任何删除都要等关项目。
  - 画布 store 还没载完（`isReady` 不为真）、当前 `projectId` 和目标文件的项目不一致（清扫期间换了项目）、或装配抛错 → 返回 `null` → 保留。
  - 普查表 `PROJECT_SESSION_FIELD_ROLES`（放在 `src/workbench/project/workbenchProjectContent.ts`，和组成载荷的那段在一起，加载荷字段时归类跟着改）：每个声明为「项目寿命」的 store 字段归一类（写盘 / 会话未发输入 / 会话撤销材料 / 不装引用 + 理由 / 界面状态），`projectLivenessContent.census.test.ts` 守。
  - 关闭的项目：读盘得到的整份 `payload`（同样去掉待删清单、换上摘后的节点）；读不出就照旧报错不删。
- 消费者（数门：`node scripts/door-map.mjs isProjectFileReferenced` 2 个文件 3 处；`planAssetDeletion` 1 扇；`deleteAssetResult` 4 扇——素材库多选、素材库单张、浏览器素材盒经能力转交、版本卡片；`trashProjectFiles` 2 扇）：
  1. 删除计划 `planAssetDeletion → fileFate`（当场判 trash / keep）；
  2. 延后回收 `pendingAssetDeletions.release`（撤销挤出、关项目两个到点口）；
  3. 重开清扫 `sweepPersistedAssetDeletions`（同一个 `release`，在 `draft-save` 交接处上，照它的图走，不升级验收状态）；
  4. 素材库列表的「已删待回收不列」`isAssetFileAwaitingTrash / withoutFilesAwaitingTrash`（只读；任务书只数了前三处，这是第四处，同样只问这个判定）。
- 同一事实几处：判定 1 处、内容装配 1 处；删掉旧的逐项列举 `resultReferencesFile` / 节点白板逐项读 / 时间轴逐项读，不留兜底。
- 不扫的持久数据（协调裁定选 A：不扫；进普查归类表 `MAIN_PROCESS_RECORDS_NOT_LIVE`）：助手已发出的对话历史（主进程转录里存的是素材身份 claim，不是地址；文件不在时历史里画「附件不可用」，这是设计好的显示状态，`electron/agentLane/laneDesktopAttachments.ts:10`）；制作运行的产物台账（主进程，记录的是过去发生过什么）；主进程里存的未发助手草稿（同样按 claim 存）。这三份都在主进程，渲染层同步拿不到；要算它们得给每次判定加一次 IPC 往返和主进程读盘。任何「拿不到」都不变成「判没人用」——这三份不是「读失败」，是按设计不算存活引用。
- **已知限制**：主进程里排队、还没发出去的助手输入（按 claim 存，不是地址）不算引用；创作者把一张图贴进助手输入、在它发出前删掉产出它的那一版并关项目，这张图可能被回收。渲染层输入框里的附件照算（第 1 条）。
- 没有靠「东西不见了」猜意图：删除仍是用户显式点的删除。

## ★3 一致与复用

- 以前定过什么：2026-10-06 起延后删除与当场删除共用一个判定（之前延后那条路自己拿子串包含判，两套）；2026-10-12 加了结果里的白板图层；2026-10-24 显式判定 `planAssetDeletion`（`docs/engineering/direction-checks/2026-10-24-asset-library-delete-verdict.md`）——那次写明「沿用现有引用判定，不是新规则」。都还算数：一个判定、三（四）处消费、当场 / 延后两条执行路径都不变，这次只换判定的输入范围和比较方式。
- 三条路：
  - 沿原方向修（在列举里补分镜、节点参考、助手输入三行）：最小，但正是类根因本身，下一种引用位置照样漏（Obsidian 那条就是这么丢的）。不选。
  - 换做法——整体保守扫描（协调定的方向）：**确认，选它**。证据：项目的持久内容在渲染层已经有唯一的装配函数 `readCurrentWorkbenchProjectPayload`（写盘就用它），拿来扫就天然覆盖以后新加的持久字段；三种已证实的丢失位置全在这份内容或会话输入里；关闭项目的那条路本来就读整份 payload。替代方案「引用计数」（每处写引用时 +1、解除时 −1）要求每一个写引用的入口都记账，入口比判定多得多，漏记同样丢文件，不选。
  - 删掉（不再删文件，只摘结果）：最安全但把「删了版本、文件进回收站」这条已拍板的行为整个拿掉，盘会越积越多；不选。
- 规范化（地址的几种写法，比较前统一成「项目 id + 相对路径」或「相对路径后缀」）：
  1. `nomi-local://asset/<项目>/<路径>`：逐段解码（只在含 `%` 时解），去掉 `?` `#` 之后的部分；复用现有 `parseNomiLocalAssetUrl`；
  2. `nomi-local://production-preview/<项目>/<run>/<artifact>/<路径>?preview=…`：取项目和路径；
  3. 长文本里夹着的地址（原稿、提示词、富文本节点 JSON 的 `src`）：在字符串里找出每一段 `nomi-local://…` 逐个按 1/2 解析；
  4. 裸相对路径与带前缀的路径（`assets/generated/a.png`、时间轴的 `asset:<路径>` 与 `asset:<项目>:<路径>`、`file://` 或绝对路径指到项目目录里）：按路径段后缀比对相对路径（没有项目 id 可核，宁可多留）；段里带冒号的，冒号前后两种切法都记；
  5. 统一：`\` 换 `/`、Unicode NFC、按不区分大小写比（macOS / Windows 文件系统默认不区分大小写）。
  `nomi-local://asset/` 地址带着别的项目 id 的，不算本项目文件的引用（跨项目复制会生成另一份文件）。`data:` 开头的字符串、不含 `/` 或 `\` 的字符串跳过（快路径，见 ★7）。
- 复用：`parseNomiLocalAssetUrl`、`readCurrentWorkbenchProjectPayload`、现有 `applyAssetResultDeletion`；不引新库（JSON 树遍历几十行，P0：领域内的「哪些内容属于项目」才是这里独有的）。

## ★4 全状态

- 空（项目没有任何引用）：判 trash，和以前一样进回收站（护栏）。
- 加载中（项目还没载完、store 的项目 id 不是目标项目）：判保留，待删条目只销账不删——宁可多留一份文件在盘上。
- 成功：被任何一处引用 → 保留，素材库提示计入「被别处用着」；没人用 → 照旧延后 / 当场进回收站。
- 失败：关闭项目读盘失败照旧报错、什么都不删；进回收站失败照旧记失败次数、到上限放弃。
- 部分成功：多选删除逐项判，每项独立。
- 取消中 / 过期：删除没有取消态；撤销照旧在撤销窗口内把版本找回。
- 能力不可用：不适用：判定不依赖模型或外部资源。
- 文案：不新增、不改文案（`check:i18n` 不涉及）。

## ★7 性能

- ①操作：素材库删除 / 版本卡片删一版（点击到提示，同步判定）；切换 / 关闭项目（释放前同步判定，排在 store 换项目之前）；重开项目后的后台清扫；素材库列表在有待删条目时的过滤（每次列表重算）。
- ②最坏规模（以仓库现有最大画布场景 600 节点为上限往上放）：600 个节点 × 每个 20 版结果（1.2 万条结果，10% 带白板图层 8 张）、每个节点参考列表 4 张；分镜 20 份方案 × 50 个镜头 × 每镜 3 张参考绑定；时间轴 500 个片段；20 篇原稿 × 8000 字（夹 20 个地址）；助手输入 20 个附件；待删清单 50 条；素材库列表 1000 项。
- ③预算：一次整份扫描建索引 ≤50ms（中位数，Apple M 系列；占「操作到可见反馈 ≤100ms」的一半，剩下留给 store 更新和存盘）；单个文件查索引 ≤0.01ms；列表 1000 项过滤 = 一次扫描 + 1000 次查表 ≤60ms，且同一份 store 状态只扫一次（按 store 引用记忆）；关项目释放 50 条 = 一次扫描，不随条目数线性变慢。超预算 → 停下报协调（停点「代价超出预算」）。
- 实测（`node tests/perf/asset-liveness-scan-bench.mjs` 直接跑，本机 Apple M 系列，最坏规模）：首版 `scanMs` 约 72ms 超预算 → 加快路径（不含路径分隔符的字符串跳过、整串就是一个地址时直接解析、纯 ASCII 只做小写、只在含 `%` 时解码）后 5 次 `scanMs` 45 / 29 / 31 / 34 / 29，中位约 31ms；`lookupMs` 约 0.0003ms；`listFilterMs` 约 31ms。场景冒烟数字见 PR 正文。
- ④场景：新登记 `asset-liveness-scan-worst`（`tests/perf/node-json-bench.mjs` + 新量具 `tests/perf/asset-liveness-scan-bench.mjs`，用 tsx 直接载入真函数，造上面那份最坏规模内容，量 `scanMs`（主）/ `lookupMs` / `listFilterMs`），`budgetStatus: proposed`，实现线贴冒烟和 5 次数字，基线由协调写。

## ★9 验收与回滚

### 真实场景复现

- 用户的流程：查证报告里的创作者场景（选生成图当分镜参考 / 节点参考 / 助手输入 → 回画布删掉那一版 → 切换或关闭项目 → 文件进了系统废纸篓）。
- 我走的：真画布 store + 真 `deleteAssetResult` + 真 `writeWorkspaceManifest` 存盘 + 真 `nomi:workspace:delete-files` 主进程处理，三种情形各走「引用 → 删结果 → 关项目释放 → 重开清扫」；对照组时间轴、真没人用。
- 差别：真闭环测试没起窗口；第 10 条真窗口走查补上分镜参考这一种的真手势（选图走选择器，不是拖拽）；节点参考列表与助手输入两种没有真窗口走查。系统废纸篓：单测用临时目录替身，走查用一次性磁盘映像卷自带的废纸篓，不碰真废纸篓。
- 修前：在主分支上同一测试三种情形红（文件被移走）、对照组绿，留日志；真窗口走查修前在主分支代码上跑一次留红证——实测文件被移进映像卷的回收站、重开后不走缓存的读取解不出像素；同一次运行里参考小图仍靠内存缓存显示，裂图那一帧没拍到（见第 12 条）。
- 修后：三种情形绿（文件在原路径、引用还在）；对照「真没人用」照旧被回收。

### 验收清单（实现线按它自验，验收线只核它）

1. 三种已证实情形（分镜参考绑定 / 节点参考列表 / 助手输入框附件）在 删结果当场判、撤销挤出释放、关项目释放、重开清扫 四个点都判保留，真文件在原路径。
2. 门数出来的其它位置也判保留：节点 `prompt` / `references` 字段、节点 `meta` 任意字段（含 `artifact.url`）、别的结果的地址 / 封面 / 白板、原稿正文里夹的地址、分镜方案里的首帧规划图、时间轴 `asset:<路径>`、找回的未发草稿附件、时间轴撤销栈（会话活着时）。
3. 被删的那一版自身的回显不算引用：真没人用的文件，当场 / 延后 / 清扫三处都照旧回收（现有 `assetDeletionMatrix.test.ts`、`deleteAssetResult*.test.ts` 全绿，不改它们的期望）。
4. 读不到完整内容 → 保留：store 项目 id 不是目标项目、装配抛错，都判保留。
5. 待删清单释放前用新判定重判：旧版本存出的项目文件带 `pendingAssetDeletions`、条目只被分镜引用 → 重开清扫只销账、文件还在。
6. 规范化：同一文件的五种写法（编码不同 / 带查询串 / 夹在长文本 / 裸相对路径与 `asset:` 前缀 / 大小写或 NFD）都判保留；别的项目 id 的同名路径不算引用。
7. 性质测试：往项目持久内容（写盘那份 payload）里任意一个新字段、任意深度放一个文件地址，判定必须保留；另有一条普查：工作台 store 里声明为「项目寿命」的字段，每一个要么在写盘 payload 里、要么在会话输入 / 会话撤销材料清单里、要么在「不装引用」清单里带理由——新加一个项目寿命字段没归类就红。普查是遍历源码的扫描型测试，登记进 `scripts/pre-push-scan-guards.mjs` 的 SCAN_GUARDS；性质测试不读源码、随单测跑，不登记。
8. 性能：`asset-liveness-scan-worst` 冒烟 + 5 次，中位数在预算内。
9. 关项目那一次释放不把会话撤销材料算作引用（否则文件永远删不掉）。
10. 真窗口免费走查（协调裁定新增）：`tests/ux/asset-liveness-storyboard-ref.walk.mjs`，隔离资料目录、不连供应商、只跑 zh 一轨——把一张已有结果经镜头参考格的「+」选作分镜参考 → 回画布在版本卡上删掉原结果 → 回项目库关项目 → 断言文件还在原路径、没进回收站 → 重开后分镜参考图能显示。修前在主分支代码上跑一次留红证。项目放在一次性磁盘映像卷上，修前那一跑文件进的是映像卷自己的废纸篓。
11. 素材库列表的记忆随 store 变化失效：同一份 store 状态只扫一次，store 一变就重扫（`assetLivenessScan.test.ts`）。
12. 给验收线（实现线的走查做不到）：按第 10 条走到关项目后，退出应用，用同一份资料目录重新启动、打开项目进分镜。修后参考格应该还显示这张图；修前应该是裂图。第 10 条的走查不重启应用，同一次运行里小图靠内存缓存还显示着，所以它只能用「文件在不在原路径、不走缓存的读取能不能解出像素」来判，拍不到裂图那一帧。

### 反例（每条：改坏 → 哪条检查红 → 还原 → 绿）

- 恢复逐项列举、漏掉分镜参考 → 第 1 条真闭环测试 + 第 7 条性质测试红。
- 读失败时判成没人用（装配返回空内容而不是 null）→ 第 4 条红。
- 待删清单释放前不重判（release 直接删）→ 第 5 条红。
- 规范化漏掉一种写法（例如不去查询串 / 不认长文本里夹的地址 / 不比大小写）→ 第 6 条对应格红。
- 扫描没排除待删清单本身或没先摘被删的那一版 → 第 3 条红（什么都删不掉）。
- 关项目释放时仍算会话撤销材料 → 第 9 条红。
- 新加一个项目寿命 store 字段不归类 → 第 7 条普查红。
