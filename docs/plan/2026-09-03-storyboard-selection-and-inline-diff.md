# 分镜表：选中即引用 + 改动就地预览

状态：✅ **样张已拍板**（2026-09-03，用户逐轮确认）

> ⚠️ 本文档是**方案**，不是现状。现状见 `docs/ARCHITECTURE-NOW.md`。

## 0. 要解决的真实摩擦

`patch_shots` 落地后，Agent 能改分镜了，但「改**哪一镜**」是模型从用户的话里**猜**出来的
（「第 3 镜」→ `indexes:[3]`）。于是要操心序号漂移、要加版本令牌防串台。

用户一句话点破：**让他自己点。** 点了就没有"指错"这回事——寻址问题不是"让模型指得更准"，
是**根本不让它指**。这与本轮反复用的手法同源：把「求它做对」换成「让它做不到错的」。

## 1. 三个选中粒度（其余不做，有判据）

判据：**能一键点到的东西，不该拿去跟 AI 说。** 时长有下拉、模型有下拉、参考有 `@`、画幅有胶囊——
这些点一下就改完，让 AI 代劳更慢。对话的价值只在**点不出来的东西**上。

| 选中 | 引用的是 | 对应说不清的意图 |
|---|---|---|
| **整行** | 这一镜整体 | 「这镜改成近景」 |
| **画面格** | 已生成的**产物** | 「这张脸糊了」——讲的是图，不是镜头设定 |
| **一段提示词文字** | 那个范围 | 「这半句太干」 |

不做：参考 tile、参数胶囊（各有直接控件）。

## 2. 引用胶囊住在输入框**内部**（用户 2026-09-03 亲自纠正）

**现状是错的**：`ProjectAgentResidentShell.tsx:768` 把 references/skill/prompt 胶囊排成
框**外**独立一行，`AutoGrowTextarea` 在 769 行的另一个盒子里——**两个盒子**。

后果是胶囊的生命周期模糊：发完消息它该消失还是留着？用户看不出来。

**改后一个盒子**：胶囊与正在输入的文字同处一个边框内 = 它们是同一条消息，一起发、一起清空。
这也与 `AttachmentRail` 的语义一致（附件本来就跟消息走）。

三条实现约束：
- `maxHeight={120}` 改为**只管文字部分**，否则胶囊多了会把输入区挤没。
- 胶囊超过 3 个**折叠成「第 3 镜 +2」**，点开展全部——比现状的 `max-h-14 overflow-y-auto` 干净。
- **附件轨（AttachmentRail）留在框外**：它带缩略图、比文字胶囊高得多，进框会把输入区挤满。
  语义上也不同——附件是「我传了个文件」（持久物），引用是「我指的是这个」（消息的一部分）。

## 3. 改动就地预览（文字选区）

**关键认识**：范围漂移不是技术问题，是交互问题。模型返回**改后的完整文本**，用户看 diff 后
批准即整段替换——不做区间拼接，漂移问题被「批准」这一步吃掉。

**选型实查结论（2026-09-03，非记忆）**：

| 候选 | 判决 |
|---|---|
| `react-diff-viewer` / `react-diff-view` | ❌ 是**代码 diff 查看器**（分栏/行号/语法高亮/吃 git unified diff），形态完全不匹配「一句 30 字中文在输入框内显示改动」 |
| Tiptap **Tracked Changes** | ❌ 能力正确（`acceptSuggestion`/`rejectSuggestion`）但是**付费 add-on**（Cloud $49–999/月） |
| `sungkhum/tiptap-track-changes`（开源） | ❌ Google Docs 式**全文档修订模式**，量级差太远——我们要的是一次性、局部、用完即走 |
| **ProseMirror `Decoration.inline`** | ✅ 这不是持久修订状态，是**一次临时视觉叠加**。仓里 Phase C 骨架段已在用同一机制 |
| `Intl.Segmenter`（中文分词） | ✅ **JS 内置、0 KB、0 依赖**。已实测：「远景/，/雨夜/中的/主角」切得干净 |

**实测暴露的坑**：新造词分词器认不出（「雨幕里被路灯拉长影子的」被切成 9 段）。
故 diff 必须**把连续变动合并成一段**再渲染，不能逐词标红绿，否则一堆碎块。

**视觉**：删除用删除线 + 弱化（`text-tertiary`），新增用 `background-info` 高亮。
**不用红绿**——红绿在本 token 体系里是 danger/success，用在这里等于说「改动是个错误」，语义错配。

**三个按钮不是两个**：采用 / 丢弃 / **直接在框里接着改**。
前例是 `GenerationProposalEditor`——确认卡上的参数本来就可编辑。模型给的十有八九是
「差不多但不完全对」，只能二选一会逼用户为一个词而整段重来。

## 4. 设计系统对账（§1.5 / §1.6）

- 选中态用**左侧竖条 + 底色微提**，不加边框不加浮层 —— §1.5「动作不许压在内容上」
- 「采用/丢弃」**贴提示词框就近浮现**，不进上面那排 chips —— §1.5.3「情境控件不许挤常驻条，否则布局会抖」
- 三种选中**用不同 icon 区分**，不用颜色 —— 颜色在暗色模式下不稳，icon 是语义的
- 引用胶囊带 `×` —— §1.6 C2「作用域跟选中走」，必须能明确取消
- 画面格选中态：样张里用了 info 底色，**真实场景那格有图会被盖住 → 实现时改用外圈描边**
  （样张骗人的地方，已标出）

## 5. 不动项 / 回滚 / 验收门

**不动**：`patch_shots` 的契约与执行器（本方案只改它 `select` 的**来源**：从模型猜 → 用户给）；
`propose_storyboard_plan`；参考 `@` 机制；生成与花费闸。

**不做并行版（P1）**：不新建「局部编辑工具」。就地 diff 是让 `patch_shots` 从「改完直接落地」
变成「改完先挂起、等批准」，是同一个工具的两个阶段，不是两个工具。

**回滚**：胶囊位置改动是纯 UI，可单独 revert；就地 diff 是新增，摘掉即回现状。

**验收门**：
1. 五门全绿；
2. 与本文档 §2/§3 逐项对账 + **真机截图人眼确认**（R13）；
3. 三个选中粒度各走通一次真实任务（R16）；
4. **中文 diff 不碎**：造一个新造词的改写，确认渲染成连续段而不是逐字碎块。

## 6. 未定（需用户再拍一次）

多镜批量改时的确认粒度：**全部采用 + 单条可否决**（我的倾向）vs 逐条勾选。
取决于用户实际会不会真的逐条看，样张未画。

## 7. 下一批（已讨论、待出样张）

### 7.1 锚区（跨镜头要一致的）补齐生成控制

**实查确认的不对称**：镜头行有模型/画幅/时长胶囊 + 可编辑提示词；锚卡**一个都没有**——
它用 `resolveDefaults()` 的默认模型、`buildAnchorSheetPrompt()` 自动拼的提示词生成，
用户对「怎么生成」零控制、零可见。

**这个不对称是反的**：锚是一致性的源头，一张锚图不满意影响 8 个镜头，一个镜头不满意只影响自己。
**控制最该多的地方反而最少。** 而且「出图不对」最常见的两个解法——换模型、换画幅——完全没有入口。

做法（用户 2026-09-03 拍板）：
- 锚卡展开成**与镜头行同构的一行**，补**模型 + 画幅**两个胶囊（不补时长：锚是图不是片）
- **生成按钮留在画面格里**，不进胶囊排 —— 镜头行和锚卡现有实现**都是这么做的**，
  我第一版样张把它挪进胶囊排是自己瞎改，被用户当场指出
- **引用机制一个字不动**：`scope`（style 默认 all、其余 selective）+ 镜头 `anchorIds` 唯一持有
  + `onToggleAnchor` 加删 + `@` 回写 —— 这套已经是「自动引用 + 可加可删」，不许在旁边再造一套
- 两态由**状态 derive**，不记开关：有锚未出图 → 默认展开（还有活没干）；全部锁定 → 默认收起
  成一条真图带（不是文字，下面调镜头时抬眼能看见主角长什么样）
- 收起态高度 144px → 约 66px

### 7.2 参数：用**摘要 pill + 统一参数面板**，不是「露几个收几个」

> ⚠️ **本节已被推翻重写（2026-09-03，Codex 核实）。** 原版提的是「露 1–2 个、其余收 ▾」，
> 依据是 `NodeGenerationComposer.tsx:692` 那条注释「最常调的内联、其余收起」。
> **那是一条过期注释，描述的是已被替换掉的方案 B。**
> 更糟的是：我提的正是那个**被明确否决**的方案，连否决理由都写在权威实现里。

**当前权威实现**：`InlineParameterBar.tsx:80-84`，2026-07-17 用户拍板，
样张 `docs/design/mockups/node-param-panel.html`：

> 底栏 = 模型芯片 + 变体 + **摘要 pill**（当前参数一句话）。
> 点摘要 pill 弹**统一参数面板**：每个参数一组「小标题 + 分段选择器」，点即改、面板不关。
> **替代旧「前 2 内联 + 更多弹层」方案 B** —— 参数多时内联下拉挤、**分层线武断**；
> 摘要 pill 让当前配置一眼读完、面板给全部参数。
> 「生成方式」（文生/图生 tab）保持在 composer 顶部不进面板。

**所以分镜行该做的是**：底沿放**模型芯片 + 摘要 pill**（一句话读完当前参数），
点 pill 弹同一个统一参数面板——**复用 `InlineParameterBar` 那套，不另画分层**。

位置结论不变（从提示词上方挪到下沿、不增加行高），**变的是"下沿放什么"**：
不是「挑 1–2 个露出来」，是「一句话摘要 + 一个入口」。

**这条的教训比结论重要**：我把一条过期注释当权威原则引用了。
注释会过期而没人删——`ARCHITECTURE-NOW.md` 的存在就是为了给出"现在真正跑的是什么"，
而我没查它。同一个毛病今天第五次。

### 7.3 参考区是**模型声明式**的——锚行同构时别画死格子数

用户 2026-09-03 提醒：「不同模型需要的参考数量、参考模式都不一样」。实查确认**这已经是既有行为**，
不是要新设计的东西——`shotRowModel.ts:85 referenceZoneView()` 完全由 `ArchetypeMode.slots` derive：

| 情况 | 渲染 |
|---|---|
| 模式声明具名槽（首帧/尾帧…） | 按槽渲染，**几个槽就几格** |
| 模式吃数组参考（`image_ref` 等） | 通用 `@` 入口 |
| `mode.slots.length === 0` | `none-accepted` ——「此模型不吃参考」，整格换成一句说明 |
| 无档案的默认模型 | 按最宽形态：已引用的锚 + `@` 占位（契约未知不假装知道） |

**我的样张把这一格画成了固定两个 tile，是简化出来的假象**——真实情况是换个模型这格整个变样。
锚行与镜头行同构时，这一格**必须走同一个 `referenceZoneView`**，不许另画一套固定格子。

连带三条实现约束（`ARCHITECTURE-NOW.md` 已记，别重新发明）：
- **`modeId` 决定一切**：哪些槽、哪些参数、transport task kind；切模式只改变「显示哪些槽」
- 参考值按 slot 键**全局**存在 flat meta 里，**跨模式持久不清空**——换模型不该丢用户已绑的参考
- `slotReachByKey` 有运行时上限；`slot.max` 缺省 = 供应商没公布上限，**别渲染成具体数字**

**锚自己也要选模型，所以锚行同样吃这套**：锚生成时若所选模型的模式声明了参考槽
（例如「照这张脸画」），锚行那一格就该出现——不能因为「锚是被参考的」就假设它不吃参考。

### 7.4 锚行第 3 格的反向引用需要新建派生索引

样张里锚行第 3 格显示「3 镜在等它 + 那几镜缩略」，但**绑定关系目前由镜头的 `anchorIds`
单向持有**，锚不知道谁引用了它。反查可做（遍历镜头），但**不是现成的**。

实现注意：别在渲染里每行遍历一遍全表。8 镜 × 3 锚尚可，24 镜就该做成**一次性反向索引**
（`Map<anchorId, shotIndex[]>`，随 plan 变化重算一次）。
