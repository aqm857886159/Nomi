# 分镜表：选中即引用 + 改动就地预览

状态：✅ **样张已拍板**（2026-09-03，用户逐轮确认）

> ⚠️ 本文档是**方案**，不是现状。现状见 `docs/ARCHITECTURE-NOW.md`。

## 0. 要解决的真实摩擦

`patch_shots` 落地后，Agent 能改分镜了，但「改**哪一镜**」是模型从用户的话里**猜**出来的
（「第 3 镜」→ `indexes:[3]`）。于是要操心序号漂移、要加版本令牌防串台。

用户一句话点破：**让他自己点。** 点了就没有"指错"这回事——寻址问题不是"让模型指得更准"，
是**根本不让它指**。这与本轮反复用的手法同源：把「求它做对」换成「让它做不到错的」。

## 1. 三个选中粒度（其余不做，有判据）

判据：**能一键点到的东西，不该拿去跟 AI 说。** 时长有下拉、模型有下拉、参考有 `@`、画幅有胶囊——
这些点一下就改完，让 AI 代劳更慢。对话的价值只在**点不出来的东西**上。

| 选中 | 引用的是 | 对应说不清的意图 |
|---|---|---|
| **整行** | 这一镜整体 | 「这镜改成近景」 |
| **画面格** | 已生成的**产物** | 「这张脸糊了」——讲的是图，不是镜头设定 |
| **一段提示词文字** | 那个范围 | 「这半句太干」 |

不做：参考 tile、参数胶囊（各有直接控件）。

## 2. 引用胶囊住在输入框**内部**（用户 2026-09-03 亲自纠正）

**现状是错的**：`ProjectAgentResidentShell.tsx:768` 把 references/skill/prompt 胶囊排成
框**外**独立一行，`AutoGrowTextarea` 在 769 行的另一个盒子里——**两个盒子**。

后果是胶囊的生命周期模糊：发完消息它该消失还是留着？用户看不出来。

**改后一个盒子**：胶囊与正在输入的文字同处一个边框内 = 它们是同一条消息，一起发、一起清空。
这也与 `AttachmentRail` 的语义一致（附件本来就跟消息走）。

三条实现约束：
- `maxHeight={120}` 改为**只管文字部分**，否则胶囊多了会把输入区挤没。
- 胶囊超过 3 个**折叠成「第 3 镜 +2」**，点开展全部——比现状的 `max-h-14 overflow-y-auto` 干净。
- **附件轨（AttachmentRail）留在框外**：它带缩略图、比文字胶囊高得多，进框会把输入区挤满。
  语义上也不同——附件是「我传了个文件」（持久物），引用是「我指的是这个」（消息的一部分）。

## 3. 改动就地预览（文字选区）

**关键认识**：范围漂移不是技术问题，是交互问题。模型返回**改后的完整文本**，用户看 diff 后
批准即整段替换——不做区间拼接，漂移问题被「批准」这一步吃掉。

**选型实查结论（2026-09-03，非记忆）**：

| 候选 | 判决 |
|---|---|
| `react-diff-viewer` / `react-diff-view` | ❌ 是**代码 diff 查看器**（分栏/行号/语法高亮/吃 git unified diff），形态完全不匹配「一句 30 字中文在输入框内显示改动」 |
| Tiptap **Tracked Changes** | ❌ 能力正确（`acceptSuggestion`/`rejectSuggestion`）但是**付费 add-on**（Cloud $49–999/月） |
| `sungkhum/tiptap-track-changes`（开源） | ❌ Google Docs 式**全文档修订模式**，量级差太远——我们要的是一次性、局部、用完即走 |
| **ProseMirror `Decoration.inline`** | ✅ 这不是持久修订状态，是**一次临时视觉叠加**。仓里 Phase C 骨架段已在用同一机制 |
| `Intl.Segmenter`（中文分词） | ✅ **JS 内置、0 KB、0 依赖**。已实测：「远景/，/雨夜/中的/主角」切得干净 |

**实测暴露的坑**：新造词分词器认不出（「雨幕里被路灯拉长影子的」被切成 9 段）。
故 diff 必须**把连续变动合并成一段**再渲染，不能逐词标红绿，否则一堆碎块。

**视觉**：删除用删除线 + 弱化（`text-tertiary`），新增用 `background-info` 高亮。
**不用红绿**——红绿在本 token 体系里是 danger/success，用在这里等于说「改动是个错误」，语义错配。

**三个按钮不是两个**：采用 / 丢弃 / **直接在框里接着改**。
前例是 `GenerationProposalEditor`——确认卡上的参数本来就可编辑。模型给的十有八九是
「差不多但不完全对」，只能二选一会逼用户为一个词而整段重来。

## 4. 设计系统对账（§1.5 / §1.6）

- 选中态用**左侧竖条 + 底色微提**，不加边框不加浮层 —— §1.5「动作不许压在内容上」
- 「采用/丢弃」**贴提示词框就近浮现**，不进上面那排 chips —— §1.5.3「情境控件不许挤常驻条，否则布局会抖」
- 三种选中**用不同 icon 区分**，不用颜色 —— 颜色在暗色模式下不稳，icon 是语义的
- 引用胶囊带 `×` —— §1.6 C2「作用域跟选中走」，必须能明确取消
- 画面格选中态：样张里用了 info 底色，**真实场景那格有图会被盖住 → 实现时改用外圈描边**
  （样张骗人的地方，已标出）

## 5. 不动项 / 回滚 / 验收门

**不动**：`patch_shots` 的契约与执行器（本方案只改它 `select` 的**来源**：从模型猜 → 用户给）；
`propose_storyboard_plan`；参考 `@` 机制；生成与花费闸。

**不做并行版（P1）**：不新建「局部编辑工具」。就地 diff 是让 `patch_shots` 从「改完直接落地」
变成「改完先挂起、等批准」，是同一个工具的两个阶段，不是两个工具。

**回滚**：胶囊位置改动是纯 UI，可单独 revert；就地 diff 是新增，摘掉即回现状。

**验收门**：
1. 五门全绿；
2. 与本文档 §2/§3 逐项对账 + **真机截图人眼确认**（R13）；
3. 三个选中粒度各走通一次真实任务（R16）；
4. **中文 diff 不碎**：造一个新造词的改写，确认渲染成连续段而不是逐字碎块。

## 6. 未定（需用户再拍一次）
