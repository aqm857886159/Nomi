# B4 统一 Harness：给产品负责人的现状说明

**先把误解消掉：B4 目前只交付了 build-vs-buy 调研报告，统一 Harness 没有交付；B4 实施计划还没有写，B4 专属实现代码是零行。** 本文解释它是什么、为什么要做、现在手里有什么，以及下一步会怎样推进。

## 1. 先从你会看到的体验说起

你点「生成」，理想的完整体验是：任务跑起来；需要花钱时出现一张确认卡，写清楚会花多少、确认后哪些东西不能再改；你可以停；失败能从正确的位置重试；最后能回答“这次到底花了多少、为什么花”。

B4 不是另一个生成模型，也不是一个新的页面。它是**让这些行为始终由同一套现场规则驱动的控制层**。

贯穿全文的比喻是剧组里的**场记 + 制片主任**：场记把每个动作按顺序记下来，制片主任管谁能做什么、什么时候要签字、预算有没有超。四件套就是这两个人的工作拆成四个可检查的部分。比喻到这里就失效：Harness 不会写剧本、生成画面或替用户做创意决定；它只保证这些动作可追溯、可暂停、可恢复、可对账。

## 2. B4 到底是什么：四件套各管一件事

### 2.1 事件日志：场记本

**它是什么。** “事件”就是已经发生的一件事，例如“开始这一轮对话”“提出调用某工具”“用户批准”“这一镜生成失败”。“事件日志”就是只追加、不偷偷改写的时间顺序记录；把系统状态从这些已发生的事件重新算出来，叫**事件溯源（event sourcing）**。它不是让用户学一个新按钮，而是让系统在重启后有证据可回放。

**为什么要它。** 如果只把当前画面写成“进行中”，重启后没人知道它是怎么走到这里的，也无法解释钱是在哪一步被授权的。把变化记下来，系统才能回放、恢复和回答“发生过什么”。

**会发生什么。** 对话进度、工具结果、失败提示和写入回执都可以从同一条可读轨迹投影出来；但生产账本仍保持自己的更强持久化契约（见第 7 节）。

**你会看到什么。** 任务中途关掉窗口再回来，不是从一张“看起来还在跑”的假卡片开始，而是能看到停在哪一步、下一步是什么。当前通用日志的事件字段已经预留 `causeId`、`txnId`、`proposalId`，可用于把“谁导致了这件事”串起来（`origin/main:electron/events/types.ts:9-26`）。日志用 JSONL（每行一条 JSON 记录）保存；较大的附带内容会放进 sidecar（与日志并存的附属文件），避免主日志被一张大图拖慢。

### 2.2 Thread / Turn / Item：场记的分场、轮次、条目

这些是描述事件流层级的名字，不是用户要背的新产品名：

- **Thread（线程）**：一个项目里持续的对话/工作上下文，例如“这部片的创作过程”。
- **Turn（轮次）**：用户说一次、Agent 做一轮回应，直到完成、失败或暂停。
- **Item（条目）**：这一轮里可单独显示的一件事，例如“正在拆镜”“等待确认”“生成失败”“已写入 7 个节点”。

**为什么要分层。** 现在的流事件已经有 `tool-call`、`tool-result`、`tool-error`、`step-finish` 等形状（`origin/main:electron/ai/agentChatV2.ts:267-274`），但它们还不是统一的项目级产品语义。分层后，内部 Nomi 和外部 **MCP（让 Claude/Codex 等外部 Agent 接入 Nomi 的协议）** 都能把同一件事显示成各自的界面，而不各写一套状态。

**会发生什么。** 失败时可以重试某个条目，而不是把整段对话当成一团黑箱；停止时知道停的是哪一轮；回放时知道哪个确认卡属于哪个任务。

**你会看到什么。** 对话里会出现清楚的人话状态：“等待你确认本批最多花 30 点”“第 3 镜失败，可重试/换模型”，而不是一串工程事件名。这里的比喻也有边界：Thread/Turn/Item 不是把剧组真的拆成三个人，而是为了让界面、恢复和审计有共同的分组方式。

### 2.3 策略引擎：制片主任的规矩

**它是什么。** 策略引擎（policy engine）是一个集中判断器：对每个动作给出“禁止、先问用户、允许”中的一个决定。它检查能力、阶段、来源、预算、模型和当前授权，而不是相信提示词里写了“请先确认”。

**为什么要它。** 只要每个功能自己判断一次，下一次加功能就可能漏掉预算、权限或重复提交检查。规矩集中在一个地方，才不会出现“画布入口有闸门、MCP 入口绕过去”的两套真相。

**会发生什么。** Agent 只能提出方案；策略引擎决定是否要问、是否能调用；生产账本负责最终记录和扣账。弱模型能力不足时可以诚实收窄工具范围，而不是假装全自动。

**你会看到什么。** 同一个动作无论从 Nomi 内部 Agent 还是外部客户端发起，都会得到同样的“能不能做、要不要确认、预计花费”答案。当前能力核已有阶段和范围判断（`origin/main:electron/capabilityCore/mcpGenerationPolicy.ts:123-203`），但还没有成为整个 Agent 控制面的统一策略引擎。

### 2.4 单一审批信道：全剧组只有一个签字口

**它是什么。** “审批信道”就是确认请求从哪里发出、用户在哪里签字、结果如何回到任务。单一不是只能有一个画面，而是**只能有一个确认语义**：内部对话卡、MCP 客户端表单、必要时的 Nomi 浮窗，都是同一个决定的不同投影。MCP 里的 challenge 是“请你确认这件事”的请求，elicitation 是客户端提供的确认界面。

**为什么要它。** 两张卡可能让用户以为只确认了一次，实际却放行两笔生成；或者外部客户端说“已批准”，Nomi 却没有可靠收据。确认必须和范围、价格、冻结项、过期时间及收据绑在一起。

**会发生什么。** 同一个挑战并发到来时只出现一张确认面；用户拒绝、超时或窗口销毁都能收口为可恢复的结果。现有 MCP 确认绑定已经让同一 `challengeId` 共享同一个尚未结束的确认请求（`origin/main:electron/capabilityCore/mcpGateConfirmation.ts:61-64`），内部 Agent 也有超时拒绝和 Stop 共用的取消出口（`origin/main:electron/ai/agentChatV2Ipc.ts:22-45,84-105`）。

**你会看到什么。** 不会先在对话里问一次、又在 MCP 或中央弹窗里再问一次；确认卡会明确“这次确认覆盖什么、最多花多少、过闸后不能改什么”。

## 4. Nomi 已经有什么：有底座，但还不成体系

### 4.1 已有通用事件日志，但它目前是旁路观察

通用日志按项目写 JSONL，单写者递增 `seq`，有 4KB 限制、分段、sidecar 和脱敏；IO 失败只记录错误，不阻断主流程（`origin/main:electron/events/eventLogRepository.ts:1-9,218-249`）。Agent 对话已经把 turn 开始、工具提议、工具结果、批准/拒绝和 gate denied 写进这条日志（`origin/main:electron/events/agentChatTrace.ts:33-47,50-110,114-150`）。

**为什么“有但不成体系”。** 它能回答“观察到哪些对话事件”，但它不是 ProductionRun 的花费事实源；如果直接把旁路观察当账本，日志写失败或被截断就会影响钱的判断。B4 要做的是让它成为统一事件投影的入口之一，不是假装它已经拥有 Run 权威。

### 4.2 已有 ProductionRun：生产事实源、确认漏斗和账本

ProductionRun（一次生产任务的可恢复账本）用自己的事件文件、快照、命令记录、审批文件和预算账本。创建 Run 时会写 `run.created` 与 `gate.waiting`（`origin/main:electron/productionRun/productionRunRepository.ts:256-283`）；命令执行按 `commandId` 幂等（同一命令重来不会重复生效），按 `revision` 版本号检查有没有别人先改，并把 approval 与 budget authorization 写入各自文件（`origin/main:electron/productionRun/productionRunRepository.ts:360-395,399-447`）。服务层还提供事件 cursor（读到哪一条的序号）/长轮询和安全投影（把账本转换成界面能看的摘要）（`origin/main:electron/productionRun/productionRunService.ts:713-756,781-789`）。

**为什么“有但不成体系”。** 这条漏斗已经能保护真金：先形成计划，再过 gate，再授权，再提交，再对账；但对话轨迹、MCP 确认、Run 事件目前仍由不同模块各自投影。加一个新功能，工程师仍要逐处记得接日志、接确认、接预算、接恢复。

### 4.3 已有确认面和能力核，但入口仍是散装的

内部 Agent 的 `makeAgentTool` 会在工具真正执行前等待用户决定（`origin/main:electron/ai/agentChatV2.ts:276-318`）；IPC 层把批准、拒绝、gate deny、取消和窗口销毁接到同一会话出口（`origin/main:electron/ai/agentChatV2Ipc.ts:35-45,124-169`）。MCP 侧则有“客户端 elicitation → Nomi GUI fallback → 没有 surface 就拒绝”的单挑战确认路径（`origin/main:electron/capabilityCore/mcpGateConfirmation.ts:4-7,73-149`）。

**为什么“有但不成体系”。** 现在是多个已经很可靠的岗位各自守门，还没有一张共同的值班表：内部 Agent、MCP、ProductionRun 各有自己的请求形状和回执。B4 的工作是把它们接到同一个 `ApprovalDecision` 语义和同一个策略决定上，不是再造第四张卡。

## 5. 不做 B4 会怎样

每加一个功能，团队都要重新回答同一组问题：事件写哪里？用户何时被问？确认覆盖什么？中途关窗怎么停？失败重试会不会重复扣费？外部入口和内部入口是否绕过彼此？这就是“散装可靠”：单个岗位可能没问题，整条链却靠人记。

一个真实例子是“新增一个需要付费的 Agent 工具”。现在至少要同时接：内部工具确认（`agentChatV2Ipc.ts`）、MCP 的 challenge/elicitation（`mcpGateConfirmation.ts`）、ProductionRun 的 gate、approval 和预算授权（`productionRunRepository.ts`），还要把 Agent 提议和画布事务用 `causeId/proposalId/txnId` 对账（`agentChatTrace.ts:114-150`）。这里的 **Proposal（提案）** 就是“准备执行、还没落地、等待用户批准的一组参数和动作”；任何一处漏接，用户就可能看到确认卡却没有账，或账记了却无法解释是哪一轮触发。

不做的直接后果不是“少一个漂亮架构图”，而是：

1. 同一种动作在不同入口的确认、停止、重试语义继续漂移；
2. 恢复只能靠每个功能自己猜状态，不能从共同事件回放；
3. 账本、对话和产物之间的解释成本随功能数线性增加，用户会问“为什么又问一次、为什么又扣一次”。

## 6. 调研结论：为什么外面买不到一套直接装上

外部方案能买到“通用发动机零件”，买不到 Nomi 的整套控制面。通用框架不知道 Nomi 的项目资产、锚一致性、Proposal/撤销、预算收据、幂等和本地优先部署；直接引入通常会带来第二个运行时、第二份状态或第二个确认权威。

### 最反直觉的例子：AI SDK 7 看起来正好，却最不能直接接管

AI SDK 7 新增的 **durable execution**，意思是长任务的步骤和状态能持久保存，进程重启后可以接着跑；**tool approvals**，意思是模型准备调用工具时可以暂停，等人批准再继续。这两个词听起来就是“能恢复、会先问”，像是 B4 的答案。

但它们解决的是**通用 Agent 循环**问题，不是 Nomi 的钱和生产事实问题。Nomi 的 ProductionRun 账本、预算授权、收据、幂等、锚一致性和 Proposal/撤销已经是护城河，并在主方案列为“永不被反向改写”的保护项（`docs/superpowers/plans/2026-08-24-unified-agent-master-plan.md:138`）。AI SDK 的 approval 不能替代“这张卡覆盖哪几镜、最多多少钱、过闸后哪些字段冻结、这笔授权是否已落账”；它的 durable history 也不能替代 Nomi 的 Run event cursor 和预算账本。

所以结论是：**买模型抽象、流式、工具循环、标准协议适配；自建事件语义、策略、账本和审批权威。** 这里的 SDK（软件开发工具包）只是供应商提供的通用零件，不是 Nomi 的产品规则。当前 `origin/main` 仍使用 `ai@4.3.19`（`package.json:99-151`），已有 `generateText/streamText`、maxSteps、retry、repair、abort 的统一循环（`electron/ai/agentLoop.ts:1-9,42-91`）。调研建议未来只做隔离、只读的 SDK 7 compatibility spike；不能让 SDK 直接写 ProductionRun、预算或画布（`docs/plan/2026-08-26-b4-harness-build-vs-buy.md:120-145,260-292`）。

## 7. 已经拍板的决定：两条日志各走各的，用键关联

**决定：通用事件日志和 ProductionRun 事件不物理合并，各自保留自己的持久化契约；用 `runId`、`causeId`、`txnId`、`proposalId` 显式关联。** 这不是“暂时没想好”，而是已拍板的安全取舍。

### 为什么不能把两本场记本硬订成一本

两条日志故意承担不同风险：

- 通用事件日志是高频观察记录，使用 `fs.appendFileSync` 追加、**不调用 fsync**；它的设计是旁路观察，写失败不阻断产品（`origin/main:electron/events/eventLogRepository.ts:218-249`）。
- ProductionRun 是生产账本，使用 `writeSync` 后调用 `fsyncIfDurable`（`origin/main:electron/productionRun/productionRunRepository.ts:90-97`）。
- `electron/durability.ts` 是全仓唯一决定是否真的 fsync 的地方（`origin/main:electron/durability.ts:1-9,24-32,53-63`）。

**fsync 是什么。** 写盘分两步：第一步只是把字节交给操作系统的缓存；第二步 `fsync` 才是要求它真正落到物理存储。正常退出时两者看起来都能读到；突然断电或内核崩溃时，没 fsync 的那批字节可能还没落盘，甚至只剩半行。对聊天事件，逐条做这道昂贵的保险会拖慢高频交互；对真金账本，不做这道保险又可能丢掉授权记录。

如果物理合并，就被迫二选一：要么每条普通对话事件都 fsync，交互被拖慢；要么让 ProductionRun 跟着普通日志不 fsync，掉电保证倒退。**因此我们不合并文件，合并的是可查询的关联关系。**

### 四个键各自回答什么

| 键 | 大白话问题 | 例子 |
|---|---|---|
| `runId` | 属于哪一次生产任务？ | “这一批 7 镜生成” |
| `causeId` | 是哪一个事件导致的？ | “这次工具结果由哪次提议触发” |
| `txnId` | 属于哪一笔一起提交/撤销的事务？ | “整批写入回执” |
| `proposalId` | 用户批准的具体提案是哪一张？ | “确认卡批准的参数版本” |

owner 看到的仍是一条连续故事；工程上保留两种写盘速度和可靠性。比喻在此再次失效：这是两本有交叉索引的账册，不是把场记和制片主任真的关在两个房间里。

## 8. 接下来会发生什么

下面是推进顺序。每一阶段都写清你会看到什么、需要你决定什么；尚未拍板的地方不会伪装成已定。

### 阶段 0：把实施合同写出来（尚未开始）

**要做什么。** 把 `Thread/Turn/Item`、统一 `ApprovalDecision`、`PolicyDecision`、事件 envelope（事件外壳）和 upcast（旧事件读成新格式的兼容规则）写成实现计划和验收表；明确两条日志只通过四个键关联。IPC（应用内部进程之间传消息的通道）和 MCP 只负责把这份决定送到各自界面。

**你会看到什么。** 没有新 UI；你会拿到一份可审的文件清单、字段和不变量。

**需要你决定什么。** B4 v1 是否先保证恢复/审计，还是同时承诺 fork/replay（从历史分叉并重新跑一遍）；Thread/Turn/Item 的内部字段是否采用 Nomi 自有类型、只对外适配 SDK/ACP（外部 Agent 协议的事件形状）；SDK 7 隔离验证的只读边界是否维持。两条日志不合并这一项已不再是待决。

### 阶段 1：先接线，不改用户习惯

**要做什么。** 让现有 Agent trace、MCP challenge、ProductionRun gate 都写入共同的关联键，并由一个 domain decision（领域决定）向内部 IPC 和 MCP 投影。

**你会看到什么。** 确认卡长相可以基本不变，但同一次确认能在对话、Run 状态和账本里对上；不会新增第二个弹窗。

**你需要决定什么。** 确认卡上“冻结项、预估花费、过期时间”的默认文案和是否允许会话级信任推广。

### 阶段 2：策略与单循环收口

**要做什么。** 在现有 `agentLoop` 外接统一能力登记表和策略接线层，把“禁止/先问/允许”、最大轮数、预算硬顶和停止/恢复出口集中起来；旧的散装入口同 commit 收敛，不保留并行逃生口。

**你会看到什么。** 新增一个需要确认的能力时，确认、停止、失败重试和预算记录遵循同一规则；弱模型会被诚实地限制工具范围。

**你需要决定什么。** 哪些创意门允许外部客户端确认，哪些预算/导出门必须回 Nomi；当前主方案倾向前者可外部、后者回 Nomi，但还要在实施验收里钉死。

### 阶段 3：Thread/Turn/Item 投影与恢复验收

**要做什么。** 把事件流投影成对话里的进度条目、确认条、失败条、产物回执，并验证停止、重启、重试、并发确认和账本对账。

**你会看到什么。** “点生成 → 跑起来 → 要花钱时问 → 能停 → 失败可重试 → 看得到花费”成为一条可走查的闭环；内部 Agent 与 MCP 看到的是同一个 Run。

**你需要做什么。** 以真实用户任务验收：不看工程日志，只看确认是否只出现一次、停止是否真的停、重试是否不重复扣费、失败是否给下一步。

### 阶段 4：再考虑 SDK 7 兼容性，不让它反客为主

**要做什么。** 做隔离验证（spike），验证 Node/ESM（模块加载方式）、Electron bundling（把依赖打进桌面应用的过程）、事件/审批映射和性能；验证代码不写 ProductionRun、预算或画布。

**你会看到什么。** 可能得到更好的模型循环或协议适配，但不会改变账本和确认权威。

**你需要决定什么。** 只有当 spike 证明收益大于迁移成本，才讨论升级；“SDK 有 durable execution”本身不是升级理由。

## 9. 你现在应该怎样理解 B4

B4 的价值不是“换一个更大的 Agent 框架”，而是把 Nomi 已经有的可靠岗位编成一套剧组纪律：**一条可追溯的工作故事、一个统一的权限判断、一个签字口、一本不会被外部框架改写的生产账本。**

现在的真实状态是：底座和调研在，统一 Harness 不在；下一步不是宣布完工，而是先交付实施合同，再逐阶段把散装接线收成一条可恢复、可停、可重试、可对账的主链。
