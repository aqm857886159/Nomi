Toonflow
把剧本变成动画短剧

Toonflow 是一套 TypeScript 为主的小说 / 剧本到动画短剧工作台：无限画布承载创作，三层 Agent 负责决策、执行和监督，章节事件图谱与持久化记忆把长项目串起来。

一句话结论Toonflow 最值得研究的是“产品化 Agent 系统”的完整拼装：能力目录、供应商适配、事件与记忆、实时通道和桌面部署。Nomi 可以借它的能力分层和可观测性，但不应复制其服务端 store 或另起一套时间线真相源。

Positioning

从文本资产到动画成片的工作台

Toonflow 处理的不只是“生成一张图”：它覆盖 AI 编剧、智能分镜、角色资产、视频生成、章节组织、实时协作和桌面 / 服务端部署。项目以 TypeScript 为主，应用层由 Express、SQLite、Socket.IO、Electron 等组成，模型通过可编程供应商适配。

README 还描述了 Markdown Skill 文件化配置、章节事件图谱和基于 ONNX 向量检索的持久化 Agent 记忆。这些机制共同回答一个长项目问题：Agent 如何记住世界观、人物和已发生的事件，并把结果交给下一次执行。

三层 Agent

职责分离比“一个万能 Agent”更可控
决策层理解目标、拆解章节和步骤，选择下一项能力。
执行层调用模型、供应商、脚本与生产工具，生成实际资产。
监督层检查结果、状态、失败和重试条件，回报给决策层。
共享记忆通过事件图谱和向量检索回收角色、世界观和历史结果。
Skill 文件用 Markdown 保存可读、可改、可版本化的工作规则。
供应商接口以 TypeScript 编程方式接入不同模型，而不是把厂商写死在 UI。

为什么拆三层

决策、执行、监督分别拥有不同失败模式：计划不合理、调用失败和结果不合格不应混成一次不可解释的重试。分层后，可以分别记录成本、输入、输出和责任。

记忆不是聊天记录

向量检索适合找“相似语义”，事件图谱适合表达“谁在何时做了什么”。两者结合，才能支持跨章节一致性；但检索命中仍需回到项目事实源验证。

Skill 是可审计配置

Markdown 文件让规则进入版本控制，产品团队可以 review 规则变更，而不必重新编译 Agent runtime。

值得借鉴

  • 将 capability 作为模型可见的稳定目录。
  • 把供应商适配放在独立 TypeScript 边界，统一成本和错误。
  • 用结构化事件记录 Agent 决策、执行、监督和重试。
  • 为长项目建立章节级 artifact 与可检索记忆。
  • 把 Skill 作为可 review 的版本化配置。
Keep out

不要直接复制

  • 不要让 Toonflow 的 SQLite / 服务端状态替代 Nomi 的 TimelineState。
  • 不要让 Agent 直接写 React Flow、Zustand 或外部 NLE store。
  • 不要把供应商选择结果当作时间线事实；它只是一次可审计的执行决策。
  • 不要默认 ONNX 记忆命中就是事实，必须保留来源和 revision。
与当前 #223 的关系：Project Agent Host 已经在推进文稿读写、冻结 target / revision / content hash、审批边界以及 Canvas / Timeline capability。Toonflow 的三层职责可以帮助组织这些能力，但不能绕过 Host 的写入审批，也不能把本次选区持久高亮修复扩大成新的 Agent 状态系统。

协议、补充条款与 Nomi 当前政策

先区分标准许可证，再看项目声明

Toonflow：Apache-2.0 + 项目补充商业协议

仓库许可证页面标记 Apache-2.0。Apache 2.0 通常提供较宽的使用、修改、分发和专利许可，只需保留版权、许可证和 NOTICE 等要求。

README 另写了补充商业安排：以产品形式向 2 个及以上独立第三方分发需要书面商业授权；不超过 5 个法人联合内部使用，README 声称不需要授权；不得删除或修改 Toonflow 标识、版权信息；v1.0.8 之前基于 AGPL-3.0 使用的用户继续按 AGPL-3.0。后面这些不是 Apache-2.0 标准文本本身，能否构成可执行的附加条件，要以仓库 LICENSE 原文、贡献历史和律师意见为准。

Nomi：AGPL-only，不要求 CLA

Nomi 当前 AGPL-3.0-only，只发布这一种开源版本，不要求贡献者签署 CLA。AGPL 让修改后的分发版本和网络交互服务承担更强的源代码提供义务，避免改进被锁在闭源服务端。

团队可以收费提供遵守 AGPL 的定制开发、集成、部署、培训和持续迭代，但 Nomi 不提供只交安装包、不提供对应源代码的闭源版本。

复制代码到 Nomi需保留 Apache notices，且要确认 AGPL / 自定义条款兼容性登记依赖、版权和来源；只借设计不等于可以复制实现
Nomi 为什么不再要求 CLA

旧版 Nomi 曾用 CLA 为商业再许可准备授权，但现行政策是 AGPL-only。CLA 不是 AGPL 的强制要求，现已移除签字机器人和签名账本；CLA.md 仅保留为旧链接的说明页，贡献者无需回复或签署。

边界声明：这是基于官方仓库页面、README、Nomi 仓库文件的工程研究，不构成法律意见。Apache / AGPL、补充商业条款、商标、依赖和静态 / 动态链接的组合，必须按实际发行方式让律师复核。
