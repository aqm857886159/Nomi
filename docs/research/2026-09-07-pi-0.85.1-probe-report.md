## 2. Q1 · CJS 主进程能不能起 —— **过**

### 2.1 结论

在 Electron 43.4.1 主进程（`process.type === "browser"`）里，沿 `electron/harness/runtime/pi/nativeLoader.cts` 那条 **CJS → 动态 `import()` → ESM** 的路径，**pi 0.85.1 全部可加载、可实例化，没有 ESM-only 死结、没有 top-level await 死结**。

### 2.2 证据

`probe/main.cjs` 是真 CommonJS 入口，`probe/probe.mjs` 是被它 `await import()` 进来的 ESM——与生产 `nativeLoader.cts` 的形状一致。`probe/out/report.json`：

**实例化不是只看类型**：同一次运行里用 `AgentHarness.create({session, models, model, tools, systemPrompt})` 起了 **5 个** harness，每个都真跑完一轮对话（loopback 或真实模型），`result.ok === true`。空壳会在第一次 `create` 就抛 `HarnessNotImplemented`。

### 2.3 一条边界：`require()` 仍然不行，只有 `import()` 行

从真 CommonJS 作用域 `require()` 三个包，全部拒绝：

## 3. Q2 · 会话存储位置能否注入 —— **过**

### 3.1 结论

能。`AgentHarnessOptions.session` 收的是一个 `Session` 对象，而 `Session` 由 `JsonlSessionRepo` 造，**`sessionsRoot` 是它构造函数上的一个普通字符串参数**——不读 `~/.pi`、不读环境变量、没有隐藏默认值。

```ts
// pi-agent-core/dist/harness/session/jsonl/types.d.ts
export interface JsonlSessionRepoOptions {
  fileSystem: FileSystem;
  sessionsRoot: string;      // ← 就是这一个
  now?: () => number;
}
```

### 3.2 证据（真写、真读回、真 fork）

`probe/out/report.json` 的 `q2`：

```json
"metadata": {
  "id": "01a07676-42a4-7170-a3ac-c22da11545d9",
  "path": ".../probe/out/fake-project/.nomi/agent-sessions/--Users-…-fake-project--/2026-09-06T11-24-16-932Z_01a07676-….jsonl"
},
"underProject": true,
"homePiTouched": 0,
"runOk": true,
"readBackTranscript": [
  { "type": "message", "seq": 4,  "role": "user",      "text": "hello" },
  { "type": "message", "seq": 16, "role": "assistant", "text": "Q2 stored." }
],
"fork": {
  "tree":   { "underProject": true },
  "branch": { "underProject": true },
  "forkedTranscript": [ { "seq": 4, "role": "user" }, { "seq": 16, "role": "assistant" } ]
}
```

- 写：起 harness → `lane.prompt('hello')` → 落盘。
- **读回是真的关掉再开**：`harness.close()` → `repo.open(metadata)` → 新 harness → `lane.watch()`，拿到的 transcript 与写进去的逐条对上。
- fork 两种 scope 都试了（`{scope:'tree'}` 与 `{scope:'branch', branch:'main'}`），两份都落在 `<project>/.nomi/` 下，内容含父会话的两条 entry，header 带 `parentSessionId`。
- **`homePiTouched: 0`**：整轮跑完，`~/.pi/agent/sessions/` 一个文件都没多出来。

落盘文件（`q2.filesOnDisk`）：

```
.nomi/agent-sessions/--Users-…-fake-project--/2026-09-06T11-24-16-932Z_<uuid>.jsonl   7726 B  ← 原会话
.nomi/agent-sessions/--Users-…-fake-project--/2026-09-06T11-24-17-054Z_<uuid>.jsonl   1581 B  ← tree fork
.nomi/agent-sessions/--Users-…-fake-project--/2026-09-06T11-24-17-055Z_<uuid>.jsonl   1581 B  ← branch fork
```

JSONL 第一行是 header，之后每行是一个事务批（entry + value 写混在一个数组里）：

```json

[{"kind":"entry","id":"…","parentId":null,"type":"message","message":{"role":"user","content":[{"type":"text","text":"hello"}]},"seq":4}, {"kind":"value","op":"set","seq":5,"namespace":"pi.branch.tip","key":"main","value":"…"}, …]
```

### 3.3 落地时会咬人的一条：repo 会自己插一层 cwd slug 目录

`sessionsRoot` 不是最终目录。`JsonlSessionRepo` 在它下面按 `cwd` 生成一层 slug 子目录（上面那个 `--Users-aoqimin-…-fake-project--`），文件名是 `<ISO 时间>_<uuid>.jsonl`。

- 后果：`<project>/.nomi/agent-sessions/` 里会出现一个**含绝对路径的目录名**。项目被移动或改名后，同一个项目会长出第二个 slug 目录——旧会话还在，但 `list({cwd})` 按新 cwd 查不到。
- 最小处置（阶段 1 顺手做，不是阻塞项）：把 `sessionsRoot` 设为 `<project>/.nomi/agent-sessions`，并且**建 repo 时传一个稳定的、项目相对的 `cwd`**（而不是宿主绝对路径），slug 就跟着稳定。`create({cwd, id?})` 还允许指定会话 id，Nomi 可以直接用自己的 threadId。

### 3.4 若不过的最小绕法

不适用。（`JsonlSessionRepo` 只依赖注入进去的 `FileSystem` 接口——真要完全接管布局，实现自己的 `FileSystem` 或直接实现 `SessionRepo` 都是开放口，但今天不需要。）

## 4. Q3 · `before_tool` 的 `{block:{reason}}` 是否真把 reason 送到模型 —— **过**

### 4.1 结论

**过，而且是逐字送到。** `{block:{reason}}` 会变成那次 tool call 的 **tool result 内容本身**（`isError: true`），原样进下一轮请求；真实模型据此一轮改对。

同时探到一条方案里没写、但会直接影响 §3.3「错误契约」设计的事实：**schema 不合法的参数根本走不到 `before_tool`**，pi 自己的校验器先拦下并生成了一条自带「收到的参数」的错误回给模型。

### 4.2 三条 loopback 臂（零额度，证明机制）

`probe/out/report.json` 的 `q3`。三臂共用同一个工具 `canvas_write({anchors: string[]})`。

**臂 A — schema 不合法（`anchors: "shot-1"` 是字符串）**

```json
"beforeToolFired": 1,
"beforeToolCalls": [{ "toolName": "canvas_write", "args": { "anchors": ["shot-1"] }, "decision": null }],
"toolMessagesInNextRequest": [{
  "role": "tool",
  "tool_call_id": "call_a1",
  "content": "Validation failed for tool \"canvas_write\":\n  - anchors: must be array\n\nReceived arguments:\n{\n  \"anchors\": \"shot-1\"\n}"
}]
```

读法：`before_tool` **只被调用了 1 次**，而且那次的 `args` 已经是**第二轮**的合法数组——第一轮那个字符串调用**从来没进过钩子**。pi 在钩子之前用 JSON Schema 校验了一遍，直接产出上面那条 tool result。注意它**把收到的参数原文回显了**，这正是 §3.3 想要的「模型能自纠」的形状，而且是上游白送的。

**臂 B — schema 合法、被宿主策略拦（这才是方案真正问的那题）**

```json
"beforeToolFired": 2,
"beforeToolCalls": [
  { "args": { "anchors": ["shot-1"] }, "decision": { "block": { "reason": "shot-1 未获批准，只能写已批准的分镜；先调 canvas_list 拿到已批准列表" } } },
  { "args": { "anchors": ["shot-2"] }, "decision": null }
],
"needleReachedModelVerbatim": true,
"toolMessagesInNextRequest": [{
  "role": "tool", "tool_call_id": "call_b1",
  "content": "shot-1 未获批准，只能写已批准的分镜；先调 canvas_list 拿到已批准列表"
}],
"toolExecutionsThatActuallyRan": [{ "anchors": ["shot-2"] }],
"transcriptToolResults": [
  { "toolCallId": "call_b1", "isError": true,  "text": "shot-1 未获批准，…" },
  { "toolCallId": "call_b2", "isError": false, "text": "wrote [\"shot-2\"]" }
]
```

**reason 一个字不改地成为 tool result**，并且被拦的那次 `execute` **确实没跑**（`toolExecutionsThatActuallyRan` 里只有 shot-2）。

**臂 C — `{args}` 改写（官方容忍钩子，对应方案 §2.3④）**

```json
"beforeToolCalls": [{ "args": { "anchors": ["shot-1"] }, "decision": { "args": { "anchors": ["rewritten-by-host"] } } }],
"toolExecutionsThatActuallyRan": [{ "anchors": ["rewritten-by-host"] }]
```

`before_tool` 返回 `{args}` 就能在校验之后、执行之前改写参数——不需要 `z.preprocess`，也不需要那个会把 schema 抹成 `{}` 的 `zodToJsonSchema` override（`tools.mts:47-49`）。

### 4.3 真实模型臂（DeepSeek `deepseek-v4-flash`，$0.000531 ≈ ¥0.0038）

**臂 1 — 格式纠正（重试是唯一正解）**。工具 schema 允许任意字符串，模型按用户要求传了带空格的 `"shot 1"`；`before_tool` 拦下并说明 kebab-case 规则。

`probe/out/real2-report.json`（两次独立运行，结果一致）：

```json
"hookCalls": [
  { "args": { "anchors": ["shot 1"] },  "blocked": true },
  { "args": { "anchors": ["shot-1"] }, "blocked": false }
],
"executed": [{ "anchors": ["shot-1"] }],
"selfCorrected": true,
"reasonInNextRequest": true
```

transcript 逐条：

```
user       把 "shot 1" 这个分镜写到画布上，anchor 就用 "shot 1"。
assistant  toolCall canvas_write { anchors: ["shot 1"] }
toolResult isError=true  「anchor id 必须是 kebab-case 小写短横线格式，不能含空格。收到 "shot 1"，应写成 "shot-1"。请用 anchors: ["shot-1"] 重试。」
assistant  toolCall canvas_write { anchors: ["shot-1"] }      ← 一轮改对
toolResult isError=false 「wrote ["shot-1"]」
assistant  「已写入分镜 "shot-1"。」
```

**臂 2 — 策略拦截（重试不是唯一正解）**。同样机制、reason 同样逐字送到（`reasonInSecondRequest: true`），但模型选择**停下来问用户**而不是自作主张换 shot-2：

```
assistant  「shot-1 尚未获批，无法写入。我只能写入已批准的 "shot-2"。请先批准 shot-1，或让我写入 shot-2。」
```

这不是失败——机制这一层已经证完（reason 到了、模型读懂了、复述准确）；换不换目标是产品语义问题，正确答案本来就该是「问」。**记这一条是为了避免以后把「模型没自动重试」误判成「reason 没送到」。**

### 4.4 一条不要误读的观察：单次 `Connection error.` 是网络抖动，不是 fetch 注入问题

第一次真实模型运行整轮失败在 `stopReason: "error" / errorMessage: "Connection error."`。我怀疑是 pi 默认 fetch 在 Electron 主进程里不通，于是做了**单变量 A/B**（`probe/real2.mjs`，同一进程里跑两遍，只差注不注入 `fetch`）：

| 臂 | 请求数 | 结果 |
|---|---|---|
| 注入 `globalThis.fetch` | 3 | 全 200，自纠成功 |
| **用 pi 默认 fetch** | 3 | **全 200，自纠成功** |

所以那次是**一次性网络抖动**，与 fetch 路径无关。写进来是因为它顺带证了一件事：**探针里我把 `retry` 关了，所以抖动直接变成一次废掉的对话**；开着 `RetryPolicy` 的话这正是它该吃掉的东西（见 §6.2）。

### 4.5 若不过的最小绕法

不适用。

## 5. Q4 · `LaneSnapshot` 的 `streamingMessage` / `runningTools` 实测形状 —— **过**

场景：一轮对话，两次工具调用（`document_read` → `document_write`），第二个工具被闸住不返回，好在「工具正在跑」的中途采样。共采到 57 个 snapshot、25 条 `message_update`。证据：`probe/out/q4-lane-snapshots.json` / `q4-message-update-events.json` / `q4-events.json`。

### 5.1 有序段：`contentIndex` 是真的，交错也是真的

`harness.events.on('message_update')` 拿到的原始 `AssistantMessageEvent` 序列（第一轮）：

```
thinking_start@0 thinking_delta@0 thinking_delta@0
text_start@1     text_delta@1
toolcall_start@2 toolcall_delta@2 toolcall_delta@2 toolcall_delta@2
thinking_end@0   text_end@1       toolcall_end@2
```

`contentIndexSeen: [0, 1, 2]`。同一条助手消息里 **thinking / text / toolCall 各占一个索引位，按发生顺序排**——这正是方案 §0.3 说 Nomi 今天「数据里不存在」的那个东西。

流式中途的 `operation.streamingMessage.content`（7 个 snapshot 里都是这个形状）：

```json
[ { "type": "thinking" },
  { "type": "text", "text": "我先读一下文档。" },
  { "type": "toolCall", "name": "document_read", "args": {} } ]
```

**顺序不是靠渲染层排出来的，是落盘的**。最终 transcript 里那条 entry 的 `content` 数组：

```json
{ "seq": 26, "type": "message", "role": "assistant", "parts": ["thinking", "text", "toolCall"] }
{ "seq": 51, "type": "message", "role": "assistant", "parts": ["text", "toolCall"] }
```

> ⚠️ **一个会被踩的坑**：`lane.watch()` 的事件流**故意剥掉了** `message_update` 的 `event` 字段（类型 `LaneWatchSourceEvent` 里写着 `Omit<…, "event">`）。想要 `contentIndex` 必须走 `harness.events.on('message_update')`。设计投影通道（B4）时要把这两条流分清楚：`watch` 给的是「快照 + 粗事件」，`harness.events` 给的是「逐 delta 细事件」。

### 5.2 `runningTools` 生命周期

```json
"runningToolStatusSet": ["document_write:running", "document_write:settled"],
"midFlightRunningTools": [{
  "status": "running", "toolCallId": "call_write_1", "toolName": "document_write",
  "args": { "path": "a.md", "body": "hi" }
}]
```

settled 之后 `result` 挂上来：

```json
{ "status": "settled", "toolCallId": "call_write_1", "toolName": "document_write",
  "args": { "path": "a.md", "body": "hi" },
  "result": { "content": [{ "type": "text", "text": "wrote a.md" }], "details": { "phase": "done" } },
  "isError": false }
```

`running → settled` 两态、`args` 从头就在、`result` 落定才出现、`details` 原样透传——**渲染层要的东西这里全有**，不需要方案 §0.2 说的那份「渲染层手写的第二真相」。

### 5.3 `stats`：跨轮累计，且带真钱

```json
"stats": { "messageCount": 6, "usage": {
  "input": 300, "output": 60, "totalTokens": 360,
  "cost": { "input": 0.000042, "output": 0.0000168, "total": 0.0000588 } } }
```

一份 snapshot 里同时有 token 与 USD，harness 自己按 `model.cost` 算好——不用三层各算一遍。

### 5.4 `appendCustomEntry` / `entryProjectors`：宿主数据骑在同一条流上（岔路 2 方案 B 的地基）

实测签名：

```ts
AgentLane.appendCustomEntry(customType: string, data: JsonValue | undefined, context: Context): Promise<string>
type EntryProjector = (entry: CustomEntry, context: Context) => AgentMessage[] | undefined | Promise<AgentMessage[] | undefined>
// 注册点：AgentHarnessOptions.entryProjectors?: Record<string, EntryProjector>
```

探针里写了一条 `nomi.approval`：

```js
await lane.appendCustomEntry('nomi.approval', { decision: 'granted', target: 'a.md' }, context)
// entryProjectors['nomi.approval'] = (entry) => [{ role: 'user', content: `[host] approval ${entry.data.decision} for ${entry.data.target}` }]
```

结果：

- 它**在同一条转录里排第一**（`{ seq: 4, type: "custom", customType: "nomi.approval" }`），排在 user prompt（seq 7）之前——顺序天生正确，不需要任何合并排序。
- `customEntryVisibleToModel: true`——投影出来的那条消息**逐字出现在发给模型的请求里**。
- projector 被调了 4 次（每次组 context 时都跑一遍），所以它必须是纯函数、别在里面做副作用或慢 IO。

这条直接支撑岔路 2 的方案 B：**「审批卡/任务卡 pi 不知道」这个反对理由，被 `appendCustomEntry` + `entryProjectors` 正面回答了。**

## 6. 三条附带记录

### 6.1 `calculateCost` 单位与 `Model.cost` 形状

```ts
// pi-ai/dist/types.d.ts:702-715
interface ModelCostRates { input: number; output: number; cacheRead: number; cacheWrite: number }
interface ModelCostTier extends ModelCostRates { inputTokensAbove: number }
interface ModelCost     extends ModelCostRates { tiers?: ModelCostTier[] }

// pi-ai/dist/models.js:543
usage.cost.input = (rates.input / 1000000) * usage.input;
```

**单位 = 美元 / 每百万 token。** 实跑确认（`report.json` 的 `extras.calculateCost`）：`cost.input = 0.14` 对 100 万 input token、费率 `0.14`。方案 §2.3① 的判断正确；那份「每 token」的说法是错的。

`tiers` 是**请求级**分档，不是分段累进：取所有 `inputTokensAbove` 里命中且阈值最高的那一档，**整个请求**按它算。做 Nomi catalog 的 `pricing` 映射时别写成阶梯累加。

顺带确认 §2.3②：`getSupportedThinkingLevels({reasoning:false}) === ["off"]`，`{reasoning:true}` 才给 `["off","minimal","low","medium","high"]`。

### 6.2 `RetryPolicy` 与它的事件

```ts
// pi-ai/dist/utils/retry.d.ts:8
interface RetryPolicy { enabled: boolean; maxRetries: number; baseDelayMs: number }
// 延迟 = baseDelayMs * 2^(attempt-1) + jitter
// 入口：AgentHarnessOptions.retry / harness.getRetryPolicy() / harness.setRetryPolicy()
```

实跑（loopback 前两次返 503、第三次 200，`{enabled:true, maxRetries:3, baseDelayMs:60}`），`probe/out/extras-retry-events.json`：

```json
[ { "type": "retry_scheduled", "attempt": 2, "maxAttempts": 4, "delayMs": 60,  "errorMessage": "503: {\"message\":\"probe induced 503\"}" },
  { "type": "retry_start",     "attempt": 2 },
  { "type": "retry_scheduled", "attempt": 3, "maxAttempts": 4, "delayMs": 120, "errorMessage": "503: …" },
  { "type": "retry_start",     "attempt": 3 },
  { "type": "retry_end",       "attempt": 3, "success": true } ]
```

同时 `LaneSnapshot.operation.retry` 在重试窗口里是活的：

```json
{ "attempt": 2, "maxAttempts": 4, "nextAttemptAt": 1788694183392 }
{ "attempt": 3, "maxAttempts": 4, "nextAttemptAt": 1788694183523 }
```

退避 60 → 120 符合公式。**「面板上显示『正在重试 2/3，3 秒后』」所需的三个数（attempt / maxAttempts / nextAttemptAt）全部现成**，不用自己记账。

注意 `isRetryableAssistantError` 把配额/账单耗尽划为**不可重试**——直接失败，不会烧掉重试预算。

### 6.3 `steer` / `followUp` 在 harness 下的入口

```ts
AgentLane.steer(message: string | AgentMessage, images: ImageContent[] | undefined, ctx): Promise<QueueResult>
AgentLane.followUp(...同上)
AgentLane.nextRun(...同上)
AgentLane.cancelQueued(entryId: string, ctx): Promise<CancelQueuedResult>
AgentLane.abort(ctx): Promise<AbortResult>   // 返回未消费的 { steer, followUp }
// 模式：AgentHarnessOptions.steeringMode / followUpMode（QueueMode），也可 harness.setSteeringMode() 改
```

实跑（`report.json` 的 `extras.steering`）：一个工具被闸住时插入 steer + followUp，两条都被受理（`ok: true`），运行中的 `LaneSnapshot.queues` 里能看到它们：

```json
[ { "entryId": "…", "kind": "steer",    "type": "message", "message": { "role": "user", "content": [{ "type": "text", "text": "不对，横屏" }] } },
  { "entryId": "…", "kind": "followUp", "type": "message", "message": { "role": "user", "content": [{ "type": "text", "text": "顺便再答一次" }] } } ]
```

跑完后两条都进了同一条转录、都到达了模型，`finalQueues: []`：

```
user 开始 → assistant <toolCall> → toolResult done
→ user「不对，横屏」→ assistant「收到你的中途指示，改横屏。」
→ user「顺便再答一次」→ assistant「再答一次。」
```

方案 §0.3 说的「Nomi 结构性用不了 steering（每回合开新 session、队列跨不过回合边界）」——**在 harness 下这个结构性障碍不存在**：队列是 lane 级、跨回合活着，且在 snapshot 里可见可取消。

## 7. 岔路 1 的建议

**建议 A：升到 0.85.1，用 `AgentHarness` / `AgentLane`。**

理由按证据强度排：

1. **四题全过，且过的方式是「跑起来了」而不是「类型对得上」**——5 个 harness 实例、6 次真实模型请求、57 个 snapshot、151 条既有测试全绿。
2. **升级本身的风险比想象中小得多。** 现有代码走 `createAgentSession` 那条老路，在 0.85.1 上 `build` / `typecheck` / `test:agent-runtime`（151/151）全过。也就是说升级可以**先落地、后改用法**——这把「赌一个发布一天的版本」拆成了两步，第一步几乎无风险。
3. **要一起动的是 3 个直接依赖，不是 6 个**（§1.1）；`pi-client` / `pi-protocol` 两条 overrides 是死的，顺手删。
4. **B 方案要手写的那几样，探针里全部实测到上游已经做好**：有序段（contentIndex）、runningTools 两态、跨轮 stats 带钱、retry 三个数、lane 级队列、custom entry 投影。选 B 就是明知这些存在还再写一遍——正是 R20 要拦的。
5. **C 明确不选**：探针证明 CJS 不是死结（§2.3），隔离的理由不成立。

**降低「只发布一天」这个风险的两条具体动作**（不改结论，只改节奏）：

- **拆成两个 PR。** PR-1 只升版本（三个直接依赖 + 清掉两条死 overrides），验收门就是本报告 §2.4 那三条；PR-2 才是阶段 1 的垂直切片。PR-1 若在真机走查里翻车，回滚面积是一行版本号。
- **锁死版本、别用 `^`。** `pnpm.overrides` 保持精确 `0.85.1`；上游再发新版由我们主动决定何时动。

**一条留给阶段 1 的已知细节**（不影响 A/B 选择）：`JsonlSessionRepo` 会在 `sessionsRoot` 下按 cwd 生成 slug 子目录（§3.3）。传一个稳定的、项目相对的 `cwd`，并复用 Nomi 自己的 id 作 `create({id})`，这层就不会在项目改名后咬人。
