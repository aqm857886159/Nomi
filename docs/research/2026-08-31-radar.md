## 🟡 架构教训

### GroundShot: Visually Consistent Multi-Shot Long Video Generation via Entity-Grounded Shot Scheduling

- 证据：[arXiv:2606.20799](https://arxiv.org/abs/2606.20799) · 2026-06-18，[官方 HTML](https://arxiv.org/html/2606.20799v1)。**training-free、model-agnostic**，明确「无需额外训练或模型改动」，即黑盒 provider 之上可套。本轮**未找到官方代码仓或项目页**（WebSearch 只返回论文与 awesome-list 收录，无 repo）。
- 它解决什么：多镜长视频里，重复出现的实体（人物/道具/地点）会一镜镜漂离它「第一次清晰出现」的样子——而观众正是拿后面每次出现去和第一次比。
- 机制（这才是要借的）：① 从**已接受**的镜头在线建「实体级视觉记忆」；② 把**生成顺序**按「这一镜作为后续实体参考的预期价值」排（不是按剧本线性顺序）；③ 实体入库前先 ground + 验可靠性；④ 每镜生成前从记忆里检索最合适的参考。配套诊断基准 GroundBench（在实体级隔离受控挑战维度量一致性）。
- 对 Nomi 的意思：Nomi 现在把有序 `character_ref` 作为同一次请求的联合条件（`generationReferenceResolver.ts`），但**排镜顺序**（`storyboardPlan.ts`）还是叙事线性；GroundShot 说「先生成最能当参考的镜、再把它喂给后面」能压跨镜漂移。这条**不碰 provider 内部**，正好落在 Nomi 已有的 agent/记忆层。
- 最小落点：不接依赖、不加入口。在 `referenceSlots.ts` 的参考解析里加一条「优先复用已接受镜头里被验证过的实体裁片」，在 `storyboardPlan.ts` 里加一个「按实体覆盖度重排生成顺序」的可选策略；用 3–5 条多镜多角色真实任务对比「线性顺序 + 首帧参考」vs「按参考价值排序 + 已接受实体记忆」的身份保持与成本。失败也记录。
- 限制：无官方仓 = 不能接代码、不能宣称复现；GroundBench 细节指标论文摘要未给全，接 eval 前需读正文核实。

### UnityShots: Memory-Driven Multi-Shot Audio-Video Generation with Boundary-Aware Gating

- 证据：[arXiv:2606.21661](https://arxiv.org/abs/2606.21661) · 2026-06-19，[项目页](https://jackailab.github.io/Projects/UnityShots)。**不是黑盒可套**——它在 LTX-2.3 上重训，靠 speaker token + 离散 cut-type 先验做专门训练。
- 它解决什么：跨镜连贯。双记忆架构——长期记忆槽锚在开场镜、短期记忆槽存紧邻的上一镜尾帧，由「边界条件门」在每个切点用**视觉切镜概率 + 节拍信号**更新。
- 报告：200 条多文化多镜序列（6 大族裔区、10+ 语言）基准上，领先全部开源基线的跨镜连贯指标，在多镜轴上追平最强闭源。
- 对 Nomi 的意思（只借设计、不接模型）：Nomi 的 relay 已有「上一段尾帧接下一段首帧」（`relayFrameResolver.ts`）——UnityShots 说**别只传尾帧**，应同时保留一个「开场锚点」长期记忆，并在**切点**（而非固定间隔）由切镜信号触发记忆更新。`electron/video/detectShotCuts.ts` 已有切镜检测，正好供这个「边界门」用。
- 限制：需重训 LTX-2.3 + 多卡，solo 本地产品接不了；只取「双记忆 + 边界门控」的结构启发，不复制其模型层。

## 🔵 对标基准

### KathaTrace: Diagnosing Semantic Trajectory Collapse in Generated Visual Narratives

- 证据：[arXiv:2607.01312](https://arxiv.org/abs/2607.01312) · 2026-07-01。**generator-agnostic 诊断协议**；本轮未见代码释出说明（指标可复现，套件是否开放待核实）。
- 它测什么：正中 Nomi 方向 #4（镜间转场——DirectorBench 已指认是全行业中心瓶颈）。「语义轨迹坍塌」= 画面各自连贯，但**镜与镜之间的语义链断了**，观众看不懂这镜怎么接上一镜。提出 **Semantic Trajectory Gap (STG)** 指标 = 「只给文字的可恢复度 − 只给图像的可恢复度」，量化「意思在可视化过程中丢了多少」；配 KathaBench-25K（5,000 叙事 / 20,000 转场 / 28,712 可恢复性问题）。
- 对 Nomi 的意思：Nomi 的验收现在偏「每镜首帧对不对」（`shotVerifyRunner.ts` / `shotVerifyOrchestrate.ts`），**测不到「镜间意思断没断」**。STG 给了一把可复现的尺子——不需要它的数据集，只借指标形式：对 Nomi 生成的相邻镜对，比较「只读 prompt」与「只看画面」的转场可恢复度，差值大 = 转场语义在生成时被抹平。
- 接法：在 `evals/journeys/` 定义一个「转场可恢复度」验收槽，喂给 `shotVerifyOrchestrate.ts` 作为**跨镜维度**（区别于现有单镜首帧维度）；先在 2–3 条多镜真实任务上取 STG 基线，不整包引入 KathaBench。
- 限制：代码开放情况未确认；STG 的「可恢复度」判定需要一个 VLM 打分器，接前要定清用哪个模型、成本多少。

### EntityBench（08-27 已进 🔵 · 本轮升级为「已实查可执行」，非新增）

- 证据：[arXiv:2605.15199](https://arxiv.org/abs/2605.15199) · 2026-05-14。**08-27 已列过**，当时仅「论文声明官方代码与数据已公开」。本轮实查仓库 [Catherine-R-He/EntityBench](https://github.com/Catherine-R-He/EntityBench)（12 stars / 5 commits）：**评测码确实可运行**——`eval/evaluate_benchmark.py`（单卡）、`run_eval_distributed.py`（多卡）、`compare_methods.py`，example 脚本 `examples/run_eval_example.sh`；按 `<results_dir>/<episode_id>/<scene>_<shot>.mp4` 目录约定即可对**任意生成器输出**打三支柱分（intra-shot 画质 / prompt 对齐 / 跨镜实体一致）。140 集 2,491 镜，覆盖到 50 镜、recurrence gap 48 镜。
- 为什么记这条：把 08-27 的「待核实」明确升级成「可执行」——这是本轮对已有 🔵 的**实证 diff**，不是重复发现。
- 接法（承接 08-27 结论）：从其 recurrence-gap 分层借一组最小真实任务（角色/道具/地点间隔 1/8/24 镜后再现），接 `shotVerifyOrchestrate.ts` 时先加 fidelity gate（实体没按 prompt 出现就不算「像不像」）。
- 接入边界（本轮实查补充）：依赖 `groundingdino-py + vbench + pyiqa`，且需 **Azure OpenAI endpoint + Gemini API keys**（round-robin）——不是零成本；先跑最小子集验证，别整包当默认门岗。

## 本周建议的最小验证（都先产证据，不接依赖、不加入口）

### A. GroundShot 式「按参考价值排镜 + 已接受实体记忆」原型
- 落 `referenceSlots.ts`（复用已验证实体裁片）+ `storyboardPlan.ts`（按实体覆盖度重排生成顺序），不接 GroundShot 代码（无仓）。
- 3–5 条多镜多角色真实任务，对比「线性顺序+首帧参考」vs「按参考价值排序+已接受实体记忆」的身份保持/漂移/成本；失败样例也留。
- 通过条件：跨镜身份改善不以排镜成本成倍或动作僵化为代价。

### B. STG 转场可恢复度 + EntityBench 实体一致，接进跨镜验收维度
- 在 `evals/journeys/` 加「转场可恢复度(STG)」与「实体 fidelity gate」两个验收槽，喂 `shotVerifyOrchestrate.ts` 作为**跨镜**维度（区别于现有单镜首帧）。
- STG 先在 2–3 条多镜任务取基线（借指标形式、不引 KathaBench 数据集）；EntityBench 先跑其 `evaluate_benchmark.py` 最小子集（备好 Azure/Gemini 凭证），验证「能对 Nomi 输出打分」再谈是否入门岗。
- 两项都先产证据再决定架构/门岗，不与项目级统一 Agent/MCP/Skill 的单一能力合同争第二套状态源。
