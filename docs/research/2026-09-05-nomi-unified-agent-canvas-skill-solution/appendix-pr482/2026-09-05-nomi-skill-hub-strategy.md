# Nomi Skill Hub 总体研究与双端方案

> 研究日期：2026-09-04
> 当前阶段：研究与产品方案，不进入 UI 和代码实现

## 1. 结论先行

Nomi 不应该做一个单纯的“提示词转载站”，而应该做一个面向 AI 影视创作的 **Skill 发现、验证、安装和执行网络**。

它同时承担两个目标：

1. 官网获客：用大量可搜索、可预览、可验证的剧本、图片和视频创作内容承接自然搜索与社交流量。
2. 客户端留存：把有明确许可、通过安全审核且能真实执行的内容，转为 Nomi 现有 Skill 体系中的内置项或一键安装项。

两端必须使用同一个内容源和同一套版本、许可、作者、测试记录。不能让官网维护“提示词库”，客户端再维护另一套“Skill 库”。

推荐的供给分层：

| 层级 | 建议规模 | 展示位置 | 准入标准 |
|---|---:|---|---|
| 核心内置 | 20-30 个 | Nomi 安装包内 | 高价值、许可清晰、无危险依赖、持续维护 |
| 官方精选目录 | 100-300 个 | 官网和客户端目录 | 可一键安装、已审计、已测试、固定版本 |
| 官网发现库 | 20,000+ 条原始记录 | 官网索引和运营后台 | 可追溯来源，允许全文或仅做摘要/链接 |
| 首发 SEO 页面 | 150-300 页 | 官网公开页 | 有独特价值、有预览、有参数、有验证，不是薄页 |

## 2. 为什么不能把所有内容都叫 Skill

外部网站把 prompt、案例图、工作流 JSON、教程和 `SKILL.md` 混在一起。为了不欺骗用户，也为了让客户端知道什么可以执行，Nomi 数据层必须区分四种对象：

| 对象 | 定义 | 官网能力 | 客户端能力 |
|---|---|---|---|
| Agent Skill | 有指令、资源、脚本、输入输出契约的可安装包 | 阅读、下载、版本、依赖、测试 | 安装和执行 |
| Prompt Recipe | 有变量、参数、模型和示例的提示词模板 | 复制、填参、导出、收藏 | 作为模板使用，或被 Skill 调用 |
| Workflow | ComfyUI JSON、多阶段 Playbook、节点图或自动化流程 | 预览节点、下载、查看依赖 | 导入、配置和运行 |
| Showcase | 结果媒体、提示词、参数和来源证据 | 浏览、对比、查看原帖 | 可复用为新创作，但不能假装成完整 Skill |

官网导航可以统一叫“创作 Skills”，但详情页必须明确类型。只有前三种在具备许可与安全条件时才能进入客户端。

## 3. 现状与机会

### 3.1 官网现状

当前 Nomi 官网主要由首页、新手指南、手册等少量可索引页面构成。技术 SEO 不是主要瓶颈，真正缺少的是长期、可持续增长的内容面。

内部 14 天快照显示：

- GitHub 页面 2,926 views / 607 uniques。
- GitHub clones 5,988 / 675 uniques。
- Google referrer 93，Bing referrer 50。
- 官网到 GitHub referrer 仅 4。
- 累计下载约 4,339。

这说明产品已经有真实关注，但官网没有足够多的搜索入口，也没有把内容兴趣稳定转化为软件下载和 Skill 使用。

### 3.2 客户端现状

Nomi 已有 Skill 库、搜索、导入、导出、删除和“在创作区使用”，并采用 `SKILL.md + skill.json`，支持文本、图片、视频 provider 和多阶段 Playbook。

因此正确方向是扩展现有 Skill catalog，而不是另造一个平行的“提示词系统”。平行系统会造成：

- 同一内容维护两份版本。
- 官网看到的内容无法直接在客户端运行。
- 作者、许可和下架状态不能同步。
- 客户端上下文被上万条 prompt 污染。

## 4. 获取策略：广发现，严发布，分级使用

### 4.1 来源池

| 来源 | 主要价值 | 主要风险 | 推荐处理 |
|---|---|---|---|
| GitHub | 原生 Skill、工作流、脚本、版本和许可证 | 仓库许可未必覆盖转载媒体 | 读取 LICENSE、固定 commit、逐文件追溯来源 |
| Skill 市场/目录 | 快速发现安装项和热门主题 | 镜像、刷量、作者归属混乱 | 作为发现入口，回溯上游仓库和原作者 |
| Prompt/图片网站 | 海量案例、标签和搜索需求 | 复制限制、图片权利、薄内容 | 研究产品机制；内容只按许可导入 |
| X | 高质量创作者、原始线程、热度数据 | 普通帖子不等于可转载许可 | 官方嵌入或原创摘要，联系作者授权 |
| 抖音 | 中文视频工作流、运镜和短剧实操 | 嵌入与媒体复用权不明确 | 摘要、作者和原帖跳转；授权后再托管 |
| 小红书 | 收藏导向的教程和模板，商业场景丰富 | 登录、反爬、转载风险高 | TikHub 发现，按收藏排序，默认摘要跳转 |
| 作者投稿 | 许可链最清楚，可形成独家内容 | 需要审核和激励 | 建立投稿、认领、更新和收益机制 |
| Nomi 自测 | 可形成独特页面和可信预览 | 有模型成本与审核成本 | 优先对高价值 Skill 生成 Nomi 实测样例 |

### 4.2 获取漏斗

```text
发现候选
  -> 解析作者与原始来源
  -> 判断对象类型
  -> 权利分级
  -> 内容去重
  -> 安全扫描
  -> 人工质量审核
  -> Nomi 实测
  -> 官网发布
  -> 客户端内置或目录上架
  -> 更新、投诉和下架同步
```

“尽可能多”应发生在候选库；“尽可能优质”应发生在公开页和客户端。不能因为原始数据多，就让未经验证的内容直接面对用户。

## 5. 内容分类体系

### 5.1 剧本 Skill

剧本页的第一信号必须是用户能一眼理解的名称或任务描述，例如：

- 小说改编为 60 集竖屏短剧
- 爆款短剧前 3 集开场设计
- 角色小传与人物弧光生成
- 单场戏冲突升级与反转
- 分场大纲转标准影视剧本
- 剧本转分镜表和镜头清单
- 漫剧对白压缩与旁白改写
- 连续剧角色一致性审查

建议一级分类：

- 故事开发：选题、世界观、题材、核心冲突、受众。
- 人物：角色设定、关系、成长弧、对白口吻、一致性。
- 结构：三幕式、节拍、分集、钩子、悬念、反转。
- 写作：大纲、分场、场景、对白、旁白、标准格式。
- 改编：小说转剧本、长剧转短剧、真人转漫剧、IP 改编。
- 导演前期：分镜、镜头表、场面调度、视觉提示词。
- 制作管理：资产清单、预算、连续性、审核和交付。
- 题材：都市、甜宠、悬疑、古装、科幻、喜剧、动作等。

### 5.2 图片 Skill

图片页必须直接展示结果图，不能只给一段 prompt。建议按以下维度交叉筛选：

- 任务：文生图、图生图、局部重绘、扩图、抠图、换背景、修复、风格化。
- 影视用途：角色定妆、场景概念、道具、服装、海报、分镜、关键帧、缩略图。
- 商业用途：产品图、电商图、广告 KV、品牌视觉、社交媒体、教育图解。
- 风格：写实、电影感、二次元、3D、插画、像素、平面设计、摄影棚。
- 控制：角色一致性、姿态、构图、光线、镜头、文字排版、色彩。
- 模型：GPT Image、Midjourney、Flux、Stable Diffusion、即梦及其他当前模型。

### 5.3 视频 Skill：必须覆盖各种类型

视频不能只围绕 Seedance 或“电影感运镜”。分类需要同时覆盖五个维度。

#### 内容类型

- 电影短片、竖屏短剧、漫剧、动画、纪录片、预告片、MV。
- 产品广告、品牌片、电商视频、口播、UGC、探店。
- 地产、汽车、时尚、美妆、旅游、教育、知识讲解。

#### 视觉形式

- 写实、二次元、3D、定格、VFX、转场、循环。
- 延时、航拍、微距、慢动作、舞蹈、角色表演、群像。

#### 输入与编辑方式

- 文生视频。
- 图生视频。
- 多图参考。
- 首尾帧。
- 视频转视频。
- 参考视频复刻。
- 局部编辑。
- 延长、补帧、扩展。
- 口型、声音、动作或表情驱动。

#### 镜头与导演语言

- pan、tilt、dolly、truck、crane、orbit、drone。
- push in、pull out、zoom、handheld、POV、over-the-shoulder。
- 一镜到底、穿越机、跟拍、环绕、过肩反打、景别切换。
- 按秒时间线、多镜头 `[cut]`、首尾帧控制、连续性控制。

#### 模型与运行环境

- Seedance、Kling、Veo、Wan、Sora、Runway。
- ComfyUI 本地工作流和云端工作流。
- 后续新模型通过能力字段接入，不为每个模型复制一套分类。

## 6. 官网信息架构

推荐首批路由：

```text
/skills
/skills/script/{slug}
/skills/image/{slug}
/skills/video/{slug}
/skills/workflow/{slug}
/authors/{handle}
/models/{model}/prompts
/use-cases/{category}
/collections/{theme}
```

各路由职责：

| 页面 | 用户问题 | 核心内容 |
|---|---|---|
| 聚合首页 | 我能找到什么 | 搜索、分类、精选、趋势、最近验证 |
| 分类页 | 哪些适合我的任务 | 场景筛选、模型筛选、结果预览、质量信号 |
| 详情页 | 这个到底能不能用 | 内容、变量、参数、预览、测试、来源、许可 |
| 作者页 | 还有谁做过类似内容 | 作者简介、主页、作品、许可和认领状态 |
| 模型页 | 某模型怎么写 | 适配该模型的 verified recipes 与能力限制 |
| 场景页 | 我要做某种成片 | 从剧本到图片到视频的一组组合 Skill |
| Collection | 一套任务怎么完成 | 编辑精选的端到端工作流，而非简单标签页 |

### 6.1 Skill 详情页统一结构

首屏必须回答四件事：

1. 这是什么任务。
2. 输出效果是什么。
3. 是否适合我当前模型或工作流。
4. 我现在能做什么。

固定模块建议：

- 标题、单句摘要、类型、作者。
- 图片或视频真实预览；剧本类展示结构化输出片段。
- 主操作：`在 Nomi 中打开`。
- 次操作：复制、收藏、下载、导出、分享。
- 输入要求、变量和填写控件。
- 完整提示词、Skill 指令或 workflow 预览。
- 支持的模型、版本、画幅、时长、镜头、音频。
- Nomi 实测环境、时间、参数和成功/失败记录。
- 作者主页、原始内容 URL、许可、Nomi 是否改编。
- 依赖、费用、密钥、网络访问、文件权限和风险提示。
- 相似 Skill、同作者内容、上下游 Skill。

### 6.2 三类详情页的差异

剧本页重点：

- 标题和任务描述优先，不用大图喧宾夺主。
- 展示适用题材、输入素材、输出结构、评审标准和示例片段。
- 让用户看到“输入一个故事后，会得到哪种结构”，而不是只展示长 prompt。

图片页重点：

- 结果图为主视觉。
- 支持输入图和输出图对照。
- 展示画幅、种子、参考强度、模型版本和后期处理。
- 复制 prompt 时同时复制必要参数，避免只有文字没有复现条件。

视频页重点：

- 默认展示可播放短预览、时长和是否有声音。
- 提供关键帧、时间线或镜头段落结构。
- 展示输入素材、运动控制、首尾帧、多镜头切换和负面约束。
- 标明视频是否来自原作者、官方嵌入，还是 Nomi 合法复现。

## 7. 功能设计与权限逻辑

用户要求的复制、下载、导出、点赞或收藏都应该有，但不能对所有来源一刀切开放。

| 功能 | 开放许可/书面授权 | 官方嵌入/可引用 | 权利不明/付费内容 |
|---|---|---|---|
| 阅读摘要 | 是 | 是 | 是，保持必要限度 |
| 查看原帖 | 是 | 是 | 是 |
| 复制全文 | 是 | 否 | 否 |
| 下载原文件 | 是 | 否 | 否 |
| 导出 JSON/Markdown | 是 | 仅导出 Nomi 原创元数据 | 仅导出收藏链接 |
| 收藏 | 是 | 是 | 是 |
| 点赞 | 是 | 是 | 是 |
| 官方嵌入媒体 | 按许可 | 平台允许时 | 付费墙内容不嵌入 |
| 在 Nomi 中安装 | 通过安全审核后 | 否 | 否 |

### 7.1 核心交互

- `复制`：可选择复制 prompt、变量化模板或完整参数。
- `下载`：Agent Skill 下载包，Workflow 下载 JSON，Recipe 下载 Markdown/JSON。
- `导出`：支持 Nomi 包、Markdown、JSON；导出时携带作者和许可字段。
- `收藏`：登录用户跨设备同步；未登录可本地暂存。
- `点赞`：用于社区信号，不直接等同于质量。
- `分享`：生成规范链接和适合社交传播的预览卡。
- `在 Nomi 中打开`：已安装客户端则使用深链；未安装则进入下载流程，并保存待安装 Skill。
- `查看原帖`：对于未授权内容，这应是主操作之一。

深链不能把用户带到下载页后丢失上下文。下载完成首次打开 Nomi 时，应自动恢复刚才的 Skill 安装意图。

## 8. 排序、质量与个性化

不能按点赞数或 GitHub star 简单排序。公开热度容易被刷，也会让早期内容永远占据顶部。

建议质量分由以下维度组成：

```text
quality_score =
  0.22 * task_fit
  + 0.20 * reproducibility
  + 0.16 * output_quality
  + 0.12 * completeness
  + 0.10 * rights_confidence
  + 0.08 * freshness
  + 0.07 * author_signal
  + 0.05 * community_signal
  - risk_penalties
```

说明：

- task_fit：是否明确解决一个真实任务。
- reproducibility：能否在声明的模型和参数下复现。
- output_quality：人工和模型双重评审的结果质量。
- completeness：输入、变量、参数、示例、限制是否完整。
- rights_confidence：许可和媒体权利是否清楚。
- freshness：模型版本和链接是否仍有效。
- author_signal：原创作者、官方来源、持续维护。
- community_signal：收藏、使用、完成、分享和有帮助投票。
- risk_penalties：抄袭、重复、失效、NSFW、危险脚本、未披露费用等。

真正有价值的排序信号应是：

- 安装后首次成功运行率。
- 复用率和再次运行率。
- 用户保存结果的比例。
- 结果分享率。
- Nomi 实测通过率。
- 最近版本兼容性。

点赞与 star 只能做弱信号。

## 9. Nomi 客户端内置设计

### 9.1 核心内置

首批 20-30 个建议覆盖完整创作链，而不是把 20 个名额都给“写 prompt”：

- 选题与故事开发。
- 小说改编。
- 短剧分集和钩子。
- 角色设定与一致性。
- 剧本写作和审查。
- 分镜、镜头清单和资产清单。
- 角色图、场景图、关键帧。
- 通用视频提示词编排。
- 首尾帧、多镜头、一镜到底、参考视频等高频控制。
- 成片审核与连续性检查。

核心内置必须离线可发现，能在没有网络目录时工作。外部 API、付费服务或高风险脚本不应作为默认核心 Skill。

### 9.2 官方精选目录

100-300 个一键安装项可覆盖更细题材、模型和工作流。每个安装包必须：

- 固定到 commit SHA 或 Nomi 自有不可变版本。
- 有包 SHA-256 和签名。
- 声明作者、上游来源、许可和改编。
- 声明输入输出、依赖、网络域名、API key、费用和权限。
- 经过静态扫描、恶意内容扫描和真实运行测试。
- 有撤回、禁用和升级路径。

### 9.3 海量 prompt 的正确装法

15,000 条乃至百万级 prompt 不能逐条安装，也不能全部塞入模型上下文。正确做法是：

- 官网：每条高价值、可公开的 Recipe 有独立页面或被组织进专题页。
- 客户端：安装一个检索型 Skill，运行时按任务、模型和风格检索相关子集。
- 上下文：只注入用户当前选择的 1-5 条 Recipe 和必要参数。

```yaml
  nomi_media_ids: []
```

核心原则：作者、来源和权利字段不能是发布后补填的“说明文字”，而必须是内容对象的强制数据。

## 11. 去重和来源归一

同一内容常被多个 GitHub 聚合仓库、推文截图、公众号或短视频二次转载。去重需要组合判断：

- canonical URL。
- 规范化 prompt hash。
- Skill 文件树 hash。
- 图片 pHash 和视频关键帧指纹。
- 语义相似度。
- 作者、发布时间和引用关系。

作者归属规则：

1. 优先原始发布者或上游仓库 maintainer。
2. 镜像仓库和聚合站只作为发现来源，不自动成为作者。
3. 翻译者、整理者和 Nomi 改编者单独记录，不能覆盖原作者。
4. 来源冲突时进入人工审核，不先发布再慢慢查。

## 12. 版权和媒体策略

### 12.1 权利分级

| 状态 | 条件 | Nomi 可以做什么 |
|---|---|---|
| Green | 开放许可明确，或有作者书面授权 | 托管、全文、复制、下载、改编、安装，按许可署名 |
| Yellow | 允许链接/嵌入，但无再分发授权 | 原创摘要、官方嵌入、作者信息、原帖跳转、收藏索引 |
| Red | 无许可、许可冲突、付费墙、投诉中 | 不展示全文和媒体，不提供安装；必要时仅保留内部审核记录 |

仓库许可证不自动覆盖仓库里转载的 X、小红书、抖音图片、视频或 prompt。代码、文字、图片、视频、音乐、人物肖像、商标和 IP 必须分别判断。

### 12.2 推荐版权声明

> Nomi Skill Hub 仅收录经授权、开放许可允许，或以链接/官方嵌入方式展示的创作方法与案例。相关权利归原作者；每项内容标注作者、原始来源、许可及 Nomi 改编情况。未经许可的内容不提供全文复制、下载或客户端安装。如权利人认为内容使用不当，可提交权利证明和具体 URL，Nomi 将先暂停相关复制、下载、安装和媒体展示，再完成核验与处理。

“我们是聚合站，如侵权下架”不能替代授权。下架是补救措施，不是合法转载的依据。

### 12.3 下架同步

收到可信投诉后，第一步不是等结论，而是临时暂停高传播能力：

- 关闭复制、下载和安装。
- 隐藏第三方媒体。
- 保留来源证据和审核日志。
- 核验权利人与原始发布关系。
- 决定恢复、改为摘要链接或彻底移除。
- 同步官网、搜索索引、CDN、客户端 catalog 和深链。

## 13. SEO 与增长闭环

推荐增长链路：

```text
搜索/TikHub/GitHub 发现
  -> 权利与质量审核
  -> 有独特价值的 SEO 详情页
  -> 用户预览、复制或收藏
  -> 在 Nomi 中打开
  -> 安装并首次成功运行
  -> 用户分享 Nomi 实测结果
  -> 形成新的可索引案例页
```

这比单纯做 prompt 库更难被复制，因为 Nomi 提供了三个聚合站通常没有的东西：

1. 真实运行环境。
2. 经过验证的输入输出和结果媒体。
3. 从内容发现到影视制作的完整工作流。

### 13.1 SEO 页面质量底线

每个可索引详情页至少有以下独特内容：

- 清楚的任务描述。
- 可预览结果。
- 可填写变量和参数。
- 适用/不适用场景。
- 模型与版本信息。
- Nomi 实测证据或明确标记“未测试”。
- 作者、原始来源和许可。
- 上下游工作流关系。

只有标题、图片和复制按钮的批量页属于薄内容，不应大规模放进索引。

### 13.2 关键指标

- 非品牌搜索曝光、收录量和 CTR。
- 详情页到复制、收藏和预览的转化率。
- `Open Nomi` 点击率。
- 官网到软件下载转化率。
- Skill 安装率和首次成功运行率。
- 7 日复用率。
- 使用后分享率和分享带来的新访问。
- 按来源、作者、模型和页面类型计算的投诉率。

## 14. 首批发布节奏

### Phase 0：数据与权利底座

- 建统一对象模型、作者模型、来源证据和权利状态。
- 建 GitHub、网站和 TikHub 候选导入流程。
- 建 prompt、文件、图片和语义去重。
- 建 Green/Yellow/Red 发布权限矩阵。

### Phase 1：可验证的最小内容面

- 20-30 个核心内置 Skill。
- 100-300 个官方精选目录候选。
- 150-300 个公开详情页。
- 剧本、图片和视频至少各有完整分类，不偏科。
- 每个公开页都经过人工审核；视觉页有预览。

### Phase 2：作者与社区供给

- 作者认领和投稿。
- 版本更新、changelog、作者主页。
- 收藏、点赞、有帮助反馈和实测结果投稿。
- 授权模板和作者合作计划。

### Phase 3：规模化与程序化 SEO

- 只有当质量、去重、权利和下架机制稳定后才扩到 20,000+。
- 围绕模型、题材、场景、镜头和工作流做高质量组合页。
- 按页面表现和成功运行数据决定继续扩张，不按抓取数量决定。

## 15. 当前明确不做

- 不把普通 prompt 冒充可执行 Skill。
- 不把所有外部内容一股脑内置进客户端。
- 不把海量 prompt 全部塞入模型上下文。
- 不以“聚合站”和“侵权后下架”作为转载依据。
- 不托管权利不清的第三方图片和视频。
- 不按 GitHub star 或社媒点赞直接决定质量。
- 不为每个视频模型复制一套产品和 UI。
- 不生成大量没有实测、参数和独特说明的薄 SEO 页面。

## 16. 下一轮需要验证的关键问题

这些不是现在阻塞研究的问题，但在正式设计和实现前必须拿到证据：

1. `nomiaqm.com` 现有技术栈、CMS/内容发布方式和部署流程。
2. Nomi 当前 `skill.json` 的真实 schema、catalog 更新和深链能力。
3. 是否已有登录、收藏、点赞和作者系统可复用。
4. 客户端安装包签名、权限提示和远程禁用机制现状。
5. X、抖音、小红书各自最新的嵌入、API 和内容展示条款。
6. TikHub 实际可用的账号、配额、返回字段和合规边界。
7. 首批目标市场更偏中文短剧，还是同时覆盖英文创作者和全球 SEO。

本方案先固定底层判断：**官网负责发现和获客，客户端负责可信执行，统一 catalog 负责版本、权利与下架。**
