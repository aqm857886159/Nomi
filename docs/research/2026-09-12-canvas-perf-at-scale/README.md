## 0. 起因（用户原话，2026-09-12）

> 「选中 60 个图片拖动组就开始特别卡了，拖动鼠标都不行；性能优化优化过但是还是不行。画布东西多的话那么卡，这个问题有点严重。」

同一次会话里还有两条：右下角**缩放滑杆拖起来一顿一顿**；跑**深度抽帧**任务时**画布上的图全黑了一阵、App 卡住**。

三件事这份文档一起回答，因为它们各自的根因层次不同，但都属于「画布东西多的时候发生了什么」。

## 1. 结论先说

0. **最坏的不是「拖组」，是「全选之后拖」**，而且它走的是**正规的 React Flow 内核路**。300 个图片节点全选后拖动：**12.4 fps、p95 251 ms、最长帧 768 ms、251 次长任务（最长 647 ms）**。曲线是超线性的——节点 ×5，fps ÷7.8——因为每帧重渲染的实例数恰好等于节点总数，而每个实例又各扫一遍全表（`BaseGenerationNode` 的整表选择器），**N × O(N) = O(N²)**。这条推翻了初稿「把组框收回内核就好了」的排序：**收回内核 ≠ 快**，内核只保证别把位置写进业务 store，它管不住「N 个节点各自重渲染」。

1. **拖动组 ≠ 拖动节点，它们走的是两条不同的代码路**。2026-09-01 那场性能战役（PR #341/#346/#393）把**节点拖动**搬进了 React Flow 内核（松手才写 store），把 4× 节流腿的帧时间从 49.3ms 压到 12.9ms。**组框拖动没跟上**：它至今仍是一条手搓的 `window pointermove` + rAF 循环，**每一帧替换整个 Zustand `nodes` 数组**——正是 S4 为节点拖动删掉的那个形状。用户说的「拖动组特别卡」量到的就是它。
2. **这条路从来没被基准测过**。现有门岗的场景里没有任何一个拖组框，也没有任何一个「全选后拖」——`grep -rn "nodesselection\|groupFrame\|group-frame\|frame-drag" tests/ux/canvas-perf/ tests/ux/canvas-performance-benchmark.e2e.mjs` **零命中**（2026-09-12 在 `499f3c943` 上核过）。所以这两条卡了多久都不会让 CI 变红。
3. **缩放滑杆**：`<input type=range>` 的每一个 change 事件都起一段 120ms 的 d3 过渡（`GenerationCanvasReactFlow.tsx:356` 的 `flow.zoomTo(next, { duration: 120 })`）。连续拖滑杆 = 每秒几十段动画互相打断，肉眼就是顿。一行改动的事。
4. **「图全黑了」不是图片解码的锅，是主进程被同步文件 IO 堵死**。画布每张图的 `nomi-local://` 都由主进程 JS 线程上的 `protocol.handle` 供给；深度抽帧在同一个线程上做 32 次一批的 `fs.readFileSync` 无让出循环。图片请求派发不出去 → 渲染层 8 秒超时 → 卡片翻成满幅 `bg-nomi-ink-05`（暗色下就是近黑）→ 槽位释放 → 下一批接着堵，黑色像波一样扫过画布。这一族在 `check:heavy-path` 里**一条规则都没有**。
5. **LOD 的判据是「一共几个节点」，不是「这张卡在屏幕上多大」**。创始人的场景正好掉进缝里：60 张图（阈值要 >80）+ 适应视图后的缩放 0.217（阈值要 <0.55），于是每张卡在约 70×40 屏幕像素里渲染全套 chrome。

## 2. 怎么量的

- **机器**：Apple M5（10 核 CPU / 10 核 GPU）、24 GB、macOS 26.5.1。构建产物 = `pnpm build` 后的 `dist` + `dist-electron`，用开发版 Electron 二进制起（`tests/ux/_launchApp.mjs` 的标准路径，与现有走查/门岗同一条）。窗口 1600×1000。
- **夹具**：复用既有的 `tests/ux/fixtures/canvas-performance-fixture.mjs`，**新增三档纯图片规模** `I60 / I150 / I300`（60 / 150 / 300 个图片节点，边数 N/2，时间轴留空）。每个节点都带**真实文件**：ffmpeg 生成的 960×540 / 1920×1080 PNG，经真实的 `nomi-local://` 协议处理器送到真实的 `<img>` 里解码——不是空盒子。既有的 S/M/L/XL 档是图/视频各半，视频节点自带 `<video>` 解码与播放态，会盖掉「图片多」这条曲线，所以另开纯图片档。
- **手势**：全部是真实鼠标事件（Playwright `page.mouse`），不灌 store、不调桥。每个场景先点**「适应视图」按钮**（真按钮，且**验缩放真的变了**才继续），再做手势：
  - `drag-nodes-N`：框选（按住 Shift 在空白 pane 上拖矩形，React Flow 的 `selectionOnDrag` 只在 Shift 下起框）或 `Cmd+A` 全选，然后抓住一张选中的卡 / React Flow 自己盖上来的 `.react-flow__nodesselection-rect` 画一个整圆；
  - `drag-group-frame-60`：框选 60 张 → `Cmd+G` 建组 → 抓**组框本体**（密扫整框找第一个 `elementFromPoint` 命中框的点）画同样的圆；
  - 另有 `marquee-select-all` / `wheel-zoom` / `pan` / `zoom-slider-drag`。
- **仪器**：页内 rAF 计时器给帧数、p50/p95/最长帧；`PerformanceObserver('longtask')` 给长任务；`MutationObserver` 挂在 `.react-flow__viewport` 上数「每次 DOM flush 碰了几个节点实例」；CDP `Performance.getMetrics` 的**差值**给 script / style / layout 的分层耗时与布局次数。两次 CDP 读数**绑在页内探针 start/stop 的同一行**，保证量的是手势那一段、不含框选与建组的准备动作。
- **对照组 `drag-nodes-1`**：同一个 app 实例、同一个手势，只拖 1 张卡。这台机器上常年有 20+ 个工作树在跑活（本轮开始时 load average 一度 46），绝对毫秒会漂，**比值不会**；`nodeStyleWrites` / `subtreeMutations` / `layoutCount` 是**工作量计数**，与机器负载无关，是本份文档里最硬的证据。每条采样都记了当时的 load average。

这条把 §5 的修法方向钉死了：**没有一个函数值得去优化**。慢的是「我们让浏览器重画了 300 份卡片」这件事本身，所以每一条方案都得是「删掉谁被重画」，而不是「把某段代码写快点」。

**先认清最坏档是哪一个。** 初稿以为是「拖组框」，本轮补测把它顶掉了：

| 最坏的三格 | fps | 帧预算 ms | 其中「其它忙」 | 每帧空闲 | 重渲染实例/刷 | 长任务 |
|---|---|---|---|---|---|---|
| **`drag-nodes-all` @ I300**（全选 300 张后拖） | **12.4** | **80.6** | **64.6 ms（80%）** | 2.8 ms | **300** | **251 次，最长 647 ms** |
| `drag-nodes-all` @ I150（全选 150 张后拖） | 42.1 | 23.8 | 14.4 ms（61%） | 3.8 ms | 150 | 249 次，最长 93 ms |
| `drag-group-frame-60` @ I300（拖组框） | 59.9 | 16.7 | 7.9 ms（47%） | 1.5 ms | 40 | 0 次 |

`drag-nodes-all` 这条曲线是**超线性**的：节点 60 → 150 → 300（×5），fps 96.5 → 42.1 → **12.4**（÷7.8）。每帧重渲染的实例数恰好等于节点总数（60 / 150 / 300），而每个实例的 `BaseGenerationNode` 又各扫一遍全表（§3 末尾那个整表选择器）——**N 个节点 × 每个 O(N) = O(N²)**，这就是曲线弯上去的形状。对照组 `drag-nodes-1` 在同样三档是平的（8.3 / 7.7 / 8.6 ms），所以弯的不是「节点多」，是「**同时在动的节点多**」。

**注意 p50 和 fps 在这一格是矛盾的，这本身是证据。** `drag-nodes-all` @ I300 的 p50 只有 10.0 ms（看着像 100 fps），实际 fps 是 12.4。两个数都对：帧时间分布是**双峰**的——大多数帧照常 8–10 ms，但夹着一串 250 ms 以上的长帧（p95 251 ms、最长 371–768 ms、251 次长任务）。**手上的感觉由长帧决定，不由 p50 决定**，这也是 §6 预算把「最长帧 + 长任务次数」当硬门岗、把 p50 当参考的原因。

对照着读，拖组框（手搓路）和拖同样多张卡（内核路）在同一个规模上的差别是这样的：

| 问的是什么 | 用哪一格回答 | 内核路 `drag-nodes-60` · I150 | 手搓路 `drag-group-frame-60` · I150 |
|---|---|---|---|
| **React 提交/调和**贵不贵 | 采样表 `react-vendor` | 3.1% | **4.3%**（+39%） |
| **store 写**（Zustand/immer）贵不贵 | 采样表 `state-vendor` | 0.2% | **0.9%**（**4.5×**） |
| **布局/样式**贵不贵 | 每帧 style + layout | 0.4 + 0.1 = 0.5 ms | **2.1 + 0.1 = 2.2 ms**（**4.4×**） |
| **绘制/合成/派发**（含图片解码派发） | 每帧「其它忙」 | 3.5 ms | **6.9 ms**（2.0×） |
| 一帧里**重渲染了几个节点实例** | 每刷重渲染实例 | 50（= 正在动的那些） | **50**，但 I60 上是 **75 > 挂载的 60** |
| 一帧还剩多少余量 | 每帧空闲 | 4.4 ms | **2.0 ms** |

**三个热点，按实测占比排**（以全局最坏的 `drag-nodes-all` @ I300 为准，括号里是它占 80.6 ms 帧预算的份额）：

1. **「其它忙」：64.6 ms/帧（80%）** —— 绘制 + 合成 + 事件派发那一格。它**不是**某一行代码慢，是「一帧里有 300 个节点实例被重渲染、229.6 处 DOM 变更要绘制与合成」的直接结果。CPU 采样表从另一个方向证实了同一件事：这一格对应的 `(program)` 占 **82.1%**，而点名的 JS 全部加起来只有 **8.9%**。**根因在上游**：只要每帧重渲染的还是 N 个而不是「在动的那些」，这一格就下不来。
2. **script：11.3 ms/帧（14%）** —— 是对照组（0.5 ms/帧）的 **22.6×**，而节点数只涨了 5 倍。这条超线性就是 O(N²) 选择器的指纹。
3. **style：1.8 ms/帧（2%）+ layout 0.1 ms/帧** —— 绝对值不大，但相对对照组（0.1 ms）是 18×；在**拖组框**那条路上它是全表最突出的一列（§2.3 里 **16.4× 对照组**）。

换句话说：**一到两成是 JS 自己慢，八成是「让浏览器重画了不该重画的东西」**。这也决定了修法——§5 的每一条都在删「谁被重画」，没有一条是在优化某个函数内部。

**没法从这些数字里分出来的两件事**（`§7` 另有完整清单）：

- **React 每次 commit 的毫秒数**。prod bundle 没有 Profiler 名字，`react-vendor` 的采样占比是**代理量**不是 commit 时长。要真数字得跑 dev 腿，那条腿的绝对值又不能和 prod 比。另外采样表只取自时间前 25 名，尾巴没算进来，所以「点名合计」是**下界**——真实的 JS 占比比 8.9% 高一些，但高不到能翻转「八成在 `(program)`」这个结论的程度。
- **图片解码**。解码在渲染进程的 raster/decoder 线程上，不进 `TaskDuration`；主线程只承担派发。所以「图片解码贵不贵」这个问题**本轮没有量到**，只能说：`nodeStyleWrites` 全程是 transform 写、`wheel-zoom` 的 style 只有对照组的 2–3×，没有证据指向解码。§5 S8（图片分级）因此**保持延后**，不拿它当热点。

### 2.5 这些数字说了什么

**① 「画布上有多少东西」本身不是问题——「同时在动多少个」才是。** 对照组 `drag-nodes-1` 从 60 到 300 个节点，p50 是 8.3 / 7.7 / 8.6 ms，基本平的；`pan`（只改视口 transform，一个节点都不重渲染）在三档是 120 / 108 / 86 fps。React Flow 的剔除是有效的。

但只要把「在动的个数」拉上去，曲线立刻弯：

| 同时在动几个 | I60 | I150 | I300 |
|---|---|---|---|
| 1 个（对照） | 120 fps | 120 fps | 108.3 fps |
| 20 个 | 119.1 | 118.0 | （跳过，见 §7.4） |
| 50 个 | 118.8 | 94.5 | 88.6 |
| **全部** | **96.5**（60 个） | **42.1**（150 个） | **12.4**（300 个） |

同一行从左往右是「画布上东西变多」，同一列从上往下是「在动的变多」。**行是平的，列是塌的。** 9-01 战役的结论「拖动成本已与节点规模解耦」今天**只对到 50 个为止**；全选那一格从来没被测过，也从来没成立过。

**② 出问题的是「选中一批之后做什么」，而且分两条路，代价差一个量级。**

| 量的是什么 | 拖 50 张选中的卡（内核路 `drag-nodes-60`） | 拖装着同一批卡的组框（手搓路 `drag-group-frame-60`） |
|---|---|---|
| p50 / fps · I60 | 9.0 ms / 118.8 | **19.8 ms / 62.2** |
| p50 / fps · I150 | 10.0 ms / 94.5 | **13.7 ms / 61.8** |
| p50 / fps · I300 | 8.7 ms / 88.6 | **13.0 ms / 59.9** |
| p95 · I60 / I150 / I300 | 14.4 / 16.3 / 20.3 ms | **26.2 / 30.4 / 32.7 ms** |
| 主线程忙 · I60 / I150 / I300 | 50.3% / 58.7% / 58.6% | **91.8% / 87.7% / 90.9%** |
| script ms/s · I60 / I150 / I300 | 163 / 212 / 167 | **444 / 318 / 319** |
| style ms/s · I60 / I150 / I300 | 28 / 37 / 36 | **130 / 130 / 108** |
| 布局次/s · I150 | 26.8 | **35.9** |
| 每次 flush 触碰的不同节点 | 50 / 50 / 40 —— **恰好等于在动的那些** | 75 / 75 / 60 —— **比在动的多 50%** |
| CPU profile 里的 idle · I150 | 45.2% | **17.0%** |

同样的手势、同样数量的卡在动，只因为抓的是**组框**而不是**卡**，主线程就从「一半空着」变成「几乎没有空隙」。60 帧是这条路的天花板——不是机器不够快，是每一帧要重建整张投影。

最后一行值得单独留意：内核路每次 DOM flush 碰到的**不同** `data-id` 恰好等于正在被拖的节点数（50 / 50 / 40），手搓路却稳定多出 50%（75 / 75 / 60），在 I60 上甚至超过了当时挂载的 60 个。也就是说这条路每帧动到的不止是「在动的那些卡」，还有一批本不该被碰的——这条异常本身值得在实施 S1 时顺手查一次（怀疑是投影整表替换引起的节点卸载/重挂）。

**③ 缩放是第二个真问题，而且它随节点数长得比拖动还快。**

| 场景 | I60 最长帧 | I150 最长帧 | I300 最长帧 | I300 长任务 |
|---|---|---|---|---|
| `wheel-zoom` | 57 ms | 210 ms | **393 ms** | 10 次，最长 398 ms |
| `zoom-slider-drag` | 162 ms | 293 ms | **542 ms** | 10 次，最长 541 ms |

p50 一直是 8.4 ms（rAF 照常在跑），但**最长帧在 300 节点上是半秒**——用户手里的滑杆就是在那半秒里「不动」。这正是「拖缩放滑杆一顿一顿」的量化形态。注意 `zoom-slider-drag` 的 script 占比是对照组的 5.5–8.8×，而 style/layout 只有 1.1–2.9×：**这是 JS 的锅，不是绘制的锅**——每个 change 事件起一段 120 ms d3 过渡，过渡之间互相打断、重复计算。

**④ 平移基本干净，但 300 档已经开始脏。** `pan` 在 I60 是 120 fps / p50 8.1 ms / 最长帧 12.2 ms、`style` 只有 3.7 ms/s——同一块画布、同样多的东西，只改视口 transform 就没事，反证了问题不在「东西多」，在「每帧重建了多少状态」。**但 I300 上它不再全干净**：fps 86.3、最长帧 **92.4 ms**、**3 次长任务（最长 107 ms）**，而每帧重渲染实例仍是 1、DOM 变更只有 3.2。一个不重渲染节点的手势却出现了 90 ms 级的帧，指向的是**挂载/卸载**（`onlyRenderVisibleElements` 在 300 档只挂 204 个，平移时不断有卡进出视口要挂载与卸载）而不是重渲染。tldraw 的做法是剔除只 `display:none`、不卸载（§4）。这条本轮**没有单独量证**，列为 S5 实施时要顺手验的一条。

**⑤ i18n 在拖动热路径里。** 组框拖动的 CPU profile 里，除去 `(program)`/`(idle)`，**点名的 JS 帧第三位是 i18next 的 `formatLanguageCode`（1.4%）**（`node_modules/i18next/dist/esm/i18next.js:937`）。意思是每个节点每帧的重渲染里都在跑 `t()` 的语言码解析。它本身不大，但它是「节点内部整体重渲染」这件事的指纹——位置变了不该让文案重新查一遍。

## 3. 画布上到底有几条「搬东西」的路

> **路径约定**：下文形如 `components/xxx.ts:NN` 的相对路径，基准目录都是 `src/workbench/generationCanvas/`。
> 其余路径（`docs/`、`electron/`、`tests/`、`src/theme/`）从仓库根算起。
> 全部行号在 `499f3c943`（本轮采样用的那棵树）上逐条核过，并在合入 `origin/main` 之后
> **重新核过一遍仍然成立**——本文引用的每一个源码文件在这 68 个 commit 里都没有被改动，
> 所以「量的那份代码」和「今天 main 上的那份代码」是同一份。

**直接回答「我们的拖动是不是绕开了 React Flow 内核、每帧把位置写进 Zustand」：**
**拖卡不是，拖组框是。** 抓一张选中的卡（或 React Flow 自己盖上来的 `.react-flow__nodesselection-rect`）
走的是内核 `XYDrag` 草稿、松手才落账；抓**组框本体**走的是我们手搓的 `window pointermove` + rAF，

**R23 的含义**：R23 的边界句是「禁止第二 renderer、engine flag、fallback 或并行实现」。第 2 条路不是
第二个 renderer，但它是**同一件事（搬节点）的第二份交互实现**，而且是活的、用户天天碰的那份——
所以它落在 R23 的「并行实现」里。今天 R23 在画布上是**部分成立**：渲染与视口只有一个内核（合规），
**拖动有两条**（不合规）。S4（PR #346）的根因合同把组框记成 `not-affected`、理由「入口不同」，
正是这条不合规得以留存的那一行。

第 2 条是本次调查的核心。它做的事，正是 S4（PR #346，`a056b4ed5`）**为节点拖动删掉的那件事**：

```
pointermove → rAF → moveGroupNodes(delta)                  ← store/canvasGroupMoveActions.ts:33
  → immer: for (const node of state.nodes) { ... }         ← O(全部节点)，新的 nodes 引用
  → useStableCategoryNodes 的 filterNodesStable 返回新数组  ← reactFlow/useStableCategoryNodes.ts:44
  → collapsedProjection / edges / flowProjectionNodes 全链重算
  → toGenerationFlowNodes 重映射全部 N                      ← useGenerationCanvasReactFlowProjection.ts:43
  → syncCanvasNodeProjection → flow.setNodes(全部 N)        ← reactFlow/canvasNodeProjectionSync.ts:39
  → 全部挂载中的节点包装器重渲染
  → CanvasMinimap 重画 N 个绝对定位 div                     ← components/CanvasMinimap.tsx:37
```

两个放大器**在这条路上都是关的**：

- `nodeDragActive` 只由 React Flow 自己的 `onNodeDragStart/Stop` 翻（`GenerationCanvasReactFlow.tsx:515/:555`）。组框拖动期间它恒 `false` → `useStableCategoryNodes(..., false)` 的**引用稳定门不生效**，minimap 的**冻结门也不生效**（`useStableCategoryNodes.ts:59`）。
- `syncCanvasNodeProjection` 的 `isDragging` 分支（保住内核几何那段，`canvasNodeProjectionSync.ts:44`）同样收不到 `true`。

还有一条与 N 无关、但与**每张卡多贵**有关的：`BaseGenerationNode.tsx:224` 订阅的是
`useGenerationCanvasStore((state) => canRunGenerationNode(node, { nodes: state.nodes, edges: state.edges }))`
——选择器吃的是**整个 nodes/edges 数组**，每张卡一份。store 每写一次，N 张卡各跑一遍
`canRunGenerationNode`（内部还会 `resolveGenerationReferences` 走边表），于是组框拖动的每一帧是 **O(N²)** 级的选择器工作量。React Flow 官方文档把这条写成反面教材的原句是：
> "Every update to the `nodes` array triggers a re-render of all dependent components, even if the change is unrelated."
> — <https://reactflow.dev/learn/advanced-use/performance>

## 4. 别人怎么做（R5/R6）

## 5. 结构方案（本轮不写生产代码）

每条都按「改哪一层 / 预期效果 / **删掉什么**（P1：不留并行版）/ 怎么验」写。**S 编号是身份不是优先级**——排序在下面这张表里，依据是量到的热点，不是直觉。

**按实测热点排序**（「最坏数字」取三档里最差的那一档）：

| 排名 | 条目 | 它修的是哪个热点 | 最坏数字（今天） | 预期效果 | 代价 |
|---|---|---|---|---|---|
| **1** | **S3** 节点不再订阅整张表 | **全选后拖动**：每帧 N 个节点全部重渲染，每个再扫一遍全表 → O(N²) | `drag-nodes-all` @ I300：**12.7 fps · p95 257 ms · 最长 768 ms · 258 次长任务（最长 960 ms）** | 每帧重渲染从 N 降到「在动的那些」；长任务清零是硬判据 | 中：要动 store 派生与节点订阅 |
| **2** | **S1+S2+S4** 组框拖动收回内核、删两条死路、冻结门认单一标志 | **拖组框**：每帧替换整个 Zustand `nodes` 数组 | `drag-group-frame-60` @ I300：59.9 fps · p95 32.7 ms · **主线程忙 90.9%** | 每帧忙 −56%～−72%，fps → 88–119（见 S1 表） | 中：三条必须一起做 |
| **3** | **S6** 缩放滑杆不要动画 | **拖滑杆**：每个 change 起一段 120 ms d3 过渡，互相打断 | `zoom-slider-drag` @ I300：最长帧 **542 ms** | I60 最长帧 −65%；I150/I300 只削掉过渡那一层 | **一行改动** |
| **4** | **S5** LOD 判据换成「屏上多大」 | **缩放本身**：60 张图 @ zoom 0.22 掉进 `nodeCount>80` 的缝里 | `wheel-zoom` @ I300：最长帧 **393 ms** | 与 S3 共同决定 §2.5③ 的 542/393 残余 | 中 |
| **5** | **S7** 主进程同步 IO 堵死图片供给口 | **「图全黑了」**：与节点数无关的独立故障 | 未做真机复现（见 §7.2） | (c)(d) 便宜且独立；(a)(b) 要单独立项 | (c)(d) 小 / (a)(b) 大 |
| **6** | **S8** 图片按屏上尺寸分级 | —— | 触发条件未达标 | —— | 保持延后 |

**为什么 S3 排到了 S1 前面**：初稿把 S1 写成「最高优先」，依据是当时唯一量到的坏数字（组框拖动 62 fps）。本轮补测 `drag-nodes-all` 之后这个判断**被自己的数字推翻了**——全选拖动走的是**内核**路（harness 记的 `path` 是 `react-flow-kernel (nodesselection-rect)`，抓的是 React Flow 自己盖的罩子），却在 300 节点上掉到 **12.4 fps**（两次采样 12.7 / 12.4，表里取中位数），比手搓那条还差近 5 倍。也就是说：**「收回内核」并不等于「快」**。内核只负责别把位置写进业务 store，它管不住「N 个节点各自重渲染」。那一条归 S3。

同时这也说明 S1 仍然要做：组框拖动在 **60 个节点**上就只有 62 fps，而同规模的内核路是 119 fps——那一半是手搓路**额外**付的，S3 再好也退不回来。

### S1 把组框拖动收回 React Flow 内核，删掉手搓那条

**改哪一层**：`components/useCanvasSelectionDrag.ts` 整份退役。组框拖动接内核既有的选区拖动路径——用 `applyCanvasDragKernelPositionChanges` 草稿 + 松手一次 `moveGroupNodes`，和节点拖动**同一条**（`reactFlow/canvasDragDraft.ts` / `canvasDragWriteback.ts`）。框自身的矩形（`frameBounds`）在拖动期间只写一个 CSS transform，落账同样放到松手。

**为什么是这一层**：不是「把 rAF 调细一点」（那是症状），是「高频瞬态几何不进业务 store」这条不变量在组框这个入口上**从来没被执行过**。S4 的根因合同（`docs/fixes/2026-09-02-canvas-drag-kernel-writeback.root-cause.json`）第一条不变量原文是：

> 「节点拖动 position tick 只能更新 React Flow draft 几何，不能调用 moveNode 或替换 Zustand nodes 引用。」

而同一份合同的同类入口扫描里，`handleGroupFramePointerDown` 被判成 `not-affected`，逐字理由是：

> 「组框拖动使用独立 moveGroupNodes 手势，并非 React Flow onNodesChange position 入口；其既有高频语义和 commit 边界不由本次改动承接。」

这句话每个字都对，但它回答的是「**这次改动碰不碰它**」，不是「**这条不变量管不管它**」。不变量说的是「高频瞬态几何不进业务 store」——`moveGroupNodes` 恰恰每帧都在做这件事。**把「入口不同」当成「不适用」，正是 P2 里说的「范围声明不是论证」。** 三个半月后用户报「拖动组特别卡」，量到的就是这一格。S1 要做的第一件事，是把这条不变量的 `invariant_owner_layer` 写成「所有搬节点的入口」，而不是「React Flow onNodesChange 那一个」。

**预期效果（毫秒，有参照系不是估的）**：组框拖动的每帧工作量从「O(N) immer 写 + 全链重投影 + `setNodes(N)` + minimap 重画 N」降到「内核 nodeLookup 改 M 项（M=被拖成员数）」。**目标值不用推算——本轮已经量到了它**：同一台机器、同一个规模、同样 50 张卡在动，走内核的 `drag-nodes-60` 就是 S1 做完该有的样子。

| 规模 | 每帧忙 今天 → 目标 | fps 今天 → 目标 | p95 今天 → 目标 |
|---|---|---|---|
| I60 | 14.8 → **4.2 ms**（−10.6 ms，−72%） | 62.2 → **118.8** | 26.2 → **14.4 ms** |
| I150 | 14.2 → **6.2 ms**（−8.0 ms，−56%） | 61.8 → **94.5** | 30.4 → **16.3 ms** |
| I300 | 15.1 → **6.6 ms**（−8.5 ms，−56%） | 59.9 → **88.6** | 32.7 → **20.3 ms** |

（「每帧忙」= §2.4 表里 script + style + layout + 其它忙。）作为二次佐证：S4 在**节点**拖动上的实测是 4× 节流腿 49.3 → 12.9 ms（−74%）、prod 腿 16.5 → 10.3 ms（−37%），同一个量级。

**S1 治不了什么（要说清楚）**：本轮补测到的 `drag-nodes-all`（**全选**后拖）已经在**内核路**上了，I150 仍只有 42–44 fps。所以「收回内核」解决的是「多出来的那份手搓开销」，不解决「N 个节点全在动时每个都要重渲染」——**那是 S3 的事**。两条都要做。

**删掉什么**：`useCanvasSelectionDrag.ts` 全文（含已死的 `handleSelectionBoundsPointerDown`）；`store/canvasGroupMoveActions.ts` 的每帧调用点（函数本身留着，供松手一次写）。

**怎么验**：本份 harness 的 `drag-group-frame-60` 三档数字；外加一条结构断言，形如 `canvasControlsStructure.test.ts:55-62` 现有的 `expect(dragHandler).not.toContain('moveNode(')`——把它扩到「画布里没有任何 pointermove 监听会调 `moveGroupNodes` / `moveSelectedNodes`」。

### S2 删掉两条死拖动路，让 R23 的「单内核」重新是真的

`useCanvasSelectionDrag.ts:234` 的 `handleSelectionBoundsPointerDown`（零调用者）与 `nodes/useNodeDragResize.ts` 的拖动半边（`:170`/`:203` 一进来就 `if (flowManagedDrag) return`，生产恒不走）。零性能收益，但它是 S1 的前置：只要盘子里还摆着四份「怎么搬东西」的实现，下一个人就会去改错的那份。`canvasControlsStructure.test.ts:319-335` 现在断言四条路都写 `data-dragging` 标志——那条门岗在**追认**四条路是期望形态，随 S1/S2 一起改。

⚠️ 顺带：多选包围盒（16px 留白虚框、框内空白可整批拖）是迁移时**丢掉的用户可见能力**（`docs/plan/2026-09-11-canvas-migration-audit.md:68`），不是可删的死码。恢复它要走 R8 样张，恢复实现必须接 S1 那条内核路，不许把 `:234` 复活。

### S3（按实测排第一）节点不再订阅整张表

`nodes/BaseGenerationNode.tsx:222-229` 每张卡都 `useGenerationCanvasStore((state) => canRunGenerationNode(node, { nodes: state.nodes, edges: state.edges }))`。store 每写一次，N 张卡各扫一遍全表 → **O(N²)**。

**为什么它是第一**：这是本轮唯一能解释「曲线为什么弯上去」的机制。§2.5① 那张表里，「同时在动 = 全部」那一行从 96.5 → 42.1 → **12.4 fps**，而「在动 = 1 个」那一行是平的。中间差的就是「每帧有多少张卡各自重跑一遍 O(N) 的判据」。

**改哪一层**：把「这个节点能不能生成」变成 store 侧的一次性派生（一趟算出 `Map<nodeId, boolean>`，随 nodes/edges 变化重算一次），节点只订自己那一格；或直接用 React Flow 的 `useNodesData(id)`。这正是 React Flow 文档给的正解——原话是把那份数据**挪出 nodes 数组、单独存一个 state 字段**（§4 第二行，Context7 取回）：「decouple specific data from the main nodes array and store it in a separate state field so that components only re-render when their specific data changes」。

**预期效果（毫秒）**：目标不是「快一点」，是**把曲线掰平**——`drag-nodes-all` 该长得像 `drag-nodes-60`（每帧成本随**在动的个数**线性长，不随 N²）。今天与目标：

| 规模 | 每帧忙 今天 → 目标上限 | fps 今天 → 目标 | p95 今天 → 目标 | 长任务 今天 → 目标 |
|---|---|---|---|---|
| I60（动 60 个） | 5.5 → **≤ 5.5 ms**（今天就合格） | 96.5 | 15.4 → ≤ 20 ms | 0 → 0 |
| I150（动 150 个） | 20.0 → **≤ 9 ms**（−55%） | 42.1 → **≥ 90** | 53.7 → **≤ 24 ms** | **249 → ≤ 3** |
| I300（动 300 个） | 77.8 → **≤ 14 ms**（−82%） | 12.4 → **≥ 70** | 251.2 → **≤ 30 ms** | **251 → ≤ 5** |

目标上限的算法写在这里以便复核：取 `drag-nodes-60` @ 同档的每帧忙，按「在动的个数」线性外推（I150：6.2 ms × 150/50 = 18.6 ms 是**纯线性**的上界，而我们要的是去掉 O(N²) 那一半，故取 9 ms；I300：6.6 × 300/40 = 49.5 ms 为线性上界，目标取 14 ms）。**这几个数是设计目标不是实测**，S3 做完要用同一个 harness 重测，对不上就说明根因判错了。

**长任务次数是最硬的那条判据**：249 / 251 次是工作量计数，不随机器负载漂（同一分钟里 `marquee-select-all` @ I300 是 0 次）。它没掉到个位数，就是没修好。

**删掉什么**：`BaseGenerationNode` 里那个整表选择器（`:222-229`），以及同文件 `:110/:114/:118` 三个同形状的 `state.nodes.find` / `state.nodes.some` 选择器——**四个一起删，不留一个**（留一个就还是每写必扫全表，P1）。

**怎么验**：同 harness 的 `drag-nodes-all` 三档（上表），外加 `nodeStyleWrites` / `subtreeMutations` 计数（与机器负载无关）与 dev 腿的 `offCanvasRenderProbe`。

### S4 拖动中的「冻结门」认的是画布拖动标志，不是 React Flow 的那条

`nodeDragActive` 只由 RF 的 `onNodeDragStart/Stop` 翻（`GenerationCanvasReactFlow.tsx:515/:555`），于是组框拖动期间 minimap 不冻结、`useStableCategoryNodes` 的引用稳定门不生效、`syncCanvasNodeProjection` 的保几何分支也不走。仓库里**已经有**一个四条路都写的单一真相源：`components/canvasDraggingFlag.ts` 的 `setCanvasDragging`。把三处冻结门改成读它。

做完 S1 之后这条的收益会小很多（组框也走内核就会翻 `onNodeDragStart`），但它修的是**判据错了**这件事本身——同一个语义两份定义（R14.1）。

### S5 LOD 的判据换成「屏上多大」，不是「一共几个」

`components/canvasNodeLevelOfDetail.ts:29`：`nodeCount > 80 && zoom < 0.55`。创始人的场景正好掉进缝里——**60 张图**（<80）在**缩放 0.22**（适应视图的结果）上，每张卡在约 70×40 屏幕像素里渲染全套 chrome（提示词、按钮、参数条）。

**改哪一层**：判据从节点数换成屏上尺寸（`cardWidth * zoom < 阈值`），对齐 tldraw 的 `steppedScreenScale`（<https://tldraw.dev/sdk-features/performance>）：屏上多大就画多细。节点数只作为二级闸。

**删掉什么**：`nodeCount > 80` 这个阈值常量及其测试期望（不是加一个新判据并存）。

### S6 缩放滑杆不要动画

`components/CanvasNavigationStack.tsx:109` 的 `<input type="range" onChange>` → `GenerationCanvasReactFlow.tsx:355` 的 `flow.zoomTo(next, { duration: 120 })`。滑杆本身就是连续输入；每一个 change 事件起一段 120ms d3 过渡，后一段打断前一段，肉眼就是「拖不动/一顿一顿」。改 `{ duration: 0 }`（`:252`/`:353` 两处别的视口写入已经是 0）。本仓另有教训：`setViewport({duration})` 在这台机器上被判为不可信（`docs/lessons/canvas-autopan-suspense-pr503-20260905.md`）。

**预期效果（毫秒）**：目标同样是量出来的——同一规模下的 `wheel-zoom` 就是「同样的视口工作、但没有过渡动画」的对照：

| 规模 | 滑杆最长帧 今天 → 目标（= wheel-zoom 实测） | 长任务次数 今天 → 目标 |
|---|---|---|
| I60 | 162 → **57 ms**（−65%） | 2 → **0** |
| I150 | 293 → **210 ms**（−28%） | 8 → **7** |
| I300 | 542 → **393 ms**（−27%） | 10 → **10** |

读法很重要：**S6 只削掉「动画互相打断」那一层**，I150/I300 上剩下的 210/393 ms 是 `wheel-zoom` 也有的，属于「缩放时 N 个节点全部重算」——那是 S3/S5 的地盘。所以 S6 值得先做（一行、独立、I60 上立竿见影），但**别指望它单独让 300 节点的滑杆变顺**。

**删掉什么**：`zoomTo` 里的 duration 参数（按钮步进那条 `handleZoomByStep` 要不要保留动画，单独拍板；别为了保它而留两个 zoomTo）。

### S7 「图全黑了」：主进程同步文件 IO 堵死了唯一的图片供给口

因果链（每一环都在盘上核过）：

1. 画布上每张图的 `src` 是 `nomi-local://asset/…`，由**主进程 JS 线程**上的 `protocol.handle` 服务（`electron/main.ts:120-131` 注册权限，`electron/protocol/localProtocol.ts:239` 挂处理器）。
2. 深度抽帧任务在主进程里做 **32 × `fs.readFileSync` 的无让出循环**：`readVideoDepthFrames`（`electron/video/depthVideoJob.ts:280-290`）按 `payload.count` 同步读一批 JPEG，而那个 count 恒等于 `VIDEO_DEPTH_BATCH_FRAMES = 32`（`src/workbench/generationCanvas/videoDepth/workerProtocol.ts:14` → `videoDepthClient.ts:151-156` → `depthVideoIpc.ts:41`）。外加整段视频/产物的 `writeFileSync`/`readFileSync`。这期间主进程**派发不了**下一个 `nomi-local://` 请求。
3. 渲染层同时只给 4 个图片槽（`nodes/deferredNodeMediaQueue.ts:19`），每个槽挂一个 **8 秒**自动释放定时器（`:22`、`:84-91`）。图迟迟不回来 → 定时器到点 → `transitionTo('timeout')`（`:300`）。
4. `timeout` 态渲染 `DeferredNodeMediaFailure`：`absolute inset-0 … bg-nomi-ink-05` 满幅遮罩（`nodes/DeferredNodeMedia.tsx:46`）。暗色主题下 `--nomi-ink-05 = oklch(0.30 0.006 85)`（`src/theme/nomi-tokens.css:87`）——就是用户说的「全黑了」。
5. 槽被释放 → 下 4 张开始加载 → 同样堵住 → 黑色像波一样扫过整块画布。

**四层修法，从最早能拦住的那层起（R28）**：

- **(a) 重活离开主进程事件循环**：深度抽帧的读写搬进 utility process / worker thread；退而求其次也要换 `fs.promises` 并按批让出。「渲染层的图片供给」和「后台任务的文件 IO」不能共用一条队列。
- **(b) 协议热路径上不写盘**：`localProtocol` 每次项目资产响应都会 `appendEvents` → `fs.appendFileSync`（`electron/events/eventLogRepository.ts:231`），首次还会 `readFileSync` 回放整段。图片响应不该同步落审计日志。
- **(c) 门岗**：`check:heavy-path` 现在**一条都没有**覆盖这一族。现存五条是 `sync-image-encode`(5) / `base64-into-store`(0) / `duplicate-node-size-bounds`(0) / `node-stream-into-response`(0) / `unguarded-fsync`(0)（`scripts/heavy-path-baseline.json`）。最容易被误认为「已经覆盖了」的是 `unguarded-fsync`——**它管的是别的事**：判据是「这次 fsync 有没有过 `electron/durability.ts` 那道落盘屏障」（`scripts/check-heavy-path.mjs:170-187`），拦的是测试关不掉的落盘、不是**阻塞主进程事件循环**。
  加一条 `main-process-sync-fs`：`electron/**` 里 `readFileSync|writeFileSync|appendFileSync|statSync` 出现在协议处理器、IPC handler 或循环体内即红，基线只减不增；按 R17 先验它在今天的 main 上**确实会红**（`depthVideoJob.ts:290` 与 `eventLogRepository.ts:231` 是两个已知命中），再定基线。
- **(d) 症状层不要撒谎**：`markFailed` 会连 `readySrc` 一起清（`deferredNodeMediaQueue.ts:335-337`），于是「还没加载完」被画成「加载失败」，连上一帧都不留。超时应保留上一帧画面 + 一个安静的角标，而不是满幅黑。这条独立于 (a)-(c)：主进程再快也会有慢的那一天。

### S8（延后，带触发条件）图片按屏上尺寸分级

节点渲染的是**原图**：`BaseGenerationNode.tsx:563` 的 `<DeferredNodeImage src={node.result.url}>`；`thumbnailSrc` 只有素材库在用（`src/workbench/assets/AssetTile.tsx:144`）。9-01 战役把它记为延后项③，触发条件是「JSHeapUsedMB 接近告警 / 缩略图排队 / 用户报」。本轮 heap 数字见 §2 表；不达标就仍然延后，别提前做。

## 6. 验收预算（按节点数分档）

现在的门岗（`tests/ux/canvas-performance-benchmark.e2e.mjs:1248-1256`）对**所有规模用同一组数**：`frameGapP95Ms ≤ 33`、`maxFrameGapMs ≤ 100`（advisory）、`longTaskP95Ms ≤ 80`。平台感知**已经在 main 上**，而且只作用于时间类天花板：

```js
const NON_DARWIN_TIMING_CALIBRATION = 1.6                                  // :1231
function timingBudget(baseMax) {                                            // :1233
  return os.platform() === 'darwin' ? baseMax : Math.round(baseMax * NON_DARWIN_TIMING_CALIBRATION)
}
```

（核实结论：是的，门岗已是平台感知的，且计数类阈值不跟着放宽——这一点保持不动。）

缺的是**规模档**和**组框拖动这个场景**。建议如下（darwin 基准值，非 darwin 由现有 `timingBudget()` × 1.6 自动派生，不要另写一套）：

**拖动类**（判据是 `p95 / 最长帧`，单位 ms）：

| 场景 | 60 节点 | 150 节点 | 300 节点 | 今天实测（darwin, M5） | 备注 |
|---|---|---|---|---|---|
| `drag-nodes-1`（对照） | p95 ≤ 16 / 最长 ≤ 33 | ≤ 16 / ≤ 33 | ≤ 20 / ≤ 50 | 10.2 / 10.8 · 10.4 / 12.1 · 14.6 / 26.6 | 已经很宽裕，主要用来发现「整体变慢」 |
| `drag-nodes-60`（内核多选拖动） | p95 ≤ 20 / 最长 ≤ 40 | ≤ 22 / ≤ 45 | ≤ 26 / ≤ 55 | 14.4 / 17.2 · 16.3 / 19.7 · 20.3 / 40.4 | 今天就过得去，锁住不许退 |
| **`drag-nodes-all`（全选后拖）** | **p95 ≤ 20 / 最长 ≤ 40** | **≤ 24 / ≤ 50** | **≤ 30 / ≤ 60** | **15.4 / 20.7 · 53.7 / 73.8 · 251.2 / 371.1（150 与 300 档大幅越线，300 档超 8 倍）** | 全局最坏格。**S3 的验收就是这一行**；按 R17 先加进门岗、让它当场红，再动代码 |
| **`drag-group-frame-60`（组框拖动）** | **p95 ≤ 20 / 最长 ≤ 40** | **≤ 22 / ≤ 45** | **≤ 26 / ≤ 55** | **26.2 / 35.2 · 30.4 / 42.3 · 32.7 / 46.8（三档 p95 全越线）** | S1 做完应当与 `drag-nodes-60` 同档；同样先加门岗再动代码 |

**手势类**（`pan` 判 p95/最长帧；缩放两条判**最长帧 / 长任务次数**，因为它们的 p50 一直好看、坏的全在尾巴上）：

| 场景 | 60 节点 | 150 节点 | 300 节点 | 今天实测（darwin, M5） | 备注 |
|---|---|---|---|---|---|
| `marquee-select-all`（框选） | p95 ≤ 20 / 最长 ≤ 40 | ≤ 26 / ≤ 45 | ≤ 34 / ≤ 55 | 14.8 / 23.6 · 23.7 / 37.2 · 32.5 / 42.7 | 三档今天都过得去，锁住不许退 |
| `pan` | p95 ≤ 16 / 最长 ≤ 33 | ≤ 20 / ≤ 40 | ≤ 24 / ≤ 60 | 11.4 / 12.2 · 18.7 / 25.7 · 22.6 / 92.4 | 60/150 干净；**300 档最长帧 92.4 ms + 3 次长任务已经不干净**，这条预算是「守住今天并留一点余量」，不是「今天就合格」 |
| `wheel-zoom` | 最长 ≤ 80 / 长任务 ≤ 1 | 最长 ≤ 120 / ≤ 3 | 最长 ≤ 150 / ≤ 4 | 57 / 0 次 · 210 / 7 次 · 393 / 10 次 | 150 与 300 档今天都越线 |
| `zoom-slider-drag` | 最长 ≤ 80 / 长任务 ≤ 1 | 最长 ≤ 120 / ≤ 3 | 最长 ≤ 150 / ≤ 4 | 162 / 2 次 · 293 / 8 次 · 542 / 10 次 | 三档全越线；S6 是一行改动 |

定这几个数的依据，不是「比今天好看一点」，而是三条：

- **p95 ≤ 20 ms** = 在 120 Hz 屏上至少稳住 50 fps、在 60 Hz 屏上稳住 60 fps。今天组框拖动 62 fps 的体感被用户判成「特别卡」，所以 33 ms（=30 fps）这个既有天花板对**拖动**来说太松了——它是给「一帧偶尔超时」用的，不该当成拖动的常态目标。
- **最长帧**才是体感的那一刀。缩放那两条的预算给的是最长帧而不是 p95：p50 一直好看（8.4 ms），坏的全在尾巴上。
- **长任务次数**是**工作量计数**，不随机器负载漂——在这台常年 20+ 工作树的机器上，它比毫秒更可信，应当当硬门岗，毫秒当 advisory。

**还要补一条「长任务次数」的硬门岗。** 今天 `PERFORMANCE_BUDGETS` 里只有 `longTaskP95Ms`（毫秒，会随负载漂），没有**次数**。而本轮最刺眼的信号恰恰是次数：`drag-nodes-all` @ I150/I300 一次手势里 **249 / 251 次**长任务，同一分钟里的 `marquee-select-all` @ I300 是 **0 次**。次数是工作量计数、与机器负载无关（§2 对照组那段的理由），建议按档给：**60 节点 ≤ 1 次 / 150 节点 ≤ 3 次 / 300 节点 ≤ 5 次**，硬门岗；毫秒继续当 advisory。

**落地方式**：这几档进 `PERFORMANCE_BUDGETS`（`tests/ux/canvas-performance-benchmark.e2e.mjs:1248`）时按 `scale` 取值，时间类的一律经现有 `timingBudget()` 出口（它已经把非 darwin ×1.6 处理掉了，**不要另写一套平台分支**）；长任务**次数**按计数类处理，**不跟着平台放宽**（与现有 `maxLoadingImages` 等计数类一致）。`drag-nodes-all`、`drag-group-frame-60` 与 `zoom-slider-drag` 三个场景现有门岗里都没有，要新加。

## 7. 没量到的，以及为什么

1. **React 每次 commit 的耗时**。仓库里唯一的 React 内部探针（`tests/ux/canvas-perf/offCanvasRenderProbe.mjs`）靠 `addInitScript` 伪造 `__REACT_DEVTOOLS_GLOBAL_HOOK__`，只在 **dev 腿**有意义——prod bundle 的组件名被压掉了。本轮量的是 prod 产物，所以用了两个替代物：DOM 层面的「每次 flush 触碰了几个节点实例 / 几处变更」（工作量计数，与负载无关），加上 CDP 的 script/style/layout 三分。想要真正的 commit 时长，得另跑 `--dev-server` 腿，那条腿的绝对值又不可与 prod 比。
2. **「图全黑了」没有做真机复现**。因果链上的每一环都在代码里核过（协议处理器在主进程、深度任务 32×`readFileSync` 无让出、4 个图片槽、8 秒超时、`bg-nomi-ink-05` 满幅遮罩、暗色 token 值），但**没有真的起一个深度抽帧任务去把画布逼黑**——那需要一段真实视频 + GPU worker 跑几分钟，会和性能采样抢机器。**这条是 S7 的验收动作**：夹具画布 + 一个真实深度任务并行，断言「任何节点进入 `timeout` 态」= 红。在做出这个复现之前，S7 的因果链是「读出来的」不是「测出来的」，文档里按这个强度引用。
3. **干净机器上的绝对毫秒**。这台机器常年跑着 20+ 个工作树；本轮开始时 load average 一度 46，各档最终是在 **7–32** 之间跑的（每行都记了 `load`）。最坏的那一格 `drag-nodes-all` @ I300 正好撞在 load 26.7–32.4 上，所以**它的绝对毫秒是本份文档里最软的一个数**。但结论不靠它：同一个 app 实例、同一分钟里跑的 `marquee-select-all` @ I300 是 75–80 fps、`pan` @ I300 是 86–95 fps，**机器当时并不是普遍慢**——是这一个手势慢。**比值和工作量计数（`触碰/刷 = 300`、长任务 258 次）与负载无关**，它们才是判据。
4. **`I300` 的 `drag-nodes-20`**。300 节点时 React Flow 的选区罩子比手势安全区还大，找不到既在罩子上、又离舞台边够远（不触发自动平移）的抓点，三次都跳过。同档的 `drag-nodes-60`（实际选中 40）与 `drag-nodes-all`（300）从两头夹住了同一条内核路，结论不受影响。

5. **图片解码的毫秒数**。解码跑在渲染进程的 raster/decoder 线程上，**不进** CDP 的 `TaskDuration`，主线程只承担派发；本轮的仪器（rAF 计时器 / `Performance.getMetrics` / `MutationObserver` / CPU 采样器）没有一件能看到它。所以「图片解码贵不贵」这个问题**本轮没有答案**，文档里任何地方都没有把它算进热点。手头唯一相关的间接证据是反向的：`wheel-zoom` 的 style 只有对照组的 2–3×、`nodeStyleWrites` 全程是 transform 写，没有指向解码的迹象。要真答这个问题得开 `Media.playerEventsAdded` / 帧级 tracing，另立一轮。

6. **选中数在 `I300` 是 DOM 数出来的，不是 store 里的真值**。`drag-nodes-all` @ I300 表里记 `选中 204`，但「每刷重渲染实例」是 **300**——因为 `selectedCount()` 数的是 `.react-flow__node.selected` 这种**已挂载**的 DOM 节点，而 `onlyRenderVisibleElements` 只挂了 204 个；`Cmd+A` 在 store 里选中的是全部 300 个，也确实是 300 个在动。读这一行时以 300 为准，204 是仪器的口径不是事实。
7. **三档之间不是同一种渲染**。适应视图在 300 档会贴到 `CANVAS_MIN_ZOOM = 0.2`（`model/canvasFitBounds.ts:50`），而轻量 LOD 的触发条件是 `nodeCount > 80 && zoom < 0.55`——所以 **I60 走的是完整卡片渲染，I150/I300 走的是轻量渲染**。这不是夹具没设计好，这正是 §5 S5 要修的那个判据问题；表里每行都记了 `zoom` 和挂载数，读的时候要带着看。
8. **`drag-group-frame-60` 在 I300 上没取 CPU 采样**。`--profile` 的机时排在共享门岗锁后面，只够跑两格，优先给了全局最坏的 `drag-nodes-all`（I150 + I300）。组框那条路的采样只有 I150 一格。影响有限：组框拖动的三档帧时间几乎是平的（62.2 / 61.8 / 59.9 fps），它的瓶颈不随 N 长，I150 那一格足以代表；真要补，跑
   `pnpm run test:canvas-scale -- --scales I300 --scenarios drag-group-frame-60 --runs 1 --profile --label prof300` 即可。

9. **没量 Windows / Linux**。预算表给的是 darwin 基准值，非 darwin 由现有 `timingBudget()` ×1.6 派生——这个系数是既有的、别人校准的，本轮没有重新验证它对这几个新场景是否合适。

## 8. 建议的下一步顺序

3. **S3（节点不订整表）**：按实测它是第一热点，也是唯一能把 `drag-nodes-all` 那条超线性曲线掰平的。**单独一刀**，别和 S1 混在一个 PR 里——两者修的是不同的路，混在一起就分不清是谁把数字压下来的。
