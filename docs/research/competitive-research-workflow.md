# 竞争产品与开源能力研究工作流

状态：✅ 已交付

## 目标

把“用 Codex 点击研究竞品/开源项目，最后能指导 Nomi 迭代”固化成可复用、可复查、可验收的仓库流程。

研究的交付物不是链接堆积，而是回答四个问题：

1. 目标用户在什么时刻得到什么结果？
2. 目标产品通过什么交互和数据结构得到这个结果？
3. Nomi 当前已有哪部分、缺哪部分、哪些旧实现应保留或删除？
4. 哪些能力应该直接采用成熟开源项目，哪些只能借鉴，哪些不值得引入？

## 研究范围

本流程支持两类研究：

- **产品/网站研究**：必须使用 Codex 浏览器完成真实点击；每个有意义的动作都要保存截图，并记录“动作 → 观察 → 对 Nomi 的启发”。
- **开源项目/框架研究**：必须读取官方仓库 README、许可证、最近发布/提交信息和官方文档；需要交互证据时再用浏览器或运行项目，不把 GitHub star 当成体验证据。

对于 Nomi 的 3D 导演台，研究对象要按能力分层：

| 层 | 要回答的问题 | 当前优先候选 |
|---|---|---|
| 3D 场景运行时/编辑 | 如何让角色、道具、相机和场景可选择、可移动、可保存？ | Three.js、React Three Fiber、Theatre.js |
| 动作输入/动作清理 | 如何从一句话、视频或关键姿势得到可控动作？ | MMPose、GVHMR、WHAM 论文/实现、Rokoko/DeepMotion 外部适配 |
| 3D 资产 | 如何从文字/图片得到可放入镜头的角色和道具？ | TRELLIS.2、Hunyuan3D、TripoSR |
| 2D 参考设计台 | 如何快速裁剪、标注、分层、局部修改参考图？ | Nomi 现有 Leafer、Penpot、Fabric.js、SVG-Edit |

## 证据协议

每条判断必须带一个状态：

- `observed`：在产品、仓库或真实运行环境中直接看到。
- `documented`：官方文档/README/许可证明确写出。
- `inferred`：由多个证据推导出的结论，必须说明推导链。
- `proposed`：Nomi 的设计建议，不得伪装成竞品事实。
- `blocked`：因登录、密钥、硬件、许可证或网络条件无法验证。

以下说法不能直接作为完成证据：点击了 Login、点击了 Generate、出现了任务 ID、页面显示“处理中”、只看到 README 截图或只看到 GitHub star。

## 本次开源对齐的决策原则

1. **优先复用现有内核**：Nomi 已有 Three.js + React Three Fiber、Leafer、React Flow，不为了“看起来更专业”再引入第二个同类 renderer。
2. **编辑器体验可以借鉴**：Theatre.js 的对象选择、属性面板、时间序列和关键帧是 3D 导演台的体验参考；不把其 Studio 直接当成 Nomi 的生产 UI，且要单独核对 AGPL 边界。
3. **模型和编辑器分离**：TRELLIS.2/Hunyuan3D/TripoSR 负责资产生成；MMPose/GVHMR 等负责姿态/动作输入；Nomi 自己负责镜头语义、角色绑定、可复核调整和参考物料编译。
4. **先做“镜头结果”，不做大而全编辑器**：用户首先要得到能喂给生图/生视频的参考包，而不是学习网格、骨骼、材质和时间轴。
5. **许可证是能力的一部分**：代码许可证、模型权重、人体模型、数据集和商用限制分开记录；未核对前只能标 `blocked` 或 `inferred`。

## 标准最终交付

每次研究包至少包含：

```text
docs/research/<date>-<topic>/
├── README.md          # 给人读的最终结论
├── report-source.md   # 可追溯证据账本、来源和动作记录
└── assets/            # 研究截图；不放源视频/音频
```

README 必须包含：范围与不做项、证据状态、Nomi 当前真相、按用户任务的走查、能力矩阵、保留/重做/采用/不采用决策、风险与许可证、下一步验收任务。

## TikHub 账号宣传研究边界

账号级研究固定为“稳定账号身份 → 帖子元数据 → 小样本内容观察”。密钥只从运行时读取，不写入报告或 Git；默认最多 20 条元数据、最多 10 条下载/转写样本。报告保存公开视频链接、观察时间和结构化观察，不保存源视频/音频，也不复制完整脚本、镜头链、音乐或品牌视觉。

没有密钥、账号身份歧义、401/403、额度耗尽或 429 时，状态必须为 `blocked`，不能写成“已完成账号研究”。
