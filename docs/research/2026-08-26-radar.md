# Nomi 论文雷达 · 2026-08-26

一句话：本轮真正的新料是**「镜头契约」和「验收采样」两处 Nomi 已有字段但没闭环的地方，学术界给出了现成形状**——CineOrchestra（Snap Research，MIT 代码）把角色/运镜/转场统一成「实体在时间区间上行动」，正好是 Nomi `PlanShot` 已有 `transition`/`camIdx` 却无人消费的那块拼图；KeyFrame-Compass 则给出六维指标，直接量化 Nomi 镜级 verify **只抽首帧**这个盲区。

本轮最该动的两件事：

1. **把 `transition` 从死字段接活**（本轮实扫发现的真问题）：`storyboardPlan.ts:365` 把 `metadata.transition` 写进节点 meta，但**全仓没有任何下游读它**——planner 认真产出的转场意图落地即蒸发。CineOrchestra 的 `{transition}` / `{camera}` 统一标签给了一个可抄的目标形状（MIT 代码在手）。
2. **镜级 verify 补尾帧采样**：`shotVerifyRunner.ts:65` 每镜只 `extractFrame(which:'first')` 判一帧。Nomi 的 `PlanShot` 明明有 `lfDesc`（尾帧描述），却从不验证它是否兑现——KeyFrame-Compass 的实验结论正是「关键帧约束越密、模型执行越垮」，而我们连第二帧都没量。

> **窗口说明**：arxiv **2608（8 月）窗口依然很薄**——本轮实搜 2608 前缀在视频生成方向只捞到 2 篇够格的（2608.12290 无代码、2608.14718 是视频**理解**不是生成，见底部筛除说明）。按铁律只吃近 6 月（≥2603 在窗口内），本轮收的是 2606–2607 里前几期漏掉、经二次核验有代码/项目页的条目。08-23~08-25 已报的 ShotPlan / VideoWeaver / GroundShot / CANVAS / EntityBench / MSVBench / Gloria / InfinityStory / CineDance 一律不重复。

## 🟢 可落地

### CineOrchestra：角色/运镜/转场统一成「实体 × 时间区间」，Snap Research + MIT 代码

- **链接 / 日期**：[arXiv 2606.13768](https://arxiv.org/abs/2606.13768)，v2 **2026-06-16**；[项目页](https://snap-research.github.io/CineOrchestra/)、**代码公开** [github.com/snap-research/CineOrchestra](https://github.com/snap-research/CineOrchestra)。
- **火度核验（gh api 实查）**：**MIT license**，创建 2026-05-20，最后 push 2026-06-30，**7 star**——star 少，但**出自 Snap Inc. 研究院**（作者含 Sergey Tulyakov、Aliaksandr Siarohin，即 Snap 视频生成主力），且配套数据集已上 HF（`sharathgirish/CineBenchSyn`）。**按「很新的论文引用必然低、火度看代码/机构信号」判：机构 + MIT 代码 + 数据集三项齐 → 收。**
- **洞察**：核心断言是「**所有电影元素都是实体在时间区间上行动**」——角色、道具、镜头运动、转场，全部用同一结构表达：唯一 tag（如 `{man_old}`）+ 可选参考图 + 全局身份描述 + **带时间戳的事件描述**。运镜是 `{camera}` tag（"pans left"），转场是 `{transition}` tag（描述 fade/cut 时机）。两处位置编码改动是 **parameter-free** 的（interval-sampled temporal RoPE 处理 0.1s 硬切到 10s 运镜的变时长；2D entity-temporal cross-attention RoPE 免辅助 mask 把条件路由到正确时空区域）。CineBench 上转场召回 0.486、主体身份一致（masked DINO）0.502，六个专用 baseline 全面胜出。
- **落到 Nomi**：**这是本轮最直接的一条**。Nomi 的 `PlanShot`（`src/workbench/generationCanvas/agent/storyboardPlan.ts:50-121`）已经有了 CineOrchestra 三分之二的字段——`transition: {type: 'cut'|'dissolve'|'fade'|'match_cut'|'whip_pan', durationFrames?}`（:84-88）、`camIdx`（:99）、`ffDesc`/`lfDesc`（:78/:109）、`anchorIds`（:63）。**缺的不是字段，是消费者**：
  - **实扫结论（已核）**：`storyboardPlan.ts:365` 有 `if (shot.transition?.type) metadata.transition = { ...shot.transition }`，但对 `src/workbench` + `src/timeline` 全仓 grep `transition`，**除该写入点外没有任何业务读取**（命中的全是 framer-motion 动画属性和 `deferredNodeMediaQueue.ts` 的状态机 `transitionTo`，与镜间转场无关）。**planner 产的转场意图写进 meta 就断了**——这是一个当场看不出毛病的死字段（P2「修完还能从别的入口出现吗」→ `camIdx` 同样只有定义、需一并核实消费方）。
  - **建议动作**：① 先补一条**结构保证**——转场/机位这类「planner 产出但无下游」的字段，要么接上消费者，要么删（P1 加新必删旧的反面：留着的死字段会让人以为功能已存在）；② 接的时候抄 CineOrchestra 的统一形状而不是各接各的：转场与运镜都是「实体在区间上的事件」，这样 `{camera}`/`{transition}` 走同一条适配路径，符合 P4 通用解耦（Wan/CineOrchestra 系可原生、其它标 translated，沿用 08-23 MotionCtrl 教训）。
  - **与 08-24 ShotPlan 的关系**：ShotPlan 给的是「转场作为可控 token」的**生成侧**能力，CineOrchestra 给的是「转场/运镜/身份统一表达」的**契约侧**形状。**Nomi 眼下缺的是后者**（契约断在自己家里，还没轮到模型接不接得住）。

## 🟡 架构教训

### Beyond Trial-and-Error：把「换个种子重抽」升级成有目标的闭环优化，但成本要看清

- **链接 / 日期**：[arXiv 2608.12290](https://arxiv.org/abs/2608.12290)，v1 **2026-08-12**；作者来自 **Google Cloud + Google DeepMind**；**本轮实查未找到公开代码仓**。
- **洞察**：把黑盒 I2V 生成重构成「闭环、有目标的优化」。两阶段：① mLLM 迭代改 prompt（10 轮），由两套自动评估导航——**Davidsonian Scene Graph 查询**判语义符合度 + **Common Mistake Questions** 判伪影；② **贝叶斯优化联合调随机种子和 CFG**，用第一阶段导出的 Video-Text Adherence（VTA）分做目标。全程 **training-free**。人类偏好胜率最高 **69%**（RAHF 指标、100 次生成预算）；**降到 10 次预算只剩 47%**；对更强的 Best-of-Random baseline 是 42% vs 8%。
- **影响 Nomi 哪个决策**：这条**故意放 🟡 不放 🟢**，理由是诚实的成本账（D4）：它的 69% 建立在**每条视频跑 100 次生成**上，Nomi 是用户自己付 API 钱的本地工作台，**这个预算在产品里不可接受**——论文自己也把「显著的计算成本」列为第一条限制，且只在 Veo 2.0 上测过 100 条 V-Bench 样本，没披露任何单条成本数据。
  - **真正可拿的是它的结构，不是它的预算**：把「重生成」从盲抽升级成**带评估信号的定向重试**。Nomi 已有的 `shotVerify` 链路（`shotVerifyRunner.ts` + `shotVerifyJudge.ts`）就是现成的评估侧——今天它只判「这镜偏没偏」，**没有把判决回接到「下次重试改什么」**。DSG 式的「把 prompt 拆成可逐条问的断言」比一个总分更适合驱动重试（和 08-24 VideoWeaver「看轨迹回改」是同一方向的两份证据）。
  - **必须守住的红线**：Nomi 的重试预算是用户的钱，**任何自动重试都要在花钱前经确认闸**（仓库已有付费确认卡这条纪律）。这篇最该被记住的一句是：**10 次预算只有 47% 胜率**——即「小预算下这套方法优势有限」，别拿 69% 当能落地的数字宣传。

## 🔵 对标基准

### KeyFrame-Compass：六维量化「关键帧到底有没有被执行」——正对 Nomi verify 只看首帧的盲区

- **链接 / 日期**：[arXiv 2607.14202](https://arxiv.org/abs/2607.14202)，**2026-07-15**；有 [HF paper 页](https://huggingface.co/papers/2607.14202)；**本轮实查未见公开代码仓**（指标定义可直接借用，全量复现需等开源）。
- **洞察**：386 条精选样本，覆盖 3 个应用域 × 2 种视频结构 × 2 种 prompt 粒度 × 2 种条件格式 × **4 档关键帧密度**。把「关键帧执行」拆成**六个互补指标**：**presence（出没出现）/ fidelity（像不像）/ temporal ordering（顺序对不对）/ localization（落在对的时间点没）/ persistence（保持住没）/ uniqueness（有没有重复糊弄）**。三条关键发现：① 关键帧执行与自然度存在**明确的取舍**（越守约束画面越僵）；② **关键帧越密、性能越垮**；③ 多数开源模型**读不懂 storyboard 宫格图**是有时序的关键帧序列。
- **怎么接进 Nomi eval 体系**：这是本轮**证据最硬的一条**，因为它量的正是 Nomi 已经在做但没验的事：
  - **现状实扫（已核）**：`src/workbench/generationCanvas/agent/shotVerifyRunner.ts:65` —— `frameUrl = shot.isVideo ? await deps.extractFrame(shot.frameSourceUrl) : shot.frameSourceUrl`，配合 `shotVerifyJudge.ts:20` 的 `which: 'first'`，**每镜只抽首帧判一次**。而 `PlanShot.lfDesc`（storyboardPlan.ts:109）明确定义了尾帧快照描述、注释里也写了「首尾都给，运动落点被两端夹住」——**产出了尾帧意图，却从不验证兑现**。这与 🟢 条的 `transition` 死字段是**同一类病**（P2 通用性判定：planner 产字段 → 无消费者/无验证），值得一次扫清。
  - **接法（低成本先行）**：先取六维里 Nomi 今天就能测的三维——**presence / fidelity / temporal ordering**，做法是给 `shotVerify` 增加尾帧采样（`extractFrame` 已支持 `which:'last'`，见 `shotVerifyJudge.ts:20` 的参数位），首帧对 `ffDesc`、尾帧对 `lfDesc` 各判一次，两端都过才算该镜通过。`localization`/`persistence` 需要多点采样，留到有预算再上。
  - **另一条直接可用的结论**：「多数模型读不懂宫格图的时序」——如果 Nomi 任何地方在用**拼接宫格图**喂参考（定妆卡/场景卡的多变体并列，见 `PlanAnchor.variants` storyboardPlan.ts:47 注释「多视图+多变体集中在一张图里、整张喂参考」），**要警惕模型把它当空间构图而非时序序列**。定妆卡是身份参考（空间用途）问题不大，但若将来把宫格用于表达镜头序列，这篇是明确的反对证据。
