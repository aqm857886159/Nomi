## 本轮最该动的 2 件事

### 1. 重做方案 §3 的 S2 门岗，在「拆工具」之外再加一条「根级不得出现 `anyOf`」——否则拆完还是 0/18

**为什么**：重做方案 §3 现在的处方是「`canvas.write` 的 9 个 operation 拆成 3 个语义工具，每个 ≤4 分支」（门岗 S2）。但 [pi 一致性核对](2026-09-07-pi-reference-implementation-conformance.md) §0 已经指出——拆完**仍然是根级 `anyOf`**，而 Anthropic 适配器会把根级 `anyOf` 静默丢掉、Google 的 legacy `parameters` 路径（OpenAPI 3.03）压根不支持它。也就是说 0/18 可能有第三个成因，拆工具治不了。

**新证据从正面说了同一件事**：`HEART`（[2609.01736](https://arxiv.org/html/2609.01736)，2026-09-01）的核心动作就是**把刚性 API schema 换成自然语言接口、schema 解析收进工具内部**，实测比监督微调模型高 10%、比 GPT-5.4 / Claude-4.6-Sonnet / Gemini-3.1-Pro 高 6%、**API 成本降到 15%**，50 个真实任务上 84% vs 三个商业模型的 22%。它证明的不是「union 少一点更好」，是**union 根本不该出现在线上的 wire schema 里**。

**落到哪里**：`docs/plan/2026-09-07-agent-runtime-rebuild.md` §3 的 S2 一行 + `electron/shared/agentCapabilities/canvasWrite.ts`（那 11 个 `z.discriminatedUnion`）+ `electron/harness/tools/modelToolSurfaceManifest.ts`。改动是**门岗判据 + schema 形状**，不是新功能，属阶段 2 的既定范围内、不扩范围。

### 2. G2 复测别只报一个「一次写对率」，按 ToolRobustBench 的五段归因拆开量

**为什么**：现在 0/18 摆在三个互不排斥的假设之间——① 9 分支太多让模型选错、② 两个字节级相同的别名工具让它抛硬币、③ 根级 `anyOf` 被适配器丢掉导致它压根没看见分支。**一个总成功率分不开这三个**，改完只会知道「变好了」，不知道是哪一刀起的作用（P2：修根因不修症状，得先能归因）。

`ToolRobustBench`（[2608.23635](https://arxiv.org/html/2608.23635)，2026-08-23）给的正是现成的归因框架：把失败归到 **工具选择 / schema 落地（schema grounding）/ 参数绑定（argument binding）/ 工具输出与运行时反馈处理 / 端到端成功** 五段。它跑 15 456 个单族扰动实例后的结论还额外提醒我们一件事——**「工具输出/观察扰动」才是最大瓶颈**，不是输入端；而我们的方案里对「拒收回执长什么样」恰恰一次都没量过（用户撞到的那条真实摩擦就是「连续 6 次被自己拒收」）。

**落到哪里**：`docs/plan/2026-09-07-agent-runtime-rebuild.md` §G2 的验收表——同一套 5 任务 × 3 次不变，只把结果列从「过/不过」换成五段归因。零额外额度成本（同一批跑，只是多记一列）。

## 🟢 可落地（这月能进 Nomi 的具体能力）

### HEART — 用「agent 原生可复用工具原语」替刚性 API schema
- arxiv **2609.01736**（2026-09-01） · <https://arxiv.org/html/2609.01736>
- **洞察**：Planner / Router / Verifier 三件套，外加**每个工具包一层 LLM 接口、schema 解析在工具内部完成**，模型面只看到自然语言接口；工具间可嵌套、可多轮通信。配套 `ToolFace` 是一个 25 519 个函数的仓库 + 推理期动态检索（**这一条也回答了「工具太多会不会拉低选择准确率」——它的答案是别全发，按需检索**）。
- **数字**：优于监督微调模型 10%；优于 GPT-5.4 / Claude-4.6-Sonnet / Gemini-3.1-Pro 6%；API 成本最多降 85%；50 个真实任务 84% vs 22%。
- **落到哪个文件 / 怎么改**：`electron/shared/agentCapabilities/canvasWrite.ts`（根级 union 下沉进工具内部）+ `electron/harness/tools/modelToolSurfaceManifest.ts`（模型面 schema 扁平化）+ 重做方案 §3 的 S2 判据。**别照抄它的 Planner/Router/Verifier**——我们已经在换 pi 的 `AgentHarness`，再塞一层自研编排就是 P1 并行版。只取「工具接口形状」这一条。
- **成熟度**：未见公开代码仓（本轮实抓无 repo 链接）。但我们要的是**接口形状**不是它的实现，所以不受影响。

### ToolRobustBench — 工具调用失败的五段归因框架
- arxiv **2608.23635**（2026-08-23） · <https://arxiv.org/html/2608.23635>
- **洞察**：四族扰动（工具接口 / 用户意图 / 工具输出与观察 / 运行时环境）对齐工具使用流水线，失败归因到五段：工具选择、schema 落地、参数绑定、输出与运行时反馈处理、端到端成功。15 456 个单族实例；**混合族扰动呈非可加失败**（单族结果预测不了组合结果）。
- **数字**：干净场景表现高但不均匀，**「工具输出/观察扰动」是主导瓶颈**。
- **落到哪个文件 / 怎么改**：不是接它的数据集，是**借它的归因维度重画 G2 验收表**（`docs/plan/2026-09-07-agent-runtime-rebuild.md` §G2）。同一批任务、同一批额度，多记一列归因。
- **成熟度**：未见明确 code/data release 说明（**待核实**）。归因维度本身不依赖它的代码。

### EditVid（One Editor, Many Edits）— 训练无关的统一视频编辑
- arxiv **2609.04190**（2026-09-03） · <https://arxiv.org/abs/2609.04190> · 项目页 <https://plan-lab.github.io/editvid>
- **洞察**：一个训练无关框架同时覆盖风格迁移、属性修改、物体插入、**部件级编辑**、主体替换；机制是稀疏因果记忆（局部连贯）+ 基于对应关系的注意力后 token 注入（长程身份）+ 软 latent 混合（**编辑局部性**）。
- **数字**：FiVE 基准 **78.16 FiVE-Acc**，最强训练无关基线 58.95；用户研究对 7 个竞品 51.8% 总体偏好。
- **落到哪个文件 / 怎么改**：对应记忆里 09-06 用户点名框工具时那句「**指哪改哪 mask 要先逐模型核实**」——EditVid 的「软 latent 混合保证编辑局部性」是**不逐模型定制**的那条路的现成参照。当前先当**目标形态与核实基准**记下来（我们不训模型），落地点是矩形框/Frame 工具的「局部改」语义设计，不是这个月写码。
- **成熟度**：有项目页，代码是否释出**待核实**。

## 🟡 架构教训（不直接落地，但影响设计决策）

### Harness 设计 × 后训练的相互作用 — 「补丁贴在管道外面」有了实证
- arxiv **2606.25447**（2026-06-24） · <https://arxiv.org/abs/2606.25447>
- **洞察**：把 harness（暴露哪些工具、工具怎么描述、每步观察附带什么上下文）当**可控变量**在 ALFWorld 上做实验。结论：**最小努力的 harness 在工具环境漂移下崩得最狠**；harness 感知的后训练不仅提升分布内表现，还让 agent 能稳健适应分布外。
- **影响 Nomi 哪个决策**：这是重做方案 §0.1 那个判断的外部佐证——「我们把 pi 当 HTTP 客户端在用」不是风格问题，是**在工具面演化时会成倍付账**的结构问题。与上一轮 `MCPEvol-Bench`（MCP server 演化时 agent 掉 13.7~14.4 个点）同向、互相独立。**用法**：给「重做而不是补丁」这个已拍板的决定补一条可引用的证据，不改方案。

### EM-Vid — 实体银行是 GroundShot 的轻量对偶（预算化记忆）
- arxiv **2605.23610**（2026-05-22） · <https://arxiv.org/html/2605.23610>
- **洞察**：训练无关。**实体索引的 latent patch 银行**把持久实体信息与瞬时场景上下文**分开存**（不让背景污染角色）；稀疏 token 条件把注意力限制在实体相关信息上；**预算化记忆更新**保持表示紧凑；噪声注入控制外观。
- **影响 Nomi 哪个决策**：上一轮头条 GroundShot 讲的是「按参考有用度调度生成顺序」，EM-Vid 补的是另一半——**记忆库必须是有预算的**。我们的 character_ref / 设定卡如果做成「所有产物都往里塞」，会重蹈它明确要避开的那个坑。列 🟡 而非 🟢：本轮实抓**未见公开代码、未见量化数字**，火度信号不足，只取设计取向。

### Thinking on Shots — 镜头级 agentic 推理做多镜编辑
- arxiv **2608.26809**（2026-08-26） · <https://arxiv.org/abs/2608.26809>
- **洞察**：用 LLM + VLM 做**镜头级**（不是帧级、不是整片级）的一致编辑推理。
- **影响 Nomi 哪个决策**：印证「镜头是编辑的原子单位」这个我们已经选了的粒度（分镜表一行 = 一个镜 = 画布上一组节点）。**用法**：当阶段 2 之后设计「改一个镜、下游怎么连带」的语义时，这条是可比参照。

### 节点式画布的认知负荷是有实证的高门槛（框工具/画布直接相关）
- `VisCanvas`（arxiv **2607.21886**，2026-07）：LLM 驱动的节点式探索性可视化编排 · <https://arxiv.org/html/2607.21886>
- `Workflow-Net`（Archives of Design Research 39(2), 2026）：**对比节点式 vs prompt 式界面**的设计师工作流实证 · <https://www.aodr.org/_PR/view/index.php?aidx=49535&bidx=4446>
- **洞察**：节点式界面的门槛与认知负荷来自「要先懂节点功能与参数配置」+「从空白画布手搭工作流本身就是劳动」；文献里提到的一个缓解方向是 **positional control——节点的空间位置直接决定执行顺序**，用空间换掉一部分连线交互成本。
- **影响 Nomi 哪个决策**：① 「从空白画布手搭」是真门槛 → 支持我们「Agent 建完节点、用户只改 prompt」和「批量产出自动编组」的既定方向；② **positional control 值得在框工具（Frame）设计里想一想**——如果框内的空间位置本身就能承载语义（顺序/分组），那 Frame 就不只是个装饰性矩形。列 🟡：这是设计取向的证据，不是可落地代码，**且要先过样张与用户拍板**（P5/R8），别直接改交互。

## 🔵 对标基准（能拿来量化自评 Nomi）

### KathaTrace / KathaBench-25K — 「语义轨迹坍缩」与 STG 指标（本轮最推荐先接的一把尺）
- arxiv **2607.01312**（2026-07-01） · <https://arxiv.org/pdf/2607.01312>
- **它量什么**：**语义轨迹坍缩** = 画面之间看着连贯、但「这一镜为什么接上一镜」的**转场语义丢了**。方法是在三种条件下测转场可理解性（只给文本 / 只给图 / 图文都给），定义 **STG（Semantic Trajectory Gap）= 只给文本的可恢复分 − 只给图的可恢复分**。
- **数字**：多个 SOTA 生成器上 STG 高达 **23.5 ± 1.3**；人工验证 Fleiss' κ = **0.845**（一致性很高，说明这把尺不虚）。数据集 KathaBench-25K：5 000 篇叙事、20 000 个转场、28 712 道评测题。
- **怎么接进 eval 体系**：接到 `evals/` 的生成质量 lane。**接法比数据集更重要**——STG 的构造（同一段叙事，分别只喂文本和只喂图去问「这一镜为什么接上一镜」）可以直接用我们已有的 VLM 走查基建复现，不必依赖它的数据集（数据/代码是否释出**待核实**）。这也正好量的是上一轮 DirectorBench 指认的那个全行业瓶颈（转场质量均值 0.256）。

### PersonaShot — 人物中心的多镜叙事连续性基准
- arxiv **2608.16717**（2026-08-17） · <https://arxiv.org/html/2608.16717>
- **它量什么**：首个人物中心的多镜叙事连续性基准，约 1 000 个多镜片段、**16 个指标三条轴**——物理连续性（镜内/跨转场/序列级轨迹）、**情绪动态**（表情与情绪状态）、电影语法（镜间关系连续性）。
- **关键发现**：**视觉上很好看的片子，照样频繁出现「物理状态重置、情绪突变、镜间关系断裂」**——画质与叙事连贯是两件事。
- **怎么接进 eval 体系**：它的**情绪动态**轴是我们身份 lane 现在没有的一维（上一轮建议先接一条身份指标，那条量的是「长得像不像」，这条量的是「情绪接不接得上」）。**建议先只接情绪动态这一轴**，别整套搬，理由同上轮：别把 eval 变成收件箱。数据/代码释出**待核实**。

### 最有价值的一条 —— 「分镜节奏」是真实摩擦，不是我们推测的

> **抖音 · 小陈AIGC · 2026-07-21** ——「为什么AI生成了20个分镜，成片还是很僵硬？很多人做AI漫剧，最大的问题不是画面不够精致，而是分镜节奏出了问题。**AI最常犯的错误，就是把每句话平均切成一个镜头，结果整部片子没有轻重、没有停顿、没有情绪爆点。**」
> <https://www.douyin.com/video/7664920212981992739>

这条为什么重要：它和本轮两篇论文**说的是同一件事的三个面**——KathaTrace 叫它「语义轨迹坍缩」（转场为什么接得上，说不出来）、PersonaShot 叫它「情绪突变 / 镜间关系断裂」、这位创作者叫它「没有轻重、没有停顿、没有情绪爆点」。三个独立来源指向同一个诊断：**一句话一个镜头是错的默认，正确的默认是先拆情节节拍，再按冲突/反转/情绪设计镜头。**

**对我们的意思**（先记，别急着改）：`electron/capabilityCore/mcpStoryboardPlanner.ts` 的拆镜策略、以及分镜表 v6 的列结构（[`docs/design/2026-09-05-storyboard-table-v6-design-contract.md`](../design/2026-09-05-storyboard-table-v6-design-contract.md)），**可能缺一个「节拍/情绪」维度**。但这是**产品取舍不是卫生清理**——加一列会动已拍板的 v6 契约，要先出样张给用户看（P5/R8）。本轮只把证据摆齐，不动设计。
