## 结论

相关 PR 没有可直接恢复的统一实现。应保留的共同判断是：Nomi 的能力、权限、预算、审批、作品事实和 UI 状态必须各自只有一个 semantic owner；Pi 只提供通用运行循环；MCP / Skill / 内嵌 Agent 通过同一能力合同进入不同 transport；UI 以已拍板设计和真实截图为基准，不能因历史 PR 落后主线就丢掉其中记录的摩擦证据。

GitHub review API 未返回这些 PR 的非空 review body 或 line review comments；因此下表的“审查输入”只把 PR 正文、changed-files 和可见 issue comments 当作证据，不把 CI bot 部署评论冒充代码审查。唯一有实质性人工 issue comment 的是 #199：作者说明按产品复核撤下，要求补齐折叠编组聚合端口并完成全量/真实 Electron 走查后重新提交；这也是 #201 的直接背景。

## 硬性使用规则

1. Phase 5 开始前，补做一次 GitHub open/closed/merged PR 枚举，确认本表没有漏掉新的相关 PR，并逐项更新 `changed files`、review 讨论和相对最新 `main` 的漂移。
2. MCP / Skill / Registry 实现必须先在本表找到对应证据和 `adopt/adapt/reject` 结论，再开始 RED；没有结论的历史 PR 是 hard fail。
3. UI 实现先读取现有批准设计、真实运行界面和 #194/#196/#199/#201/#203 的核心判断；只有证据证明信息层级不足时，才改 `docs/design/nomi-design-system.md` 对应 token/规范并重新出样张。
4. 任何历史方案都不能恢复第二个 transcript、pending、receipt、capability schema、executor、ProductionRun 或 timeline owner。历史 PR 的价值是问题证据和设计输入，代码基线永远是最新 `main`。
