# `src/config` 结构评审：模型身份这一层为什么 7 天里挨了 4 份根因合同

触发：`check:symptom-cluster`（R21，同一模块 7 天内 ≥3 份根因合同）。2026-09-11 到 09-17，落在 `src/config` 的合同有四份：

| 合同 | 它当时在修什么 | 那份合同自己写的类根因 |
|---|---|---|
| `2026-09-11-audio-reference-slot-gate` | 声音节点连不进视频节点，即使模型档案声明了 `audio_ref` | 「参考媒体的种类」被好几处各自建模成闭合的二元枚举（image \| video），而不是从**实际声明/可产出的集合**派生 |
| `2026-09-11-shot-pricing-single-rule` | 画布确认条印的金额比真扣的少 | 「一镜多少钱」没有单一持有者；算式住在主进程实现层，渲染层每多一个要显示价格的界面就再长一份 |
| `2026-09-12-model-availability-single-owner` | 同一时刻设置页说「2 个可使用」、首页说「尚未连接」 | 「这个模型现在能不能用」没有 owner；每个新界面自己拼一次「启用+发布+钥匙」的合取 |
| `2026-09-17-local-speech-provider`（本次） | 接本地离线转写 | 「按需下载的第三方可执行物与权重」没有共用地基，第二家要用只能抄一份 |

## 这四份是同一个结构问题吗？前三份是，第四份不是

**前三份是同一件事的三个切面**：`src/config/modelArchetypes/` 这一层同时在扮演两个角色——它既是**模型身份的声明**（这个模型有哪些模式、哪些参数、哪些参考槽），又在事实上成为**跨进程共享契约的落脚点**（主进程的 `electron/shared/videoCapabilities`、`electron/catalog/archetype*.generated.ts` 都从它 derive）。一个声明层被当成契约层用，后果是固定的：

- 契约层该有的东西它没有——没有「这一条语义归谁回答」的显式 owner，于是读者各自重算（定价、可用性、参考种类，三次都是这个形状）；
- 声明层该有的自由它也保不住——每加一个字段都要连带跑 `gen:archetype-defaults` 往主进程那边生成三份桥接文件，任何一处没跟上就是一次静默不一致。

四份里有三份的类根因，翻译过来都是同一句：**这一层的读者跨了进程，而语义的 owner 没跟着一起跨。** 三份合同各自在自己那条路上把 owner 补上了（`anchorPolicy` 派生参考种类、定价下沉到 `electron/shared/`、可用性收到单一 owner），但**这一层本身仍然是「声明 + 事实契约」的混合体**——所以它还会有第四次、第五次。

**第四份（本次）不是这个结构问题**。它落在 `src/config` 的只有一个文件：`src/config/modelArchetypes/localSpeech.ts`，一份 60 行的新档案，没有新的跨进程语义、没有新的派生桥接（它的模式里一个参数都没有）。它真正的类根因在 `electron/downloads/`——「按需下载的第三方资产」此前只有深度权重一家，被抽成共用地基，且那一层新增了会红的门岗（`check:supply-chain-pins`）。把它算进 `src/config` 的簇里是**聚类判据按目录前缀算**的结果，不是同类症状。

## 裁决：不在本次拦，但把真正的结构项立起来

**不改本次交付**。理由：本次在 `src/config` 的增量是一份新档案，删掉它不会让上面那个结构问题好一点，加上它也不会更糟。为了凑聚类门岗而把一份 60 行档案挪到别处，只会让「档案住在哪」这件事多一个例外——那是给门岗打补丁，不是修结构。

**立项**：`src/config/modelArchetypes` 的定位要一次性说清楚——它是纯声明层，还是跨进程契约层？两条路各自的代价：

| 方案 | 用户看到 | 代价 |
|---|---|---|
| A. 承认它是契约层，整层下沉到 `electron/shared/modelArchetypes/` | 无变化 | 一次大搬家；渲染层要改一大片 import；但从此声明与契约同址，三份桥接生成文件可以删掉两份 |
| B. 保持声明层，把所有跨进程语义显式收进 `electron/shared/` 的 owner（定价、可用性、参考种类已经各自做过一次，把剩下的扫完） | 无变化 | 要先做一次 R14.1 式的七维横扫，把「还有哪些语义正在被两边各算一次」数出来；工作量不确定 |
| C. 什么都不做 | 无变化，直到下一次两个界面给出不同答案 | 下一份合同会在几周内到来（过去 7 天已经到了三份） |

这份评审**不替用户拍板**（R3：涉及取舍先给对比表）。建议先做 B 的第一步——那次横扫本身就是 A/B 之间做选择所缺的那份数据。

## 复发监测

下一份落在 `src/config` 的合同要在自己的 `recurrence.same_class_scan` 里回答一句：它的类根因是不是又一次「读者跨进程、owner 没跨」。如果是第五次，那就不用再评审了，直接按 A 或 B 执行。
