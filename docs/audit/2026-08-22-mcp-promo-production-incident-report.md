# Nomi MCP 宣传片制作过程问题报告

日期：2026-08-22  
范围：本次 Nomi v0.20.1 安装包替换、对标视频研究、MCP 生成、真实页面参考、HyperFrames 合成、FFmpeg 后期、配音与最终交付全过程。  
性质：过程复盘与问题归因；本报告不修改业务代码、不改变核心规则。

## 一句话结论

这次最根本的问题不是某一个节点失败，而是“意图、参数、素材、运行状态、最终文件”没有形成同一条可验证的生产链：用户想要的是“替换 v0.20.1 → 用真实页面作参考 → 通过 MCP 生成并制作 → 对标视频效果 → 输出成片”，实际却在多个阶段切换成了“先解释、再补计划、再用本地素材和 FFmpeg/HyperFrames 拼装”，导致用户不断纠正方向，多个质量问题只能在最终试听或封装后才被发现。

## 一、全过程时间线：问题从哪里开始

### 1. 目标一开始就被拆成了多个没有闭环的任务

用户最初的核心要求很明确：先删除旧的安装包，安装最新的 v0.20.1，然后制作产品宣传片。随后用户补充了对标视频、MCP、真实页面参考图、时长和画质等约束。

但执行过程中没有先建立一份“任务合同”，把工作拆为互相独立又有验收条件的阶段。因此安装包替换、对标研究、宣传片创意、MCP 节点生成和本地后期混在了一条对话里。

用户因此多次纠正：

> “啥意思 首先把本地的安装包替换成最新的 然后做个我们的产品宣传片”

> “不是啊 干嘛呢”

> “删掉原来的旧的安装包 安装新的”

这说明用户不是在改变目标，而是在反复把执行拉回原目标。根因是缺少任务级状态机：`安装包替换` 没有完成标记，也没有版本校验，就被默认进入了宣传片阶段。

### 2. 对标视频被当成了文字灵感，而不是待分析的输入资产

用户明确要求：

> “去先找一下b站视频下载工具 下载抽帧拆解一下 然后学些”

随后又强调要研究运镜、炫技、爆款效果，并且用真实页面截图作为参考图。

实际过程中没有建立以下中间产物：

- 对标视频本地下载文件及校验信息；
- 抽帧 contact sheet；
- 按时间码标注的镜头、转场、运镜、字幕、音频节奏；
- “对标特征 → Nomi 可复用做法 → 禁止照搬内容”的映射表。

后续成片主要复用了本地现有视频和真实页面截图，再用 HyperFrames/FFmpeg 组装。这样可以完成一条片子，但不能证明它真正“对标了”用户给的视频效果。

根因是缺少“参考研究完成门”：只要用户明确给了参考视频，制作流程就应先产出可复核的分析物，再进入分镜和生成；当前流程没有这个硬门。

### 3. 分镜和素材计划反复返工，说明生产前没有锁定资产结构

用户先要完整分镜表，随后指出不能把所有内容塞进一个页面：

> “所有塞到一个页面里也不现实”

> “重新校准你的分镜表吧 我觉得”

实际的 45 秒片子最终被拆成 9 个镜头，包含真实创建页、创建到画布、真实画布页、画布到纸片猫、纸片猫英雄镜头、真实时间轴页、时间轴到预览、真实预览页和 CTA。这一版结构后来是可用的，但它是在多次纠正后才形成的，不是生成前由约束推导出来的。

根因是没有先回答三个结构问题：

1. 哪些镜头必须用真实页面证明产品可信度；
2. 哪些镜头可以由 AI 视频提供视觉惊喜；
3. 哪些镜头必须合并，才能控制时长和 MCP 生成成本。

改进方式是先做“镜头预算表”，明确每个镜头的 viewer job、来源、时长、是否生成、是否需要参考图，再把它编译成节点，而不是先堆节点再反推分镜。

## 二、MCP 调用与参数链问题

### MCP-01：视频时长写进提示词，而不是写进节点参数

#### 发生了什么

用户明确指出：

> “你点击视频节点 下面不是可以选择模型和参数吗 你现在把提示词里面放秒数其实没用的”

这说明实际操作中把“生成 8 秒/更长时长”的意图写到了 prompt 文本里，而没有可靠地写入视频节点的 duration 参数。

#### 为什么发生

- Prompt 与结构化生成参数没有统一合同；
- MCP 工具层允许 `prompt` 有内容，但没有要求 `durationSec`、`resolution`、`modelKey`、`references` 成套出现；
- 调用之后没有回显“实际生效参数”，用户只能从节点 UI 下面观察是否传入；
- 参数缺失时没有 fail-fast，而是继续生成，造成“看起来调用成功、实际上没按要求生成”。

#### 后续改进

- 在生成节点 schema 中把 `durationSec`、`resolution`、`fps`、`modelKey`、`vendor`、`references` 作为一等字段；
- prompt 中出现“8 秒/高清”等词不能替代结构化字段；
- 生成前返回一张参数回执：`模型 / 供应商 / 时长 / 清晰度 / 参考图数量 / 预计费用`；
- 对视频生成增加校验：缺少实际 duration 或模型参数时不允许提交，只能保存为草稿。

分诊：🔵 B 产品取舍 + 🟡 C 字段收纳。它既是字段展示问题，也是“调用成功是否等于按参数执行”的产品合同问题。

### MCP-02：参考图没有进入生成调用，真实截图只是被当成说明材料

#### 发生了什么

用户两次直接指出：

> “似乎没有调用图片节点 因为下面都没有参数”

> “你好像没传参考图”

用户的要求是使用真实 Nomi 页面截图作为参考图，让 AI 生成的大部分镜头围绕真实页面和产品视觉展开。但可见调用路径中，参考图没有被稳定地绑定到具体视频节点。

#### 为什么发生

- 真实截图被复制到了本地素材目录，却没有形成 `shot → referenceAssetId → generationJob` 的强关联；
- `references` 在 MCP 接口里是可选字段，缺失不会报错；
- 参考图模式没有在节点 UI 中显示“已传入几张、分别是哪几张”；
- 生成后的结果没有记录 provider 实际收到的参考图 ID，无法做输入输出对账。

#### 后续改进

- 参考模式节点必须显示参考图缩略图、资产 ID 和数量；
- `referenceMode=true` 时，`references.length >= 1` 设为硬校验；
- 每个生成 job 记录完整输入快照：prompt、参考图、模型、参数、时间和项目版本；
- 结果卡中显示“本镜头使用了哪些参考图”，避免用户只能猜。

分诊：⚫ D 大重构 / 名实不符。当前“支持参考图”与“这次生成确实使用参考图”不是同一件事。

### MCP-03：模型、供应商和 UI 参数没有形成一次任务的可执行证明

#### 发生了什么

用户要求使用 APIMart，并强调要在视频节点实际选择模型、时长和清晰度，而不是写在提示词里。实际制作后来主要由本地已有素材、HyperFrames 和 FFmpeg 完成；可见过程没有形成一份完整的 MCP 回执，证明每个镜头实际使用了哪个 APIMart 模型、哪个时长档位和哪种清晰度。

#### 为什么发生

- 供应商选择、模型选择、视频节点参数和最终产物元数据分散在不同表面；
- 生成调用返回 job/asset，但没有返回“生效配置快照”；
- 生产路线在 MCP 生成、ChatCut/HyperFrames 合成和本地 FFmpeg 之间切换，资产来源断开；
- 用户想验证“我设置的参数有没有生效”，系统只能展示部分状态。

#### 后续改进

- 为每个镜头生成一条不可变的 `GenerationReceipt`；
- 交付报告自动列出 `shotId / provider / model / duration / resolution / referenceIds / outputAssetId`；
- UI 把“候选可用”与“本次已实际使用”分开显示；
- MCP 生成和本地后期要共享同一个 runId 和 asset lineage，而不是各自生成孤立文件。

分诊：⚫ D 大重构 / 名实不符。现有能力更像“能发起调用”，还不是“能证明调用按合同执行”。

### MCP-04：生成节点和后期节点的边界不清，导致用户不断追问“到底在哪里做了”

#### 发生了什么

用户先要求“用 MCP 做宣传片”，之后又说：

> “你自己调用ffmpeg 和需要的去做不就行了”

这说明用户接受本地工具作为实现手段，但前提是 MCP 节点、真实页面参考、参数设置和最终剪辑之间的关系要清楚。实际流程中，MCP 生成、HyperFrames 合成、FFmpeg 音画封装、浏览器下载配音各自产生文件，用户很难从轨迹看出哪一步对应哪个镜头。

#### 为什么发生

- 没有在开工时声明“哪些步骤必须走 MCP，哪些步骤允许本地后期”；
- 没有用统一 EDL/run manifest 把所有节点和文件串起来；
- 本地后期是有效的能力，但它没有反向回写 Nomi 项目或 MCP Run 状态。

#### 后续改进

- 先发布一份执行边界：`MCP=生成与资产登记`、`HyperFrames=包装与动画`、`FFmpeg=编解码/混音/质检`；
- 所有本地产物必须带 `runId`、`shotId`、`sourceAssetIds`；
- 最终交付卡显示完整链路，不再让用户从多个目录和日志自行拼图。

分诊：🔵 B 产品取舍。核心取舍是“本地工具效率”与“全程可追踪”不能再互相牺牲，应以同一 run manifest 连接两者。

## 三、素材、媒体和合成管线问题

### MEDIA-01：原始视频没有在进入 HyperFrames 前统一媒体契约

#### 发生了什么

四条视频直接作为宣传片素材使用时，HyperFrames 出现了画面冻结/寻址不稳定问题。后来通过 FFmpeg 对片段重新编码，设置 `-r 30 -g 30 -keyint_min 30 -sc_threshold 0` 后才稳定。

#### 为什么发生

- 生成视频的帧率、关键帧间隔、编码器和容器不一定适合时间线随机寻址；
- HyperFrames 假设输入媒体可按目标帧稳定 seek，但没有在导入前统一转码；
- 媒体预处理没有作为固定 preflight，而是等渲染异常后再补。

#### 后续改进

- 所有外部/AI 视频进入时间线前执行统一 `media-normalize`：fps、GOP、像素格式、音频采样率、时长；
- 预处理输出写入 manifest，并保留原始文件与 normalized 文件的映射；
- 生成一张 seek smoke：首帧、中间帧、末帧随机抽取，检查没有冻结或黑帧。

分诊：🟢 A 卫生清理，可直接做成导入前自动化门禁。

### MEDIA-02：HyperFrames 源文件结构触发重复合成警告

#### 发生了什么

为了让 HyperFrames 找到入口，根目录有多个 HTML 合成文件，渲染时出现重复 composition 警告。后来把 `master-edit.html` 移到 `docs/`，根目录只保留 `index.html` 入口链接才恢复清晰。

#### 为什么发生

- HyperFrames 的入口约定没有在项目脚手架中固化；
- 源文件和文档文件放在同一扫描范围，工具按文件发现 composition，而不是按明确 manifest 发现 composition。

#### 后续改进

- 新建宣传片项目时固定 `index.html` 唯一入口；
- 其他版本、说明和测试文件放入 `docs/`、`preview/`、`tests/`；
- doctor 阶段把“发现多个 composition”升级为错误，而不是非阻塞 warning。

分诊：🟢 A 卫生清理。

### MEDIA-03：CTA 的布局问题只能在目视抽帧后才被发现

#### 发生了什么

初版 CTA 中 Logo/文字/纸片猫卡片发生布局挤压或重叠，接触表抽帧后才发现，随后调整了 CTA 结构并从视频中抽取更合适的纸片猫 hero still。

#### 为什么发生

- CTA 先凭代码坐标实现，后做视觉验证；
- 没有安全区、最小间距和文字/Logo/角色卡的布局约束；
- HyperFrames 成功渲染被误当成视觉正确。

#### 后续改进

- CTA 组件加安全区和碰撞检查；
- 固定首帧、转场帧、CTA settle frame 的自动抽帧清单；
- 交付前必须对照获批样张做“画面、文字、Logo、角色、收尾”五项人眼检查。

分诊：🟢 A 卫生清理 + 🔵 B 视觉取舍。

### MEDIA-04：时间线过密警告没有被纳入质量门

#### 发生了什么

HyperFrames 渲染成功，但出现 `timeline_track_too_dense` 警告：track 0 有 18 个元素、track 1 有 27 个元素、track 2 有 4 个元素。因为它不是 fatal error，流程继续了。

#### 为什么发生

- 当前验收只关注“能否渲染”和“是否有输出文件”，没有把警告与可维护性、渲染稳定性关联起来；
- 没有规定每轨元素数量、重叠层级和动画密度的阈值；
- 复杂度被隐藏在单个 HTML 合成文件中。

#### 后续改进

- 对密度 warning 分级：可接受、需复核、阻塞交付；
- 输出轨道统计、重叠区间和单轨元素清单；
- 通过 precomposed layer 或组件拆分降低单轨复杂度，而不是把所有效果继续叠在一条轨上。

分诊：🟡 C 字段/信息收纳 + ⚫ D 架构治理。

## 四、音频与配音问题

### AUDIO-01：BGM 的算法结构与“商业产品片”听感目标冲突

#### 发生了什么

用户听到上一版成片后反馈：

> “背景音乐感觉很扯 呼呼的声音”

追溯后确认，上一版占位 BGM 使用了持续低频正弦叠加周期性振幅调制。它在波形上是连续的，在听感上就像风噪或呼吸声，而不是有明确节拍和段落的产品音乐。

#### 为什么发生

- 用程序化信号快速占位时，优先满足了“有声音”和“有动态”，没有满足“像音乐”；
- `apulsator` 这类周期性调制没有经过人耳试听；
- 只检查了峰值/平均音量，没有检查声源结构、低频持续性和人声频段遮挡。

#### 后续改进

- 占位 BGM 也必须先过 10 秒试听门；
- 禁止持续低频正弦和未审听的周期性振幅调制进入交付音轨；
- BGM 规范写成可检查的规则：无持续风噪层、低频可控、旁白段自动 duck、CTA 有明确 resolve；
- 交付前同时提供 BGM 单独试听和人声+BGM 混音试听。

分诊：🟢 A 音频卫生清理；如果要支持长期音乐生成，则属于 🔵 B 音乐方向能力。

### AUDIO-02：配音音色的用户选择没有绑定成明确的 provider + voiceId 合同

#### 发生了什么

助手先推荐了三个中文音色：大壹、知性女声、流畅女声。用户随后说：

> “给我最终成片 就用这个音色”

执行时把它解释为推荐的 Doubao `dayi`，最终通过 `submit_voice` 生成了 `jobId=f2cb3a2b5a`、`outputAssetId=67310664c4` 的配音。

#### 为什么发生

- “音色”同时可能指 BGM 音色和旁白音色；
- 用户可见名称没有和 provider、voiceId、语速、情绪、音高一起显示；
- 最终调用的实际参数没有立即回显给用户确认。

这次结果碰巧符合上下文，但这仍然是一个高风险歧义点。

#### 后续改进

- 选择卡固定显示：`声音名称 / provider / voiceId / 语速 / 情绪 / 音高`；
- 用户说“用这个声音”时，系统引用具体卡片，而不是依赖最近一句自然语言；
- TTS job 提交前展示单行确认回执，提交后把回执写入交付 manifest。

分诊：🔵 B 产品取舍。

### AUDIO-03：一整段 27.24 秒 TTS 没有按镜头时间线切段

#### 发生了什么

最终大壹配音长 27.24 秒，而片子总长 45 秒。旁白以一整段连续音频生成，再与整条 BGM 混音，没有为 S01–S09 建立逐镜头的旁白入点、出点和停顿。结果是前半段叙事可以连续听到，后半段 CTA 主要由音乐收尾，旁白与具体镜头不一定一一对齐。

#### 为什么发生

- 分镜表有“配音草稿”列，但没有被编译成时间编码的 audio EDL；
- TTS 生成被当成“文本转一个音频文件”，而不是“按镜头生成可编辑语音片段”；
- 没有做旁白波形与镜头边界的自动/人工对账。

#### 后续改进

- 短片旁白按镜头或语义段生成，至少输出 `segmentId / text / start / end / voiceId`；
- 不足 45 秒的旁白必须明确剩余时间是音乐留白、音效还是无声；
- 对“讲解型片子”优先生成 6–9 个短 TTS 片段；对“品牌宣言型片子”才允许一条连续旁白；
- 交付前播放检查：字幕、旁白、镜头切点、BGM duck 四者逐段对账。

分诊：🔵 B 产品取舍 + 🟡 C 时间线字段收纳。

### AUDIO-04：云端 MCP 音频无法直接进入本地 FFmpeg 后期

#### 发生了什么

TTS 任务成功后，`inspect_asset` 能看到音频为 `cloud: available`，但 `pull_asset` 说明云端资产不能拉到本地。直接用 `curl` 访问下载地址返回 401；直接在浏览器打开下载地址又被客户端拦截。最后只能借助浏览器会话，通过临时本地页面触发下载，再把下载到 Downloads 的文件复制进宣传片 run 目录。

#### 为什么发生

- MCP 生成资产和本地后期工具之间缺少“导出到本机路径”的正式能力；
- `request_asset_download` 的设计偏向“给用户下载”，不是“给 agent 继续用 FFmpeg”；
- 云端鉴权、浏览器会话和本地 shell 的权限边界没有被统一处理。

#### 后续改进

- 新增明确的 `export_asset_to_local`：接受 assetId、目标路径、项目权限，返回本地绝对路径和校验 hash；
- 区分三种动作：`inspect`（读元数据）、`user_download`（交付给用户）、`agent_pull`（继续本地处理）；
- agent_pull 失败时返回结构化原因和建议，不要只给一个对用户有用、对本地后期无用的下载 URL；
- 对导出的音频/视频记录 hash，防止下载到 HTML 错误页或过期响应却继续混音。

分诊：⚫ D 大重构 / 能力边界缺口。

## 五、错误处理与运行状态问题

### ERROR-01：ReadableStream 重复关闭导致未捕获异常

#### 发生了什么

用户报告：

```text
TypeError [ERR_INVALID_STATE]: Invalid state: ReadableStream is already closed
at ReadableByteStreamController.close
at node:internal/deps/undici/undici
```

这类异常直接冒泡成 `Uncaught Exception`，而不是被一次 MCP 任务标记为失败、可重试或可对账的状态。

#### 为什么发生

从 stack trace 能确认的是：Node/Undici 的响应流在已关闭后又执行了一次 `close()`。最可能的根因是上游结束、客户端 abort、超时清理或错误处理之间存在竞态，多个路径拥有同一个 ReadableStream 的结束权。当前轨迹没有留下完整 requestId、jobId、abort 原因和 transport lifecycle，因此还不能把责任精确定位到某一层代码。

关键问题不只是“多 close 一次”，而是异常没有被 MCP 边界吸收：一个流生命周期竞态变成了整个宿主的 Uncaught Exception。

#### 后续改进

- 统一一个 stream owner，所有结束路径通过幂等 `safeClose/safeAbort`；
- 对 `close`、`cancel`、`abort` 和 response body error 加状态保护，禁止重复终结；
- 将 transport 错误转换为结构化 `RunEvent`：`transport_error / retryable / reconciliation_required`；
- 增加竞态测试：正常结束后 abort、abort 后上游结束、超时与 body close 同时发生、读取到一半宿主断开；
- 记录 `requestId / jobId / assetId / streamState / abortReason`，否则下次仍只能凭 stack trace 猜。

分诊：⚫ D 大重构 / 运行时可靠性。这个问题在本次成片中没有真正修复，只能通过后续流程绕开。

### ERROR-02：错误没有在离生成最近的节点呈现，用户只能从最终效果反推

#### 发生了什么

参考图未传、视频参数未生效、BGM 听感异常、配音导出困难等问题都不是在提交或导入时被阻止，而是用户通过“看节点下面没有参数”“听最终音乐不对”“检查最终文件长度”才发现。

#### 为什么发生

- MCP 工具成功返回的含义过宽：网络请求成功不等于生成合同满足；
- 缺少节点级验证结果和输入输出对账；
- UI 没有区分“请求已提交”“provider 已接受”“资产已落库”“资产符合分镜约束”。

#### 后续改进

每个节点至少要有四个阶段状态：

```text
配置完整 → 已提交 → provider 已接受 → 产物验收通过
```

任一阶段失败都要显示具体原因和可执行动作，例如“缺少参考图”“时长没有落到结构化字段”“资产只存在云端”“视频关键帧不适合随机寻址”。

分诊：⚫ D 运行状态投影问题。

## 六、交付与验证问题

### DELIVERY-01：文件名和版本语义容易互相覆盖

#### 发生了什么

先输出了 `nomi-v0201-promo-no-voice.mp4`，之后修订 BGM 时覆盖了同名无配音文件；加入大壹后又新建 `nomi-v0201-promo-final.mp4`。这个过程中“无配音版”“BGM 修订版”“含配音最终版”的关系依赖对话记忆，而不是文件元数据。

#### 为什么发生

- 交付目录没有 immutable artifact naming 规则；
- 同一个语义文件名被用于多个版本；
- 没有 manifest 写明音频、画面、配音、模型和生成时间。

#### 后续改进

采用不可覆盖的版本命名，例如：

```text
nomi-v0201-promo-picture-r01.mp4
nomi-v0201-promo-music-clean-r02.mp4
nomi-v0201-promo-vo-dayi-r03.mp4
```

最终交付卡再指向一个明确的 `release.json`，而不是依赖“当前目录里哪个文件最新”。

分诊：🟢 A 卫生清理。

### DELIVERY-02：最终验收先验证技术参数，后补主观试听，顺序反了

#### 发生了什么

此前验证了 45 秒、1920×1080、30fps、H.264、AAC、音频峰值等技术信息，也做了画面 contact sheet。但 BGM 的“呼呼”听感直到用户亲自听成片后才暴露；这说明技术验证先通过并不代表内容质量通过。

#### 为什么发生

- 把 `ffprobe/volumedetect` 当成了音频质量验收；
- 没有“单独试听 BGM → 人声+BGM试听 → 最终成片试听”的三段式门禁；
- 没有建立用户验收标准：真实页面可信度、对标效果、运镜炫技、旁白自然度、音乐不抢戏。

#### 后续改进

最终验收应分成四层：

1. 技术：时长、编码、帧率、分辨率、音频采样率、可解码；
2. 画面：首帧、每个镜头切点、CTA、安全区、黑帧/冻结；
3. 声音：BGM 单听、人声单听、混音听、旁白与镜头对齐；
4. 目标：对标视频的节奏特征是否被转译、真实页面是否真正承担可信度证明。

分诊：🟢 A 验收流程卫生清理。

### DELIVERY-03：最终成片是否“符合原始请求”没有单独对账

#### 发生了什么

最终视频确实存在，但它主要证明“本地现有素材被剪成了一条片”，不能单独证明以下原始要求都被完成：

- 本地旧安装包是否已删除并替换成 v0.20.1；
- Bilibili 参考视频是否下载并拆解；
- 生成视频是否实际使用真实页面参考图；
- 视频节点是否使用了用户要求的模型、时长和清晰度；
- 最终旁白是否按分镜对齐。

#### 为什么发生

- 交付验收围绕“文件存在和能播放”，没有围绕“用户原始意图逐项闭环”；
- 过程产物和最终交付物之间没有验收矩阵。

#### 后续改进

最终报告必须有一张原始要求对账表：

| 原始要求 | 证据 | 状态 |
|---|---|---|
| 安装 v0.20.1 | 安装日志 + 启动后版本截图/命令 | 未完成/已完成 |
| 研究对标片 | 下载文件 + 抽帧 + 时间码分析 | 未完成/已完成 |
| 使用真实页面参考 | 节点 referenceIds + 缩略图 + job 回执 | 未完成/已完成 |
| 参数真实生效 | provider/model/duration/resolution 回执 | 未完成/已完成 |
| 输出最终片 | final 文件 + ffprobe + 人眼走查 | 已完成 |

没有证据的项目不能写“已完成”，只能写“未验证”。

## 七、沟通和协作层问题

### COLLAB-01：反复让用户确认已经给过的创意方向

#### 发生了什么

用户已经给了对标视频、现有素材、真实页面、MCP、参考图、时长和画质要求，但执行过程中仍出现让用户确认创意方向的动作。用户直接反问：

> “那你为什么要让我确认创意方向？”

> “为什么要搞这个 你不是复用我们的素材吗”

#### 为什么发生

- 没有把“用户已经确认的约束”与“需要用户拍板的关键不可逆决策”区分开；
- 对已经足够明确的执行任务继续做创意问答，增加了用户负担；
- 没有建立“已确认事实清单”，每轮都重新解释上下文。

#### 后续改进

- 对话开头生成一张短合同，只列：必须做、可以自主决定、需要用户拍板；
- 用户已经明确授权的实现细节直接执行；
- 只有供应商/模型/音色、不可逆花费、发布范围等真正改变结果的事项才停下来问；
- 每次进度更新用“已完成证据 + 下一步动作”，不要重复询问方向。

分诊：🔵 B 交互流程取舍。

### COLLAB-02：用户只能通过负反馈发现执行偏差

#### 发生了什么

轨迹中多次出现“不是”“不对”“干嘛呢”“重新校准”等纠偏。用户不断承担了需求解析、状态审计和质量验收三种角色。

#### 为什么发生

- agent 没有在每个关键阶段主动暴露实际输入和输出；
- 没有主动报告“这一步没有做到”的缺口；
- 过早把“能继续执行”当成“方向已经正确”。

#### 后续改进

每个阶段完成时主动给出三行：

```text
本阶段目标：……
实际使用的输入：……
已验证/未验证：……
```

这样用户可以在小范围纠偏，不必等到最终成片才发现方向偏了。

- 将 4 条素材统一为适合 HyperFrames seek 的 30fps/GOP 媒体；
- 清理 HyperFrames 重复入口文件，固定根合成入口；

- 对最终 MP4 做了 `ffprobe` 和 FFmpeg 全量解码检查。

### 仍然存在或尚未验证

3. 最终画面使用了真实页面截图，但没有证明每个 AI 生成镜头在 MCP 层真正提交了参考图；
4. 最终成片中的现有视频素材没有形成逐镜头的 provider/model/duration/resolution 回执；

6. 大壹配音是单个 27.24 秒音频，不是按 S01–S09 对齐的分段旁白；
7. HyperFrames 的 `timeline_track_too_dense` 仍是非阻塞 warning，没有转成复杂度门禁；
8. MCP 云端资产到本地 FFmpeg 的正式导出能力仍缺失，本次依赖浏览器下载绕行。

## 九、优先级整改建议

### 第一优先级：先把“生成是否按要求执行”变成可证明的事实

1. 增加结构化生成合同和回执，强制记录模型、供应商、时长、画质、参考图、jobId、assetId；
2. 参考图模式没有 reference 时硬阻止提交；
3. 在节点和 MCP 结果中直接显示实际生效参数，而不是只显示 prompt；
4. 交付时自动生成原始要求对账表。

这组改动解决的是用户最核心的摩擦：他不想听解释，只想知道“我设置的东西到底有没有真正传进去”。

### 第二优先级：补齐资产和运行状态链

1. 建立统一 run manifest，连接 MCP job、节点、素材、HyperFrames 合成和 FFmpeg 输出；
2. 增加云端 asset 的 agent-local export；
3. 让所有生成任务显示阶段状态和下一步动作；
4. 修复流终结竞态，并用四组 abort/close 场景测试锁住根因。

这组改动解决的是“中间发生了什么无法追踪”和“出了问题只能靠用户发现”。

### 第三优先级：把质量检查前移

1. 对标视频先下载、抽帧、拆解，再允许进入分镜；
2. 生成素材进入 HyperFrames 前统一转码和 seek smoke；
3. BGM 和配音都先单独试听，再做混音；
4. 交付前执行技术、画面、声音、原始需求四层验收；
5. 旁白按镜头拆段，或明确允许“前半段连续旁白 + 后半段音乐 CTA”的创意选择。

## 十、建议沉淀为自动化验收的最小清单

```text
[ ] 安装包：旧版本路径已定位，v0.20.1 已安装，启动后版本可见
[ ] 参考片：本地文件存在，抽帧 contact sheet 存在，镜头时间码分析存在
[ ] 分镜：每个 shot 都有 source / reference / prompt / model / duration / expected effect
[ ] MCP：调用回执包含实际生效参数，不接受只写在 prompt 里的时长/画质
[ ] 参考图：referenceMode 开启时至少一张图，并能回显缩略图和 assetId
[ ] 媒体：fps / GOP / 分辨率 / 采样率统一，首中末帧 seek 无冻结
[ ] HyperFrames：只有一个入口，warning 分级，CTA 通过抽帧目视检查
[ ] 音频：BGM 单听、人声单听、混音试听；旁白与镜头边界已对账
[ ] 封装：ffprobe 时长等于画面时长，不能因 -shortest 误裁主片
[ ] 交付：最终文件、参数回执、素材清单和未验证项一起交付
```
