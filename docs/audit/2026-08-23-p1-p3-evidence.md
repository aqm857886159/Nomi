# P1→P3 MCP 可编辑单镜生成阶段证据

日期：2026-08-23  
分支：`codex/video-generation-parameter-research-20260823`
范围：P1/P2 边界、P3 零 provider-quota seam、真实 MCP/GUI 走查，以及一次受控的 APIMart 低规格图片 transport smoke。

## 用户价值结论

- P1 解决“换模型/供应商/输入模式就要学习一套 Nomi 私有格式”的摩擦：模块、provider、model、mode、参数和素材都是声明数据；不支持时在 provider 前明确失败。
- P2 解决“我只是改了一个参数/换了参考图，却不知道系统实际提交了什么”的摩擦：candidate 每次编辑都生成新 revision/hash；字段被丢弃时有 warning/ledger；封存后编辑返回 `new_draft_required`，不会偷偷改原任务。
- P3 seam 解决“要离开 MCP 去 Nomi 点第二次、崩溃后怕重复扣费”的摩擦：provider-neutral adapter 只接受 sealed contract；envelope 先落盘；provider 已接受但回执丢失时只进入 reconcile，不盲重提。
- 能力降级修正了一个过度保守的阻塞：供应商缺少原生幂等/取消能力时，仍可正常完成一次明确提交；缺失能力只改变异常路径的人话和可承诺范围。APIMart 现在是 `observe_only`，不是被错误挡在生成门外。

## 用户体验验收原则

- MCP 客户端优先：客户端能提供主进程可验证的 attestation 时，用户在当前客户端点一次即可由主进程签发 receipt；没有可验证证明时只回退到同一个 challenge 的一张 Nomi 卡，避免双重审批。
- 可编辑和通用：模型、供应商、image/video/audio 模式、参数和参考素材均是 candidate 数据，不写死在 dispatcher；所有编辑都在封存前发生，封存后通过新草稿保护旧合同。
- 简洁可见：用户只看到决定所需的摘要和一个 primary action；进行中用文字+图标+进度，错误写明事实与唯一下一步；内部状态名不直接甩给用户。
- 真实场景：后续 journey 必须覆盖自由换模型/供应商/模式/参数/参考素材，以及取消、重启、断线、回执丢失和 provider 能力缺失，而非只覆盖固定 fixture 的 happy path。

## APIMart 受控 smoke（2026-08-23）

- 凭证通过 Nomi 的模型目录写入本机安全存储；没有写入代码、日志或提交，也没有在输出中回显明文。
- 只跑一张 `Seedream 5.0 Pro`：`text-to-image`、`1:1`、`1K`、`n=1`；没有视频或高分辨率请求。
- `POST /v1/images/generations` 返回 HTTP 200 和 `data[0].task_id`；`GET /v1/tasks/{task_id}` 从 `pending` 到 `completed`；结果为 1024×1024 JPEG，结果地址 HTTP 200。
- 这证明凭证、模型参数和 APIMart 的异步查询传输可用，但**不证明可以安全自动重试或保证远端取消**：官方文档只明确提交与 task 查询，没有给出原生 idempotency key 或取消接口。按照能力降级方案，APIMart 作为 `observe_only` provider 正常允许一次提交；未知回执只核账，不自动重提。
- 为了让实测使用与产品网络出口一致，修正了 transport spike 漏传 Electron `session.defaultSession` 的测试入口；该修复不触碰生产生成路径。

## 继续推进记录（2026-08-24）

- `generationRuntimeAdapter` 新增统一 `query`/`reconcile` seam；provider 没有对应能力时返回结构化 observation unsupported，不触发 submit。
- runtime envelope 新增 `lastPoll { status, raw, observedAt }`；ProductionJob 记录 `providerStatus`、`lastPollAt` 和状态变化时间，查询结果可在重启后复读。
- Run-owned submission 新增 `poll`：只凭已经持久化的 providerTaskId 查询，processing 状态进入 `polling`，失败状态进入 `needs_attention`，不会自动重新提交；MCP stdio / app RPC 的 `reconcile(found)` 默认复用这条路径。
- 新增验证：runtime adapter query、envelope poll restart、submission poll exactly-once（30 个 focused tests 通过）；provider degradation E2E 仍为 8 checks / zero credit / zero network。

## 继续推进记录（2026-08-24，读取与恢复边界）

- `ProductionRunService.readProjection` 与 `listFull` 现在都保持纯读：读取运行列表不会隐式触发恢复扫描、状态改写或旧 driver 重踢；恢复必须由显式 `resumeUnfinishedRuns`/语义提交 owner 调用。
- 旧 playbook 恢复扫描识别 `generation.single-shot` Run 后跳过 legacy `submission_unknown` 改写；语义任务继续由 `ProductionGenerationSubmission.resume/poll/reconcile` 按 providerTaskId、runtime envelope 和 reconcile-only 规则处理，避免把单镜任务误交给旧生成链路。
- 新增回归：listFull 零 repository.execute；semantic single-shot restart recovery 零 legacy mutation；服务/driver/shot-gate focused 19 tests、typecheck 通过。

## 继续推进记录（2026-08-24，Run 写入 fencing）

- `ProductionRunRepository.execute` 现在在读取最新事件、revision CAS、追加事件/命令索引和写 snapshot 的整个同步临界区持有独立的短期 repository mutex；不同进程不能同时读同一 revision 后各自 append。真正需要跨重启拒绝旧 owner 的 durable fencing 仍由 semantic `run.lock` 提供。
- 现有 semantic submission 的 `run.lock` 仍负责 provider dispatch/outbox；repository mutex 独立存在，避免嵌套锁，同时让 legacy service、MCP、GUI、semantic submission 共用同一 append 保护。
- 新增回归：外部 worker 持有 repository lock 时，第二个 repository 以 `run_lock_busy` fail closed；repository / semantic submission focused 24 tests、typecheck 通过。
- 变更后的全量回归：`pnpm run test` 通过（699 test files、1 skipped；6181 tests、1 skipped）；build、filesize、tokens、i18n、archetype-sources、diff-check 通过。

## 继续推进记录（2026-08-24，结果落地与 Artifact）

- `GenerationProvider` 新增可选的 provider-owned `materialize`：供应商只负责把自己的任务响应解析成一个已验证 output descriptor（image/video/audio + URL），Runtime Adapter 不猜字段；没有该能力仍允许提交与查询，不会被错误阻塞。
- APIMart 适配器按其已验证的 `data.result.images/videos/audios` 形状解析结果；没有新增真实付费请求。默认 app RPC/stdio 的 `reconcile(found)` 在 terminal poll 后自动尝试一次 materialization，失败时返回人工核对，而不是把远端完成冒充本地文件。
- Asset store 新增确定性 materialization sink：`providerTaskId + providerOutputId/URL` 形成稳定路径，重试不会产生重复 `-2` 文件；下载经过 `hardenedFetch` 的协议、私网、大小和媒体类型校验，data URL 走受限字节路径。
- Run 在本地 receipt 写入后才追加 `artifact.add`，再把 job 置为 `ready`、runtime envelope 置为 `materialized`；中途崩溃可按同一 artifact/receipt 重放。新增 materializer、APIMart shape、Asset retry、job observation 及 submission artifact 回归。
- 结果落地 focused suites 通过（含 provider 无 materialize 时仍可提交、但不伪造 Artifact）；上一轮全量 `pnpm run test` 通过（700 test files、1 skipped；6188 tests、1 skipped）；build、filesize、tokens、i18n、archetype-sources、diff-check 通过。

## 继续推进记录（2026-08-24，真实语义 GUI 兜底）

- 桌面 RPC 与 in-Electron stdio 现在都显式使用同一份运行时 generation policy：默认关闭；`NOMI_MCP_GENERATION_SINGLE_SHOT_V1=1` 只打开零额度 E0 规划/预览；再显式设置 `NOMI_MCP_GENERATION_SINGLE_SHOT_E1_V1=1` 才打开单镜提交。两个开关分开，避免打开规划能力时意外打开付费提交。
- `session/open` 的当前项目 bootstrap 会一次发行规划所需的 scope；来源（Codex/Claude/Cursor）从已验证 transport 透传到 `ProductionRun`，并把本次候选的 provider/model 写入 Run policy。用户点一次确认后不再因来源或策略丢失而被拒绝。
- 新增真实 Electron + MCP stdio 旅程：`node tests/ux/mcp-generation-single-shot-gui-fallback.e2e.mjs`，14 assertions，使用隔离项目和 loopback APIMart fixture，真实 provider POST=1、查询 GET=1、真实额度=0。客户端不提供 elicitation 时，Nomi 只显示一张确认卡；卡片展示 provider/model、镜头摘要、参考图数量、费用边界和“忽略/确认生成”，点击确认后原 MCP 请求继续，随后 `nomi_reconcile_generation(found)` 生成可持久化 Artifact。
