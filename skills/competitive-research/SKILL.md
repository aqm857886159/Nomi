# 竞品与开源能力研究

当用户说“研究一下某产品怎么做”“对标竞品”“看开源项目/框架能不能拉齐体验”“用电脑点击完整研究”“每一步截图”“最后写报告”时使用本 Skill。

本 Skill 的产物不是链接列表，而是一份可以让工程师直接开工、让产品判断可以被复查的研究包：

```text
docs/research/<date>-<topic>/
├── README.md
├── report-source.md
└── assets/
```

## 硬规则

1. 先读 `docs/ARCHITECTURE-NOW.md`，再读旧方案；旧方案不能代替当前代码现状。
2. 先定义真实用户任务和不做项，再开始点击或读代码。
3. 网页产品必须通过 Codex 浏览器完成有意义的点击；每个动作在报告中写成 `Action:`，并在同一段落放截图。
4. “点击 Login”不等于登录成功；“点击 Generate”不等于生成成功；任务 ID、处理中、静态占位图都不能当成功证据。
5. 开源项目必须检查官方仓库、官方文档、许可证、近期发布/提交和运行前提；GitHub star 只能当热度线索，不能当体验证据。
6. 代码许可证、模型权重、人体模型、数据集和商用/再分发限制分开记录；没核对就写 `blocked` 或 `inferred`。
7. 研究结论必须区分 `observed`、`documented`、`inferred`、`proposed`、`blocked`，不得把建议写成竞品事实。
8. 不上传竞品源视频/音频到生成服务，不保存源视频/音频进报告包，不复制完整脚本、镜头链、音乐、Logo 或品牌画面。
9. 有副作用的动作（上传、删除、真实付费生成、安装插件、发布）默认不执行；需要时先写阻塞和执行条件。
10. 报告完成前运行：`pnpm run check:competitive-research --report <报告目录>`。

## 研究规划

先写一段简短 intake：

- 用户是谁，想完成什么事？
- 他现在在哪一步卡住？
- 研究对象是产品、框架、模型、开源应用，还是宣传内容？
- 最终要做保留、重做、直接采用、适配，还是不做的决定？
- 明确不研究什么，避免把任务扩成泛市场研究。

对 Nomi 的 3D 导演台，优先按“场景运行时/编辑、动作输入/清理、3D 资产、镜头输出”拆层；对参考设计台，按“对象模型、图层、变换、局部编辑、导出”拆层。不要用一个“竞品好不好”覆盖不同层的问题。

## 产品点击研究

使用 Codex 的应用内浏览器，而不是凭印象复述网页。每一步都记录：

```text
Action: 点击什么或输入什么
![证据截图](./assets/NN-action-name.png)
Result: 页面实际发生了什么
Design rationale: 这解决了用户哪个摩擦，或暴露了什么限制
Status: observed | blocked
```

点击链应覆盖真实用户任务的完整闭环：入口、首次引导、核心操作、编辑/返工、保存、导出/交接和失败状态。只点击导航菜单不算完整研究。

如果网站受登录、地区、验证码、额度或自动化限制阻塞，要保留最后一个可验证截图，写清阻塞点和没有验证的部分；不通过猜测补齐后续。

## 开源项目与框架研究

每个候选项目按同一张卡片研究：

1. 它服务的用户任务是什么？
2. 它能直接提供哪项能力？
3. 它的官方接入方式和最低运行条件是什么？
4. 代码、模型、权重、人体模型、数据集分别是什么许可证？
5. 最近是否仍维护，是否存在迁移、弃用或私有开发提示？
6. 接入 Nomi 会替换哪个现有边界、增加什么依赖和失败面？
7. 结论是 `直接采用`、`借鉴交互`、`适配为后端`、`保留观察` 还是 `不采用`？

默认先查与 Nomi 同用户任务、同媒介、同交互载体的开源近邻，再查闭源竞品，最后才用跨领域类比。已有同类依赖时先验证能否复用，不重复引入第二个 renderer 或第二套状态真相源。

## Nomi 现状对账

每个结论都要回到当前代码：

- 已有能力：给出 `file:line`，说明真实入口和持久化边界。
- 用户摩擦：给出实际 UI/状态/写入链证据。
- 缺口：区分“没有能力”“有能力但入口不好用”“有能力但状态不可靠”。
- 取舍：明确保留、删除、重做或只借鉴的部分。

不要因为竞品有一个漂亮面板，就新建一套 Nomi 状态；先确认现有画布、资源引用、动作捕捉和导出链是否已经有归属。

## TikHub 宣传研究

TikHub 只用于公开账号和公开视频的结构化研究：

1. 密钥只从同一执行进程的 `TIKHUB_API_KEY` 读取，只检查存在性，绝不回显、落盘或放入提示词。
2. 先搜索账号昵称/短 ID，再比较身份字段，最后确定稳定账号 ID；不能直接按模糊昵称拉帖子。
3. 默认最多 20 条帖子元数据，最多 10 条下载或转写样本。
4. 记录公开视频 ID/URL、发布时间、互动快照、封面/播放 URL、观察时间。
5. 观察前 5 秒钩子、平均镜长、字幕/标题位置、转场、声音切点、证明方式和 CTA；学习机制，不复制成片。
6. 没有密钥、身份歧义、401/403、额度耗尽或 429 时标 `blocked` 并停止，不轮换身份或盲目重试。

## 报告编排

README 按以下顺序组织：

1. `Scope`：目标、用户任务、范围、不做项、观察日期。
2. `Evidence`：状态协议和 Nomi 当前真相。
3. `Walkthrough`：产品点击链；纯源码研究写 `Walkthrough: not applicable — source-only study`。
4. `Capability matrix`：候选能力、Nomi 现状、证据状态和决策。
5. `Decision`：直接采用、借鉴交互、后端适配、不采用。
6. `User value and trade-offs`：真实摩擦、收益、代价和风险。
7. `License, rights and risks`：许可证、硬件、网络、密钥和商用边界。
8. `Next acceptance tasks`：可执行的实现/验证任务。
9. `Source ledger`：每个官方链接、访问日期和支撑结论。

报告包中只放截图和文本证据；源视频、源音频、密钥、Cookie、浏览器 profile 和临时下载放在任务临时目录，任务结束后清理。
